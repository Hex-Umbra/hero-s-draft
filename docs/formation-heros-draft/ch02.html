1. Pourquoi Dart, et comment le lire

Flutter n'accepte qu'un seul langage : Dart. Ce n'est pas un choix qu'on fait, c'est le ticket d'entrée. La bonne nouvelle, c'est que Dart a été conçu pour ce genre d'application : il se compile en code natif (AOT) pour la version finale du jeu, et tourne en machine virtuelle (JIT) pendant le développement — ce qui rend possible le hot reload : modifier une valeur, sauvegarder, et voir l'écran de combat se mettre à jour sans redémarrer la partie.

La version du langage est déclarée dans le manifeste du projet :

sdk: ^3.11.4 signifie « Dart 3 ». C'est important pour la suite : tout ce que nous verrons en section 7 — les records — n'existe que depuis Dart 3, et le projet s'en sert massivement.

Le point d'entrée : main()

Comme en C, en Java ou en Go, un programme Dart démarre par une fonction main(). Dans Hero's Draft, elle tient en trois lignes.

lib/main.dartdart
void main() {
  WidgetsFlutterBinding.ensureInitialized();
  runApp(const ProviderScope(child: HerosDraftApp()));
}

Trois choses à repérer, elles reviendront partout :

  • void : le type de retour s'écrit avant le nom de la fonction (comme en C# ou en Java, contrairement à TypeScript ou Rust).
  • Les point-virgules sont obligatoires. L'indentation n'a aucune valeur syntaxique, contrairement à Python : ce sont les accolades qui délimitent les blocs.
  • const ProviderScope(...) : on construit un objet sans écrire new. Le mot-clé existe encore mais n'apparaît nulle part dans le projet, ni dans le style Dart moderne.

var, final, const : trois mots pour déclarer

C'est la première source de confusion pour qui vient de JavaScript, où const signifie simplement « je ne réaffecterai pas cette variable ». En Dart, la frontière n'est pas au même endroit.

La distinction final / const est visible dès les premières lignes des constantes du jeu :

lib/game/game_constants.dartdart
class GameConstants {
  // --- Z-INDEX PRIORITIES ---
  static const int priorityBackground = -100;
  static const int priorityCardBase = 10;
  static const int priorityTargetingLine = 300;

  static const double cardHeight = 196.0;

Regardez la dernière ligne : cardSize est static final et non static const. Pourquoi ? Parce que Vector2(140.0, 196.0) est un objet de Flame construit par un constructeur ordinaire, et non par un constructeur const : le compilateur ne peut pas le figer dans le binaire. Il sera créé une seule fois, au premier accès, puis jamais réaffecté. À l'inverse, 140.0 est un littéral : const passe.

À retenir

const en Dart est plus fort qu'en JavaScript. Ce n'est pas « je ne réassigne pas », c'est « cette valeur est calculée pendant la compilation et gravée dans le binaire ». Toutes les instances const identiques sont le même objet en mémoire — c'est un des piliers de la performance de Flutter, qu'on retrouvera au chapitre 3.

Quand le type est évident, on écrit var ou final et on laisse l'inférence travailler :

Ce qui surprend quand on vient d'ailleurs

Dart est statiquement typé : chaque expression a un type connu à la compilation. Cela le rapproche de C# ou de Java et l'éloigne de Python et de JavaScript. Le type dynamic est la porte de sortie ; le projet ne l'utilise qu'aux frontières, au décodage JSON, où l'on écrit systématiquement Map<String, dynamic> puis on recaste chaque champ avec as. C'est une discipline, pas un hasard.

2. La null-safety : le point qui change tout

Dart a une null-safety saine (sound null safety). La règle est brutale et simple : un type ne peut pas contenir null, sauf si vous l'avez explicitement écrit avec un ?. Le compilateur refuse de compiler tant qu'un chemin d'exécution peut produire un null dans un type non nullable.

Ce n'est pas une contrainte administrative. C'est ce qui fait qu'un jeu qui recharge des sauvegardes potentiellement obsolètes et lit neuf fichiers JSON écrits à la main ne s'effondre pas au milieu d'un combat.

Le type nullable : T?

Dans CardData, quatre champs sur seize sont nullables — exactement ceux qui peuvent manquer dans le JSON.

Le cast nullable : as String?

lib/models/data/card_data.dartdart
      heroClass: json['heroClass'] as String?,
      rarity: CardRarity.values.firstWhere(

Trois écritures cohabitent, et la différence est essentielle :

  • json['heroClass'] as String? — « si la clé est absente, garde null ». Le champ cible est nullable, on transmet le vide tel quel.
  • json['isExhaust'] as bool? ?? false — « si la clé est absente, mets false ». L'ordre compte : on caste d'abord en bool?, puis on applique ??. Écrire as bool ?? false lèverait une exception avant même d'atteindre le ??.
  • json['cost'] as int (plus haut dans le fichier) — « ce champ est obligatoire ». Si un fichier JSON l'oublie, le jeu échoue au chargement, bruyamment, plutôt que de fabriquer une carte à coût zéro.

Chaîner : ?. et ??

Une méthode statique du projet illustre la propagation du doute :

lib/models/data/passive_data.dartdart
  static PassiveData? getById(String id) {
    final registry = GameDataRegistry.instance;
    if (registry == null) return null;
    try {
      return registry.passives.firstWhere((p) => p.id == id);
    } catch (e) {
      if (kDebugMode) {
        debugPrint('PassiveData.getById: no passive found for id "$id" ($e)');

      return null;
    }
  }

Le type de retour est PassiveData?. Deux raisons de renvoyer null : le registre de données n'est pas encore chargé, ou aucun passif ne porte cet identifiant. Le compilateur oblige donc tous les appelants à traiter le cas. C'est exactement ce que fait la sérialisation de l'état de run :

lib/game/controllers/run_controller.dartdart

activePassive?.id se lit : « si activePassive est null, n'appelle rien et renvoie null ; sinon renvoie .id ». Sans le ?., le compilateur refuserait la ligne, puisque le champ est déclaré PassiveData?. Le résultat de l'expression est String? — et c'est très bien, un champ JSON peut valoir null.

Le chargement fait le trajet inverse : si l'identifiant sauvegardé ne correspond plus à aucun passif (parce qu'une mise à jour du jeu l'a renommé), on signale l'objet manquant au joueur et on retombe sur une valeur par défaut, plutôt que de casser la partie.

Remarquez la double sécurité : json['activePassiveNameFr'] as String? ?? activePassiveId. Le nom lisible du passif est dupliqué dans la sauvegarde précisément pour pouvoir dire au joueur « tu as perdu ce passif » même si l'objet n'existe plus dans les données du jeu. ??= et ! en situation réelle

Le tirage d'une rune de forge en boutique est un enchaînement de replis, parce qu'il ne doit jamais échouer : le joueur a payé, il doit recevoir quelque chose.

lib/game/controllers/shop_controller.dartdart
  /// Helper privé pour générer un upgrade de forge aléatoire avec son tier
  String _rollRandomUpgrade(CardInstance card, List<String> existingUpgrades, Random rng) {
    final excludedIds = existingUpgrades.map((u) => u.split(':')[0]).toList();
    String? rolledId = _rollUpgradeId(card, rng, excludedIds);
    rolledId ??= _rollUpgradeId(card, rng, []);
    rolledId ??= 'sharp';

Premier tirage en excluant les runes déjà présentes sur la carte. S'il échoue, on retire l'exclusion et on retire. Si ça échoue encore, on donne 'sharp'. La variable est déclarée String? mais la fonction renvoie String : les deux ??= suffisent à convaincre le compilateur qu'après ces trois lignes, rolledId ne peut plus valoir null.

Piège : l'opérateur !

! ne vérifie rien : il dit au compilateur de se taire. Si l'objet est null à l'exécution, l'application s'arrête net. Dans Hero's Draft, il n'apparaît qu'à l'intérieur d'un test qui vient de prouver le contraire :

lib/game/heros_draft_game.dartdart
  @override
  void onGameResize(Vector2 size) {
    super.onGameResize(size);
    if (heroCard != null) {
      heroCard!.position = Vector2(size.x / 2, size.y * 0.51);
    }

Si vous vous surprenez à écrire ! sans un if juste au-dessus, c'est presque toujours que le type devrait être non nullable ailleurs. Cherchez la cause, pas le symptôme.

late : la promesse d'initialisation

late résout un problème précis : un champ qui ne peut pas être initialisé dans le constructeur, mais dont on sait qu'il le sera avant toute lecture. Un Notifier Riverpod n'a accès à ref que dans sa méthode build(), jamais dans son constructeur — d'où :

lib/game/controllers/deck_controller.dartdart
class DeckNotifier extends Notifier<DeckState> {
  late final Random _random;

  @override
  DeckState build() {
    _random = ref.read(deckRandomProvider);
    return const DeckState();
  }

late final combine deux garanties : affectation unique, et pas de null possible dans le type. Si du code lisait _random avant build(), Dart lèverait une LateInitializationError explicite — bien plus lisible qu'un null silencieux qui se propage.

3. Les classes : constructeurs, factory, static

Dart est orienté objet, avec héritage simple et une syntaxe de constructeur très dense. Cette densité est la principale difficulté de lecture au début ; une fois les cinq formes reconnues, tout le projet devient transparent.

Paramètres nommés et this.x

Un constructeur Dart prend des paramètres positionnels (entre parenthèses) ou nommés (entre accolades). Hero's Draft utilise presque exclusivement les paramètres nommés, ce qui reste lisible même avec seize champs.

lib/models/entity_stats.dartdart
  EntityStats({
    required this.maxPv,
    required this.currentPv,
    this.maxMana = 0,
    this.currentMana = 0,
    required this.armure,
    this.armorMastery = 0,
    required this.attaque,
    this.luck = 0,
    this.level = 1,
    this.xp = 0,
    this.xpToNextLevel = 100,
    this.critChance = 0,
    this.critMultiplier = 1.5,
    List<StatusEffect> statuses = const [],
    this.lastActionWasCrit = false,
  }) : statuses = List.unmodifiable(statuses);

Quatre mécanismes sont empilés dans ces dix-sept lignes :

  • { ... } : les paramètres sont nommés. À l'appel on écrit EntityStats(maxPv: 100, currentPv: 100, armure: 0, attaque: 0) ; l'ordre n'a plus d'importance.
  • this.maxPv : le raccourci d'initialisation. Dart affecte automatiquement le paramètre au champ du même nom, sans this.maxPv = maxPv; à écrire.
  • required : sans lui, un paramètre nommé est optionnel. Un paramètre nommé optionnel de type non nullable doit avoir une valeur par défaut — d'où les = 0, = 1, = 100, = 1.5.
  • : statuses = List.unmodifiable(statuses) : la liste d'initialisation, exécutée avant le corps du constructeur. statuses est le seul paramètre sans this. : c'est une variable locale, transformée avant d'atterrir dans le champ.

Ces valeurs par défaut sont des faits de gameplay : une entité commence au niveau 1, avec 100 XP à atteindre pour le niveau suivant, 0 % de chance de critique et un multiplicateur critique de ×1.5.

La liste d'initialisation, en profondeur

lib/models/card_instance.dartdart
  CardInstance({
    String? uniqueId,
    required this.data,
    CardRarity? rarity,
    List<String>? forgeUpgrades,
  })  : uniqueId = uniqueId ?? const Uuid().v4(),
        rarity = rarity ?? data.rarity,
        forgeUpgrades = forgeUpgrades != null
            ? List<String>.unmodifiable(forgeUpgrades)
            : const <String>[];

C'est le cœur de la distinction entre modèle de carte et exemplaire de carte :

  • uniqueId = uniqueId ?? const Uuid().v4() — si l'appelant ne fournit pas d'identifiant, on en génère un avec le paquet uuid. C'est ce qui permet d'avoir trois exemplaires de la même carte dans le deck et de n'en défausser qu'un seul. Le paramètre local masque le champ pendant l'expression : à droite du =, uniqueId désigne le paramètre ; à gauche, le champ.
  • rarity = rarity ?? data.rarity — la rareté de l'exemplaire peut diverger de celle du modèle : c'est exactement ce que produit la fusion de trois cartes identiques.
  • La liste de runes est rendue non modifiable, ou remplacée par const <String>[] — une liste vide partagée en mémoire par toutes les cartes sans rune.

Les constructeurs factory

Un constructeur normal doit renvoyer une nouvelle instance de sa classe. Un constructeur factory est libre : il peut calculer, choisir entre plusieurs branches, ou renvoyer un objet existant. Dans le projet, ils servent presque tous à construire un objet depuis une Map JSON.

lib/models/data/card_data.dartdart
  factory CardData.fromJson(Map<String, dynamic> json) {
    final nEn = json['name_en'] as String? ?? json['name'] as String? ?? '';
    final nFr = json['name_fr'] as String? ?? json['name'] as String? ?? '';
    final dEn =
        json['description_en'] as String? ??
        json['description'] as String? ??
        '';
    // ...
    return CardData(
      id: json['id'] as String,
      nameEn: nEn,
      nameFr: nFr,
      cost: json['cost'] as int,
      type: CardType.values.firstWhere((e) => e.name == json['type']),
      // ...

CardData.fromJson est un constructeur nommé (le .fromJson après le nom de classe) et une factory. La raison d'être du factory ici : les premières lignes font du travail — lire name_fr, sinon name, sinon la chaîne vide — avant de pouvoir appeler le constructeur. Un constructeur ordinaire ne peut pas exécuter d'instructions avant sa liste d'initialisation.

Cette triple cascade est la stratégie de localisation du projet : les fichiers JSON peuvent contenir soit des clés bilingues (name_fr / name_en), soit une clé name unique héritée d'une version antérieure. Le code accepte les deux formats.

== et hashCode

Par défaut, deux objets Dart ne sont égaux que s'ils sont le même objet en mémoire. Pour comparer par valeur, il faut redéfinir operator == et hashCode ensemble. Le projet ne le fait qu'à un seul endroit :

lib/models/missing_save_item.dartdart
class MissingSaveItem {
  final String id;
  final String nameFr;
  final String nameEn;
  final String category;

  const MissingSaveItem({
    required this.id,
    required this.nameFr,
    required this.nameEn,
    required this.category,
  });

  @override
  bool operator ==(Object other) =>
      identical(this, other) ||
      (other is MissingSaveItem &&
          other.id == id &&
          other.nameFr == nameFr &&
          other.nameEn == nameEn &&
          other.category == category);

  @override
  int get hashCode => Object.hash(id, nameFr, nameEn, category);
  • identical(this, other) : court-circuit rapide, vrai si c'est littéralement la même référence.
  • other is MissingSaveItem : Dart pratique la promotion de type. Après ce test, dans la même expression, other est traité comme un MissingSaveItem — on écrit other.id sans cast.
  • Object.hash(...) : la fonction du SDK pour combiner plusieurs champs en un hachage. L'écrire soi-même est une source classique de bugs.
Piège : redéfinir == sans hashCode

Le contrat de Dart exige que deux objets égaux aient le même hashCode. Si vous redéfinissez == et oubliez hashCode, votre objet se comportera correctement avec == mais se dupliquera silencieusement dans un Set ou une Map. C'est précisément ce qui compte ici : MissingSaveItem sert à dédoublonner la liste des objets manquants d'une sauvegarde — la même carte perdue dans cinq piles différentes ne doit être signalée qu'une fois au joueur.

4. Immutabilité et le pattern copyWith

Hero's Draft est bâti sur une règle simple : un objet d'état ne change jamais. Quand le héros prend des dégâts, on ne modifie pas ses PV : on fabrique un nouvel EntityStats avec les nouveaux PV, et on remplace l'ancien. Plus coûteux en apparence, infiniment plus sûr en pratique.

List.unmodifiable : l'immuabilité en profondeur

Déclarer final List<StatusEffect> statuses empêche de remplacer la liste, mais pas d'y ajouter un élément. C'est le piège classique. Le projet le referme dans la liste d'initialisation :

    List<EnemyInstance> pendingEnemies = const [],
    List<EnemyInstance> defeatedEnemies = const [],

List.unmodifiable(x) crée une copie figée de x. Tout appel à .add(), .remove() ou [i] = sur le résultat lève une UnsupportedError. Corollaire pour la suite : partout dans le projet, un contrôleur qui veut modifier une liste d'état commence par List.from(state.xxx). Impossible de faire autrement.

Pourquoi copyWith existe

Si tout est immuable, comment fait-on évoluer l'état ? On construit un nouvel objet identique sauf sur les champs qui changent. Écrit à la main, cela donnerait un appel de constructeur de seize lignes à chaque fois. copyWith automatise exactement ça.

lib/models/entity_stats.dartdart
  EntityStats copyWith({
    int? maxPv,
    int? currentPv,
    int? armure,
    // ...
  }) {
    return EntityStats(
      maxPv: maxPv ?? this.maxPv,
      currentPv: currentPv ?? this.currentPv,
      armure: armure ?? this.armure,
      // ...
    );
  }

Le mécanisme tient dans une ligne : maxPv ?? this.maxPv. Tous les paramètres sont nullables et optionnels ; ne pas les passer signifie null, donc « garde la valeur actuelle ». L'appelant n'écrit que ce qui change :

lib/models/entity_stats.dartdart
  EntityStats takeDamage(int amount, {bool isCrit = false}) {
    if (amount <= 0) return copyWith(lastActionWasCrit: isCrit);

    // 2. Absorption via Armure
    int damageAfterArmor = amount - armure;
    int newArmor = armure;
    int newPv = currentPv;

    if (damageAfterArmor > 0) {
      // L'armure est brisée, le reste va aux PV
      newArmor = 0;
      newPv -= damageAfterArmor;
    } else {
      // L'armure encaisse tout
      newArmor -= amount;
    }

    if (newPv < 0) newPv = 0;

    return copyWith(armure: newArmor, currentPv: newPv, lastActionWasCrit: isCrit);
  }
Règle du jeu

Ces vingt lignes sont la règle d'absorption complète de Hero's Draft : l'armure encaisse d'abord. Si les dégâts dépassent l'armure, l'armure tombe à 0 et le reste est retiré des PV. Sinon, l'armure est simplement réduite du montant des dégâts et les PV ne bougent pas. Les PV sont bornés à 0, jamais négatifs.

Le piège : comment remettre un champ à null ?

Voici le trou dans le pattern copyWith, et le projet le rencontre pour de vrai. L'ennemi ciblé est stocké dans String? selectedEnemyId. Quand le joueur désélectionne, ou quand l'ennemi ciblé meurt, il faut remettre ce champ à null.

Mais copyWith(selectedEnemyId: null) ne fait rien du tout : l'implémentation lit selectedEnemyId ?? this.selectedEnemyId, et null ?? ancienne_valeur vaut l'ancienne valeur. Passer null est indistinguable de ne rien passer. La solution retenue est un drapeau booléen explicite :

Point d'attention

Le champ type est le seul des quatre à ne pas avoir d'orElse. L'ordre des valeurs comme progression de rareté

Voici le point le plus important de cette section. Dans CardRarity, l'ordre de déclaration n'est pas cosmétique : c'est la règle de progression de rareté du jeu.

7. Records et destructuration (Dart 3)

Les records sont la grande nouveauté de Dart 3, et Hero's Draft en fait un usage intensif. Un record est un agrégat anonyme de valeurs : un tuple. Il permet à une fonction de renvoyer plusieurs choses sans créer de classe dédiée.

Le record positionnel : (int, bool)

Le calcul de dégâts doit renvoyer deux informations : le montant final, et le fait qu'il s'agisse ou non d'un coup critique — l'interface affiche un texte flottant différent. Créer une classe DamageResult pour deux valeurs serait disproportionné.

lib/game/services/damage_pipeline.dartdart
class DamagePipeline {
  static (int damage, bool isCrit) calculate({
    required int initialDamage,
    required EntityStats attackerStats,
    required EntityStats defenderStats,
    bool canCrit = true,
  }) {
    int totalDamage = initialDamage;

    // 1. Weakness (faiblesse) de l'attaquant : réduit les dégâts de 25% (arrondi)
    final hasWeakness = attackerStats.statuses.any((s) => s.id == 'weakness');
    if (hasWeakness) {
      totalDamage = (totalDamage * 0.75).round();
    }

    // 2. Coup critique de l'attaquant : multiplie les dégâts par critMultiplier
    bool isCrit = false;
    if (canCrit) {
      final random = Random();
      if (random.nextInt(100) < attackerStats.effectiveCritChance) {
        totalDamage = (totalDamage * attackerStats.critMultiplier).round();
        isCrit = true;
      }
    }
    // ...
    return (totalDamage, isCrit);
  }
}
  • (int damage, bool isCrit) est le type de retour. Les noms damage et isCrit sont ici purement documentaires : sur un record positionnel, les champs s'accèdent par .$1 et .$2. Les nommer sert uniquement le lecteur.
  • return (totalDamage, isCrit); — un record littéral, avec de simples parenthèses. Un record à un seul élément s'écrit (x,), avec une virgule finale, pour le distinguer d'une parenthèse de groupement.

    final missing = <MissingSaveItem>[];

    final (masterDeck, m1) = _decodePile(json['masterDeck'] as List<dynamic>?);
    final (drawPile, m2) = _decodePile(json['drawPile'] as List<dynamic>?);
    final (hand, m3) = _decodePile(json['hand'] as List<dynamic>?);

      ..addAll(m2)

      ..addAll(m4)
      ..addAll(m5);
Bonne pratique du projet

Ce style « renvoie le résultat et le rapport » remplace avantageusement les exceptions pour un cas qui n'est pas exceptionnel : une sauvegarde qui référence une carte supprimée par une mise à jour du jeu. Le joueur récupère sa partie, amputée des objets disparus, et voit la liste de ce qu'il a perdu. Sans records, il aurait fallu une classe par fonction de décodage.

Le record nommé : ({int min, int max})

Quand un record a plus de deux champs, ou que ses champs ne se distinguent pas par leur type, on les nomme. La syntaxe ajoute des accolades à l'intérieur des parenthèses.

  // --- MAP GENERATION QUOTAS ---
  static const Map<MapNodeType, ({int min, int max})> nodeQuotas = {
    MapNodeType.combat: (min: 12, max: 22),
    MapNodeType.elite: (min: 3, max: 6),
    MapNodeType.rest: (min: 3, max: 6),
    MapNodeType.shop: (min: 2, max: 5),
    MapNodeType.event: (min: 4, max: 9),

Règle du jeu

Voilà, en six lignes, les quotas de génération d'une carte du monde : entre 12 et 22 combats normaux, 3 à 6 élites, 3 à 6 repos, 2 à 5 boutiques, 4 à 9 événements. Le const signifie que ces bornes sont figées à la compilation ; la génération de carte du chapitre 12 les respecte comme un contrat.

Trois remarques. D'abord, ({int min, int max}) est un type utilisable partout, y compris comme paramètre générique de Map. Ensuite, le record est const-compatible, ce qui autorise la Map entière à être static const. Enfin, les champs s'accèdent par leur nom, comme sur un objet ordinaire :

      for (var entry in GameConstants.nodeQuotas.entries) {
        final type = entry.key;
        final min = entry.value.min;
        if ((counts[type] ?? 0) < min) {
          deficientType = type;
          break;

Et un peu plus loin, la combinaison ?. + ?? sur un champ de record : final currentMin = GameConstants.nodeQuotas[currentType]?.min ?? 0;. L'accès map[clé] renvoie toujours un type nullable en Dart — d'où le ?.min, puis le ?? 0 pour un type de nœud qui n'a pas de quota, comme MapNodeType.boss.

Set<(String, String)> est un ensemble de paires d'identifiants. Avec une classe ordinaire, il aurait fallu écrire == et hashCode à la main, exactement comme pour MissingSaveItem en section 3. Avec un record, c'est automatique.

8. Extensions et typedef

Les extensions : ajouter des méthodes à une classe qu'on ne possède pas

Une extension ajoute des méthodes et des getters à un type existant, sans en hériter et sans le modifier. Dans Hero's Draft, elle sert un objectif d'architecture précis : garder la couche de données propre.

HeroData contient une liste d'identifiants de compétences (List<String> skills). Pour obtenir les vraies cartes correspondantes, il faut consulter le registre. Mais on ne veut pas que hero_data.dart dépende de game_data_registry.dart — la couche Données doit rester un ensemble de structures inertes. Solution : un fichier séparé qui ajoute la méthode.

lib/models/data/hero_skills_link.dartdart
import 'hero_data.dart';
import 'card_data.dart';
import 'game_data_registry.dart';

extension HeroSkillsLink on HeroData {
  List<CardData> getHeroCards(GameDataRegistry gameData) {
    return skills
        .map((skillId) {
          final matches = gameData.cards.where((c) => c.id == skillId);
          return matches.isNotEmpty ? matches.first : null;
        })
        .whereType<CardData>()
        .toList();
  }
}
  • extension NomDeLExtension on TypeCible — le nom sert seulement à résoudre les conflits ; à l'usage, il est invisible.
  • Dans le corps, skills désigne directement le champ de l'instance : à l'intérieur d'une extension, this est implicite comme dans une méthode normale.
  • .map(...) peut renvoyer null pour un identifiant introuvable ; le type intermédiaire est donc Iterable<CardData?>. C'est .whereType<CardData>() qui fait le travail : il filtre les null et retire le ? du type. Deux opérations en un appel.

À l'usage, la méthode se comporte comme si elle appartenait à HeroData : final classCards = widget.playerClass.getHeroCards(gameData); dans lib/ui/screens/starter_deck_draft_screen.dart.

Étendre un enum

On peut aussi étendre un enum. C'est ce qui permet à CardRarity — déclaré dans un fichier de données qui n'importe que flutter/foundation.dart — d'avoir une couleur et un libellé traduit, sans jamais importer material.dart ni le système de localisation.

  String getLabel(AppLocalizations l10n) {
    switch (this) {
      case CardRarity.common:

      case CardRarity.uncommon:

      case CardRarity.rare:

        return l10n.rarityLegendary;

      case CardRarity.common:

Ici this désigne la valeur d'enum elle-même. Le switch n'a pas de default, et c'est délibéré : quand un switch couvre toutes les valeurs d'un enum, Dart le considère exhaustif et n'exige pas de branche par défaut. Corollaire précieux : si quelqu'un ajoute une septième rareté, le compilateur signalera immédiatement tous les switch devenus incomplets.

L'appel, côté interface, ne trahit rien de cette mécanique :

      target: card.data.target.getLabel(l10n),

À retenir

Une extension n'est pas du polymorphisme : la résolution se fait à la compilation, sur le type statique de l'expression. Elle n'est visible que dans les fichiers qui importent celui où elle est déclarée. C'est précisément ce qui en fait un bon outil de séparation des couches : la couche UI importe model_extensions.dart, la couche données l'ignore.

Un typedef crée un alias. Le cas le plus simple du projet consiste à nommer un record devenu trop long à écrire :

Le typedef générique de save_service.dart

Le deuxième typedef du projet est le plus subtil de tout ce chapitre. Prenez le temps.

lib/services/save_service.dartdart
/// The subset of Ref/WidgetRef/ProviderContainer that SaveService needs:
/// a plain synchronous provider read. Accepting this instead of `Ref`
/// lets the same code run from a Notifier's `ref`, a widget's `WidgetRef`,
/// and a bare `ProviderContainer` in tests — none of which share a common
/// supertype in riverpod 2.6.1, but all of which expose this exact method.
typedef RefReader = T Function<T>(ProviderListenable<T> provider);
  1. Function<T>(ProviderListenable<T> provider) : une fonction qui prend un argument de type ProviderListenable<T>.
  2. T Function... : elle renvoie un T. Donnez-lui un provider de DeckState, elle renvoie un DeckState ; un provider de RunState, elle renvoie un RunState.
  3. Et voici le point crucial : le <T> est placé après Function, pas après RefReader.

Cette position change tout. Comparez :

exempledart
// (A) Générique sur l'ALIAS — il faut choisir T à la déclaration de la variable.

LecteurA<DeckState> lireDeck = ...;   // ne sait lire QUE des DeckState

// (B) Générique sur la FONCTION — le T est choisi à chaque appel. (le vrai projet)

RefReader read = ...;

final run  = read(runProvider);    // T = RunState — même variable !

Avec la forme (B), une seule valeur de type RefReader peut lire n'importe quel provider, chaque appel instanciant T de son côté. On parle de fonction générique. C'est exactement ce dont SaveService a besoin :

9. L'asynchrone : Future, async, await

Dart est mono-thread. Un seul fil d'exécution traite les entrées du joueur, la logique du jeu et le rendu à 60 images par seconde. Il n'y a pas de fil séparé pour l'interface. Conséquence directe : toute opération qui bloque ce fil gèle le jeu. Les animations figent, les clics sont ignorés.

La solution de Dart est une boucle d'événements : au lieu d'attendre, on enregistre « ce qu'il faudra faire quand ce sera prêt » et on rend la main. C'est le rôle de Future.

Future, async et await

Un Future<T> est la promesse d'un T plus tard. Une fonction marquée async renvoie forcément un Future, et peut utiliser await pour suspendre son exécution jusqu'à ce qu'un Future se résolve — sans bloquer : pendant l'attente, la boucle d'événements traite tout le reste.

lib/services/game_data_service.dartdart
Future<List<dynamic>> _loadJsonList(String path) async {
  try {
    final String content = await rootBundle.loadString(path);
    final decoded = jsonDecode(content);
    if (decoded is! List) {
      throw FormatException('Le fichier JSON doit être une liste à la racine.');
    }
    return decoded;
  } catch (e, stack) {
    throw Exception('Erreur de chargement/décodage pour le fichier "$path": $e\n$stack');
  }
}
  • Le type de retour est Future<List<dynamic>>, mais le corps écrit return decoded; — Dart emballe automatiquement.
  • await rootBundle.loadString(path) : sans await, on manipulerait un Future au lieu d'une String, et le compilateur refuserait.
  • catch (e, stack) : Dart donne accès à la pile d'appels en second paramètre. Le projet la réinjecte dans le message d'erreur — précieux quand un JSON écrit à la main est mal formé.

Future.wait : neuf chargements en parallèle

Hero's Draft charge neuf fichiers JSON au démarrage. Les charger l'un après l'autre avec neuf await successifs additionnerait neuf temps d'attente. Future.wait les lance tous, puis attend que tous soient terminés.

  final heroesList = results[1];
  // ...

Future.wait renvoie une List dans l'ordre des futures soumises, pas dans l'ordre où elles se terminent. D'où les neuf lignes results[0] à results[8], qui doivent correspondre exactement à l'ordre du tableau au-dessus. Insérer un dixième fichier au milieu de la liste décalerait silencieusement toutes les affectations suivantes — le jeu chargerait les reliques comme des événements. C'est le prix de la concision ici ; un record nommé aurait été plus sûr.

Côté interface, ce FutureProvider est consommé sans une seule ligne d'asynchrone explicite. Riverpod expose les trois états possibles, et l'écran de démarrage se contente de les peindre :

Future.delayed : rythmer le combat sans figer le jeu

Le deuxième grand usage de l'asynchrone n'est pas de l'attente d'entrée/sortie, mais de la mise en scène. Quand le joueur lance une compétence, il ne faut pas que tout se résolve dans la même image : le héros doit s'élancer, frapper, puis les ennemis doivent riposter l'un après l'autre. Les durées sont centralisées, en millisecondes, dans les constantes du jeu :

lib/game/game_constants.dartdart

  /// Délai du dash du héros avant d'appliquer les dégâts d'une compétence.
  static const int combatDelayHeroDashMs = 200;
  /// Délai après l'exécution d'une compétence avant de continuer ou de riposter.
  static const int combatDelayAfterSkillMs = 400;
  /// Délai avant le début du tour des ennemis.
  static const int combatDelayEnemyTurnStartMs = 600;
  /// Délai après la résolution des ticks (poison, buffs, etc.) au début du tour ennemi.
  static const int combatDelayAfterTicksMs = 400;
  /// Délai du dash d'un ennemi lors de son attaque.
  static const int combatDelayEnemyDashMs = 200;
  /// Délai avant de finaliser le tour des ennemis.
  static const int combatDelayEnemyTurnEndMs = 300;

Et la phase de riposte des ennemis les enchaîne :

lib/game/heros_draft_game.dartdart

    onPhaseChanged(TurnPhase.enemy);
    await Future.delayed(const Duration(milliseconds: GameConstants.combatDelayEnemyTurnStartMs));

    onStartEnemyTurn();

    await Future.delayed(const Duration(milliseconds: GameConstants.combatDelayAfterTicksMs));

    final activeEnemies = List<EnemyCard>.from(enemyCards);
    for (var enemy in activeEnemies) {
      if (currentRunState == null || currentRunState!.isDead) break;

      final intent = enemy.effectiveIntent;
      if (intent == null) continue;

      if (intent.type == IntentType.attack) {
        enemy.dashAnimation();
      } else {
        enemy.buffAnimation(intent.type);
      }

      await Future.delayed(const Duration(milliseconds: GameConstants.combatDelayEnemyDashMs));

      onResolveEnemyIntent(enemy.id);

      await Future.delayed(const Duration(milliseconds: GameConstants.combatDelayAfterIntentResolveMs));
    }

    await Future.delayed(const Duration(milliseconds: GameConstants.combatDelayEnemyTurnEndMs));

    onEndEnemyTurn();

Le point à comprendre absolument : await Future.delayed(...) ne bloque pas. Pendant ces 200 ou 600 millisecondes, la boucle Flame continue de tourner à plein régime — les animations de dash s'exécutent, les particules se déplacent, les textes flottants montent. La fonction, elle, est simplement mise en pause et sa suite est replanifiée.

Piège : l'équivalent bloquant n'existe pas (heureusement)

Dans un langage à threads, on écrirait Thread.sleep(600). Il n'existe rien de tel en Dart pour le fil principal, et c'est délibéré : une boucle d'attente active (while (DateTime.now() < fin) {}) figerait complètement l'écran, les entrées et le rendu pendant toute sa durée. Le seul moyen d'attendre en Dart, c'est de rendre la main.

Rendre la main a une contrepartie : pendant l'attente, le joueur peut cliquer. Si rien ne l'empêchait, il pourrait lancer une seconde compétence au milieu de la première. La parade du projet est un verrou, posé avant le premier await :

À retenir

Après chaque await, l'état du monde a pu changer. C'est la règle d'or de l'asynchrone dans un jeu : ne jamais faire confiance à une variable lue avant une suspension. Relisez l'état, ou vérifiez à nouveau vos conditions.

Future<T>

La promesse d'une valeur plus tard. Type de retour de toute fonction async.

async

Autorise await dans le corps et emballe automatiquement le retour dans un Future.

await

Suspend la fonction sans bloquer le fil. La boucle d'événements continue de tourner.

Future.wait

Lance plusieurs opérations en parallèle et attend qu'elles soient toutes terminées. Résultats dans l'ordre de soumission.

Future.delayed

Attend une durée. Sert au rythme du combat, jamais à synchroniser des données.

FutureProvider

Le pont Riverpod : expose un Future à l'interface sous forme de trois états (données, chargement, erreur).

Quiz — vérifiez vos acquis

1. Que renvoie exactement DamagePipeline.calculate(...) ?

  • Un int, le montant des dégâts
  • Une classe DamageResult avec deux champs
  • Un record (int damage, bool isCrit)
  • Un Future<int>, car le calcul est asynchrone

2. Dans CombatState.copyWith, comment remet-on selectedEnemyId à null ?

  • En appelant copyWith(selectedEnemyId: null)
  • En passant le paramètre booléen clearSelectedEnemy: true
  • En reconstruisant un CombatState complet à la main
  • En appelant copyWith() sans aucun argument
Réponse : passer null est indistinguable de ne rien passer, puisque l'implémentation lit selectedEnemyId ?? this.selectedEnemyId. lib/models/combat_state.dart ajoute donc un paramètre bool clearSelectedEnemy = false, utilisé dans combat_controller.dart sous la forme clearSelectedEnemy: enemyId == null. 3. Que se passe-t-il si l'on construit un CardInstance sans fournir de uniqueId ?

  • Le compilateur refuse : uniqueId est required
  • Le champ vaut null et la carte n'est pas identifiable
  • Le champ reprend l'id de la CardData associée
  • La liste d'initialisation génère un UUID avec const Uuid().v4()
Réponse : dans lib/models/card_instance.dart, la liste d'initialisation contient uniqueId = uniqueId ?? const Uuid().v4(). C'est ce qui permet d'avoir plusieurs exemplaires de la même carte dans le deck tout en n'en défaussant qu'un seul — playCard localise la carte avec indexWhere((c) => c.uniqueId == card.uniqueId).

4. Dans mergeCards, pourquoi la rareté suivante est-elle calculée avec min(rarity.index + 1, CardRarity.values.length - 1) ?

  • Pour plafonner à la dernière valeur de l'enum, unique (indice 5)
  • Parce que CardRarity ne contient que 3 valeurs
  • Pour interdire la fusion des cartes communes
  • Parce que .index commence à 1 en Dart
Réponse : CardRarity déclare six valeurs (common, uncommon, rare, epic, legendary, unique), donc values.length - 1 vaut 5. min, importé de dart:math, empêche de sortir du tableau. L'ordre de déclaration de l'enum est la progression de rareté du jeu ; le même indice sert aussi de bonus d'emplacements de runes, via baseMaxForgeUpgrades + rarityIndex.

5. Que permet précisément le typedef RefReader = T Function<T>(ProviderListenable<T> provider) de save_service.dart ?

  • De déclarer une variable qui lit un seul type de provider, choisi à la déclaration
  • De rendre les lectures de providers asynchrones
  • Qu'une même valeur lise n'importe quel provider, T étant résolu à chaque appel
  • De créer un alias pour Ref, le type de Riverpod
Réponse : le <T> porte sur Function et non sur l'alias : c'est une fonction générique, dont le paramètre de type est instancié à l'appel. C'est pourquoi SaveService.save peut écrire à la suite read(runProvider), read(deckProvider), read(inventoryProvider) et read(skillProvider) avec le même paramètre. Le commentaire du fichier précise le motif : Ref, WidgetRef et ProviderContainer n'ont pas de supertype commun en riverpod 2.6.1, mais exposent tous cette méthode.
