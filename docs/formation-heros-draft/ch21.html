Chapitre 21

Tests, outillage, dette technique et évolutions

Un dernier tour de piste : comment on vérifie que le jeu marche, comment on le publie, et ce qu'il reste à nettoyer.

Dans ce chapitre

  2. La pyramide de tests du projet

Les vingt chapitres précédents ont démonté le jeu système par système. Celui-ci change d'angle : on ne regarde plus ce que le code fait, mais comment on sait qu'il le fait correctement, et comment on le livre. C'est la partie la moins spectaculaire d'un projet, et de loin la plus rentable — un test qui échoue coûte trente secondes, un bug en production coûte une soirée.

On finira par l'exercice le plus honnête possible : un inventaire de la dette technique réelle du dépôt, point par point, chacun vérifié dans le code. Aucun projet n'en est exempt ; le seul écart qui compte est entre ceux qui la connaissent et ceux qui la découvrent.

1. L'outillage quotidien

Le fichier CLAUDE.md, à la racine du dépôt, sert de contrat pour tout contributeur (humain ou agent). Il commence par sept commandes. Elles suffisent à couvrir 95 % du travail quotidien.

CommandeCe qu'elle faitQuand la lancer

flutter run Compile et lance l'application sur l'appareil par défaut Développement courant (avec le hot reload)
flutter test Exécute l'intégralité du dossier test/ Avant chaque commit
flutter test test/unit/combat_controller_test.dart N'exécute qu'un seul fichier Quand on itère sur un système précis
flutter test --plain-name "test description" N'exécute que les tests dont le nom contient la chaîne donnée Pour isoler un cas au milieu d'un gros fichier

flutter build <apk|ios|web|windows|macos|linux> Produit un binaire pour la cible demandée Publication, ou vérification qu'une plateforme compile encore

La commande la moins glamour de la liste est celle qui a le statut le plus fort dans ce dépôt. Voici la ligne exacte de CLAUDE.md :

CLAUDE.mdtext
- Lint/analyze: `dart analyze` — **must be run and be clean (zero issues) after any code
  change**, before considering work done

Lint rules come from `package:flutter_lints/flutter.yaml` (see `analysis_options.yaml`).
La règle du zéro

dart analyze doit rendre zéro problème. Pas « zéro erreur mais quelques warnings » : zéro. Un projet où l'analyse rend trois warnings tolérés devient, six mois plus tard, un projet où elle en rend quarante et où plus personne ne les lit. Le seuil zéro est le seul seuil qui se maintienne tout seul.

Les règles de lint ne sont pas écrites à la main. Le fichier de configuration tient en une ligne :

analysis_options.yamlyaml
include: package:flutter_lints/flutter.yaml

Flutter flutter_lints est le jeu de règles officiel recommandé par l'équipe Flutter. Il vérifie des choses comme : pas d'import inutilisé, pas de print() en production, préférer const quand c'est possible, nommer les types en UpperCamelCase, ne pas utiliser BuildContext après un await. C'est volontairement un socle modeste — l'intérêt est qu'il soit identique d'un projet Flutter à l'autre, donc qu'un nouveau contributeur n'ait rien à apprendre.

2. La pyramide de tests du projet

Le dossier test/ contient 42 fichiers, organisés en trois familles. Ce n'est pas une organisation décorative : chaque famille a un coût d'exécution et un pouvoir de détection différents.

test/ ├── encounter_system_test.dart // 1 fichier — test système, à la racine ├── tutorial/ // 2 fichiers — le sous-système d'onboarding ├── unit/ // 24 fichiers — la logique métier pure └── widget/ // 15 fichiers — les écrans Flutter

Pourquoi cette forme ? Parce que le coût d'un test et sa précision de diagnostic évoluent en sens inverse. Un test unitaire sur DeckNotifier s'exécute en une milliseconde et, s'il échoue, vous savez immédiatement quelle méthode est cassée. Un test de widget sur MapScreen construit un arbre entier de widgets, pompe des frames d'animation, et s'il échoue vous savez seulement que « quelque chose dans l'écran de carte ne va plus ». Les deux sont utiles ; le premier doit juste être beaucoup plus nombreux.

3. Tester un Notifier Riverpod

C'est le patron le plus important du chapitre, parce que c'est celui que vous appliquerez le plus souvent. La bonne nouvelle : tester un Notifier Riverpod ne demande ni widget, ni ProviderScope, ni testWidgets. Un simple test() suffit.

Voici le squelette exact utilisé par deck_controller_test.dart :

test/unit/deck_controller_test.dartdart
void main() {
  group('DeckNotifier Tests', () {
    late ProviderContainer container;
    late DeckNotifier notifier;

    setUp(() {
      container = ProviderContainer();
      notifier = container.read(deckProvider.notifier);
    });

    tearDown(() {
      container.dispose();
    });

    test(
      'drawCards remélange désormais la défausse quand la pioche est vide',
      () {
        final cardA = _card('strike');
        final cardB = _card('defend');

        notifier.initializeStarterDeck([cardA, cardB]);
        notifier.state = notifier.state.copyWith(
          drawPile: [cardA],
          hand: [],
          discardPile: [cardB],
        );

        notifier.drawCards(2, maxHandSize: 10);

        // Comportement inversé par P-02 : cardB ne reste plus bloquée en défausse.
        expect(notifier.state.hand.length, 2);
        expect(notifier.state.drawPile, isEmpty);
        expect(notifier.state.discardPile, isEmpty);
        expect(notifier.state.reshuffleCount, 1);
      },
    );

Décomposons

ProviderContainer()

C'est l'implémentation « nue » du conteneur de providers. En temps normal, ProviderScope en crée un et le range dans l'arbre de widgets. Ici on le crée directement, sans arbre.

container.read(deckProvider.notifier)

Demande l'objet DeckNotifier lui-même (et non son état). C'est cette lecture qui déclenche build() et instancie le contrôleur.

container.dispose()

Libère tous les providers du conteneur. Sans ça, les tests suivants pourraient hériter d'un état résiduel — la source de bugs de tests la plus pénible à diagnostiquer.

setUp / tearDown

Fournis par flutter_test. Ils s'exécutent avant et après chaque test() du group. Chaque test repart donc d'un deck vierge.

À retenir

Un Notifier Riverpod est une classe Dart ordinaire dont l'état est un champ. Il ne dépend d'aucun BuildContext, d'aucun rendu, d'aucune plateforme. C'est exactement pour ça que CLAUDE.md impose que toute la logique métier vive dans lib/game/controllers/ : c'est la couche testable en une milliseconde. Si une règle du jeu se retrouve dans un widget, elle devient un test de widget — cent fois plus lent et dix fois plus fragile.

Rendre l'aléatoire reproductible

Un problème saute aux yeux avec un test de pioche : drawCards remélange la défausse. Un mélange, c'est du hasard. Comment écrire un expect() sur un résultat aléatoire ?

La réponse du projet est élégante : l'aléatoire est un provider, donc il est surchargeable.

lib/game/controllers/deck_controller.dartdart
/// Source d'aléatoire de la pioche. Surchargeable en test via
/// `deckRandomProvider.overrideWithValue(Random(42))` pour rendre les
/// séquences de pioche reproductibles.
final deckRandomProvider = Provider<Random>((ref) => Random());

final deckProvider = NotifierProvider<DeckNotifier, DeckState>(DeckNotifier.new);

Le DeckNotifier ne fabrique jamais son propre Random. Il le demande au conteneur, une seule fois, dans build() :

lib/game/controllers/deck_controller.dartdart
class DeckNotifier extends Notifier<DeckState> {
  late final Random _random;

  @override
  DeckState build() {
    _random = ref.read(deckRandomProvider);
    return const DeckState();
  }

Résultat : en test, il suffit de construire le conteneur avec une surcharge. Un Random(42) est un générateur pseudo-aléatoire déterministe : à graine identique, séquence identique, sur toutes les machines.

illustrationdart
setUp(() {
  container = ProviderContainer(
    overrides: [
      deckRandomProvider.overrideWithValue(Random(42)),
    ],
  );
  notifier = container.read(deckProvider.notifier);
});

Le mélange devient alors une permutation fixe, et on peut écrire expect(notifier.state.hand.first.data.id, 'defend') sans risque de test « intermittent ». C'est l'application directe du principe d'injection de dépendance : ne jamais construire une dépendance non déterministe à l'intérieur de l'objet qui l'utilise.

Bonne pratique

Le même raisonnement s'applique à l'horloge (DateTime.now()) et au réseau. Dès qu'un objet appelle une source d'imprévisibilité en dur, il devient non testable. Passez-la par un Provider — le coût est d'une ligne, le gain est un test déterministe.

Le gobelin de test a maxHp: 20 et baseDamage: 5. Le gobelin réel de assets/data/enemies.json a 28 PV et 5 de dégâts. C'est voulu : le test vérifie la mécanique de mise à l'échelle, pas l'équilibrage. 4. Tester un écran

Passons à l'étage du dessus. Un test de widget construit un vrai arbre Flutter dans un environnement de test, puis interroge ce qui est affiché. Le fichier test/widget/map_screen_test.dart concentre les quatre difficultés du genre.

Difficulté 1 — court-circuiter le chargement des assets

L'écran de carte dépend indirectement du registre de données du jeu, chargé par un FutureProvider qui lit neuf fichiers JSON depuis le bundle. Dans un test, ce bundle n'existe pas vraiment. La parade : déclarer un provider de remplacement qui renvoie un registre vide.

À retenir : ProviderScope vs UncontrolledProviderScope

ProviderScope crée son conteneur et le possède : vous ne pouvez pas y toucher avant que l'arbre existe. UncontrolledProviderScope prend un conteneur que vous avez déjà créé et se contente de l'exposer à l'arbre. C'est le pont entre le monde du test unitaire (rapide, direct) et le monde du test de widget. Le addTearDown(container.dispose) garantit sa libération même si le test échoue en cours de route.

Piège classique

Difficulté 4 — pumpAndSettle() ne termine jamais

Voici le meilleur point pédagogique du dossier test/. Le commentaire est écrit directement dans le fichier, au-dessus du contournement :

test/widget/map_screen_test.dartdart
// MapScreen's dash-line animation repeats forever, so pumpAndSettle() never
// terminates here; pump a fixed duration instead to let transitions finish.
Future<void> _settle(WidgetTester tester) async {
  await tester.pump();
  await tester.pump(const Duration(milliseconds: 500));
}

Décortiquons, parce que ce piège vous attend dans n'importe quel projet Flutter avec des animations d'ambiance.

tester.pumpAndSettle() est la méthode de confort : elle pompe des frames en boucle jusqu'à ce qu'aucune animation ne soit plus en cours. C'est parfait pour attendre la fin d'une transition de page ou d'un fondu. Mais sa condition d'arrêt est « plus rien ne bouge ». Or, l'écran de carte fait ceci :

lib/ui/screens/map_screen.dartdart
  @override
  void initState() {
    super.initState();
    _dashController = AnimationController(
      vsync: this,
      duration: const Duration(seconds: 2),
    )..repeat();

Le ..repeat() lance une animation infinie : c'est elle qui fait défiler les pointillés le long des chemins entre les nœuds (lib/ui/widgets/map/map_connection_painter.dart calcule une phase à partir de animation.value). Du point de vue de pumpAndSettle(), quelque chose bouge encore… et bougera toujours. Le test se bloque jusqu'au timeout.

La parade tient en deux lignes. On abandonne « pompe jusqu'à ce que ce soit calme » pour « pompe une durée décidée par moi » :

  • await tester.pump() — construit la première frame (les initState s'exécutent, les FutureBuilder partent).
  • await tester.pump(const Duration(milliseconds: 500)) — avance l'horloge virtuelle de 500 ms d'un coup, ce qui laisse les transitions finies se terminer, sans jamais attendre l'animation infinie.
Bonne pratique : documenter le contournement sur place

Le vrai enseignement n'est pas le helper, c'est le commentaire de deux lignes qui l'accompagne. Sans lui, le prochain développeur remplacerait _settle() par pumpAndSettle() « pour faire plus propre », et passerait une heure à comprendre pourquoi la CI expire. Un contournement non documenté est une bombe à retardement ; un contournement documenté est une décision.

5. Tester des règles de jeu

Le générateur de carte pose un problème apparemment insoluble : il est aléatoire. MapGeneratorService.generateMap() tire les types de nœuds, les connexions et les événements avec un Random interne. Deux exécutions ne produisent jamais la même carte. Sur quoi écrire un expect() ?

La réponse : on ne teste pas des valeurs, on teste des propriétés — des affirmations qui doivent rester vraies quelle que soit la carte tirée. C'est ce qu'on appelle un test de propriété (par opposition au test de valeur figée).

Propriété 1 — le bon nombre d'étages

test/unit/map_generator_test.dartdart
    test('generates expected number of floors', () {
      final nodes = MapGeneratorService.generateMap(floors: 10, maxWidth: 5);

      // Determine the number of floors by grouping by Y position
      final floors = <double>{};
      for (var node in nodes) {
        floors.add(node.position.y);
      }

      expect(floors.length, 10);
    });

Remarquez la technique : le test ne demande pas au générateur combien d'étages il a produits, il le déduit des positions. En rangeant tous les position.y dans un Set<double>, les doublons disparaissent et il ne reste que le nombre d'ordonnées distinctes. C'est un test « boîte noire » : il mesure le résultat observable, pas l'implémentation.

Propriété 2 — trois boss au sommet, sans connexion sortante

test/unit/map_generator_test.dartdart
    test('boss nodes are at the top (last floor), rowWidth is 3, and they have no boss IDs', () {
      final nodes = MapGeneratorService.generateMap(floors: 10, maxWidth: 5);

      final bossNodes = nodes.where((n) => n.type == MapNodeType.boss).toList();
      expect(bossNodes.length, 3);

      for (var bossNode in bossNodes) {
        expect(bossNode.bossEnemyId, isNull);
        // posY for floor 9 is 0
        expect(bossNode.position.y, 0.0);
        expect(bossNode.connections.isEmpty, true);
      }
    });

Trois affirmations en une : il y a exactement 3 boss ; ils sont tout en haut (position.y == 0.0, parce que posY = (floors - 1 - y) * 200.0 et que l'étage 9 donne 0) ; et aucun n'a de connexion sortante, ce qui est logique — après le boss, il n'y a plus rien.

Ce test documente un champ mort

expect(bossNode.bossEnemyId, isNull) n'est pas une exigence de design, c'est un constat. Dans lib/services/map/map_node_generator.dart, la variable String? bossEnemyId; est déclarée puis passée au constructeur sans jamais recevoir de valeur. On y revient en section 8.

Propriété 3 — le chokepoint élite au milieu

test/unit/map_generator_test.dartdart

      final nodes = MapGeneratorService.generateMap(floors: 10, maxWidth: 5);

Bonne pratique : le paramètre reason:

expect(..., reason: 'Node ${node.id} has no connections') transforme un échec illisible (« Expected: true, Actual: false ») en diagnostic immédiat (« Node node_4_2 has no connections »). Sur un test de propriété qui boucle sur plusieurs dizaines d'éléments, c'est ce qui fait la différence entre cinq secondes et une demi-heure de débogage.

Un test de propriété d'un autre genre : le repli de langue

test/unit/localization_test.dart vérifie une propriété différente : que le système bilingue ne casse jamais, même face à une langue non prévue. Rappel du modèle :

lib/models/data/card_data.dartdart
  String getName(String locale) => locale == 'fr' ? nameFr : nameEn;

La règle est donc : français si et seulement si 'fr', anglais dans tous les autres cas. L'anglais n'est pas « l'autre langue », c'est le repli universel. Le test le formalise :

test/unit/localization_test.dartdart
        final cardData = CardData.fromJson(jsonFragment);

        // Verify English translation
        expect(cardData.getName('en'), 'Strike Test');
        expect(cardData.getDescription('en'), 'Deals 6 damage.');

        // Verify French translation
        expect(cardData.getName('fr'), 'Frappe Test');
        expect(cardData.getDescription('fr'), 'Inflige 6 dégâts.');

        // Verify fallback behavior on unknown/default locale (falls back to English nameEn/descriptionEn)
        expect(cardData.getName('es'), 'Strike Test');
        expect(cardData.getDescription('de'), 'Deals 6 damage.');

Les deux dernières lignes sont les plus importantes. Elles disent : si demain quelqu'un lance le jeu sur un téléphone configuré en espagnol ou en allemand, il verra de l'anglais — pas une chaîne vide, pas un plantage, pas null. Et le test part d'un vrai fragment JSON passé à CardData.fromJson, donc il couvre aussi le parsing des clés name_en / name_fr / description_en / description_fr.

À retenir

Trois familles de tests coexistent dans test/unit/ : les tests de comportement (le deck, les contrôleurs), les tests de propriété (le générateur de carte), et les tests d'aller-retour (les cinq fichiers *_persistence_test.dart, qui sérialisent puis désérialisent et comparent). Chacune attrape une classe de bug différente.

7. Publier une version

La procédure de release tient en trois étapes et une commande. Le README les décrit ainsi :

README.mdtext
## Publier une version

1. Faire rédiger les patch notes par le skill `patch-notes-writer` — il écrit
   l'entrée dans `assets/data/patch_notes.json` et synchronise `pubspec.yaml`.
2. Committer et pousser sur `main`.
3. Poser le tag correspondant.
README.mdbash
git tag v0.4.8
git push origin v0.4.8

C'est le push du tag qui déclenche tout. Tant que le tag n'est pas poussé, rien ne se passe : vous pouvez committer sur main autant que vous voulez.

Ce que vérifie le pipeline

La règle est simple et impitoyable : trois sources doivent annoncer le même numéro de version.

SourceCe qu'elle porteQui l'écrit
Le tag Gitv0.4.8Vous, à la main
pubspec.yamlversion: 0.4.8+1 Le skill patch-notes-writer
assets/data/patch_notes.jsonL'entrée la plus récente, "version": "0.4.8"Le skill patch-notes-writer

Cette redondance n'est pas de la paranoïa. Sans elle, on déploie un build web sous /v0.4.8/ dont l'écran « Patch Notes » affiche fièrement les nouveautés de la 0.4.7 — et personne ne s'en aperçoit avant qu'un joueur le signale.

À retenir : versions web archivées

Le déploiement web est versionné par chemin : la 0.4.8 va sur /v0.4.8/, la 0.4.7 reste sur /v0.4.7/. Les anciennes versions ne disparaissent pas. C'est précieux pour reproduire un bug signalé sur une version précédente, ou pour comparer un ressenti d'équilibrage entre deux patches.

Le build Windows et la pre-release

En parallèle du web, le pipeline produit le build Windows (flutter build windows) et le publie comme pre-release GitHub. Le statut « pre-release » est cohérent avec un numéro de version en 0.x.y : tant que la majeure est à 0, l'API et l'équilibrage peuvent bouger sans préavis. Le projet est en 0.4.7+1 à l'heure où ce chapitre est écrit.

C'est la définition même d'une dette : un coût nul maintenant, un coût aléatoire plus tard.

Point d'attention : l'autosave silencieuse

Le déclencheur d'autosauvegarde tient en cinq lignes. Repérez ce qui manque.

lib/game/controllers/checkpoint_controller.dartdart
/// Écoute checkpointProvider et déclenche une sauvegarde à chaque bump().
/// Doit être lu une fois au démarrage de l'app pour s'activer (voir main.dart).
final autosaveOrchestratorProvider = Provider<void>((ref) {
  ref.listen<int>(checkpointProvider, (previous, next) {
    SaveService.save(ref.read);
  });
});

Il manque le await — ou, à défaut, un .catchError(...). La signature est static Future<void> save(RefReader read) : on lance une opération asynchrone d'écriture sur SharedPreferences et on jette la Future. Tant que tout va bien, personne ne voit la différence. Le jour où l'écriture échoue (disque plein, permissions, plateforme web capricieuse), le joueur croit sa partie sauvegardée et ne l'est pas. Le callback de ref.listen étant synchrone, la correction propre consiste à passer par une méthode async dédiée qui attend et journalise.

Par où commencer si vous reprenez ce projet

Cinq pistes concrètes, classées par rapport gain / effort. Les deux premières se font en une soirée et rendent le reste plus facile.

1. Extraire les nombres magiques restants

Le 5 de cleanDeadEnemies() devient GameConstants.maxActiveEnemies, le 2 * k d'effect_resolver.dart devient une lecture de ForgeUpgradeData.valueMultiplier. Deux commits, aucun changement de comportement, deux sources de désynchronisation en moins.

2. Trancher sur le code mort

priorityCardBase, priorityCardTrail, bossEnemyId, skills.json + SkillData : pour chacun, soit on le branche, soit on le supprime. La règle « no dead code » de CLAUDE.md tranche déjà en cas d'hésitation — git conserve l'historique.

3. Unifier les couleurs de rareté

Un seul point d'entrée : CardRarityExtension.color pour les cartes, un RelicRarityExtension.color à créer pour les reliques. Supprimer les deux _getRelicRarityColor dupliqués et faire pointer CardComponent.getRarityColor() vers AppColors. Bénéfice immédiat : le jeu devient cohérent visuellement, et une seule ligne suffit ensuite pour changer une teinte.

4. Fiabiliser l'autosauvegarde

Rendre l'appel attendu, sérialiser les écritures concurrentes, journaliser l'échec et — idéalement — remonter un toast via notificationProvider. C'est le seul point de la liste qui peut coûter une partie à un joueur.

5. Réveiller les mécaniques dormantes

weakness et vulnerable sont déjà calculés par DamagePipeline : il suffit d'ajouter deux cartes dans cards.json avec le bon statusId pour doubler la profondeur tactique sans écrire une ligne de Dart. lifesteal demande un peu plus : le brancher réellement sur les dégâts infligés.

La bonne habitude à emporter

Avant chaque commit : flutter test puis dart analyze. Deux commandes, moins d'une minute, et la garantie que les 42 fichiers de test et le linter sont d'accord avec vous. C'est tout ce que CLAUDE.md exige — et c'est déjà plus que ce que font beaucoup de projets.

Quiz — vérifiez vos acquis

1. Pourquoi test/widget/map_screen_test.dart définit-il un helper _settle() au lieu d'appeler tester.pumpAndSettle() ?

  • Parce que pumpAndSettle() n'existe pas pour les widgets Riverpod
  • Parce que le registre de données mocké met trop longtemps à se charger
  • Parce que l'animation de pointillés de la carte est lancée avec ..repeat(), donc pumpAndSettle() attendrait indéfiniment qu'elle se termine
  • Parce que pumpAndSettle() est incompatible avec UncontrolledProviderScope
Réponse : le commentaire du fichier le dit explicitement — « MapScreen's dash-line animation repeats forever, so pumpAndSettle() never terminates here ». Dans lib/ui/screens/map_screen.dart, le _dashController est créé avec ..repeat(), donc une animation est toujours en cours. _settle() pompe une frame puis avance de 500 ms fixes.

2. Dans deck_controller_test.dart, à quoi sert container.dispose() dans le tearDown ?

  • À écrire l'état du deck sur disque avant le test suivant
  • À libérer tous les providers du conteneur, pour que chaque test reparte d'un état vierge
  • À forcer la reconstruction de l'arbre de widgets
  • À annuler la surcharge de deckRandomProvider
Réponse : le ProviderContainer créé dans setUp détient l'instance de DeckNotifier et son état. Sans dispose(), un état résiduel pourrait fuir vers le test suivant. Dans map_screen_test.dart, le même rôle est tenu par addTearDown(container.dispose).

3. Que vérifient les deux dernières lignes de test/unit/localization_test.dart, expect(cardData.getName('es'), 'Strike Test') et expect(cardData.getDescription('de'), 'Deals 6 damage.') ?

  • Que l'espagnol et l'allemand sont des locales supportées par le jeu
  • Que CardData.fromJson refuse les locales inconnues
  • Que les clés name_es et description_de sont bien lues du JSON
  • Que toute locale autre que 'fr' retombe sur l'anglais, car getName s'écrit locale == 'fr' ? nameFr : nameEn
Réponse : dans lib/models/data/card_data.dart, getName est un ternaire : locale == 'fr' ? nameFr : nameEn. L'anglais n'est pas « l'autre langue », c'est le repli universel. Le test garantit qu'un téléphone configuré en espagnol affiche de l'anglais plutôt qu'une chaîne vide.

4. Le pipeline de publication échoue immédiatement après le push du tag v0.4.8. Quelle est la cause la plus probable ?

  • Le tag, le champ version: de pubspec.yaml et la dernière entrée de patch_notes.json ne concordent pas
  • Le build Windows n'a pas été lancé localement avant le push
  • Le déploiement web écrase le dossier /v0.4.7/ existant
  • dart analyze n'a pas été relancé après le tag
Réponse : le README l'annonce : « Le pipeline vérifie que le tag, pubspec.yaml et patch_notes.json concordent ». C'est le premier contrôle. Si le tag est vraiment erroné, on le supprime (git push --delete origin v0.4.8), on corrige et on le repose ; sinon « Re-run failed jobs » est sûr sur tous les jobs.

5. Les statuts weakness (−25 % de dégâts) et vulnerable (+50 %) sont calculés dans DamagePipeline.calculate. Pourquoi ne les voit-on jamais en jeu ?

  • Parce que DamagePipeline n'est appelé que pour les boss
  • Parce que EffectResolver.createStatus ne sait pas les construire
  • Parce qu'aucune entrée d'assets/data/ n'utilise ces statusId : cards.json ne référence que poison, burn, freeze, shock, strength et armor_regen
  • Parce que le HUD ne sait pas afficher d'icône pour ces deux statuts
Réponse : toute la chaîne technique existe — createStatus les fabrique, DamagePipeline les applique aux étapes 1 et 4, status_effects_panel.dart et status_indicator.dart les affichent. Il manque uniquement du contenu : une carte avec "statusId": "weakness" suffirait à réveiller la mécanique.
