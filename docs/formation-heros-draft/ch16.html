Événements, repos et autel des reliques

Trois nœuds sans combat, trois façons différentes de dépenser une ressource. Ils partagent un même contrat : on ne quitte pas le nœud sans avoir agi.

Une carte de Hero's Draft n'est pas faite que de combats. Sur les huit valeurs de MapNodeType, trois désignent des nœuds où l'on ne joue aucune carte, où aucun ennemi n'apparaît, et où pourtant l'état de la run change de façon définitive :

lib/models/map_node.dartdart
enum MapNodeType { combat, elite, shop, rest, event, boss, relicExchange, forgeFusion }

Ce chapitre traite de event (l'événement narratif à choix multiples), rest (le feu de camp) et relicExchange (l'autel des reliques). Le nœud shop a son propre chapitre, et forgeFusion aussi. Les trois nœuds étudiés ici ont un point commun structurant : ils vous obligent à faire un choix. Ce ne sont pas des salles de repos optionnelles où l'on passe sans rien faire — le code va jusqu'à désactiver le bouton « retour » du système tant que vous n'avez pas agi.

Le routage vers les trois écrans se fait au même endroit, dans le switch de la carte :

lib/ui/screens/map_screen.dartdart

    switch (node.type) {
      // ...
      case MapNodeType.rest:
        destination = const RestScreen();
        break;
      case MapNodeType.event:
        destination = const EventScreen();
        break;
      case MapNodeType.relicExchange:
        destination = RelicExchangeScreen(node: node);
        break;
      // ...
    }

    Navigator.of(
      context,
    ).push(MaterialPageRoute(builder: (context) => destination));

Notez la différence : RestScreen et EventScreen sont des const sans paramètre — ils lisent tout ce dont ils ont besoin dans les providers. RelicExchangeScreen, lui, reçoit le node. Vous verrez en section 7 pourquoi : l'identifiant du nœud sert de graine à un tirage aléatoire déterministe.

1. Le modèle d'événement

Un événement, dans Hero's Draft, est une donnée pure. Aucun code Dart ne décrit « L'Autel Mystérieux » : le fichier Données assets/data/events.json contient cinq objets, et c'est tout le contenu narratif du jeu. Le modèle qui les charge tient en trois classes emboîtées, dans un seul fichier.

lib/models/data/event_data.dart ├── EventData // un événement : titre, description, liste de choix │ └── EventChoice // un bouton : libellé, texte de résultat, liste d'actions │ └── EventAction // une paire { type, value }

Cette hiérarchie est volontairement plate. Un EventChoice n'est pas une classe polymorphe avec des sous-types (DamageChoice, GoldChoice…) : c'est une simple liste d'actions typées. Le type est une String, la valeur est un dynamic. Toute la logique de dispatch se fait dans un switch sur cette chaîne, dans le contrôleur. C'est un choix de conception qui a un coût (aucune vérification au compile-time) et un bénéfice énorme (ajouter un événement ne demande pas une ligne de Dart).

Quatre remarques importantes sur cette structure.

1. Le bilinguisme est dans les données, pas dans les fichiers ARB. Le reste de l'interface passe par AppLocalizations (les clés l10n.eventGainGold(…) que vous verrez plus loin). Mais le contenu des événements — titres, descriptions, libellés de choix, textes de résultat — est stocké en double dans le JSON, suffixé _fr et _en. Il n'y a pas de troisième langue possible sans toucher au modèle.

2. Le libellé du bouton répète les effets à la main. Regardez "text_fr": "Sacrifier votre sang (-15 PV, +1 Attaque)" : la parenthèse est du texte libre, pas généré. Si vous changez "value": 15 en 20 sans corriger le libellé, le joueur lira « -15 PV » et en prendra 20. Rien ne le détectera.

3. Le tableau actions peut être vide. C'est le cas du troisième choix. Un choix sans action reste un choix valide : il résout l'événement, affiche son texte de résultat, et libère le nœud. C'est le « je passe » assumé.

4. Les actions sont ordonnées et exécutées séquentiellement. take_damage puis gain_strength : l'ordre du tableau est l'ordre d'application. Sur ces cinq événements l'ordre n'a pas d'impact, mais si vous ajoutiez {"type": "gain_max_hp", "value": 20} suivi de {"type": "heal", "value": 20}, l'inverse ne donnerait pas le même résultat.

Le désérialiseur

EventData.fromJson gère deux formats : le format bilingue actuel (title_fr / title_en) et un format monolingue historique (title seul). Le ?? en cascade fait toute la rétrocompatibilité :

lib/models/data/event_data.dartdart
class EventData {
  final String id;
  final String titleEn;
  final String titleFr;
  final String descriptionEn;
  final String descriptionFr;
  final List<EventChoice> choices;

  // ...

  String getTitle(String locale) => locale == 'fr' ? titleFr : titleEn;
  String getDescription(String locale) =>
      locale == 'fr' ? descriptionFr : descriptionEn;

  factory EventData.fromJson(Map<String, dynamic> json) {
    final tEn = json['title_en'] as String? ?? json['title'] as String? ?? '';
    final tFr = json['title_fr'] as String? ?? json['title'] as String? ?? '';
    final dEn =
        json['description_en'] as String? ??
        json['description'] as String? ??
        '';
    final dFr =
        json['description_fr'] as String? ??
        json['description'] as String? ??
        '';

    return EventData(
      id: json['id'] as String,
      titleEn: tEn,
      titleFr: tFr,
      descriptionEn: dEn,
      descriptionFr: dFr,
      choices: (json['choices'] as List)
          .map((c) => EventChoice.fromJson(c as Map<String, dynamic>))
          .toList(),
    );
  }
}

Le sélecteur de langue est la méthode getTitle(locale) : une comparaison de chaîne, locale == 'fr', avec l'anglais en défaut implicite. Même schéma pour EventChoice.getText et getResultText. Le locale vient toujours de Localizations.localeOf(context).languageCode dans les écrans.

Le maillon terminal, EventAction, est d'une simplicité désarmante :

lib/models/data/event_data.dartdart
class EventAction {
  final String type; // gain_gold, take_damage, heal, gain_relic
  final dynamic value;

  EventAction({required this.type, required this.value});

  factory EventAction.fromJson(Map<String, dynamic> json) {
    return EventAction(type: json['type'] as String, value: json['value']);
  }
}
Piège : dynamic value

value n'est pas typé. Dans EventController.selectChoice, chaque branche fait un action.value as int — un cast qui explose à l'exécution si le JSON contient "value": "15" (une chaîne) ou "value": 1.5. En revanche EventChoice.isSelectable, lui, est défensif : il fait action.value is int ? action.value as int : int.tryParse(action.value.toString()) ?? 0. Les deux endroits ne font donc pas les mêmes hypothèses sur les données. Un JSON avec une valeur en chaîne passerait le test de sélectionnabilité et planterait à l'application.

Le chargement se fait avec tous les autres fichiers de données, dans le gameDataLoaderProvider : neuf _loadJsonList lancés en parallèle par un Future.wait, dont le cinquième est le nôtre.

Côté état de jeu, un événement en cours tient dans trois champs. Riverpod EventState est immuable, comme tous les états du projet :

lib/models/event_state.dartdart
class EventState {
  final EventData? activeEvent;
  final EventChoice? selectedChoice;
  final bool isResolved;

  const EventState({
    this.activeEvent,
    this.selectedChoice,
    this.isResolved = false,
  });

  EventState copyWith({
    EventData? activeEvent,
    EventChoice? selectedChoice,
    bool? isResolved,
    bool clearSelectedChoice = false,
  }) {
    return EventState(
      activeEvent: activeEvent ?? this.activeEvent,
      selectedChoice: clearSelectedChoice
          ? null
          : (selectedChoice ?? this.selectedChoice),
      isResolved: isResolved ?? this.isResolved,
    );
  }
}

Le drapeau clearSelectedChoice est le motif habituel du projet pour « remettre à null » un champ nullable : sans lui, selectedChoice: null serait indiscernable de « ne change pas ce champ », puisque null ?? this.selectedChoice renvoie l'ancienne valeur. Ce drapeau n'est en fait jamais utilisé par EventController, qui reconstruit toujours un EventState complet quand il repart de zéro.

Et l'entrée dans l'écran déclenche un tirage uniforme parmi les cinq événements disponibles :

lib/game/controllers/event_controller.dartdart
  /// Sélectionne un événement aléatoire parmi la liste disponible
  void initializeEvent(List<EventData> events) {
    if (events.isEmpty) {
      state = const EventState(
        activeEvent: null,
        selectedChoice: null,
        isResolved: false,
      );
      return;
    }

    final random = Random();
    final chosen = events[random.nextInt(events.length)];
    state = EventState(
      activeEvent: chosen,
      selectedChoice: null,
      isResolved: false,
    );
  }

  /// Initialise un événement spécifique (utile pour les tests unitaires)
  void setEvent(EventData event) { /* ... */ }
Règle du jeu

Le tirage est uniforme et sans mémoire : random.nextInt(events.length) sur les 5 événements, soit 20 % chacun, à chaque nœud event. Rien n'empêche le même événement de tomber deux fois d'affilée, et aucun événement n'est « consommé » après avoir été vu.

L'appel est fait depuis initState, mais différé d'une microtask :

lib/ui/screens/event_screen.dartdart
  @override
  void initState() {
    super.initState();
    Future.microtask(() {
      final gameData = ref.read(gameDataLoaderProvider).requireValue;
      ref.read(eventProvider.notifier).initializeEvent(gameData.events);
    });
  }
Bonne pratique

Modifier un provider directement dans initState lèverait une assertion Riverpod : on ne peut pas notifier des listeners pendant la construction de l'arbre. Le Future.microtask repousse l'appel juste après la première frame, quand l'arbre est stable. C'est le motif standard pour « initialiser un état au montage d'un écran ».

2. Les huit types d'action

Toute la mécanique des événements passe par un unique switch sur action.type, dans EventController.selectChoice. Sept chaînes y sont reconnues ; un huitième cas — la liste d'actions vide — n'entre jamais dans la boucle.

lib/game/controllers/event_controller.dartdart
    state = state.copyWith(selectedChoice: choice, isResolved: true);

    RelicData? chosenRelic;
    final runController = ref.read(runProvider.notifier);
    final inventoryController = ref.read(inventoryProvider.notifier);

    for (var action in choice.actions) {
      switch (action.type) {
        case 'gain_gold':
          inventoryController.gainGold(action.value as int);
          break;
        case 'spend_gold':
          inventoryController.spendGold(action.value as int);
          break;
        case 'take_damage':
          runController.takeDamage(action.value as int);
          break;
        case 'heal':
          runController.heal(action.value as int);
          break;
        case 'gain_max_hp':
          runController.applyHeroStatModifier(maxPvAcc: action.value as int);
          break;
        case 'gain_strength':
          runController.applyHeroStatModifier(attackAcc: action.value as int);
          break;
        case 'gain_relic':
          // bloc de tirage détaillé en section 5
          break;
      }
    }

    return chosenRelic;

Remarquez la première ligne : isResolved passe à true avant que la moindre action soit appliquée. Si un cast échouait au milieu de la boucle, l'événement serait déjà marqué résolu avec des effets partiellement appliqués.

type Valeurs présentes dans events.json Méthode appelée dans selectChoice Effet exact sur l'état
gain_gold 15, 50, 100 inventoryController.gainGold(value) gold = gold + value. Aucun plafond, aucune vérification.
spend_gold 20, 25, 40, 50 inventoryController.spendGold(value) Retourne false et ne fait rien si gold < value ; sinon gold = gold - value. La valeur de retour est ignorée.
take_damage 10, 12, 15, 18 runController.takeDamage(value) Passe par EntityStats.takeDamage : l'armure absorbe d'abord, puis les PV, avec if (newPv < 0) newPv = 0. Hors combat l'armure vaut 0 (remise à zéro dans completeCurrentNode), donc les dégâts vont intégralement aux PV.
heal 15, 25, 30 runController.heal(value) currentPv = (currentPv + value).clamp(0, maxPv). Le surplus est perdu.
gain_max_hp −12, 8, 10 runController.applyHeroStatModifier(maxPvAcc: value) maxPv += value, puis currentPv = (currentPv + (value > 0 ? value : 0)).clamp(0, newMaxPv). Un gain soigne d'autant ; une perte ne retire pas de PV courants mais les rabote par le clamp si l'on était trop haut.
gain_strength 1 runController.applyHeroStatModifier(attackAcc: value) attaque = attaque + value, définitivement pour la run.
gain_relic 1 Bloc de tirage interne (voir section 5) Tire une rareté, filtre le catalogue, choisit une relique, appelle inventoryController.addRelic. La value n'est jamais lue : "value": 1 ou "value": 3 donnent une seule relique.
liste vide [] — Aucune : la boucle for ne s'exécute pas isResolved passe à true, selectedChoice est mémorisé, l'écran affiche le badge « Aucun effet » (_buildNoEffectBadge) et le bouton CONTINUER.

Le cas gain_max_hp négatif

C'est le seul type dont la valeur peut être négative dans les données. Le choix « Purifier son esprit » de la Fontaine Bénie retire 12 PV maximum en échange de +1 attaque :

assets/data/events.jsonjson
      {
        "text_en": "Purify your mind (-12 Max HP, +1 Attack)",
        "text_fr": "Purifier son esprit (-12 PV Max, +1 Attaque)",
        "result_text_en": "You plunge your head into the fountain. The pain is intense, but your mind becomes incredibly sharp.",
        "result_text_fr": "Vous plongez votre tête dans la fontaine. La douleur est vive, mais votre esprit devient incroyablement aiguisé.",

Voici pourquoi le signe change tout, dans applyHeroStatModifier :

lib/game/controllers/run/player_stats_manager.dartdart
  void applyHeroStatModifier({
    int maxPvAcc = 0,
    int attackAcc = 0,
    // ...
  }) {
    final currentStats = controller.currentState.heroStats;
    final newMaxPv = currentStats.maxPv + maxPvAcc;
    final newCurrentPv =
        (currentStats.currentPv + (maxPvAcc > 0 ? maxPvAcc : 0)).clamp(
          0,
          newMaxPv,
        );
    // ...
  }

Le ternaire (maxPvAcc > 0 ? maxPvAcc : 0) est le cœur de la mécanique. Déroulons les deux sens avec un Paladin (100 PV max) :

Règle du jeu

Un gain_max_hp positif soigne également du même montant : +10 PV max vaut +10 PV max et +10 PV courants. À l'inverse, un gain_max_hp négatif ne retire jamais de PV courants directement — mais le clamp final vous rabote si vous dépassiez le nouveau maximum. Un héros à pleine vie perd donc bien 12 PV effectifs à la Fontaine ; un héros à 60/100 n'en perd aucun.

Piège de débutant

Si vous ajoutez {"type": "gain_luck", "value": 1} dans events.json, le jeu ne plantera pas et ne vous préviendra pas. Le badge affichera littéralement gain_luck: 1 avec une icône de point d'interrogation, et le contrôleur n'appliquera rien. C'est le prix des types en String : le compilateur ne peut pas vous aider. Ajoutez toujours le case dans selectChoice et dans les deux méthodes de badge (_buildActionBadge et _buildCompactActionBadge).

4. Les choix impossibles

Un choix qui coûte 50 or n'a pas de sens si le joueur en a 30. Un choix qui inflige 15 dégâts à un héros qui a 12 PV le tuerait sur un nœud sans combat — ce qui n'est pas l'expérience visée. Une seule méthode répond à ces trois questions : EventChoice.isSelectable.

lib/models/data/event_data.dartdart
  bool isSelectable(int currentHp, int currentGold, int currentMaxHp) {
    for (final action in actions) {
      if (action.type == 'take_damage') {
        final damage = action.value is int
            ? action.value as int
            : int.tryParse(action.value.toString()) ?? 0;
        if (currentHp <= damage) {
          return false;
        }
      } else if (action.type == 'spend_gold') {
        final cost = action.value is int
            ? action.value as int
            : int.tryParse(action.value.toString()) ?? 0;
        if (currentGold < cost) {
          return false;
        }
      } else if (action.type == 'gain_max_hp') {
        final val = action.value is int
            ? action.value as int
            : int.tryParse(action.value.toString()) ?? 0;
        if (val < 0 && currentMaxHp <= -val) {
          return false;
        }
      }
    }
    return true;
  }

Trois règles, et trois seulement. Notez l'asymétrie des comparateurs — elle n'est pas accidentelle.

Soustractions successives contre seuils cumulés

Le point technique intéressant de ce bloc est sa forme. Le contrôleur de récompenses, qui utilise exactement les mêmes quatre valeurs, les écrit en seuils cumulés :

lib/game/controllers/reward_controller.dartdart

        double roll = rand;

          rarity = RelicRarity.epic;
        } else if (roll < legChance + epicChance + rareChance) {
          rarity = RelicRarity.rare;
        } else if (roll < legChance + epicChance + rareChance + uncommonChance) {
          rarity = RelicRarity.uncommon;
        } else {
          rarity = RelicRarity.common;

EventController, lui, décrémente une variable de travail et compare toujours à un seuil simple. Les deux écritures sont rigoureusement équivalentes. Déroulons l'algèbre, en notant L, E, R, U les quatre probabilités :

illustrationtext
Branche épique
  cumulée     : roll < L + E
  soustractive: (roll - L) < E          ⟺  roll < L + E          ✔ identique

Branche rare
  cumulée     : roll < L + E + R
  soustractive: (roll - L - E) < R      ⟺  roll < L + E + R      ✔ identique

Branche peu commune
  cumulée     : roll < L + E + R + U
  soustractive: (roll - L - E - R) < U  ⟺  roll < L + E + R + U  ✔ identique

À chaque étage, la soustraction déjà appliquée reconstitue exactement la somme du seuil cumulé. Prenons un exemple chiffré avec luck = 0 (donc L=1, E=5, R=14, U=20) et un jet de 17,3 :

ÉtapeForme cumuléeForme soustractiveVerdict
Légendaire17,3 < 1 → fauxcurrentRoll = 17,3 < 1 → fauxnon
Épique17,3 < 6 → fauxcurrentRoll = 16,3 < 5 → fauxnon
Rare17,3 < 20 → vraicurrentRoll = 11,3 < 14 → vrairare

Même verdict, deux chemins. Pourquoi deux écritures alors ? Aucune raison technique : c'est une duplication de logique métier. La forme soustractive économise trois additions et évite de réécrire legChance + epicChance + rareChance, mais elle mute une variable locale, ce qui rend le raisonnement légèrement plus dur à suivre. La forme cumulée se lit comme un tableau de seuils.

Point d'attention : trois copies de la même table

Les quatre formules 1.0 + 0.5×L / 5.0 + 1.0×L / 14.0 + 2.0×L / 20.0 + 3.0×L apparaissent à l'identique dans trois fichiers : event_controller.dart, reward_controller.dart et ui/widgets/map/dialogs/probabilities_dialog.dart (méthode calculateRelicProbabilities, qui affiche les pourcentages au joueur). Rééquilibrer la chance demande de modifier les trois. Le jour où l'une des trois est oubliée, l'écran de probabilités mentira au joueur sans qu'aucun test ne s'en aperçoive.

La graine déterministe

C'est le point le plus intéressant de cet écran. L'offre de l'autel — quelle relique est proposée — ne doit pas changer si le joueur quitte l'écran et y revient. Sinon, il suffirait d'entrer et sortir en boucle pour faire apparaître une légendaire.

lib/ui/screens/relic_exchange_screen.dartdart
        data: (gameData) {
          if (_offeredRelic == null) {
            final seed = (widget.node.id.hashCode ^ runState.act).abs();
            final random = Random(seed);

            // 1. Roll for rarity: Uncommon (40%), Rare (35%), Epic (20%), Legendary (5%)
            final double roll = random.nextDouble();

            } else if (roll < 0.75) {

            } else if (roll < 0.95) {

            } else {

Décomposons (widget.node.id.hashCode ^ runState.act).abs() :

  • widget.node.id est une chaîne du type node_3_2 — les identifiants sont générés par 'node_${y}_$x' dans map_node_generator.dart.
  • .hashCode transforme cette chaîne en entier de façon déterministe : la même chaîne donne toujours le même entier.
  • ^ runState.act est un OU exclusif bit à bit avec le numéro d'acte. C'est indispensable : les identifiants de nœuds se répètent d'un acte à l'autre (node_3_2 existe à l'acte 5 comme à l'acte 10). Sans ce XOR, la même position sur la carte offrirait éternellement la même relique.
  • .abs() normalise en positif — un hashCode peut être négatif.

Comme Random(seed) est réinstancié à chaque appel avec la même graine, la séquence de tirages est identique à chaque fois. Le premier nextDouble() donne toujours le même nombre, et le nextInt(eligibleRelics.length) qui suit aussi.

Règle du jeu

L'offre d'un autel est figée par la paire (identifiant du nœud, acte). Quitter l'écran et y revenir donne rigoureusement la même relique. Il n'y a rien à « rerouler ». En revanche le même nœud d'un acte à l'autre offrira autre chose, grâce au XOR.

Piège de conception : la légendaire est presque inatteignable

Le catalogue ne compte que 3 reliques épiques (Trèfle Enchanté 🍀, Pierre d'Énergie ⚡, Plume de Phénix 🪶). Pour saisir une offre légendaire — déjà tirée à 5 % — il faut donc posséder simultanément trois reliques épiques, ce qui, avec un taux de drop épique de 5 % à luck 0, arrive rarement. Symétriquement, l'offre la plus fréquente (peu commune, 40 %) demande 3 communes, dont le jeu regorge. Le taux de tirage et la faisabilité vont dans le même sens.

Sélectionner exactement trois reliques

Règle du jeu

Il faut sacrifier exactement trois reliques, ni deux ni quatre, toutes de la rareté immédiatement inférieure à celle offerte. Si vous en possédez moins de trois, l'écran affiche un encadré rouge à la place de la grille et il ne reste que le bouton PARTIR. Le taux de change est donc fixe : 3 pour 1, avec un gain d'un cran de rareté.

exchangeRelics : retirer avant d'ajouter

La transaction elle-même est de six lignes, mais l'ordre de ces lignes est essentiel :

lib/game/controllers/run/player_stats_manager.dartdart
  void exchangeRelics(List<RelicData> sacrificed, RelicData gained) {
    for (var relic in sacrificed) {
      removeRelicEffect(relic);
    }
    final sacrificedIds = sacrificed.map((r) => r.id).toList();
    ref.read(inventoryProvider.notifier).removeRelics(sacrificedIds);
    ref.read(inventoryProvider.notifier).addRelic(gained);
  }

Pourquoi cette étape removeRelicEffect ? Parce que certaines reliques ne s'appliquent pas « quand un événement arrive » mais une fois pour toutes, à l'acquisition. Ce sont celles dont le trigger vaut startOfRun : elles poussent définitivement une statistique du héros. Les retirer de l'inventaire ne suffirait pas — le bonus resterait acquis.

lib/game/controllers/run/player_stats_manager.dartdart
  void removeRelicEffect(RelicData relic) {
    if (relic.trigger == RelicTrigger.startOfRun) {
      switch (relic.effectType) {
        case 'gain_mana':
          applyHeroStatModifier(maxManaAcc: -relic.value);
          break;
        case 'gain_strength':
          applyHeroStatModifier(attackAcc: -relic.value);
          break;
        case 'gain_luck':
          applyHeroStatModifier(luckAcc: -relic.value);
          break;
        case 'gain_crit':
          applyHeroStatModifier(critChanceAcc: -relic.value);
          break;
        case 'increase_cards_per_turn':
          applyRunRuleModifier(cardsPerTurnAcc: -relic.value);
          break;
      }
    }
  }

Le miroir exact de applyRelicEffect, avec les valeurs négatives. Sur les 25 reliques du catalogue, 9 ont le trigger startOfRun — ce sont les seules concernées. Les autres (startOfCombat, endOfTurn, onEnemyKilled…) n'ont aucun état permanent à défaire : elles agissent au moment du déclencheur, en lisant l'inventaire. Les faire disparaître de l'inventaire suffit.

À retenir — la symétrie acquisition / perte

InventoryController.addRelic appelle applyRelicEffect si le trigger est startOfRun. exchangeRelics appelle removeRelicEffect qui ne fait quelque chose que si le trigger est startOfRun. Les deux moitiés sont écrites dans deux fichiers différents mais forment une paire : toute nouvelle valeur d'effectType startOfRun doit être ajoutée aux deux switch, sinon l'échange laissera un bonus fantôme.

Point d'attention : le tirage se fait dans build()

Relisez le code de la graine : il est à l'intérieur du build(), dans la branche data: du gameDataAsync.when(...), et il écrit dans deux champs de State (_offeredRelic et _requiredRarity). C'est un anti-pattern Flutter caractérisé : build() doit être une fonction pure de l'état vers les widgets. Flutter se réserve le droit de l'appeler à n'importe quel moment, plusieurs fois de suite, sans que rien n'ait changé (redimensionnement, changement de thème, rebuild d'un ancêtre, animation de route…).

Pourquoi ça marche quand même ici ? Deux raisons cumulées. D'abord la garde if (_offeredRelic == null) rend l'écriture idempotente : elle n'a lieu qu'une fois par instance de State. Ensuite, et c'est le vrai filet de sécurité, la graine est déterministe : Random(seed) est reconstruit à chaque passage avec la même valeur, donc même si la garde sautait, les rebuilds successifs recalculeraient exactement la même relique. Le déterminisme du tirage neutralise l'impureté du build.

Cela reste fragile. La place correcte de ce calcul est initState — impossible en l'état, car il a besoin de gameData, encore en cours de chargement au montage. Un ref.listen sur gameDataLoaderProvider, ou un provider dédié prenant le node en paramètre, résoudrait proprement le problème.

La sortie de l'autel

L'écran a deux boutons, et les deux appellent completeCurrentNode() :

  void _leave() {
    ref.read(runProvider.notifier).completeCurrentNode();

Piège : l'autel n'a pas de PopScope

RelicExchangeScreen construit son ScreenScaffold sans passer canPop ni onPopInvokedWithResult. Or le gabarit n'enveloppe dans un PopScope que si l'un des deux est fourni. Résultat : le geste de retour système sort de l'écran sans appeler completeCurrentNode(). Le nœud reste marqué non complété et le joueur peut y revenir — pour retrouver, grâce à la graine déterministe, exactement la même offre. Le bug est donc sans conséquence sur l'équilibrage, mais c'est bien un oubli : les deux autres nœuds sans combat verrouillent leur sortie, celui-ci non.
