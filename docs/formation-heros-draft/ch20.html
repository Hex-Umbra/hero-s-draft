Chapitre 20

Sauvegarde, localisation et tutoriel

Trois systèmes transverses qui ne touchent pas aux règles du jeu, mais sans lesquels une run ne survivrait pas à la fermeture de l'application.

Dans ce chapitre

  2. Les points de sauvegarde
  3. Le chargement tolérant aux pannes
  4. Le patron « re-résoudre plutôt que dupliquer »

Les dix-neuf chapitres précédents ont décrit le jeu : les cartes, les combats, la carte du monde, la forge. Tout cela vit en mémoire, dans des Notifier Riverpod. Si l'utilisateur ferme l'application, tout disparaît. Ce chapitre s'occupe des trois systèmes qui entourent le jeu sans en faire partie :

  • la sauvegarde, qui écrit l'état de la run sur le disque et sait le relire même quand le jeu a changé entre-temps ;
  • la localisation, qui existe en deux exemplaires — un pour l'interface, un pour le contenu du jeu — et qui a de bonnes raisons de ne pas être unifiée ;
  • le tutoriel, un module complètement isolé qui rejoue le jeu en carton-pâte sans jamais toucher à l'état réel.

Ces trois systèmes ont un point commun : ils sont transverses. Ils traversent toutes les couches de l'application sans appartenir à aucune. C'est exactement le genre de code qui pourrit vite si on ne se donne pas des contrats clairs. Regardons ceux qu'a choisis Hero's Draft.

1. Le contrat de sauvegarde

Le contrat tient en une phrase : une seule clé, un seul blob JSON, une seule version de schéma. Tout est dans lib/services/save_service.dart, et le fichier fait moins de 110 lignes.

lib/services/save_service.dartdart
class SaveService {
  static const String _saveKey = 'run_save_v1';
  static const int _schemaVersion = 1;

Deux constantes, et le vocabulaire du chapitre est posé. run_save_v1 est le nom de la clé dans shared_preferences — le petit magasin clé/valeur persistant que Flutter expose sur toutes les plateformes (il s'appuie sur SharedPreferences sur Android, NSUserDefaults sur iOS, un fichier JSON sur desktop, localStorage sur le web). _schemaVersion = 1 est le numéro de format écrit dans le blob.

Notez le v1 présent deux fois : dans le nom de la clé et dans le champ schemaVersion. Ce n'est pas redondant, ce sont deux leviers différents. Changer le nom de clé (run_save_v2) rend l'ancienne sauvegarde invisible : elle reste sur le disque, elle n'est simplement plus lue. Changer _schemaVersion rend l'ancienne sauvegarde détectable et rejetable — on verra en section 3 que le code s'en sert pour l'effacer proprement.

Le payload complet

Voici la méthode save en entier. C'est le cœur du système : six clés, aucune logique conditionnelle, aucune exception attrapée.

lib/services/save_service.dartdart
  static Future<void> save(RefReader read) async {
    final prefs = await SharedPreferences.getInstance();
    final payload = {
      'schemaVersion': _schemaVersion,
      'savedAt': DateTime.now().toIso8601String(),
      'run': read(runProvider).toJson(),
      'deck': read(deckProvider).toJson(),
      'inventory': read(inventoryProvider).toJson(),
      'skills': read(skillProvider).toJson(),
    };
    await prefs.setString(_saveKey, jsonEncode(payload));
  }

Lisez-la comme une déclaration de ce qui compose une run. Quatre états, pas un de plus :

Piège : savedAt est écrit mais jamais lu

Cherchez savedAt dans tout lib/ : une seule occurrence, celle de l'écriture. Aucun écran n'affiche « dernière sauvegarde : il y a 3 minutes », aucune logique ne compare deux horodatages. C'est un champ de confort posé pour plus tard. Ce n'est pas grave — un champ JSON inutilisé ne coûte rien — mais il ne faut pas croire qu'il fait quelque chose.

Le typedef RefReader

Un détail de signature mérite un arrêt. save ne prend pas un Ref Riverpod, ni un WidgetRef : elle prend un RefReader.

lib/services/save_service.dartdart
/// The subset of Ref/WidgetRef/ProviderContainer that SaveService needs:
/// a plain synchronous provider read. Accepting this instead of `Ref`
/// lets the same code run from a Notifier's `ref`, a widget's `WidgetRef`,
/// and a bare `ProviderContainer` in tests — none of which share a common
/// supertype in riverpod 2.6.1, but all of which expose this exact method.
typedef RefReader = T Function<T>(ProviderListenable<T> provider);

C'est un type de fonction générique. En Dart, typedef peut nommer une signature de fonction, et ici la signature est elle-même générique (T Function<T>(...)). Traduction : « n'importe quelle fonction qui, pour un type T quelconque, prend un provider de T et rend un T ».

Le commentaire explique le vrai motif : dans Riverpod 2.6.1, Ref.read, WidgetRef.read et ProviderContainer.read ont exactement la même forme mais n'ont aucun ancêtre commun. Accepter le type le plus large aurait forcé à écrire trois surcharges. Accepter la capacité plutôt que l'objet règle le problème : à l'appel, on passe simplement ref.read (la méthode elle-même, sans parenthèses — un tear-off).

Bonne pratique — dépendre d'une capacité, pas d'un type

Quand un service n'a besoin que d'une méthode d'un gros objet, prenez cette méthode en paramètre plutôt que l'objet. Le service devient testable sans mock : dans un test, on lui passe container.read et c'est terminé. C'est la version Dart du principe de ségrégation des interfaces.

Cette liste n'est pas un oubli, c'est une décision de granularité. Hero's Draft ne sauvegarde pas « l'instant » : il sauvegarde « le dernier nœud terminé ». Les quatre providers absents contiennent tous de l'état intra-nœud.

Conséquence concrète pour le joueur

Fermer l'application en plein combat fait perdre le combat en cours. Au redémarrage, « Continuer » recharge l'état tel qu'il était avant d'entrer dans le nœud : le joueur se retrouve sur la carte du monde, avec ses PV et son deck d'avant le combat, et le nœud qu'il était en train de jouer n'est pas marqué comme complété. Il devra le refaire. Aucun progrès n'est corrompu — mais le nœud en cours est perdu.

Notez la subtilité : les PV du héros sont dans EntityStats.toJson, avec les statuts, l'armure et l'XP. Ils sont donc bien sérialisés. Mais comme la sauvegarde n'est déclenchée qu'à la fin d'un nœud (section 2), la valeur écrite sur disque est toujours celle d'une fin de nœud, jamais celle du milieu d'un combat. La granularité de déclenchement compte autant que le contenu du payload.

2. Les points de sauvegarde

Question naturelle : qui appelle SaveService.save ? Grepez le projet — la réponse est un seul endroit, et ce n'est pas un écran.

lib/game/controllers/checkpoint_controller.dartdart
class CheckpointNotifier extends Notifier<int> {
  @override
  int build() => 0;

  /// Signale qu'un nœud de la carte vient d'être résolu (combat, boutique,
  /// repos, event, forge, échange de reliques, ou draft de Level Up).
  void bump() => state = state + 1;
}

final checkpointProvider =
    NotifierProvider<CheckpointNotifier, int>(CheckpointNotifier.new);

/// Écoute checkpointProvider et déclenche une sauvegarde à chaque bump().
/// Doit être lu une fois au démarrage de l'app pour s'activer (voir main.dart).
final autosaveOrchestratorProvider = Provider<void>((ref) {
  ref.listen<int>(checkpointProvider, (previous, next) {
    SaveService.save(ref.read);
  });
});

Ce fichier de vingt-trois lignes est un petit chef-d'œuvre de découplage. Décomposons-le.

Un compteur, pas un événement

CheckpointNotifier est un Notifier<int> dont l'état est un entier qui ne fait que monter. bump() ne transporte aucune donnée : il ne dit pas quel nœud a été terminé, ni quand. Il dit juste « il s'est passé quelque chose de sauvegardable ».

Pourquoi un entier plutôt qu'un vrai bus d'événements ? Parce que Riverpod ne notifie ses écouteurs que si l'état change. Si bump() mettait l'état à true, le deuxième bump() ne réveillerait personne : true == true. Un compteur qui s'incrémente garantit que chaque appel produit une valeur neuve, donc une notification. C'est le patron « ticker » et il est plus court que n'importe quelle alternative.

Un Provider<void> comme point d'ancrage

autosaveOrchestratorProvider est déclaré Provider<void> : il ne produit aucune valeur. Personne ne lira jamais son résultat. Il n'existe que pour ses effets de bord — le ref.listen installé dans son corps.

ref.listen est le pendant impératif de ref.watch : au lieu de recalculer le provider quand la dépendance change, il exécute un callback. Ici le callback ignore previous et next et lance simplement la sauvegarde. Il lui passe ref.read — le tear-off dont on parlait en section 1.

Piège : un provider Riverpod est paresseux

Un provider qui n'est jamais lu n'est jamais construit. Le corps de autosaveOrchestratorProvider ne s'exécute pas tant que personne ne le demande — donc le ref.listen n'est jamais installé, donc rien n'est jamais sauvegardé, et l'application fonctionne parfaitement… jusqu'au premier redémarrage. C'est le genre de bug qu'on ne voit pas en développement.

D'où la ligne de main.dart, avec son commentaire explicite :

ref.watch sur un Provider<void> a l'air absurde — on « observe » quelque chose qui vaut toujours null. Mais watch a un second effet, celui qui compte ici : il abonne le widget au provider, ce qui force sa construction et le maintient vivant tant que HerosDraftApp est monté. Comme HerosDraftApp est la racine de l'arbre, l'orchestrateur vit aussi longtemps que l'application.

Les deux appelants de bump()

Deux endroits seulement dans tout lib/ appellent bump(). Le premier est la fin d'un nœud de carte :

lib/game/controllers/run/map_progression_manager.dartdart
  /// Marque le nœud actuel comme complété
  void completeCurrentNode() {
    if (controller.currentState.currentNodeId == null) return;

    MapNode? completedNode;
    final updatedNodes = controller.currentState.mapNodes.map((node) {
      if (node.id == controller.currentState.currentNodeId) {
        node.isCompleted = true;
        completedNode = node;
      }
      return node;
    }).toList();

    // Reset de l'armure et nettoyage des statuts à la fin du combat pour préserver les passifs
    controller.updateState(
      controller.currentState.copyWith(
        mapNodes: updatedNodes,
        heroStats: controller.currentState.heroStats.copyWith(armure: 0, statuses: []),
      ),
    );

    if (completedNode != null && completedNode!.type == MapNodeType.boss) {
      advanceToNextWorld();
    }

    ref.read(checkpointProvider.notifier).bump();
  }

Observez l'ordre : le bump() est la dernière ligne. Le nœud est marqué complété, l'armure est remise à zéro, les statuts sont nettoyés, et si c'était un boss on a déjà généré la carte du monde suivante — ensuite seulement on sauvegarde. La sauvegarde capture donc toujours un état stable, jamais un état à moitié mis à jour.

Le second appelant est la consommation d'un draft de montée de niveau :

lib/game/controllers/run/player_stats_manager.dartdart
  void decrementPendingDrafts() {
    if (controller.currentState.pendingDrafts > 0) {
      controller.updateState(
        controller.currentState.copyWith(
          pendingDrafts: controller.currentState.pendingDrafts - 1,
        ),
      );
      ref.read(checkpointProvider.notifier).bump();
    }
  }

Même structure : on modifie l'état, puis on bump. Et le bump() est à l'intérieur du if : si le compteur de drafts est déjà à zéro, rien ne change et rien n'est sauvegardé. Pas de sauvegarde à vide.

Pourquoi ce second point de contrôle ? Parce qu'un level up peut arriver au milieu d'un combat et mettre plusieurs drafts en attente (pendingDrafts). Le joueur les consomme un par un sur des écrans successifs. Sans ce bump(), fermer l'application entre deux drafts ferait perdre les choix déjà faits.

Bonne pratique — un seul point d'écriture

Aucun écran de jeu n'appelle SaveService.save. Les écrans appellent des méthodes métier (completeCurrentNode, decrementPendingDrafts) qui, elles, bumpent le checkpoint. Résultat : ajouter un nouveau type de nœud ne demande aucune modification du système de sauvegarde, tant que le nœud termine par completeCurrentNode(). Le jour où il faudra sauvegarder ailleurs (une base de données, un serveur), on modifie un seul fichier.

Et l'effacement ?

Trois endroits effacent la sauvegarde, tous via SaveService.clear() : home_screen.dart quand on confirme l'écrasement pour une nouvelle partie, death_overlay.dart sur les deux boutons de l'écran de mort (« Menu principal » et « Changer de classe »), et SaveService.load lui-même en cas de sauvegarde corrompue. Une run morte ne laisse aucune trace : c'est un roguelike, la permadeath doit être réelle.

3. Le chargement tolérant aux pannes

Écrire une sauvegarde est facile. La relire six mois plus tard, après que le jeu a gagné dix cartes et en a perdu trois, c'est le vrai problème. Voici load en entier — c'est la méthode la plus longue du service, et chaque ligne compte.

lib/services/save_service.dartdart
  static Future<SaveLoadResult> load(RefReader read) async {
    final prefs = await SharedPreferences.getInstance();
    final raw = prefs.getString(_saveKey);
    if (raw == null) {
      return const SaveLoadResult(success: false);
    }

    Map<String, dynamic> json;
    try {
      final decoded = jsonDecode(raw);
      if (decoded is! Map<String, dynamic> ||
          decoded['schemaVersion'] != _schemaVersion) {
        throw const FormatException('Unsupported or missing schemaVersion');
      }
      json = decoded;
    } catch (e) {
      if (kDebugMode) {
        debugPrint('SaveService.load: corrupted or unsupported save data ($e)');
      }
      await clear();
      return const SaveLoadResult(success: false);
    }

Premier try/catch. Il couvre trois pannes différentes d'un seul geste :

  1. Le JSON est illisible. jsonDecode lève une FormatException. Ça arrive si l'écriture a été coupée (batterie, kill de l'OS).
  2. Le JSON est valide mais n'est pas un objet. Le test decoded is! Map<String, dynamic> attrape le cas où quelqu'un aurait écrit un tableau ou une chaîne sous la même clé.
  3. La version de schéma ne correspond pas. Le test decoded['schemaVersion'] != _schemaVersion couvre à la fois « pas de champ du tout » (null != 1) et « version 2 lue par un binaire v1 » — un cas réel si l'utilisateur réinstalle une version antérieure de l'application.

Les trois convergent vers le même catch, qui fait deux choses : effacer la sauvegarde et rendre un échec silencieux. Le debugPrint est gardé par kDebugMode — une constante de compilation que le compilateur AOT évalue à false en release, ce qui permet au tree shaker de supprimer complètement le bloc du binaire de production.

La règle : jamais de sauvegarde zombie

Une sauvegarde illisible est effacée, pas ignorée. Si on se contentait de rendre false, SaveService.hasSave() continuerait à répondre true (la clé existe toujours), le bouton « Continuer » resterait affiché, et l'utilisateur cliquerait dessus indéfiniment sans rien obtenir. En effaçant, le prochain build de HomeScreen fait disparaître le bouton. L'échec devient visible et cohérent.

Le second try/catch : l'hydratation

lib/services/save_service.dartdart

Trois choses à remarquer.

Un. Les décodages sont tous faits avant la première hydratation. Ce n'est pas cosmétique : si RunState.fromJsonWithReport lève une exception, on n'a encore écrit dans aucun provider. Le jeu reste dans son état initial propre au lieu d'être à moitié chargé. C'est une transaction manuelle : préparer d'abord, publier ensuite.

Deux. L'ordre d'hydratation est skills → inventory → deck → run, c'est-à-dire du plus simple au plus dépendant. Les compétences ne dépendent de rien, l'inventaire des reliques du catalogue, le deck du catalogue de cartes, et la run de tout le reste (son passif, ses slots de forge). Écrire le plus dépendant en dernier limite le risque qu'un Notifier réagisse à un état incohérent pendant la reconstruction.

Trois. La syntaxe final (inventory, invMissing) = ... est la déstructuration de records, arrivée avec Dart 3. La méthode rend un (InventoryState, List<MissingSaveItem>) — un couple anonyme, sans avoir besoin de déclarer une classe résultat. Idem pour ...invMissing, l'opérateur spread qui aplatit les trois listes de manquants en une seule.

lib/services/save_service.dartdart
class SaveLoadResult {
  final bool success;
  final List<MissingSaveItem> missingItems;

  const SaveLoadResult({required this.success, this.missingItems = const []});

Le patron fromJsonWithReport

C'est l'idée centrale de tout le système de chargement, et elle mérite d'être énoncée seule :

Plutôt que planter, reconstruire ce qui existe et rapporter ce qui manque

Un fromJson classique lève une exception dès qu'une donnée référencée n'existe plus. Un fromJsonWithReport rend un couple (État reconstruit, List<MissingSaveItem>) : il garde tout ce qu'il peut résoudre, jette silencieusement le reste, et consigne chaque perte dans une liste que l'interface affichera au joueur.

Le rapport lui-même est un modèle minuscule, volontairement bilingue :

lib/models/missing_save_item.dartdart
class MissingSaveItem {
  final String id;
  final String nameFr;
  final String nameEn;
  final String category;

  const MissingSaveItem({
    required this.id,
    required this.nameFr,
    required this.nameEn,
    required this.category,
  });

Quatre category sont produites dans le projet : 'card' (dans DeckState._decodePile), 'relic' (dans InventoryState.fromJsonWithReport), 'passive' (dans RunState.fromJsonWithReport) et 'forgeUpgrade' (dans ForgeUpgradeData.filterValidRefs).

DeckState._decodePile, le cas le plus riche

lib/game/controllers/deck_controller.dartdart
  static (List<CardInstance>, List<MissingSaveItem>) _decodePile(
    List<dynamic>? rawPile,
  ) {
    final kept = <CardInstance>[];
    final missing = <MissingSaveItem>[];

    for (final entry in (rawPile ?? const [])) {
      final instance = CardInstance.fromJson(entry as Map<String, dynamic>);
      final freshData = CardData.getById(instance.data.id);
      if (freshData == null) {
        missing.add(
          MissingSaveItem(
            id: instance.data.id,
            nameFr: instance.data.nameFr,
            nameEn: instance.data.nameEn,
            category: 'card',
          ),
        );
        continue;
      }
      final (validUpgrades, upgradesMissing) =
          ForgeUpgradeData.filterValidRefs(instance.forgeUpgrades);
      missing.addAll(upgradesMissing);
      kept.add(instance.copyWith(data: freshData, forgeUpgrades: validUpgrades));
    }

    return (kept, missing);
  }

Quatre gestes en dix-huit lignes :

  1. Décoder l'instance telle qu'elle a été écrite, avec sa CardData complète figée au moment de la sauvegarde.
  2. Re-résoudre la définition fraîche par son identifiant : CardData.getById(instance.data.id) va chercher dans le GameDataRegistry chargé depuis assets/data/cards.json.
  3. Écarter si la carte n'existe plus : on ajoute un MissingSaveItem — en utilisant les noms FR/EN figés dans la sauvegarde, seule trace restante d'une carte supprimée — puis continue.
  4. Remplacer : instance.copyWith(data: freshData, ...) jette la CardData sauvegardée et lui substitue celle du catalogue, tout en conservant uniqueId, rarity et les améliorations de forge encore valides.

Le troisième point est celui qu'on rate quand on écrit ça soi-même. Au moment où l'on veut prévenir le joueur qu'il a perdu « Boule de Feu », la carte n'existe plus dans le catalogue : impossible d'en lire le nom. La seule source disponible est la copie gelée dans le JSON. C'est précisément pour ça que le deck sérialise toute la CardData plutôt qu'un simple identifiant — voir section 4.

_decodePile est appelé cinq fois, une par pile :

Le .. est l'opérateur de cascade de Dart : il appelle une méthode sur un objet et rend l'objet lui-même, ce qui permet d'enchaîner sans répéter missing..

Piège : une carte supprimée peut apparaître cinq fois

Une carte présente dans le master deck et dans la pioche produit deux MissingSaveItem distincts. Le dialogue de home_screen.dart les affiche tels quels, joints par des virgules : le joueur peut donc lire deux fois le même nom. Ce n'est pas faux (deux exemplaires ont bien disparu), mais ce n'est pas dédupliqué non plus. MissingSaveItem implémente pourtant == et hashCode sur ses quatre champs — tout ce qu'il faut pour un .toSet() qui n'est jamais appelé.

ForgeUpgradeData.filterValidRefs

Le même patron, en plus resserré, pour les améliorations de forge :

lib/models/data/forge_upgrade_data.dartdart
  static (List<String>, List<MissingSaveItem>) filterValidRefs(
    List<dynamic>? raw,
  ) {
    final kept = <String>[];
    final missing = <MissingSaveItem>[];
    for (final entry in (raw ?? const [])) {
      final ref = entry as String;
      final id = ref.split(':').first;
      if (getById(id) != null) {
        kept.add(ref);
      } else {
        missing.add(
          MissingSaveItem(
            id: id,
            nameFr: id,
            nameEn: id,
            category: 'forgeUpgrade',
          ),
        );
      }
    }
    return (kept, missing);
  }

Deux détails. D'abord ref.split(':').first : une référence d'amélioration de forge n'est pas un simple identifiant, c'est une chaîne composée id:tier. On ne valide que la partie gauche, le tier étant un nombre qui ne peut pas « disparaître » du catalogue.

Ensuite nameFr: id, nameEn: id. Contrairement aux cartes, la sauvegarde ne stocke pas les noms lisibles des améliorations : elle ne stocke que la référence. Quand une amélioration disparaît, il ne reste que son identifiant technique, et c'est lui qui sera affiché au joueur. C'est un compromis assumé — un identifiant est moins joli mais reste actionnable pour un rapport de bug.

filterValidRefs est appelé à trois endroits : sur les forgeUpgrades de chaque CardInstance (dans _decodePile), sur json['forgeSlots'] et sur chaque entrée de forgeTargetSessions (dans RunState.fromJsonWithReport). Une seule fonction couvre les trois endroits où le jeu mémorise des références de forge.

Point d'attention — une asymétrie qui coûte de la place

L'inventaire ne stocke que ce qu'il utilise (3 champs) ; le deck stocke tout et n'en utilise que 3 (id, nameFr, nameEn) — plus uniqueId, rarity et forgeUpgrades, qui appartiennent à l'instance et non à la définition. Le data.toJson() complet est un reliquat : réduire CardInstance.toJson au triplet identifiant + noms produirait exactement le même comportement pour une fraction de la taille. Rien ne casse aujourd'hui, mais c'est de la dette latente : chaque nouveau champ de CardData grossit toutes les sauvegardes sans jamais être relu.

5. La localisation, système double

Hero's Draft parle français et anglais. Mais il le fait de deux façons complètement séparées, avec deux fichiers sources différents, deux outillages différents et deux syntaxes d'appel différentes. Ce n'est pas un accident historique : les deux ont des contraintes opposées.

(a) L'interface : le système ARB

ARB signifie Application Resource Bundle. C'est le format officiel de Flutter pour les chaînes d'interface : un fichier JSON par langue, plus un générateur de code qui en tire une classe Dart typée.

l10n.yamlyaml
arb-dir: lib/l10n
template-arb-file: app_en.arb
output-localization-file: app_localizations.dart

Trois lignes à la racine du projet, et c'est toute la configuration. arb-dir indique où chercher les fichiers, template-arb-file désigne le modèle de référence (ici l'anglais : c'est lui qui définit les clés et les métadonnées, les autres langues ne font que traduire), output-localization-file nomme le fichier Dart généré.

La génération est déclenchée par la ligne generate: true de pubspec.yaml sous la section flutter: — dès lors, flutter pub get et flutter run régénèrent app_localizations.dart automatiquement. Le paquet flutter_localizations et intl: ^0.20.2 sont déclarés en dépendances.

illustrationjson
{
  "@@locale": "fr",

  "continueGame": "CONTINUER",

  "missingItemsTitle": "Objets manquants",
  "missingItemsMessage": "Ces éléments n'existent plus et ont été retirés : {names}",
  "@missingItemsMessage": {
    "placeholders": {
      "names": { "type": "String" }
    }
  },

  "actLevel": "Acte {act} — Niveau {level}",
  "@actLevel": {
    "placeholders": {
      "act":   { "type": "int" },
      "level": { "type": "int" }
    }
  }
}

Cet extrait montre la forme d'un fichier ARB. Les noms de clés (continueGame, missingItemsTitle, missingItemsMessage, actLevel), le nombre et le type des placeholders sont ceux réellement appelés dans le code du projet ; seuls les libellés sont reconstitués pour l'exemple. Retenez la mécanique : une clé simple est une paire chaîne/chaîne ; une clé paramétrée ajoute une entrée jumelle préfixée @ qui déclare ses placeholders et leur type.

Le générateur transforme ça en méthodes Dart :

  • continueGame devient un getter : l10n.continueGame ;
  • missingItemsMessage devient une méthode à un argument : l10n.missingItemsMessage(names) ;
  • actLevel devient une méthode à deux arguments int : l10n.actLevel(act, currentLevel).

C'est ce typage qui fait tout l'intérêt du système : oublier un placeholder ou en passer deux au lieu d'un devient une erreur de compilation, pas un texte cassé à l'exécution.

Brancher les délégués

Sans eux, un showDatePicker resterait obstinément en anglais.

Enfin onGenerateTitle plutôt que title : le titre de l'application (celui du sélecteur de tâches Android) doit lui aussi être traduit, et il ne peut l'être qu'à l'intérieur d'un contexte où les délégués sont installés — d'où la version « callback ».

Le repli sur l'anglais

Le test est locale == 'fr' ? nameFr : nameEn, pas un switch exhaustif. Autrement dit : toute locale qui n'est pas exactement 'fr' reçoit l'anglais. Allemand, japonais, espagnol, chaîne vide — tout retombe sur nameEn. C'est le comportement le plus sûr possible : le jeu ne peut jamais afficher une chaîne vide ou planter sur une locale inconnue, il devient juste anglophone.

Le même esprit gouverne le décodage. Chaque fromJson tolère un ancien format monolingue :

    final nEn = json['name_en'] as String? ?? json['name'] as String? ?? '';

        json['description_en'] as String? ??

Trois niveaux de repli par champ : la variante localisée, puis le champ générique (name, description) d'un format plus ancien, puis la chaîne vide. Une entrée JSON écrite avant l'introduction du bilinguisme continue donc de charger — elle affichera juste le même texte dans les deux langues. Cette même tolérance est reproduite à l'identique dans hero_data.dart, relic_data.dart, passive_data.dart et event_data.dart.

Règle du projet

Toute entrée JSON de assets/data/ comportant du texte visible par le joueur doit fournir ses deux variantes : name_fr + name_en, description_fr + description_en (ou title_fr + title_en pour les événements). Le repli sur name existe pour la compatibilité, pas pour économiser une traduction : une entrée monolingue passera les tests mais affichera de l'anglais à un joueur français, ou l'inverse.

Le cas Flame : getTranslation

Une complication surgit dans la couche de rendu. Les composants Flame ne sont pas des widgets : ils n'ont pas de BuildContext propre, donc pas d'accès direct à AppLocalizations.of(context). CardComponent contourne le problème avec deux helpers :

    if (context != null) {

    String fallback = '',
  }) {
    final context = game.buildContext;

Le paramètre select est une fonction qui reçoit l'objet AppLocalizations et en extrait la chaîne voulue. À l'appel, ça donne getTranslation((l) => l.cardTypeAttack, fallback: 'Attaque') : on passe le chemin d'accès à la clé plutôt que la clé résolue, ce qui permet de ne rien évaluer quand le contexte est absent. Le fallback couvre la fenêtre où le composant Flame est construit avant que l'arbre de widgets soit prêt.

Piège — deux valeurs de secours contradictoires

activeLocale retombe sur 'fr' ; les fallback de getTranslation sont écrits tantôt en français ('Attaque', 'Compétence'), tantôt en anglais ('Single enemy', 'Common'). Les getters du catalogue, eux, retombent sur l'anglais. Dans la fenêtre — très courte — où le contexte n'est pas encore disponible, une même carte peut donc afficher un type en français et une cible en anglais. Ce n'est pas visible en pratique, mais c'est une incohérence de conception.

La ligne décisive est « Ajouter une entrée ». Un game designer qui crée une carte veut écrire une entrée, pas deux moitiés dans deux fichiers qu'il faut garder alignés. Le format bilingue rend la désynchronisation structurellement impossible : le nom français et le nom anglais sont dans le même objet, à trois lignes d'écart.

À l'inverse, l'interface a besoin de ce que le JSON ne sait pas faire : des placeholders typés, des pluriels, et surtout une vérification à la compilation. Une faute de frappe dans un nom de clé ARB casse le build ; la même faute dans un champ JSON produit silencieusement une chaîne vide affichée à l'écran.

6. Le tutoriel

Le troisième système transverse est le plus autonome des trois. Tout le tutoriel tient dans lib/tutorial/ : cinq fichiers à la racine, treize widgets d'illustration. Sa caractéristique principale, celle qui justifie son isolation, est simple :

Le tutoriel ne touche jamais l'état réel

Aucun fichier de lib/tutorial/ n'importe flutter_riverpod, ni runProvider, ni deckProvider, ni combatProvider. Le tutoriel a son propre état factice, TutorialMockState, et sa propre logique, TutorialEngine. Un joueur peut lancer le tutoriel au milieu d'une run en cours : à la sortie, rien n'a bougé. C'est aussi ce qui permet au tutoriel de mentir librement — il montre des valeurs rondes et pédagogiques plutôt que les vraies.

Le gating : quatre étapes exigent une action

lib/tutorial/tutorial_screen.dartdart
  bool _isStepActionComplete(TutorialEngine engine) {
    final step = kTutorialSteps[engine.currentStepIndex];
    switch (step.type) {
      case TutorialStepType.playCard:
        return engine.mockState.enemy != null &&
            engine.mockState.enemy!.hp < 20 &&
            engine.mockState.heroArmor > 0;
      case TutorialStepType.merge:
        return engine.mockState.hand.length == 1 &&
            engine.mockState.hand.first.id == 'strike_upgraded';
      case TutorialStepType.xp:
        return engine.mockState.playerLevel > 1;
      case TutorialStepType.draft:
        return engine.mockState.hasDrafted;
      default:
        return true;
    }
  }

Quatre cas explicites, un default: return true pour les neuf autres. Chaque condition est une observation de l'état factice, pas un drapeau « l'utilisateur a cliqué » :

  • playCard — l'ennemi doit exister, avoir moins de 20 PV (il en a 20 au départ, donc il faut l'avoir frappé) et le héros doit avoir de l'armure. Deux cartes différentes doivent avoir été jouées, sur deux cibles différentes.
  • merge — la main doit contenir exactement une carte, d'identifiant 'strike_upgraded'. C'est engine.mergeCards() qui produit cet état.
  • xp — le niveau doit avoir dépassé 1. Le bouton du widget donne gainXp(35) et il faut 100 XP : trois clics minimum.
  • draft — le drapeau hasDrafted, mis par engine.draftReward() quand une option est choisie.
Bonne pratique — le switch porte sur le type

Contrairement à resetMockState, qui compare des index numériques, _isStepActionComplete commence par kTutorialSteps[index].type et fait son switch sur l'énumération. Insérer une étape au milieu de la liste ne casse rien ici. C'est exactement le même problème traité de deux manières, dans deux fichiers voisins — et une seule des deux est robuste.

7. Ce que le tutoriel enseigne, et ses limites

Les treize widgets d'illustration constituent, ensemble, la plus grosse partie du module (environ 150 Ko de Dart contre 40 Ko pour le moteur, les données et l'écran réunis). Quatre d'entre eux valent qu'on les regarde de près.

TutorialElementsWidget ne demande aucune interaction : il fait tourner un Timer.periodic de 2 secondes qui joue en boucle les quatre décroissances.

Les points d'attention

Le module est propre, mais il porte quelques défauts qu'il faut connaître avant d'y toucher. Chacun a été vérifié dans le code.

Point d'attention — quatre fragilités vérifiées dans lib/tutorial/

1. Couplage par index numérique. TutorialEngine.resetMockState() fait un switch (_currentStepIndex) sur les valeurs littérales 4, 5, 6, 9, 10, 11, avec des commentaires (// Step 5: Cards & Mana) comme seule documentation. Insérer une étape en position 3 dans kTutorialSteps décale tout : le décor du Slime se retrouverait monté sur l'étape « Armure & Dégâts », sans aucune erreur de compilation. _isStepActionComplete, dans le fichier voisin, fait pourtant son switch sur step.type — la version robuste existe, elle n'a simplement pas été appliquée des deux côtés.

2. La dernière étape n'est pas gatée. TutorialStepType.relics tombe dans le default: return true; de _isStepActionComplete. Le bouton affiche donc TERMINER et est cliquable dès l'affichage. Or le texte de l'étape dit explicitement « Terminez cette étape pour finir le tutoriel ! » et TutorialRelicsWidget propose bien une interaction (_collectRelic(), la relique rétrécit à scale 0.2 puis un « Relique Collectée ! » s'affiche). Le joueur peut valider sans jamais collecter la relique : le texte promet un gating qui n'existe pas.

3. « Passer » ne marque pas la complétion. Le bouton d'en-tête '✕ Passer' a pour tout code onPressed: () => Navigator.pop(context). Aucun appel à markTutorialCompleted(). Un joueur qui parcourt douze étapes puis abandonne à la treizième retrouve le badge « NEW » sur le bouton TUTORIEL au menu principal. Seul le chemin isLastStep + clic sur TERMINER pose le drapeau.

4. Divergences entre tutorial_data.dart et les widgets. Quatre écarts constatés : (a) l'étape 7 décrit la Foudre comme « Augmente les dégâts subis par l'ennemi lors de votre prochaine attaque » alors que TutorialElementsWidget dit « Subit des dégâts supplémentaires à chaque coup reçu » — et c'est le widget qui a raison, DamagePipeline.calculate ajoute shockStatus.value à chaque calcul de dégâts tant que le statut dure ; (b) le même statut s'appelle « Foudre » dans les données et « Électrocution » dans le widget ; (c) l'étape 9 affirme que trois cartes identiques « fusionnent automatiquement », alors que deck_screen.dart exige un clic sur un bouton mergeLabel(3) puis une confirmation dans _MergeDialog — la fusion est manuelle ; (d) le titre français de l'étape 8 contient une coquille : 'Les Intentions Ennies'.

Piège bonus — du code mort dans le moteur

TutorialEngine.simulateDamageTake({required bool withArmor}) est déclaré, écrit, et jamais appelé : TutorialArmorWidget gère sa propre paire d'états locaux (_leftHp, _rightHp, _leftArmor, _rightArmor) et ignore complètement mockState. Conséquence en cascade : le case 6 de resetMockState, qui met en place un « Mannequin de Test » de 30 PV avec une intention à 10, ne sert à rien non plus. Et si l'on voulait un jour brancher simulateDamageTake, il faudrait d'abord la corriger : sa branche withArmor: true pose heroArmor = 4 puis retire 6 PV pleins sans que l'armure n'absorbe quoi que ce soit — l'inverse de la règle que l'étape est censée enseigner.

  • Elle charge quand même en ignorant les champs inconnus
  • Elle rend success: false mais laisse la sauvegarde intacte
  • Elle lève une FormatException, attrapée par le catch qui appelle clear() puis rend success: false
Réponse : le test decoded['schemaVersion'] != _schemaVersion déclenche throw const FormatException('Unsupported or missing schemaVersion'). Le catch journalise sous kDebugMode, appelle await clear() et rend const SaveLoadResult(success: false). Il n'existe aucun code de migration dans le projet.

4. Dans DeckState._decodePile, pourquoi la CardData sauvegardée est-elle remplacée par CardData.getById(instance.data.id) ?

  • Pour que tout rééquilibrage du catalogue s'applique immédiatement aux sauvegardes existantes
  • Parce que CardData.fromJson ne sait pas relire ce que toJson écrit
  • Pour économiser de la mémoire en partageant une seule instance par carte
  • Parce que la sauvegarde ne contient que l'identifiant de la carte
Réponse : c'est le patron « re-résoudre plutôt que dupliquer ». instance.copyWith(data: freshData, forgeUpgrades: validUpgrades) jette la définition figée au profit de celle du catalogue. La copie sauvegardée ne sert que dans un cas : quand getById rend null, ses nameFr/nameEn alimentent le MissingSaveItem affiché au joueur.

5. Un utilisateur lance le jeu avec la locale de (allemand). Que renvoie relic.getName('de') pour le Talisman de Fer ?

  • Une chaîne vide, puisqu'aucune traduction allemande n'existe
  • « Talisman de Fer » — le français est la langue de repli du projet
  • « Iron Talisman » — toute locale différente de 'fr' reçoit l'anglais
  • Une ArgumentError, la locale n'étant pas dans supportedLocales
Réponse : le getter s'écrit String getName(String locale) => locale == 'fr' ? nameFr : nameEn;. Le test n'est pas exhaustif : toute valeur autre que 'fr' tombe dans la branche anglaise. Même règle dans card_data.dart, hero_data.dart, passive_data.dart, event_data.dart et forge_upgrade_data.dart.

6. Combien d'étapes compte kTutorialSteps, combien exigent une action réelle avant de pouvoir continuer, et sous quelle clé la complétion est-elle stockée ?

  • 10 étapes, 3 gatées, clé tutorial_done
  • 13 étapes, 4 gatées (playCard, merge, xp, draft), clé tutorial_completed
  • 13 étapes, toutes gatées, clé run_save_v1
  • 12 étapes, 4 gatées, clé tutorial_progress
Réponse : tutorial_data.dart contient 13 TutorialStep, autant que de valeurs dans TutorialStepType. _isStepActionComplete ne traite explicitement que quatre types — playCard, merge, xp, draft — les neuf autres tombant dans default: return true;. La clé est static const String _tutorialCompletedKey = 'tutorial_completed'; dans tutorial_progress_service.dart.
