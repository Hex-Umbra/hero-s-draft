Le combat : boucle de tour, dégâts et effets

Le combat est la mécanique la plus dense du projet. On y suit une carte depuis le doigt du joueur jusqu'aux points de vie d'un ennemi, en passant par six couches de code.

Un combat de Hero's Draft, vu de l'extérieur, c'est simple : le joueur pose des cartes, appuie sur « Fin de tour », les ennemis répliquent, on recommence. Vu de l'intérieur, c'est six couches qui se passent le relais, chacune avec une responsabilité stricte :

lib/ ├── models/ │ ├── combat_state.dart // l'état immuable du combat │ ├── enemy_instance.dart // un ennemi sur le terrain + effectiveIntent │ ├── enemy_intent.dart // EnemyIntent + IntentType │ ├── status_effect.dart // StatusEffect + combine() │ └── entity_stats.dart // PV, armure, statuts, takeDamage() ├── game/ │ ├── game_constants.dart // les 7 délais de combat │ ├── heros_draft_game.dart // executeTurn / _enemyRipostePhase (le séquenceur) │ ├── controllers/ │ │ ├── combat_controller.dart // LE fichier central │ │ └── combat/ │ │ ├── turn_phase_manager.dart // les phases de tour │ │ └── status_effect_processor.dart // les ticks de début de tour │ ├── services/ │ │ ├── damage_pipeline.dart // le calcul des dégâts │ │ ├── effect_resolver.dart // mana, runes, boucle d'effets │ │ └── effects/ │ │ ├── effect_strategy.dart // interface + registre │ │ └── strategies.dart // les 6 implémentations │ └── systems/ │ └── trait_system.dart // les passifs de classe └── ui/screens/ └── game_screen.dart // le pont Flutter ↔ Flame

La règle à garder en tête pendant tout le chapitre : Flame séquence, Riverpod calcule. Le fichier heros_draft_game.dart ne connaît aucune règle de jeu — il joue des animations et attend des millisecondes. Le fichier combat_controller.dart ne connaît aucune animation — il transforme un CombatState en un autre CombatState.

1. L'état du combat : CombatState

Tout ce que le jeu sait d'un combat en cours tient dans une seule classe immuable (Riverpod), exposée par un NotifierProvider. Huit champs, pas un de plus.

lib/models/combat_state.dartdart
enum TurnPhase { player, enemy }

@immutable
class CombatState {
  final List<EnemyInstance> enemies;
  final List<EnemyInstance> pendingEnemies;
  final List<EnemyInstance> defeatedEnemies;
  final TurnPhase turnPhase;
  final int turnCount;
  final String? selectedEnemyId;
  final bool isCombatEnded;
  final bool isVictory;

  CombatState({
    List<EnemyInstance> enemies = const [],
    List<EnemyInstance> pendingEnemies = const [],
    List<EnemyInstance> defeatedEnemies = const [],
    this.turnPhase = TurnPhase.player,
    this.turnCount = 1,
    this.selectedEnemyId,
    this.isCombatEnded = false,
    this.isVictory = false,
  })  : enemies = List.unmodifiable(enemies),
        pendingEnemies = List.unmodifiable(pendingEnemies),
        defeatedEnemies = List.unmodifiable(defeatedEnemies);

Les trois listes sont passées par List.unmodifiable(...) dans la liste d'initialisation du constructeur. C'est une protection réelle, pas décorative : si un morceau de code UI tentait un state.enemies.add(...), il lèverait une UnsupportedError à l'exécution plutôt que de corrompre silencieusement l'état partagé.

Le rôle de pendingEnemies : la file d'attente

Un combat peut générer plus de cinq ennemis (l'EncounterSystem raisonne en budget, pas en nombre). Mais l'écran de combat ne peut pas en afficher davantage sans devenir illisible. La solution retenue est une file d'attente : les cinq premiers entrent, les autres patientent, et chaque mort libère une place.

La répartition se fait une fois pour toutes à l'initialisation du combat, avec un 5 écrit en dur dans la boucle :

lib/game/controllers/combat_controller.dartdart
final List<EnemyInstance> activeEnemies = [];
final List<EnemyInstance> pendingEnemies = [];

for (int i = 0; i < allEnemyInstances.length; i++) {
  var enemy = allEnemyInstances[i];
  if (i < 5) {
    enemy = rollIntent(enemy);
    activeEnemies.add(enemy);
  } else {
    pendingEnemies.add(enemy);
  }
}

state = CombatState(
  enemies: activeEnemies,
  pendingEnemies: pendingEnemies,
  defeatedEnemies: const [],
  turnPhase: TurnPhase.player,
  turnCount: 1,
  selectedEnemyId: null,
  isCombatEnded: false,
  isVictory: false,
);

Notez le détail : rollIntent(enemy) n'est appelé que sur les ennemis actifs. Un ennemi en attente n'a pas d'intention — ce serait inutile puisqu'il ne joue pas, et l'affichage de son intention n'aurait aucun sens. Il reçoit la sienne au moment exact où il entre en scène.

La promotion, elle, a lieu dans cleanDeadEnemies() (détaillé en section 9). Le principe tient en trois lignes : pour chaque mort constatée, si la scène compte moins de 5 combattants et que la file n'est pas vide, on sort le premier de la file, on lui tire une intention, et on le pose sur le terrain.

Cinq ennemis actifs au maximum. Toute mort libère immédiatement une place, occupée aussitôt par le premier ennemi de pendingEnemies. Un renfort qui arrive de cette façon agit dès la phase ennemie suivante : il reçoit son intention à l'instant de son entrée, pas au tour d'après.

Piège

Le nombre 5 apparaît à deux endroits (la boucle d'initialisation et la boucle de promotion) et n'est pas dans GameConstants. Si vous voulez passer à six ennemis, il faut modifier les deux — en oublier un donne un combat qui commence à 6 mais qui, après la première mort, ne remonte plus jamais au-dessus de 5.

2. La chronologie d'un tour

C'est le point que les débutants comprennent le plus lentement, parce que la boucle est éclatée entre trois fichiers : le widget Flutter (le bouton), le jeu Flame (le séquenceur asynchrone) et le contrôleur Riverpod (les règles). Voici le cycle complet.

2.1 Le déclencheur : le bouton « Fin de tour »

Tout part d'un onTap dans game_screen.dart. C'est ce widget, pas le contrôleur, qui déclenche les trois effets de fin de tour avant de passer la main à Flame :

Deux choses méritent d'être soulignées.

L'avertissement de mana restant. Si le joueur a encore du mana et que _showRemainingManaWarning est false, le premier appui ne termine pas le tour : il se contente d'allumer l'avertissement et de faire return. Il faut donc appuyer une seconde fois pour confirmer. C'est un garde-fou « anti-gâchis » classique, implémenté sans la moindre boîte de dialogue — juste un booléen d'état local du State.

Il existe un second avertissement, symétrique, déclenché non pas par le bouton mais par le fait de jouer une carte. Quand une carte fait tomber le mana de « strictement positif » à zéro, l'écran attend 600 ms puis affiche un rappel « vous pouvez finir votre tour », à condition qu'il reste des ennemis et que le mana soit toujours nul :

La double condition de canEndTurn. Le bouton n'est actif que si les deux notions de phase concordent : celle de Riverpod (combatState.turnPhase) et celle de Flame (_game.currentPhase), plus l'absence d'animation de carte en cours. C'est la conséquence directe de l'architecture : la phase est stockée à deux endroits, et pendant les quelques centaines de millisecondes où Flame a déjà basculé mais où Riverpod n'a pas encore reçu l'ordre, il ne faut surtout pas laisser le joueur cliquer.

2.2 Le séquenceur : executeTurn et _enemyRipostePhase

executeTurn() est volontairement minuscule. Il vérifie, bascule la phase locale, gère le cas « plus aucun ennemi » et délègue :

lib/game/heros_draft_game.dartdart
Future<void> executeTurn() async {
  if (currentPhase != TurnPhase.player ||
      currentRunState == null ||
      currentRunState!.isDead) {
    return;
  }

  currentPhase = TurnPhase.enemy;

  if (enemyCards.isEmpty) {
    onEnemiesDead();
    currentPhase = TurnPhase.player;
    return;
  }

  await _enemyRipostePhase();
}

Toute la chorégraphie est dans _enemyRipostePhase(). C'est une méthode async qui alterne « je fais quelque chose » et « j'attends N millisecondes ». Les await Future.delayed(...) ne sont pas du confort : ce sont eux qui laissent aux animations Flame le temps de se jouer avant que l'état ne change sous leurs pieds.

lib/game/heros_draft_game.dartdart
Future<void> _enemyRipostePhase() async {
  onPhaseChanged(TurnPhase.enemy);
  await Future.delayed(const Duration(milliseconds: GameConstants.combatDelayEnemyTurnStartMs));

  onStartEnemyTurn();

  await Future.delayed(const Duration(milliseconds: GameConstants.combatDelayAfterTicksMs));

  final activeEnemies = List<EnemyCard>.from(enemyCards);
  for (var enemy in activeEnemies) {
    if (currentRunState == null || currentRunState!.isDead) break;

    final intent = enemy.effectiveIntent;
    if (intent == null) continue;

    if (intent.type == IntentType.attack) {
      enemy.dashAnimation();
    } else {
      enemy.buffAnimation(intent.type);
    }

    await Future.delayed(const Duration(milliseconds: GameConstants.combatDelayEnemyDashMs));

    onResolveEnemyIntent(enemy.id);

    await Future.delayed(const Duration(milliseconds: GameConstants.combatDelayAfterIntentResolveMs));
  }

  await Future.delayed(const Duration(milliseconds: GameConstants.combatDelayEnemyTurnEndMs));

  onEndEnemyTurn();
}

Trois détails de robustesse valent d'être notés :

  • List<EnemyCard>.from(enemyCards) : on itère sur une copie. Sans elle, la mort d'un ennemi par poison en cours de boucle modifierait la collection pendant l'itération — erreur classique en Dart (ConcurrentModificationError).
  • if (... isDead) break; : si le héros meurt au milieu de la riposte, les ennemis restants n'attaquent pas un cadavre.
  • if (intent == null) continue; : un ennemi qui vient d'entrer en scène sans intention est simplement sauté.

2.4 Le retour à la phase joueur

Le dernier maillon, endEnemyTurn(), est ce qui fait réellement avancer le compteur de tours. Il vit dans le TurnPhaseManager, une classe extraite du contrôleur pour lui éviter de grossir indéfiniment :

lib/game/controllers/combat/turn_phase_manager.dartdart
/// Début du tour de l'ennemi (application des statuts autonomes)
void startEnemyTurn() {
  controller.updateState(
    controller.currentState.copyWith(turnPhase: TurnPhase.enemy),
  );

  final List<EnemyInstance> updatedEnemies = [];
  for (var enemy in controller.currentState.enemies) {
    final updatedStats = StatusEffectProcessor.processEnemyStatuses(enemy.stats);
    updatedEnemies.add(enemy.copyWith(stats: updatedStats));
  }

  controller.updateState(
    controller.currentState.copyWith(enemies: updatedEnemies),
  );

  // Nettoyer les morts (par exemple à cause du poison de début de tour)
  controller.cleanDeadEnemies();
}

/// Fin de la phase ennemie : roll intents et retour au joueur
void endEnemyTurn() {
  final List<EnemyInstance> rolledEnemies = controller.currentState.enemies
      .map((enemy) => controller.rollIntent(enemy))
      .toList();

  controller.updateState(
    controller.currentState.copyWith(
      enemies: rolledEnemies,
      turnPhase: TurnPhase.player,
      turnCount: controller.currentState.turnCount + 1,
    ),
  );
}

Règle du jeu

L'armure du héros est remise à zéro à chaque début de tour (étape 1), avant les reliques et avant les statuts. Le bouclier ne se reporte donc jamais d'un tour sur l'autre : tout ce qui a été gagné au tour précédent et non consommé est perdu. Le mana, lui, est restauré au maximum (il ne s'accumule pas non plus).

3. Les intentions ennemies

Une intention, c'est ce que l'ennemi annonce qu'il fera à son prochain tour. C'est le cœur de la lisibilité tactique : le joueur voit l'icône et le chiffre au-dessus de l'ennemi, et décide s'il attaque ou s'il se protège. Le modèle est minimal :

3.1 rollIntent : script d'abord, hasard ensuite

Le choix de l'intention suivante se fait dans le contrôleur. Il y a deux modes, et le premier a la priorité :

lib/game/controllers/combat_controller.dartdart
/// Calcule l'intention suivante d'un ennemi
EnemyInstance rollIntent(EnemyInstance enemy) {
  final data = enemy.data;
  EnemyIntent nextIntent;
  int nextStep = enemy.intentStep;

  if (data.intents != null && data.intents!.isNotEmpty) {
    nextIntent = data.intents![enemy.intentStep];
    nextStep = (enemy.intentStep + 1) % data.intents!.length;
  } else {
    final random = Random();
    final roll = random.nextInt(100);

    if (roll < 60) {
      nextIntent = EnemyIntent(
        type: IntentType.attack,
        value: data.baseDamage,
      );
    } else if (roll < 85) {
      nextIntent = EnemyIntent(
        type: IntentType.defend,
        value: 5 + random.nextInt(6),
      );
    } else {
      nextIntent = EnemyIntent(type: IntentType.buff, value: 2);
    }
  }
  return enemy.copyWith(currentIntent: nextIntent, intentStep: nextStep);
}

Mode 1 — le script. Si le JSON de l'ennemi contient une liste intents non vide, elle est parcourue en boucle grâce à intentStep et à un modulo : (intentStep + 1) % intents.length. Le comportement est donc parfaitement déterministe et apprenable par le joueur — c'est un choix de game design, pas une facilité technique.

Les quatre ennemis livrés dans assets/data/enemies.json ont tous une liste d'intentions. L'orc est le plus intéressant : trois étapes, dont un buff au milieu.

3.2 effectiveIntent : de la valeur affichée à la valeur réelle

La valeur écrite dans le JSON est une valeur de référence, pensée pour un ennemi au niveau 1 de l'acte 1. En jeu, l'ennemi a été « gonflé » à l'apparition par l'EncounterSystem, et il peut avoir gagné de la Force pendant le combat. C'est effectiveIntent, un getter de EnemyInstance, qui réconcilie tout cela.

lib/models/enemy_instance.dartdart
EnemyIntent? get effectiveIntent {
  final intent = currentIntent;
  if (intent == null) return null;
  if (intent.type == IntentType.attack) {
    final double spawnMultiplier = data.baseDamage > 0
        ? stats.attaque / data.baseDamage
        : 1.0;
    final int scaledValue = (intent.value * spawnMultiplier).round();
    final int inBattleBonus = stats.effectiveAttaque - stats.attaque;
    int finalValue = (stats.effectiveAttaque > (scaledValue + inBattleBonus))
        ? stats.effectiveAttaque
        : (scaledValue + inBattleBonus);
    if (stats.statuses.any((s) => s.id == 'freeze')) {
      finalValue = (finalValue * 0.5).round();
    }
    return EnemyIntent(
      type: intent.type,
      value: finalValue,
    );
  }
  return intent;
}

Décortiquons, ligne par ligne.

  1. Seules les attaques sont transformées. Les intentions defend et buff sont renvoyées telles quelles (return intent; à la fin). Un ennemi de fin d'acte se défend donc du même nombre de points d'armure qu'un ennemi de départ.
  2. Le multiplicateur de spawn. spawnMultiplier = stats.attaque / data.baseDamage. C'est un rapport entre l'attaque réellement attribuée à l'instance au moment de sa création et l'attaque de référence du JSON. Ce rapport n'est jamais calculé ailleurs : il est reconstruit ici à partir de deux valeurs déjà connues. La garde data.baseDamage > 0 évite la division par zéro pour un ennemi purement défensif.
  3. La mise à l'échelle. scaledValue = (intent.value * spawnMultiplier).round(). Une intention à 12 pour un ennemi dont l'attaque a été doublée devient 24.
  4. Le bonus acquis en combat. inBattleBonus = stats.effectiveAttaque - stats.attaque. Comme effectiveAttaque vaut attaque + somme des statuts 'strength', cette soustraction isole exactement la Force gagnée depuis le début du combat.
  5. Le max des deux. La ligne ternaire prend le plus grand entre effectiveAttaque et scaledValue + inBattleBonus. C'est un plancher de sécurité : une intention scriptée volontairement faible (par exemple « attaque 2 ») ne pourra jamais rendre l'ennemi ridicule si son attaque effective est bien supérieure.
  6. Le Gel, en dernier. Si l'ennemi porte un statut freeze, la valeur finale est divisée par deux et arrondie. Comme c'est la dernière opération, le Gel s'applique bien au total, pas à la valeur de base.

Un exemple chiffré avec l'orc, supposé apparu avec attaque = 12 (contre baseDamage = 8 dans le JSON), à la troisième étape de son cycle (attack, valeur 12), et porteur de 3 points de Force :

5.2 Pourquoi scaledValue + effectiveAttaque ?

C'est la formule de dégâts la plus importante du jeu, et elle apparaît deux fois dans le fichier ci-dessus (cible unique et zone). Elle dit ceci :

illustrationtext
degats bruts d'une carte
  = (valeur JSON x multiplicateur de rarete).round()   // le potentiel de la carte
  + runes 'sharp' (2 par niveau)                       // l'amelioration de la carte
  + attaque effective du heros                         // la puissance du personnage

... ou, dans les termes du code :
  initialDamage = scaledValue + heroStats.effectiveAttaque

Autrement dit, la carte apporte un socle, le héros apporte un bonus additif. Ce choix a des conséquences de design très concrètes :

  • Une Frappe commune (6) et une Boule de Feu (6) profitent exactement autant de l'attaque du héros. La progression du personnage bénéficie à tout le deck, pas seulement aux grosses cartes.
  • Comme c'est additif et non multiplicatif, jouer beaucoup de petites cartes est meilleur que jouer une grosse carte, dès que l'attaque du héros dépasse la valeur des cartes. Deux cartes à 3 avec 10 d'attaque font 26 ; une carte à 6 avec 10 d'attaque en fait 16.
  • effectiveAttaque inclut la Force (statut strength). Une carte Forme Démoniaque (+2 Force pendant 4 tours) augmente donc les dégâts de chaque carte d'attaque jouée pendant sa durée.
  • Pour une carte de zone, le bonus d'attaque est appliqué à chaque ennemi : le pipeline est recalculé dans la boucle, avec un tirage de critique indépendant par cible.
Bonne pratique

Remarquez que DamageEffectStrategy ne calcule rien lui-même. Elle choisit les cibles, compose l'initialDamage, et délègue immédiatement à DamagePipeline puis à EntityStats.takeDamage. Une stratégie sert à répondre à « sur qui ? », pas à « combien ? ».

6. DamagePipeline : les 4 étapes

Toutes les sources de dégâts du jeu — cartes, intentions ennemies, compétences héroïques — convergent vers une unique fonction statique de 50 lignes. Elle prend des dégâts bruts et rend des dégâts finaux, plus un booléen « c'était un critique » qui sert à l'affichage.

lib/game/services/damage_pipeline.dartdart
class DamagePipeline {
  static (int damage, bool isCrit) calculate({
    required int initialDamage,
    required EntityStats attackerStats,
    required EntityStats defenderStats,
    bool canCrit = true,
  }) {
    int totalDamage = initialDamage;

    // 1. Weakness (faiblesse) de l'attaquant : réduit les dégâts de 25% (arrondi)
    final hasWeakness = attackerStats.statuses.any((s) => s.id == 'weakness');
    if (hasWeakness) {
      totalDamage = (totalDamage * 0.75).round();
    }

    // 2. Coup critique de l'attaquant : multiplie les dégâts par critMultiplier
    bool isCrit = false;
    if (canCrit) {
      final random = Random();
      if (random.nextInt(100) < attackerStats.effectiveCritChance) {
        totalDamage = (totalDamage * attackerStats.critMultiplier).round();
        isCrit = true;
      }
    }

    // 3. Shock (choc) du défenseur : ajoute la valeur de shock au total
    final shockStatus = defenderStats.statuses.firstWhere(
      (s) => s.id == 'shock',
      orElse: () => const StatusEffect(
        id: '',
        name: '',
        type: StatusType.debuff,
        value: 0,
        duration: 0,
      ),
    );
    if (shockStatus.id.isNotEmpty) {
      totalDamage += shockStatus.value;
    }

    // 4. Vulnerable (vulnérabilité) du défenseur : augmente les dégâts de 50% (arrondi)
    final hasVulnerable = defenderStats.statuses.any((s) => s.id == 'vulnerable');
    if (hasVulnerable) {
      totalDamage = (totalDamage * 1.5).round();
    }

    // Garde-fou pour éviter des dégâts négatifs
    if (totalDamage < 0) {
      totalDamage = 0;
    }

    return (totalDamage, isCrit);
  }
}

Le type de retour (int damage, bool isCrit) est un record Dart 3 : un tuple nommé, sans classe à écrire. À l'appel, on le déstructure directement en deux variables locales : final (dmg, isCrit) = DamagePipeline.calculate(...);.

Règle du jeu — l'ordre du pipeline

L'ordre est Faiblesse → Critique → Choc → Vulnérable, et il n'est pas interchangeable :

  • La Faiblesse s'applique avant le critique, donc le critique multiplie des dégâts déjà réduits. Elle est donc plus pénalisante que si l'ordre était inverse.
  • Le Choc est additif et arrive après le critique : il n'est jamais multiplié par 1,5. Un ennemi avec 5 de Choc prend toujours exactement +5, critique ou non.
  • La Vulnérabilité est dernière, elle multiplie donc tout, Choc compris. C'est le multiplicateur le plus puissant du jeu.
Piège — l'armure n'est PAS dans le pipeline

Le mot armure n'apparaît nulle part dans damage_pipeline.dart. L'absorption a lieu une couche plus bas, dans EntityStats.takeDamage(), appelée après le pipeline par la stratégie ou par le contrôleur. Conséquence directe : la Vulnérabilité augmente les dégâts avant que l'armure ne les absorbe, donc un défenseur bien blindé peut encore tout encaisser. Et surtout : si vous cherchez un bug d'armure, ce n'est pas dans ce fichier qu'il faut le chercher.

  return copyWith(armure: newArmor, currentPv: newPv, lastActionWasCrit: isCrit);
}

L'armure est donc un bouclier consommable à la Slay the Spire : elle absorbe point pour point, elle est réduite d'autant, et le surplus passe aux PV. Le champ lastActionWasCrit est un drapeau purement cosmétique, lu par les composants Flame pour choisir la taille et la couleur du texte flottant.

7.1 StatusEffect.combine : cumuler ou rafraîchir

Quand on applique un statut déjà présent, il faut décider quoi faire. C'est le rôle de combine, appelé depuis EntityStats.addStatus :

lib/models/status_effect.dartdart
/// Retourne un nouvel effet combiné si stackable, sinon rafraîchit la durée
StatusEffect combine(StatusEffect other) {
  if (id != other.id) return this;
  if (isStackable) {
    return copyWith(
      value: value + other.value,
      duration: duration > other.duration
          ? duration
          : other.duration, // Ne pas additionner les durées
    );
  } else {
    // Rafraîchit la durée si elle est plus grande
    return copyWith(
      duration: other.duration > duration ? other.duration : duration,
      value: other.value > value ? other.value : value,
    );
  }
}
lib/models/entity_stats.dartdart
/// Ajoute ou combine un effet de statut
EntityStats addStatus(StatusEffect effect) {
  final index = statuses.indexWhere((s) => s.id == effect.id);
  List<StatusEffect> newStatuses = List.from(statuses);

  if (index != -1) {
    newStatuses[index] = newStatuses[index].combine(effect);
  } else {
    newStatuses.add(effect);
  }

  return copyWith(statuses: newStatuses);
}

Les deux branches :

  • isStackable == true (le défaut) : les valeurs s'additionnent, la durée devient le maximum des deux. Le commentaire du code est explicite — « Ne pas additionner les durées ». Deux Poison de 1 pendant 2 tours donnent un Poison de 2 pendant 2 tours, pas de 2 pendant 4 tours.
  • isStackable == false : on ne cumule pas, on prend le maximum des deux durées et le maximum des deux valeurs. C'est un rafraîchissement : appliquer un statut faible ne peut jamais affaiblir un statut fort déjà en place.

La garde if (id != other.id) return this; est une sécurité : combiner deux statuts différents ne fait rien. En pratique addStatus ne peut pas produire ce cas, puisqu'il cherche l'index par identifiant.

7.2 tickStatuses : la décrémentation, avec deux exceptions

lib/models/entity_stats.dartdart
/// Décrémente la durée des statuts et supprime ceux expirés
EntityStats tickStatuses() {
  List<StatusEffect> newStatuses = statuses
      .map((s) {
        if (s.id == 'freeze') {
          return s;
        }
        if (s.id == 'burn') {
          return s.copyWith(
            value: s.value - 1,
            duration: s.duration - 1,
          );
        }
        return s.copyWith(duration: s.duration - 1);
      })
      .where((s) => s.duration > 0 && (s.id != 'burn' || s.value > 0))
      .toList();

  return copyWith(statuses: newStatuses);
}

Le cas général est banal : duration - 1, puis on filtre tout ce dont la durée est tombée à zéro ou moins. Mais deux identifiants sont traités à part.

freeze : jamais décrémenté ici

Le Gel est renvoyé tel quel par tickStatuses. Sa durée ne baisse que dans resolveEnemyIntent, et seulement quand l'ennemi gelé exécute effectivement une attaque. Un ennemi gelé qui se défend ou se renforce ne « consomme » pas son Gel.

burn : valeur ET durée baissent

La Brûlure est le seul statut dont la valeur décroît de 1 en même temps que sa durée. Elle s'éteint donc naturellement, et le filtre ajoute une seconde condition de sortie : s.id != 'burn' || s.value > 0.

Concrètement, une Boule de Feu applique burn de valeur 2 et de durée 2. Le premier tick de l'ennemi inflige 2 dégâts puis réduit le statut à (valeur 1, durée 1). Le tick suivant inflige 1 dégât puis réduit à (valeur 0, durée 0) : le filtre l'élimine. Total : 3 dégâts, pas 4.

Piège

L'ordre compte : dans processEnemyStatuses, les dégâts sont infligés avec les valeurs avant le tick, puisque tickStatuses() est appelé sur la toute dernière ligne (return updatedStats.tickStatuses();). Un statut de durée 1 produit donc bien son effet une fois avant de disparaître.

Piège

Le poison et la brûlure passent par takeDamage(), qui soustrait l'armure. Un ennemi bien blindé encaisse donc son poison avec son bouclier, sans perdre de PV. Chez le héros ce n'est pas visible, parce que startTurn() remet l'armure à zéro à l'étape 1, avant le traitement des statuts à l'étape 3. Chez l'ennemi, dont l'armure persiste d'un tour sur l'autre, l'effet est bien réel.

static EntityStats processPlayerStatuses(EntityStats stats) {
  int poisonDamage = 0;
  int strengthGain = 0;
  int armorGain = 0;

  for (var status in stats.statuses) {

      poisonDamage += status.value;

    } else if (status.id == 'armor_regen') {

8.1 Différence 1 — le joueur ne brûle pas

La boucle de processPlayerStatuses ne contient aucune branche else if (status.id == 'burn'). Un statut burn posé sur le héros serait donc inerte : il apparaîtrait dans le panneau de statuts, il serait décrémenté par tickStatuses (valeur et durée), mais il n'infligerait jamais le moindre dégât.

Est-ce un oubli ? Dans l'état actuel du contenu, ça n'a aucune conséquence : la Brûlure ne peut être posée que par une carte du joueur ou une rune de forge, donc toujours sur un ennemi. Aucune intention ennemie n'applique de statut — le cas buff pose uniquement strength sur l'ennemi lui-même. La Brûlure est donc, de fait, une arme à sens unique.

8.2 Différence 2 — trois tours contre un

Le statut strength_regen (« Éveil d'Attaque ») ne donne pas de Force directement : il fabrique un statut strength à chaque début de tour. Et la durée de ce statut fabriqué diffère selon le porteur : 3 tours pour le joueur, 1 tour pour l'ennemi.

La conséquence est un empilement, parce que strength est cumulable par défaut. Chez le joueur, un strength_regen de valeur 2 actif pendant 3 tours produit :

9. Fin de combat et nettoyage

Une seule méthode décide qui est mort, qui entre en scène, et si le combat est terminé. Elle est appelée à cinq endroits : après une carte, après une compétence de zone, après une compétence ciblée, après une compétence perforante, et au début de la phase ennemie (pour les morts par poison).

lib/game/controllers/combat_controller.dartdart
/// Nettoie les ennemis décédés et met à jour les indicateurs de fin de combat
void cleanDeadEnemies() {
  final runController = ref.read(runProvider.notifier);
  final List<EnemyInstance> remainingEnemies = [];
  final List<EnemyInstance> newlyKilledEnemies = [];
  int killedCount = 0;

  for (var enemy in state.enemies) {
    if (enemy.stats.currentPv <= 0) {
      killedCount++;
      newlyKilledEnemies.add(enemy);
      runController.onEnemyKilled();
    } else {
      remainingEnemies.add(enemy);
    }
  }

  if (killedCount > 0) {
    final List<EnemyInstance> nextPending = List.from(state.pendingEnemies);
    for (int i = 0; i < killedCount; i++) {
      if (remainingEnemies.length < 5 && nextPending.isNotEmpty) {
        var incoming = nextPending.removeAt(0);
        incoming = rollIntent(incoming);
        remainingEnemies.add(incoming);
      }
    }

    String? nextSelected = state.selectedEnemyId;
    if (nextSelected != null &&
        !remainingEnemies.any((e) => e.id == nextSelected)) {
      nextSelected = null;
    }

    final bool isCombatEnded = remainingEnemies.isEmpty && nextPending.isEmpty;
    final bool isVictory = isCombatEnded;

    state = state.copyWith(
      enemies: remainingEnemies,
      pendingEnemies: nextPending,
      defeatedEnemies: [...state.defeatedEnemies, ...newlyKilledEnemies],
      selectedEnemyId: nextSelected,
      clearSelectedEnemy: nextSelected == null,
      isCombatEnded: isCombatEnded,
      isVictory: isVictory,
    );
  }
}

Étape par étape :

  1. Détection. Un ennemi est mort si currentPv <= 0 — pas == 0, parce que takeDamage plafonne déjà à 0 mais que d'autres chemins (comme damage_pierce) écrivent directement les PV.
  2. Reliques. runController.onEnemyKilled() est appelé une fois par mort, à l'intérieur de la boucle. Cette méthode déclenche toutes les reliques dont le trigger est RelicTrigger.onEnemyKilled. Tuer trois ennemis d'un coup avec une carte de zone déclenche donc trois fois la relique.
  3. Sortie anticipée. Tout le reste est sous if (killedCount > 0). Aucun mort, aucune écriture d'état — donc aucune notification Riverpod inutile.
  4. Promotion. Autant de tentatives que de morts, chacune sous double condition (moins de 5 sur le terrain, file non vide).
  5. Désélection. Si la cible du joueur ne figure plus parmi les survivants, selectedEnemyId est remis à null via le drapeau clearSelectedEnemy. C'est indispensable : copyWith ne peut pas distinguer « je ne change pas ce champ » de « je veux le mettre à null », d'où ce paramètre supplémentaire dans CombatState.copyWith.
  6. Fin de combat. isCombatEnded exige les deux listes vides. Un dernier ennemi qui meurt alors qu'il reste des renforts en attente ne termine pas le combat — le renfort entre à la place. Et isVictory est aujourd'hui une copie stricte de isCombatEnded : il n'existe pas de chemin où le combat se termine par autre chose qu'une victoire, la défaite étant gérée séparément via runState.isDead.

9.1 La victoire peut être signalée deux fois

C'est le point le plus délicat de tout le système de combat. Il existe deux chemins indépendants qui aboutissent au même traitement de victoire.

Chemin A — le callback Flame. Dans executeTurn(), si la liste des cartes d'ennemis de Flame est vide au moment où le joueur termine son tour, le jeu appelle directement onEnemiesDead(), câblé sur _handleCombatVictory :

_game = HerosDraftGame(
  onEnemiesDead: _handleCombatVictory,
  // ... 13 autres callbacks

Chemin B — l'écoute Riverpod. Dans build, un ref.listen surveille les transitions de CombatState et déclenche la victoire au moment précis où isCombatEnded passe de false à true :

lib/ui/screens/game_screen.dartdart
ref.listen<CombatState>(combatProvider, (previous, next) {
  final wasEnded = previous?.isCombatEnded ?? false;
  if (next.isCombatEnded && next.isVictory && !wasEnded) {
    _handleCombatVictory();
  }
});

Les deux chemins peuvent se déclencher pour le même combat : le chemin B au moment où la dernière carte tue le dernier ennemi, le chemin A quelques secondes plus tard si le joueur appuie quand même sur « Fin de tour ». Sans protection, le joueur recevrait deux fois ses récompenses.

La correction repose entièrement sur _isVictoryHandled, un champ local au State du widget. Deux fragilités en découlent. D'abord, le verrou ne survit pas à une reconstruction du State : si l'écran de combat était recréé (changement de route, hot restart), le drapeau repartirait à false. Tant que ces deux sources coexistent, tout nouveau chemin de victoire devra penser à passer par _handleCombatVictory et pas ailleurs.

Un détail que le code fait bien : onEnemyKilled est déclaré comme callback de HerosDraftGame et câblé dans game_screen.dart, mais il n'est jamais invoqué par le moteur. Le callback est du code mort, mais c'est le bon des deux qui est mort.

9.2 Récapitulatif

Flame séquence

heros_draft_game.dart enchaîne animations et Future.delayed, et appelle des callbacks. Il ne calcule aucun dégât.

Riverpod calcule

combat_controller.dart et ses deux managers transforment un CombatState immuable en un autre. Aucune animation, aucun await.

Un seul pipeline

Toute source de dégâts passe par DamagePipeline.calculate, puis par EntityStats.takeDamage pour l'armure.

Un registre, pas un switch

Six stratégies d'effet enregistrées dans un Provider. Ajouter un type d'effet = une classe + une ligne d'enregistrement.

Cinq sur le terrain

pendingEnemies garde les autres en réserve ; chaque mort libère une place, occupée aussitôt par le premier de la file.

Deux ticks, deux règles

Le joueur ne brûle pas et garde sa Force 3 tours ; l'ennemi brûle et ne la garde qu'un tour.

3. Dans quel ordre DamagePipeline.calculate applique-t-il ses quatre étapes ?

  • Critique, Faiblesse, Vulnérable, Choc
