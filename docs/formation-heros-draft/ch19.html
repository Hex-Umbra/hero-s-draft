1. Le catalogue des écrans

Un « écran » dans ce projet, c'est simplement un widget qu'on pousse sur le Navigator avec une MaterialPageRoute. Il n'y a aucun système de routes nommées, aucun go_router, aucune table routes: dans le MaterialApp. Chaque écran construit lui-même l'instance de l'écran suivant et la pousse. C'est le style le plus direct de Flutter, et pour un jeu à navigation arborescente (menu → run → nœud → retour) ça se tient très bien.

Voici les dix-sept fichiers de lib/ui/screens/. La colonne « type de widget » est importante : elle vous dit tout de suite si l'écran a un état local (State) ou s'il ne fait que lire des providers.

2. Le graphe de navigation

Avant de regarder le diagramme, il faut comprendre le point de départ. Tout part de lib/main.dart, et ce fichier tient en 47 lignes :

lib/main.dartdart
void main() {
  WidgetsFlutterBinding.ensureInitialized();
  runApp(const ProviderScope(child: HerosDraftApp()));
}

class HerosDraftApp extends ConsumerWidget {
  const HerosDraftApp({super.key});

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    // Force l'activation de l'écoute d'autosave dès le démarrage de l'app.
    ref.watch(autosaveOrchestratorProvider);

    return MaterialApp(
      onGenerateTitle: (context) => AppLocalizations.of(context)!.appTitle,
      theme: AppTheme.darkNeonTheme,
      debugShowCheckedModeBanner: false,
      localizationsDelegates: const [ /* ... */ ],
      supportedLocales: const [Locale('en', ''), Locale('fr', '')],
      home: const SplashScreen(),
      builder: (context, child) {
        return Stack(
          children: [
            child ?? const SizedBox.shrink(),
            const GameNotificationOverlay(),
          ],
        );
      },
    );
  }
}

Trois choses à noter, et chacune a des conséquences dans tout le reste du projet :

  • home: const SplashScreen() — c'est la seule route déclarée. Tout le reste est poussé impérativement.
  • builder: enveloppe l'application entière dans un Stack qui superpose GameNotificationOverlay. Les notifications flottent donc au-dessus de toutes les routes, y compris des dialogues : elles survivent aux changements d'écran.
  • theme: AppTheme.darkNeonTheme et rien d'autre. Il n'y a ni darkTheme:, ni themeMode:. Nous y reviendrons — c'est la racine d'un problème réel.

Le point subtil : SplashScreen est la route isFirst

Regardez bien SplashScreen. Il ne pousse jamais HomeScreen. Il le rend comme enfant :

lib/ui/screens/splash_screen.dartdart
class SplashScreen extends ConsumerWidget {
  const SplashScreen({super.key});

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final gameData = ref.watch(gameDataLoaderProvider);

    return Scaffold(
      body: Center(
        child: gameData.when(
          data: (_) =>
              const HomeScreen(), // Si les données sont chargées, on affiche l'écran d'accueil
          loading: () =>
              const CircularProgressIndicator(), // Pendant le chargement
          error: (error, stack) =>
              Text('Erreur de chargement: $error'), // En cas d'erreur
        ),
      ),
    );
  }
}

Conséquence : la pile de navigation ne contient qu'une seule route quand on est au menu principal, et cette route est SplashScreen. HomeScreen n'est pas une route, c'est un widget à l'intérieur du body de la route racine.

C'est exactement ce qui rend l'idiome Navigator.popUntil((route) => route.isFirst) valide partout dans le projet : dépiler jusqu'à la première route, c'est revenir à SplashScreen, donc au menu principal — sans jamais recharger les JSON du jeu (le provider est déjà résolu, when retombe immédiatement dans la branche data).

Bonne pratique

Faire du splash la route racine plutôt qu'une route jetable qu'on remplace est astucieux ici : le chargement des données est un FutureProvider, donc mis en cache. Revenir à la racine réaffiche instantanément le menu, et tout le reste de la pile est détruit d'un coup. Un pushReplacement(HomeScreen) au démarrage aurait obligé à gérer un cas « et si on veut revenir tout en bas ? » beaucoup plus fragile.

Le nœud tapé sur la carte détermine la destination par un simple switch sur node.type. Pas de table de routage : un Widget destination local, puis un push.

lib/ui/screens/map_screen.dartdart
  void _onNodeTap(BuildContext context, WidgetRef ref, MapNode node) {
    if (ref.read(runProvider).pendingDrafts > 0) return;
    ref.read(runProvider.notifier).travelToNode(node.id);

    Widget destination;
    switch (node.type) {
      case MapNodeType.combat:
      case MapNodeType.elite:
      case MapNodeType.boss:
        destination = const GameScreen();
        break;
      case MapNodeType.shop:
        destination = const ShopScreen();
        break;
      case MapNodeType.rest:
        destination = const RestScreen();
        break;
      case MapNodeType.event:
        destination = const EventScreen();
        break;
      case MapNodeType.relicExchange:
        destination = RelicExchangeScreen(node: node);
        break;
      case MapNodeType.forgeFusion:
        destination = const ForgeFusionScreen();
        break;
    }

    Navigator.of(
      context,
    ).push(MaterialPageRoute(builder: (context) => destination));
  }
Piège

RelicExchangeScreen est le seul écran de nœud qui reçoit un paramètre (node: node), et donc le seul qui ne peut pas être const. Si vous ajoutez un type de nœud, souvenez-vous que ce switch n'a pas de branche default : le compilateur Dart vous signalera l'oubli, ce qui est exactement ce qu'on veut. Ne mettez pas de default ici.

3. Les trois portes de sortie d'une run

Une fois dans une run, la pile de navigation grossit : SplashScreen → MapScreen → GameScreen → éventuellement BossCardDraftScreen. Trois mécanismes très différents servent à en sortir, et chacun laisse la pile dans un état différent. C'est le genre de détail qui, mal compris, produit des bugs de « bouton retour qui ramène dans un combat mort ».

Porte 1 — popUntil((route) => route.isFirst)

Utilisée à trois endroits : le menu pause depuis MapScreen, le menu pause depuis GameScreen, et le bouton « Menu principal » de l'écran de mort.

lib/ui/screens/map_screen.dartdart
  void _showPauseMenu() {
    PauseDialog.show(
      context,
      onResume: () => Navigator.of(context).pop(),
      onExit: () => Navigator.of(context).popUntil((route) => route.isFirst),
    );
  }

Le onExit ne dépile pas explicitement le dialogue. Ce n'est pas un oubli : un dialogue Flutter est une route poussée sur le même Navigator. popUntil(isFirst) l'emporte donc avec tout le reste. Sur GameScreen, en revanche, l'auteur a écrit les deux :

lib/ui/screens/game_screen.dartdart
  void _showPauseMenu() {
    _game.pauseEngine();
    PauseDialog.show(
      context,
      onResume: () => Navigator.of(context).pop(),
      onExit: () {
        Navigator.of(context).pop();
        Navigator.of(context).popUntil((route) => route.isFirst);
      },
    ).then((_) {
      if (mounted) {
        _game.resumeEngine();
      }
    });
  }

Notez le _game.pauseEngine() / resumeEngine() : mettre le jeu Flame en pause n'a rien à voir avec la navigation, il faut le faire à la main. Le .then() s'exécute quand la route du dialogue est dépilée, quel que soit le chemin.

Porte 2 — pushReplacement(ClassSelectionScreen)

C'est le bouton « Changer de classe » de l'écran de mort. On veut recommencer une run avec une autre classe sans repasser par le menu principal.

                  ElevatedButton(

                  const SizedBox(width: 10),
                  ElevatedButton(
                    onPressed: () async {
                      await SaveService.clear();
                      if (!context.mounted) return;

pushReplacement remplace uniquement la route du sommet. Le DeathOverlay est affiché à l'intérieur de GameScreen, donc c'est GameScreen qui est remplacé par ClassSelectionScreen. MapScreen reste dessous. C'est un détail important : la pile est alors [SplashScreen, MapScreen, ClassSelectionScreen], avec un MapScreen « fantôme » qui appartient à la run précédente.

Porte 3 — pushAndRemoveUntil(MapScreen, isFirst)

C'est le démarrage d'une run, à la fin du draft de deck de départ. Et c'est précisément le mécanisme qui nettoie le fantôme laissé par la porte 2.

lib/ui/screens/starter_deck_draft_screen.dartdart
    // 3. Initialiser les providers
    ref.read(deckProvider.notifier).clearDeck();
    ref
        .read(runProvider.notifier)
        .startNewRun(widget.playerClass, widget.passive);
    ref.read(deckProvider.notifier).initializeStarterDeck(finalDeck);

    Navigator.of(context).pushAndRemoveUntil(

      (route) => route.isFirst,

Le second argument est un prédicat : continue de dépiler tant que le prédicat est faux. Ici il s'arrête à la première route. Résultat : quel que soit l'état de la pile avant (menu → classe → draft, ou run morte → classe → draft), on obtient toujours exactement [SplashScreen, MapScreen]. Le bouton retour matériel ne peut plus revenir dans l'ancienne run.

Règle du jeu

Quand on revient au menu principal par popUntil, HomeScreen n'est pas reconstruit depuis zéro : c'est la même instance de _HomeScreenState qui réapparaît. C'est pour ça que _continueGame() et _startNewGame() se terminent par un setState(() {}) après l'await du push, avec ce commentaire explicite dans le code :

« The pause menu and the death overlay both return here via Navigator.popUntil((route) => route.isFirst) rather than recreating this screen, so the save state must be re-checked on return. » Sans ce setState, le bouton « Continuer » resterait affiché après une mort qui a effacé la sauvegarde.

4. Les verrous de navigation

PopScope est le widget Flutter qui intercepte le geste « retour » (bouton matériel Android, balayage iOS, maybePop()). Il expose deux paramètres :

  • canPop : si false, le geste est bloqué ;
  • onPopInvokedWithResult(didPop, result) : rappelé dans les deux cas. On regarde didPop pour savoir si le retour a effectivement eu lieu.

Le projet en compte cinq, tous avec une intention de gameplay derrière.

Point d'attention

Il y a deux façons de déclarer un PopScope dans ce projet : soit via les paramètres canPop / onPopInvokedWithResult de ScreenScaffold (Rest, Event, Map), soit en écrivant un PopScope à la main autour du scaffold (Game, Shop). Piège

canPop: false ne bloque que les retours système et maybePop(). Un Navigator.pop() explicite passe outre. C'est pour ça que RestScreen._leave() et EventScreen._leave() peuvent appeler pop() directement sans se soucier de leur propre PopScope : ce sont des sorties « légitimes » validées par le code de jeu.

ScreenScaffold — les deux fonds du jeu

C'est le widget le plus structurant du projet. Il encapsule un Scaffold, choisit un dégradé de fond selon un enum, applique une SafeArea optionnelle, et ajoute un PopScope seulement si on lui en donne les paramètres.

Piège

ScreenScaffold peint la couleur sur le Scaffold, pas sur le Theme. Autrement dit, même sur un écran parchemin, Theme.of(context).scaffoldBackgroundColor vaut toujours AppColors.darkBg (0xFF1E1E2C). C'est pour cette raison que MapScreen doit passer GoldIndicator(isParchment: true) explicitement : aucun widget ne peut deviner le fond depuis le thème. Nous verrons en section 8 la conséquence de cette architecture sur GameButton.

GameButton — un bouton, beaucoup d'axes

Il n'y a pas d'enum de variantes ici. La « variante » se compose à partir de neuf paramètres : text, onPressed, isLoading, goldCost, baseColor, isParchmentOverride, icon, width, height (48 par défaut) et fontSize (16 par défaut). Le bouton est StatefulWidget uniquement pour mémoriser le survol (_isHovered), qui déclenche un AnimatedScale à 1.03 en 150 ms et une ombre colorée.

lib/ui/widgets/game_button.dartdart

Pourquoi deux rendus, et ce que ça coûte

La duplication n'est pas un accident, elle est structurelle : CardComponent vit dans l'arbre de composants Flame, où l'on peint sur un Canvas et où l'on gère le drag & drop avec DragCallbacks ; UiCard vit dans l'arbre de widgets Flutter, où l'on compose des Container et où l'on gère le tap avec GestureDetector. Les deux mondes n'ont pas de langage commun pour « dessiner une carte ».

GameThemeExtension — étendre ThemeData proprement

Une ThemeExtension<T> est le mécanisme officiel de Flutter pour ajouter vos propres tokens à un ThemeData. Sans elle, vous n'avez que le choix entre deux mauvaises options :

  • détourner les rôles Material existants (mettre la couleur « épique » dans colorScheme.tertiaryContainer) — illisible et fragile ;
  • importer AppColors directement partout — vos couleurs ne suivent alors plus le thème courant, et vous ne pouvez pas les animer.

Une ThemeExtension demande deux méthodes obligatoires : copyWith (pour dériver une variante) et lerp (pour interpoler entre deux thèmes pendant une transition animée). C'est lerp qui fait la différence : si l'application bascule du thème sombre au thème clair, Flutter interpole automatiquement chacune des 13 couleurs.

L'adoption partielle d'AppSpacing

Sur les 60 fichiers de lib/ui/, seuls cinq importent AppSpacing :

lib/ui/ ├── screens/ │ ├── draft_screen.dart // 8 usages │ └── rest_screen.dart // 9 usages └── widgets/ ├── game_button.dart // 4 usages ├── game_dialog.dart // 7 usages └── hud/dialogs/pause_dialog.dart // 1 usage

Partout ailleurs, on trouve des SizedBox(height: 20), des EdgeInsets.all(24.0), des EdgeInsets.symmetric(horizontal: 30, vertical: 25). Les valeurs 10, 12, 14, 15, 20, 25, 30 et 40 apparaissent régulièrement — aucune n'est dans l'échelle. Piège

Une échelle d'espacement n'a de valeur que si elle est exhaustive. Une échelle suivie à 8 % coûte plus cher qu'elle ne rapporte : elle ajoute un import et un vocabulaire à apprendre, sans donner la garantie de rythme visuel qui justifie l'effort. Si vous reprenez ce projet, le choix est binaire : soit vous généralisez AppSpacing (une passe de sed bien menée sur les valeurs 4/8/16/24/32/48 fait déjà 60 % du travail), soit vous le supprimez.

Le thème parchemin n'est jamais installé

Dernier point, et le plus contre-intuitif. Reprenons la ligne de GameButton :

lib/ui/widgets/game_button.dartdart
    final isParchment = widget.isParchmentOverride ||
        theme.scaffoldBackgroundColor == AppColors.parchmentBg;

Pour que la partie droite soit vraie, il faudrait que lightParchmentTheme soit le thème actif. Or main.dart ne déclare que theme: AppTheme.darkNeonTheme, sans darkTheme: ni themeMode:, et lightParchmentTheme n'est référencé nulle part ailleurs dans lib/. theme.scaffoldBackgroundColor vaut donc toujours AppColors.darkBg.

Point d'attention

La branche isParchment de GameButton et celle de GameDialog sont du code mort. Elles ne peuvent s'activer que par isParchmentOverride: true — qui n'est passé nulle part dans le projet. Les écrans parchemin (MapScreen, RelicExchangeScreen) contournent le problème en peignant leurs couleurs claires en dur (0xFF4A3728 pour le texte, 0xFF8B4513 pour l'or) et en passant isParchment: true à GoldIndicator et PageHeader.

Deux mécanismes de « thème clair » cohabitent donc : un vrai ThemeData jamais monté, et un booléen propagé à la main d'appelant en appelant. Le premier est correct et inerte ; le second fonctionne et se propage mal.

À retenir

Le design system de ce projet est correctement conçu et partiellement branché. Les tokens existent, l'extension de thème est écrite proprement avec copyWith et lerp, l'échelle d'espacement est cohérente, le thème clair est designé. Ce qui manque, c'est la dernière étape : supprimer les palettes concurrentes, monter le thème parchemin (ou assumer qu'il n'existe pas et supprimer son code), lire GameThemeExtension depuis les widgets, et généraliser AppSpacing. Aucune de ces quatre tâches n'exige de repenser quoi que ce soit — seulement de finir le câblage.
