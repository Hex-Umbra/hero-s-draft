Récompenses, chance et probabilités

Cinq tables de probabilité différentes cohabitent dans le jeu, toutes pilotées par une seule statistique : la Chance. Ce chapitre les met à plat et les compare.

Un roguelike de cartes tient sur une promesse simple : gagner un combat doit donner envie d'en faire un autre. Hero's Draft honore cette promesse avec un système de récompenses qui paraît banal de l'extérieur — de l'or, de l'XP, parfois une relique, parfois des cartes — et qui, à l'intérieur, empile cinq tables de probabilité distinctes. Toutes sont écrites à la main, toutes utilisent la même statistique de Chance (luck), et aucune n'utilise la même pente.

C'est exactement le genre de zone où un projet perd le contrôle : les formules sont dupliquées, la fenêtre d'aide affiche des chiffres qui ne sont plus ceux du calcul, et personne ne s'en aperçoit parce que « ça a l'air aléatoire de toute façon ». Nous allons donc faire deux choses : reconstruire chaque table à partir du code, et vérifier terme par terme ce que le jeu montre au joueur par rapport à ce qu'il calcule réellement.

Les fichiers de ce chapitre

Le cœur est lib/game/controllers/reward_controller.dart (282 lignes) : il contient à lui seul trois des cinq tables. Autour de lui gravitent lib/game/services/level_up_reward_service.dart (le draft de niveau), lib/game/controllers/event_controller.dart (les reliques d'événement), lib/ui/screens/game_screen.dart (l'orchestration de l'affichage) et lib/ui/widgets/map/dialogs/probabilities_dialog.dart (ce que le joueur voit).

1. Le séquenceur de récompenses

Quand le dernier ennemi meurt, plusieurs choses doivent arriver dans un ordre précis : une relique peut être tirée, des cartes de boss peuvent être proposées, l'or et l'XP doivent être crédités, et le combat doit se fermer. Chacune de ces étapes est asynchrone : le carrousel de relique est une animation de plusieurs secondes, la sélection de cartes est un écran complet que le joueur peut mettre dix minutes à valider.

Le problème classique dans cette situation : comment savoir où on en est ? Hero's Draft répond avec une machine à drapeaux. Toutes les récompenses sont calculées d'un coup, stockées dans un état immuable, et chaque étape terminée lève un booléen.

lib/game/controllers/reward_controller.dartdart
class RewardState {
  final int goldGained;
  final int xpGained;
  final RelicData? rolledRelic;
  final List<CardInstance> rolledCards;

  final bool isGoldXpCollected;
  final bool isRelicCollected;
  final bool isRelicSkipped;
  final bool isCardsProcessed;
  final List<CardInstance> selectedCards;
  final bool isResolved;
  final CardData? rolledBonusCard;

Lisez ce bloc comme deux moitiés. La première (goldGained, xpGained, rolledRelic, rolledCards, rolledBonusCard) contient le contenu de la récompense : ce qui a été tiré. La seconde (isGoldXpCollected, isRelicCollected, isRelicSkipped, isCardsProcessed) contient sa progression : ce que le joueur a déjà consommé.

Pourquoi des drapeaux plutôt qu'une file d'attente ?

L'alternative naturelle serait une Queue<Reward> : on empile relique, cartes, or/XP, et on dépile. Trois raisons rendent les drapeaux préférables ici.

Premièrement, l'idempotence. Chaque méthode publique du contrôleur commence par un garde qui teste son propre drapeau :

lib/game/controllers/reward_controller.dartdart
  void collectRelic() {
    if (state.rolledRelic == null || state.isRelicCollected || state.isRelicSkipped) return;

    ref.read(inventoryProvider.notifier).addRelic(state.rolledRelic!);
    state = state.copyWith(isRelicCollected: true);
    _checkResolution();
  }

Si le bouton « RÉCUPÉRER » est tapé deux fois (double-tap, rebuild inattendu, retour de navigation), la relique n'est ajoutée qu'une fois. Avec une file, un double dépilement serait un bug silencieux. Ici, le drapeau est la protection.

Deuxièmement, la reprise. L'état survit à la fermeture d'un écran. Quand BossCardDraftScreen se ferme, le code qui reprend la main n'a pas besoin de savoir ce qui a été fait avant lui : il relit l'état et recalcule ce qu'il reste à faire.

Troisièmement, l'ordre est décidé par l'UI, pas par le modèle. Une file impose son ordre au moment où on la remplit. Les drapeaux laissent l'écran choisir l'ordre de présentation, et même le changer, sans toucher au contrôleur.

La contrepartie : il faut une fonction qui répond à la question « est-ce fini ? ». C'est _checkResolution, appelée à la fin de chaque mutation.

lib/game/controllers/reward_controller.dartdart
  void _checkResolution() {
    final needsRelic = state.rolledRelic != null;
    final relicDone = !needsRelic || state.isRelicCollected || state.isRelicSkipped;

    final needsCards = state.rolledCards.isNotEmpty;
    final cardsDone = !needsCards || state.isCardsProcessed;

    if (state.isGoldXpCollected && relicDone && cardsDone) {
      state = state.copyWith(isResolved: true);
    }
  }

Le motif !needsX || xDone est l'implication logique « si cette récompense existe, alors elle doit être traitée ». Une récompense absente est considérée comme traitée : c'est ce qui permet au même code de gérer un combat normal (ni relique ni cartes) et un boss complet (les deux).

Piège de débutant : le drapeau qui ne sert à rien

isResolved est calculé consciencieusement… et n'est lu nulle part. Une recherche sur rewardProvider dans lib/ ne renvoie que quatre appels, tous dans game_screen.dart et boss_card_draft_screen.dart, et aucun ne consulte isResolved — l'écran relit les drapeaux individuels. Attention à ne pas confondre avec EventState.isResolved (dans lib/models/event_state.dart), qui, lui, est bien utilisé par event_screen.dart. Deux champs de même nom, un seul vivant.

L'ordre imposé par _presentNextReward()

La séquence réelle est écrite dans l'écran de combat. C'est une fonction récursive : chaque étape se rappelle elle-même quand l'écran qu'elle a ouvert se ferme.

lib/ui/screens/game_screen.dartdart
  void _presentNextReward() {
    if (!mounted) return;
    final rewardState = ref.read(rewardProvider);

    // 1. Present Relic if any and not processed yet

        !rewardState.isRelicSkipped) {

      return;
    }

        MaterialPageRoute(
          builder: (context) => const BossCardDraftScreen(),
        ),
      ).then((_) {
        if (mounted) {
          _presentNextReward();
        }
      });
      return;
    }
    // ...

Puis, en dernier, l'or et l'XP — et seulement là, la sortie du combat :

lib/ui/screens/game_screen.dartdart
    // 3. Process Gold and XP
    if (!rewardState.isGoldXpCollected) {
      final leveledUp = ref.read(rewardProvider.notifier).collectGoldAndXp();
      // ... notifications : or/XP, carte bonus, LEVEL UP

          _completeAndExitCombat();

L'ordre est donc relique → cartes de boss → or/XP → sortie après 800 ms. Ce n'est pas arbitraire :

  • La relique passe en premier parce que c'est la récompense la plus spectaculaire et la plus rare. On ne fait pas patienter le joueur derrière une notification d'or.
  • Les cartes passent ensuite parce qu'elles demandent une décision (choisir exactement 2 cartes sur 5) : mieux vaut la poser sur un écran dédié, sans compétition visuelle.
  • L'or et l'XP ferment la marche parce que ce sont les seuls à pouvoir déclencher une montée de niveau — donc à devoir être crédités juste avant la sortie, pour que l'overlay de level-up de la carte apparaisse au bon moment.
  • Les 800 ms laissent le temps de lire les notifications superposées (victoire, carte bonus, LEVEL UP) avant que _completeAndExitCombat() n'appelle nextLevel(), completeCurrentNode() et ne dépile l'écran.
Dette technique : les sorties non câblées

skipRelic() et skipCards() existent dans le contrôleur, mais aucun appel n'existe dans lib/. Le carrousel de relique est ouvert avec barrierDismissible: false et n'a qu'un bouton « RÉCUPÉRER », donc l'absence de skipRelic() est cohérente. En revanche BossCardDraftScreen ne pose aucun PopScope : un retour système dépile la route, ce qui déclenche le .then((_) => _presentNextReward()), qui repousse aussitôt le même écran puisque isCardsProcessed est resté false. Le joueur est enfermé jusqu'à ce qu'il sélectionne ses 2 cartes. skipCards() a été écrit exactement pour ce cas — il n'a jamais été branché.

2. Or et XP de victoire

Les deux premières sections de handleVictory sont volontairement symétriques : le même calcul est appliqué deux fois, une fois à l'XP, une fois à l'or.

lib/game/controllers/reward_controller.dartdart
    // 1. Calculate XP from defeated enemies
    int totalXp = 0;
    for (var enemy in defeatedEnemies) {
      final double levelMultiplier = 1.0 + 0.10 * (enemy.stats.level - 1);
      totalXp += (enemy.data.xp * levelMultiplier).round();
    }
    if (currentNode.bossRewardType == BossRewardType.doubleXp) {
      totalXp *= 3;
    }

    // 2. Calculate Gold from defeated enemies
    int totalGold = 0;
    for (var enemy in defeatedEnemies) {
      final double levelMultiplier = 1.0 + 0.10 * (enemy.stats.level - 1);
      totalGold += (enemy.data.gold * levelMultiplier).round();
    }
    if (currentNode.bossRewardType == BossRewardType.doubleXp) {
      totalGold *= 3;
    }

La formule est donc, par ennemi :

illustrationtext
gain = round( valeur_de_base × (1 + 0,10 × (niveau_de_l_ennemi − 1)) )

Trois détails comptent, et ils sont faciles à rater.

L'arrondi est par ennemi, pas sur le total. .round() est appelé à l'intérieur de la boucle. Battre deux gobelins n'est donc pas exactement équivalent à battre un « gobelin double » : les arrondis se cumulent séparément.

Le multiplicateur dépend du niveau de l'ennemi, pas du joueur. Or ce niveau vient de EncounterSystem.getEnemyLevel, qui vaut max(1, playerLevel + nodeModifier) avec nodeModifier à 2 sur un boss et 1 sur une élite. Un boss rapporte donc mécaniquement plus qu'un combat normal au même niveau de joueur, sans qu'aucune ligne de reward_controller.dart ne le mentionne.

Le × 3 s'applique aux deux. Malgré son nom, doubleXp triple, et il triple aussi l'or.

Pour mesurer ce que cela représente, il faut la courbe d'XP, qui vit dans le gestionnaire de stats du joueur :

lib/game/controllers/run/player_stats_manager.dartdart
    while (newXp >= currentXpToNext) {
      newXp -= currentXpToNext;
      currentLevel++;
      // Formule d'XP requise pour le nouveau niveau: 100 * (1.5 ^ (level - 1))
      currentXpToNext = (100 * pow(1.5, currentLevel - 1)).round();
      leveledUp = true;
      levelsGained++;
    }

Le seuil est 100 × 1,5^(niveau − 1) : 100, 150, 225, 338, 506, 759, 1139… La boucle while gère les montées multiples et conserve l'excédent (newXp -= currentXpToNext), en incrémentant pendingDrafts d'autant. Nos 882 XP de boss peuvent donc faire gagner deux ou trois niveaux d'un coup — et ouvrir deux ou trois drafts successifs sur la carte.

Règle du jeu

Chaque niveau de l'ennemi ajoute 10 % de la valeur de base à l'or comme à l'XP. Le boss doubleXp triple les deux (pas seulement l'XP, malgré son nom). Un niveau gagné égale un draft en attente : pendingDrafts est incrémenté d'une unité par niveau, et l'overlay de la carte reste affiché tant qu'il est > 0.

3. Les trois récompenses de boss

Le type de récompense d'un boss n'est pas tiré au sort à la victoire : il est gravé dans le nœud à la génération de la carte. Le joueur voit donc, sur l'écran de carte, trois boss distincts et choisit lequel il veut affronter.

lib/models/map_node.dartdart
enum MapNodeType { combat, elite, shop, rest, event, boss, relicExchange, forgeFusion }

enum BossRewardType { cards, doubleXp, improvedRelic }

L'attribution se fait dans le générateur, à l'étage final. Notez que cet étage a toujours exactement trois nœuds (rowWidth = 3), ce qui garantit que les trois types existent tous :

lib/services/map/map_node_generator.dartdart

C'est un choix de design fort : la récompense est positionnelle. Le boss de gauche donne toujours des cartes, celui du milieu toujours de l'or et de l'XP triplés, celui de droite toujours la relique améliorée. Aucun aléa, donc aucune frustration — le joueur décide de ce dont il a besoin.

cards : dupliquer son propre deck

Autrement dit, ce boss ne donne pas de nouvelles cartes : il duplique celles que le joueur possède déjà, améliorations de forge comprises.

4. Le tirage de relique standard

Voici la première vraie table de probabilité. Elle est utilisée sur les nœuds Élite (et, on le verra, recopiée à l'identique pour les reliques d'événement).

lib/game/controllers/reward_controller.dartdart
        } else {
          legChance = 1.0 + luck * 0.5;
          epicChance = 5.0 + luck * 1.0;
          rareChance = 14.0 + luck * 2.0;
          uncommonChance = 20.0 + luck * 3.0;
        }

        RelicRarity rarity;
        double roll = rand;
        if (roll < legChance) {
          rarity = RelicRarity.legendary;
        } else if (roll < legChance + epicChance) {
          rarity = RelicRarity.epic;
        } else if (roll < legChance + epicChance + rareChance) {
          rarity = RelicRarity.rare;
        } else if (roll < legChance + epicChance + rareChance + uncommonChance) {
          rarity = RelicRarity.uncommon;
        } else {
          rarity = RelicRarity.common;
        }

Le jet est final rand = Random().nextDouble() * 100;, donc un réel uniforme sur [0, 100[. Les quatre seuils sont cumulés : on compare le même roll à des bornes croissantes. La rareté commune n'a pas de chance propre — elle récupère tout ce qui reste.

À retenir : seuils cumulés vs soustraction

Deux écritures équivalentes existent dans ce projet. Ici, on compare roll à legChance + epicChance, puis à legChance + epicChance + rareChance. Ailleurs (event_controller.dart, level_up_reward_service.dart), on soustrait au fur et à mesure : roll -= legChance puis if (roll < epicChance). Le résultat est strictement le même ; seule la lisibilité change.

Avec les pentes 0,5 / 1,0 / 2,0 / 3,0 par point de Chance, la somme des quatre chances non communes vaut 40 + 6,5 × L. Elle atteint 100 pour L ≈ 9,23 : à partir de Chance 10, il n'y a plus de reliques communes du tout, et le peu commun commence à être écrêté.

Le peu commun ne reçoit donc que 100 − 55 = 45 points, pas 50. Le dépassement est absorbé par le bas de la table, silencieusement.

Le repli quand la rareté tirée n'existe pas

La rareté tirée n'est qu'une intention. Si aucune relique de cette rareté n'existe dans assets/data/relics.json, on retombe sur les communes ; et si même celles-ci manquent, sur la liste entière. C'est un garde-fou contre les données, pas contre le hasard : il protège le jeu d'un crash si un designer supprime la dernière relique légendaire.

Dans l'état actuel des données (25 reliques), aucune rareté n'est vide : 5 communes, 6 peu communes, 8 rares, 3 épiques, 3 légendaires. Le repli ne se déclenche donc jamais — mais le fait qu'il existe signifie que la distribution finale des reliques n'est pas celle de la table : à l'intérieur d'une rareté, le choix est uniforme sur les reliques disponibles, indépendamment de leur nombre. Une rareté qui ne contient qu'une relique la donnera systématiquement.

Piège

1 % de légendaire ne veut pas dire « 1 % de chance d'avoir telle relique légendaire ». Avec 3 légendaires en base, chacune vaut 1 %/3 ≈ 0,33 %. À l'inverse, les 8 rares se partagent 14 %, soit 1,75 % chacune : à Chance 0, une relique rare précise est plus probable qu'une légendaire précise… d'un facteur 5.

5. Le tirage de relique amélioré

Voici le bloc le plus dense du fichier. Il ne s'exécute que sur le boss improvedRelic, et il fait deux choses à la fois : monter fortement le légendaire, et faire disparaître progressivement les basses raretés au fil des actes.

lib/game/controllers/reward_controller.dartdart

Décodage pas à pas

Ligne 1 : le légendaire est réservé. legChance = 10.0 + luck * 0.5. Dix points sont mis de côté d'emblée — dix fois la valeur du tirage standard. Les 90 points restants sont ce que le reste de l'algorithme se partage.

Ligne 2 : le commun est piloté par l'acte. commonChance = max(0, 40 − (acte − 1) × 10). Il vaut 40 à l'acte 1, 30 à l'acte 2, 20 à l'acte 3, 10 à l'acte 4, et 0 à partir de l'acte 5. C'est une extinction linéaire, en quatre marches de 10 points.

Branche A (actes 1 à 4) : la re-répartition proportionnelle. Le reste à distribuer est baseRemaining = 90 − commonChance. Il est découpé selon des parts fixes 20 / 35 / 30 sur 85 — peu commun, rare, épique. Pourquoi 85 ? Parce que 20 + 35 + 30 = 85 : les trois fractions somment exactement à 1, donc les trois chances somment exactement à baseRemaining. Le total est alors 10 (leg) + baseRemaining + commonChance = 10 + 90 = 100, à Chance 0. Rien ne fuit.

Branche B (actes 5 à 7) : c'est au tour du peu commun de s'éteindre. Quand le commun est à zéro, le code repart de la valeur qu'aurait le peu commun avec tout le reste, maxUncommonBase = (20/85) × 90 ≈ 21,18, et lui applique la même extinction décalée de quatre actes : baseUncommonChance = max(0, 21,18 − (acte − 5) × 10). Les 90 points sont alors redistribués entre rare et épique seulement, avec les parts 35 / 30 sur 65 — et 65, c'est bien 35 + 30, la même astuce que précédemment.

Branche C (acte 8 et au-delà) : plus que trois raretés. Le peu commun tombe à zéro et les 90 points entiers vont à rare et épique, soit (35/65) × 90 ≈ 48,46 et (30/65) × 90 ≈ 41,54.

Bonne pratique

Cette construction en « parts sur une somme » (20/85, 35/65) est robuste : quel que soit le montant à répartir, la somme reste exacte, sans écart d'arrondi et sans normalisation a posteriori. C'est plus lisible qu'une liste de pourcentages écrits en dur pour chaque acte, et surtout impossible à désynchroniser.

Divergence confirmée entre l'affichage et le calcul

Elle est réelle et porte sur les trois panneaux de la fenêtre, à des degrés différents.

  1. Panneau « Draft standard de récompenses » : les quatre bases sont fausses. Les pentes (0,5 / 1,5 / 3 / 4) sont correctes, mais les bases affichées (1 / 5 / 14 / 20) sont celles de la table des reliques, pas celles du draft (2 / 6 / 16 / 24). Le joueur lit 60,00 % de commun à Chance 0 ; la valeur réelle est 52,00 %. Il lit 1,0 % de légendaire ; la valeur réelle est 2,00 %, soit le double.
  2. Panneau « Récompense de niveau » : il décrit une distribution qui n'existe pas. Non seulement les bases (0,5 / 4,5 / 15 / 20) ne correspondent à aucune constante de rollRarity, mais surtout generateChoices n'utilise le résultat de rollRarity(luck, isLevelReward: true) que pour tester == RewardRarity.mythic. Les issues légendaire, épique, rare, peu commune et commune de ce jet sont jetées. Le panneau détaille donc soigneusement cinq lignes dont aucune n'a d'effet en jeu, et omet la seule qui compte : le mythique, à 0,5 + 0,15·L.
  3. Panneau « Butin de Reliques » : les bases sont exactes, le périmètre ne l'est pas. 1 / 5 / 14 / 20 et 0,5 / 1 / 2 / 3 correspondent terme pour terme à reward_controller.dart et à event_controller.dart. Mais le sous-titre annonce « Boss, Élites & Événements » : or un boss cards ou doubleXp ne donne aucune relique, et le boss improvedRelic utilise la table améliorée, où le légendaire vaut 10 % et non 1 %. L'écart est d'un facteur 10 sur le seul boss qui donne une relique.

Un joueur qui optimise sa Chance en se fiant à cette fenêtre sous-estime systématiquement ses chances de draft, et n'a aucune information sur ce qui gouverne réellement le Trèfle et le Miroir.

Comment on évite ça

Le bon correctif n'est pas de recopier les bonnes valeurs dans le dialogue : c'est d'exposer une fonction publique unique — par exemple LevelUpRewardService.probabilities(luck) — et de la faire consommer par l'écran. Tant que deux fichiers portent les mêmes littéraux, ils divergeront. Le rollRarity a déjà été extrait dans un service pur pour être testable ; il ne reste qu'un pas à faire pour qu'il soit aussi la source unique de l'affichage.

Deux courbes pour comprendre l'écrêtage

Le graphe ci-dessous compare la probabilité effective d'obtenir un peu commun dans les deux tables principales, en fonction de la Chance. Le peu commun est le meilleur révélateur : il monte tant qu'il reste de la place sous 100, puis se fait écraser par les raretés supérieures.

Règle du jeu

Un point de Chance vaut 9 points de pourcentage retirés au commun dans un draft de niveau (0,5 + 1,5 + 3 + 4), contre 6,5 points dans un tirage de relique (0,5 + 1 + 2 + 3). La Chance est donc environ 1,4 fois plus efficace sur les récompenses de niveau que sur les reliques — mais elle sature aussi 1,6 fois plus vite.

8. La mise en scène

Tout ce qui précède se joue en quelques millisecondes. Le reste du temps — plusieurs secondes par récompense — est consacré à montrer le hasard. Cette mise en scène est un vrai morceau de code, et elle mérite d'être lue pour elle-même.

La machine à sous : DraftCardReel

Chaque carte de draft est un rouleau qui fait défiler de fausses récompenses avant de s'arrêter sur la vraie. Le défilement est un AnimationController de 140 ms qui se relance lui-même :

lib/ui/widgets/relic_carousel/draft_card_reel.dartdart

Le motif est important : au lieu d'une animation infinie avec repeat(), on relance manuellement à chaque cycle (forward(from: 0.0)). Cela donne un tick discret toutes les 140 ms — un point de synchronisation naturel pour un son de cliquet (widget.onTick?.call()) et un moment où l'on peut décider de s'arrêter. Les fausses cartes viennent d'une liste littérale de six intitulés : Vitalité, Aiguisage, Forge d'Acier, Sagesse, Trèfle à 4 feuilles, Miroir.

L'arrêt est programmé dès la construction, par un simple Timer :

lib/ui/widgets/relic_carousel/draft_card_reel.dartdart
      // Start fast rolling immediately
      _rollController.forward();
      // Staggered landing calculation: staggered lock-in delay based on slot index
      final int delayMs =
          1200 +
          widget.index * 600 +
          (isMythic ? 800 : (isLegendary ? 400 : 0));
      _landTimer = Timer(Duration(milliseconds: delayMs), _landReel);

Trois termes, trois intentions :

  • 1200 : le plancher. Personne ne s'arrête avant 1,2 s, sinon on ne verrait pas le défilement.
  • widget.index * 600 : le décalage. Les trois cartes s'arrêtent à 1 200 ms, 1 800 ms et 2 400 ms. C'est ce qui crée la lecture de gauche à droite, comme sur une vraie machine à sous.
  • 800 pour un mythique, 400 pour un légendaire : le suspense supplémentaire. La carte la plus rare est aussi celle qui met le plus de temps à s'immobiliser.
Piège : ce délai révèle la rareté avant la carte

Le retard supplémentaire est calculé à partir de la rareté déjà tirée. Un joueur attentif sait donc, avant même que la carte ne s'arrête, qu'une carte qui tourne trop longtemps est au moins légendaire. C'est un choix assumé de mise en scène (le même que la secousse ci-dessous), pas un défaut — mais c'est bien une fuite d'information vers l'UI.

La secousse est le second signal, encore plus explicite :

La secousse n'est active que !_hasLanded : elle s'arrête à l'atterrissage, et le _shakeController (100 ms, repeat(reverse: true)) sert uniquement d'horloge pour forcer le rebuild.

À l'atterrissage, un _rarityController de 700 ms fait apparaître progressivement la couleur de rareté (rarityProgress dans DraftChoiceCard), avec un flash plein cadre qui s'estompe : rarityColor.withValues(alpha: 0.80 * (1.0 - _rarityController.value)). Puis, et seulement puis, widget.onLand?.call() est déclenché.

À la fin de l'animation, un addStatusListener bascule vers la phase de révélation, qui affiche les cartes mythiques par-dessus un BackdropFilter flouté (sigma 8), avec le texte 'RÉCOMPENSE MYTHIQUE DÉCOUVERTE !'. Une fois tous les rouleaux mythiques posés, un délai de 1 500 ms laisse le temps d'admirer avant de rendre la main.

Le verrou de sélection

Pendant toute cette séquence, il ne faut surtout pas que le joueur puisse valider un des trois choix de base — il raterait le mythique. Le verrou est d'une simplicité désarmante :

lib/ui/screens/draft_screen.dartdart
                                            onTap: () {
                                              if (_hasMythicChoices &&
                                                  !_mythicCompleted) {
                                                return;
                                              }
                                              _onChoiceSelected(
                                                choice,
                                                index,
                                              );
                                            },

Deux booléens : _hasMythicChoices (calculé à la volée par _choices.any((c) => c.rarity == RewardRarity.mythic)) et _mythicCompleted (levé 1 500 ms après le dernier atterrissage mythique). Tant que le second est faux, le onTap ne fait rien. Ce n'est pas un widget désactivé, juste un retour anticipé — l'effet visuel de survol continue de fonctionner, ce qui est un peu trompeur, mais aucune sélection ne passe.

La liste affichée suit la même logique : final visibleChoices = _mythicCompleted ? _choices : _choices.sublist(0, 3);. Les cartes mythiques n'apparaissent dans la grille principale qu'après la révélation ; avant, seules les trois cartes de base existent.

Bonne pratique

Ce découpage — l'état du jeu est calculé d'un bloc, l'UI ne fait que le révéler progressivement — est ce qui rend l'animation totalement découplée du hasard. Si l'écran est détruit en plein défilement, rien n'est perdu : les DraftChoice existent déjà. Comparez avec un système qui tirerait la rareté au moment où le rouleau s'arrête : impossible à tester, impossible à rejouer.

2. Un boss doubleXp est vaincu avec quatre ennemis de niveau 5 (Slime, Gobelin, Squelette, Orc Furieux). Combien d'XP le joueur reçoit-il ?

  • 210 XP
  • 630 XP
  • 882 XP
  • 420 XP
Réponse : le multiplicateur vaut 1 + 0,10 × (5 − 1) = 1,4, appliqué et arrondi par ennemi : 35 + 49 + 70 + 140 = 294 XP. bossRewardType == BossRewardType.doubleXp déclenche totalXp *= 3, soit 882 XP (et 261 or, le même triplement s'appliquant à l'or).

3. Sur un nœud Élite, avec une Chance de 4, quelle est la probabilité exacte d'obtenir une relique légendaire ?

  • 2,0 %
  • 3,0 %
  • 10,0 %
Réponse : la branche standard de handleVictory utilise legChance = 1.0 + luck * 0.5, soit 1 + 4 × 0,5 = 3,0 %. Le 10 % correspondrait au boss improvedRelic (legChance = 10.0 + luck * 0.5, donc 12,0 % à Chance 4).

4. Sur un boss improvedRelic à l'acte 4, avec Chance 0, quelle est la probabilité d'obtenir une relique commune ?

  • 0 %
  • 40 %

Réponse : commonChance = max(0.0, 40.0 - (act - 1) * 10.0) vaut 40 − 3 × 10 = 10 à l'acte 4. Le commun ne s'éteint qu'à partir de l'acte 5. 18,82 % est la valeur du peu commun au même acte, et 40 % celle du commun à l'acte 1.

5. Avec une Chance de 10, quelle est la probabilité qu'un draft de montée de niveau contienne au moins une option mythique (Trèfle ou Miroir) ?

  • 2,0 %

Réponse : chaque jet vaut mythicChance = 0.5 + luck * 0.15, soit 2,00 % à Chance 10. generateChoices effectue deux jets indépendants, donc 1 − (1 − 0,02)² = 3,960 %. Le doublement naïf (4,0 %) surestime en oubliant l'intersection (0,04 %).
