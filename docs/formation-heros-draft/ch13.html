Les reliques et le système de déclencheurs

Vingt-cinq reliques, neuf moments de déclenchement, un seul aiguillage switch. C'est le système le plus simple du jeu à comprendre, et le plus facile à étendre.

Dans un roguelike de cartes, la relique est l'objet passif par excellence : on la ramasse, on ne la joue jamais, et pourtant elle change la partie. Hero's Draft en compte vingt-cinq, décrites dans un unique fichier Données assets/data/relics.json. Aucune d'elles n'a de code dédié. Aucune classe IronTalisman, aucun fichier vampiric_fang.dart. Tout passe par un couple de champs texte — trigger et effectType — et par un switch de deux cents lignes situé dans un seul fichier : lib/game/controllers/run/player_stats_manager.dart.

C'est un exemple presque scolaire de conception data-driven, et c'est pour ça qu'on lui consacre un chapitre entier. Une fois que vous aurez compris ce mécanisme, vous saurez ajouter une relique au jeu en modifiant une seule ligne de code — parfois zéro.

Ce que vous saurez faire à la fin

Lire une entrée de relics.json et prédire exactement ce qu'elle fera en jeu, savoir à quel instant précis de la boucle de combat chaque relique se déclenche, comprendre pourquoi une durée de statut de 99 veut dire « pour tout le combat », et ajouter une nouvelle relique en trois étapes.

1. Le modèle : RelicData, RelicTrigger, RelicRarity

Tout commence par la donnée. Voici une entrée complète de assets/data/relics.json — la première du fichier, le Talisman de Fer. Dix champs, pas un de plus, et ces dix champs suffisent à décrire n'importe laquelle des vingt-cinq reliques du jeu.

assets/data/relics.jsonjson
  {
    "id": "iron_talisman",
    "name_en": "Iron Talisman",
    "name_fr": "Talisman de Fer",
    "description_en": "Gain 2 Block at the start of each turn.",
    "description_fr": "Gagne 2 points d'Armure au début de chaque tour.",
    "trigger": "startOfTurn",
    "effectType": "gain_armor",
    "value": 2,
    "rarity": "common",
    "emoji": "🪙"
  }

Lisez cette entrée comme une phrase : « quand startOfTurn, fais gain_armor, avec l'intensité 2 ». Les trois champs trigger, effectType et value forment le triplet qui porte toute la mécanique. Les autres champs sont de la présentation : deux noms (anglais/français), deux descriptions, une rareté qui pilote la couleur et les tables de butin, et un emoji qui sert d'icône.

Les deux enums

Le fichier lib/models/data/relic_data.dart déclare d'abord les deux vocabulaires fermés du système. Un enum en Dart, c'est un type dont on énumère toutes les valeurs possibles : impossible d'en écrire une autre, et le compilateur vous prévient si vous oubliez d'en traiter une dans un switch.

lib/models/data/relic_data.dartdart
enum RelicTrigger {
  startOfRun,
  startOfCombat,
  startOfTurn,
  endOfTurn,
  onCardPlayed,
  onEnemyKilled,
  onAttackPlayed,
  onSkillPlayed,
  onPowerPlayed,
}

enum RelicRarity { common, uncommon, rare, epic, legendary }

Neuf déclencheurs, cinq raretés. Retenez ces deux nombres, ils structurent tout le chapitre. Notez aussi que l'enum s'appelle RelicTrigger et non Trigger — un choix de nommage qui va nous poser une question intéressante en section 8, quand on découvrira que les passifs de classe utilisent le même enum sans être des reliques.

La classe RelicData

La classe elle-même est un simple porteur de données immuable : tous les champs sont final, le constructeur est const. Une RelicData ne change jamais après sa création — c'est une fiche descriptive, pas un objet vivant.

lib/models/data/relic_data.dartdart
class RelicData {
  final String id;
  final String nameEn;
  final String nameFr;
  final String descriptionEn;
  final String descriptionFr;
  final RelicTrigger trigger;
  final String effectType; // ex: 'gain_energy', 'gain_strength', 'heal_on_kill'
  final int value;
  final RelicRarity rarity;
  final String emoji;

  const RelicData({
    required this.id,
    this.nameEn = '',
    this.nameFr = '',
    this.descriptionEn = '',
    this.descriptionFr = '',
    required this.trigger,
    required this.effectType,
    required this.value,
    required this.rarity,
    required this.emoji,
  });

  String getName(String locale) => locale == 'fr' ? nameFr : nameEn;
  String getDescription(String locale) =>
      locale == 'fr' ? descriptionFr : descriptionEn;

Deux détails à relever tout de suite.

Premier détail : trigger et rarity sont typés, pas effectType. Le trigger est un RelicTrigger, la rareté est une RelicRarity, mais l'effet reste une String brute. Ce n'est pas un oubli, c'est un arbitrage : le nombre de déclencheurs est stable (on n'en ajoute pas tous les jours), tandis que le nombre d'effets grandit à chaque relique originale. En laissant effectType en texte libre, on peut inventer charge_armor_mastery_combat dans le JSON sans toucher au modèle. Le prix à payer : aucune vérification à la compilation, et une faute de frappe ne se manifestera qu'au moment où l'effet ne se produit pas.

Second détail : l'i18n est inline. Le jeu ne passe pas par les fichiers ARB de Flutter pour les noms de reliques ; il embarque les deux langues dans la donnée et choisit avec getName(locale). Voir le chapitre 7 pour la justification de ce choix.

Le parsing

La factory fromJson transforme la Map décodée en objet Dart. Elle est tolérante sur les noms (elle accepte un name unique si les variantes name_en/name_fr manquent) et stricte sur la mécanique.

lib/models/data/relic_data.dartdart
  factory RelicData.fromJson(Map<String, dynamic> json) {
    final nEn = json['name_en'] as String? ?? json['name'] as String? ?? '';
    final nFr = json['name_fr'] as String? ?? json['name'] as String? ?? '';
    final dEn =
        json['description_en'] as String? ??
        json['description'] as String? ??
        '';
    final dFr =
        json['description_fr'] as String? ??
        json['description'] as String? ??
        '';

    return RelicData(
      id: json['id'] as String,
      nameEn: nEn,
      nameFr: nFr,
      descriptionEn: dEn,
      descriptionFr: dFr,
      trigger: RelicTrigger.values.firstWhere((e) => e.name == json['trigger']),
      effectType: json['effectType'] as String,
      value: json['value'] as int,
      rarity: RelicRarity.values.firstWhere((e) => e.name == json['rarity']),
      emoji: json['emoji'] as String? ?? '🪙',
    );
  }

La ligne qui mérite votre attention est celle-ci :

illustrationdart
trigger: RelicTrigger.values.firstWhere((e) => e.name == json['trigger']),

RelicTrigger.values est la liste des neuf valeurs de l'enum, et e.name est leur nom sous forme de chaîne ("startOfTurn", "onEnemyKilled"…). On cherche donc la valeur d'enum dont le nom correspond exactement à la chaîne du JSON. C'est le pont entre le monde texte et le monde typé.

Piège : firstWhere sans orElse

Si vous écrivez "trigger": "startofturn" (minuscule) ou "startOfRound" dans le JSON, firstWhere ne trouve rien et lève une StateError : No element. Le chargement complet des données du jeu échoue, au démarrage, sur une faute de casse. Même chose pour rarity. C'est volontairement strict — mieux vaut un crash immédiat au boot qu'une relique silencieusement inerte — mais si un jour vous ouvrez le jeu à des mods, c'est le premier endroit à sécuriser avec un orElse et un message clair.

Enfin, une méthode statique permet de retrouver une relique par son identifiant. Elle sert essentiellement au chargement d'une sauvegarde (section 7).

lib/models/data/relic_data.dartdart
  static RelicData? getById(String id) {
    final registry = GameDataRegistry.instance;
    if (registry == null) return null;
    try {
      return registry.relics.firstWhere((r) => r.id == id);
    } catch (e) {
      if (kDebugMode) {
        debugPrint('RelicData.getById: no relic found for id "$id" ($e)');
      }
      return null;
    }
  }

Ici, à l'inverse du parsing, le firstWhere est protégé : l'exception est attrapée, un message est écrit en debug, et la méthode renvoie null. Le type de retour est RelicData? — le point d'interrogation signale à l'appelant qu'il doit gérer le cas « pas trouvé ». C'est exactement ce que fait fromJsonWithReport.

Le fichier JSON est chargé par lib/services/game_data_service.dart, ligne 60, en même temps que les neuf autres fichiers de données du jeu, puis déposé dans le GameDataRegistry.

2. Les neuf déclencheurs et leurs points d'appel

Un déclencheur ne fait rien tout seul. Quelque part dans le code, à un instant précis, quelqu'un doit appeler applyRelics(RelicTrigger.xxx). La question centrale de ce chapitre est donc : qui appelle quoi, et quand ?

Le point d'entrée est une méthode de six lignes. C'est le cœur du système, et il tient dans une capture d'écran.

lib/game/controllers/run/player_stats_manager.dartdart
  /// Déclenche les effets des reliques pour un trigger donné
  void applyRelics(RelicTrigger trigger) {
    final relics = ref.read(inventoryProvider).relics;
    final relevantRelics = relics.where((r) => r.trigger == trigger).toList();
    for (var relic in relevantRelics) {
      applyRelicEffect(relic);
    }
  }

  /// Déclenche les reliques d'élimination d'ennemi
  void onEnemyKilled() {
    applyRelics(RelicTrigger.onEnemyKilled);
  }

Trois opérations : on lit la liste des reliques possédées dans l'inventaire, on filtre celles dont le trigger correspond, on applique l'effet de chacune. Rien de plus. Aucune priorité, aucun tri, aucune notion de « la relique A passe avant la relique B » : l'ordre d'application est simplement l'ordre d'acquisition, puisque addRelic ajoute en fin de liste.

Règle du jeu

Les reliques sont cumulables et les doublons comptent. Si vous possédez deux Talismans de Fer, la liste contient deux entrées avec le même id, le filtre en retient deux, et vous gagnez 4 points d'Armure par tour au lieu de 2. Aucun code n'empêche d'obtenir deux fois la même relique.

Le RunController expose une façade sur ces méthodes — c'est lui que le reste du jeu appelle, jamais le PlayerStatsManager directement.

lib/game/controllers/run_controller.dartdart

  /// Déclenche les reliques d'élimination d'ennemi

  void exchangeRelics(List<RelicData> sacrificed, RelicData gained) {
    _playerStatsManager.exchangeRelics(sacrificed, gained);
  }

Deux déclencheurs branchés dans le vide

onSkillPlayed et onPowerPlayed sont correctement câblés dans CombatController, correctement affichés dans les trois écrans de l'interface — et utilisés par zéro relique de relics.json. Ce n'est pas un bug : c'est de l'infrastructure posée d'avance. Le coût est réel mais faible (deux appels applyRelics qui parcourent une liste et n'y trouvent rien), et le jour où vous ajoutez une relique « gagne 2 Armure quand vous jouez une Compétence », vous n'écrivez qu'une entrée JSON.

Le cas particulier de startOfRun

startOfRun est le seul déclencheur qui ne passe jamais par applyRelics(). Cherchez dans tout le projet : il n'existe aucun appel applyRelics(RelicTrigger.startOfRun). À la place, l'inventaire appelle directement applyRelicEffect au moment de l'acquisition.

lib/game/controllers/inventory_controller.dartdart
  void addRelic(RelicData relic) {
    state = state.copyWith(relics: [...state.relics, relic]);
    if (relic.trigger == RelicTrigger.startOfRun) {
      ref.read(runProvider.notifier).applyRelicEffect(relic);
    }
  }

C'est la conséquence logique de ce que fait un effet startOfRun : il modifie une statistique permanente du héros. On ne l'applique donc qu'une fois, à l'acquisition. Si on le rejouait à chaque combat, la Lame Maudite donnerait +2 Force par combat et la run deviendrait absurde au bout de dix nœuds.

Le nom du déclencheur est trompeur

startOfRun se lit « au début de la run », mais le code dit « à l'obtention ». La différence compte : une relique startOfRun ramassée au nœud 12 s'applique immédiatement, pas rétroactivement, et pas au prochain lancement de partie. Le nom vient de la durée de l'effet (« pour toute la run »), pas de son instant d'application.

Chronologie complète

Les appels, dans le code

Regardons maintenant les vrais sites d'appel, un par un. D'abord l'ouverture d'un combat et d'un tour, dans RunController. Les commentaires numérotés du code disent tout de l'ordre des opérations.

lib/game/controllers/run_controller.dartdart
  void startCombat() {
    // 1. Nettoyage des buffs/debuffs du combat précédent,
    // et restauration du mana au max (l'armure est remise à 0 en fin de combat dans completeCurrentNode)
    state = state.copyWith(
      heroStats: state.heroStats.copyWith(
        statuses: [],
        currentMana: state.heroStats.maxMana,
      ),
    );
    // 2. Déclenchement des reliques
    applyRelics(RelicTrigger.startOfCombat);
    // 3. Déclenchement des passifs de début de combat/tour pour le tour 1 (ex: Berserker)
    TraitSystem.onTurnStart(this);
  }

  void startTurn() {
    // 1. Restaurer le Mana à sa valeur maximale (ne se cumule pas d'un tour à l'autre) et reset l'armure
    state = state.copyWith(
      heroStats: state.heroStats.copyWith(
        armure: 0,
        currentMana: state.heroStats.maxMana,
      ),
    );

    // 2. Déclencher les reliques de début de tour (qui peuvent maintenant rajouter du mana par-dessus)
    applyRelics(RelicTrigger.startOfTurn);

    // 3. Appliquer les effets de début de tour (ex: Poison, Regen) et décrémenter les statuts via le StatusEffectProcessor
    final updatedStats = StatusEffectProcessor.processPlayerStatuses(state.heroStats);
    state = state.copyWith(heroStats: updatedStats);

    // 4. Décrémenter les cooldowns via le skill provider
    ref.read(skillProvider.notifier).tickCooldowns();

    // 5. Déclencher les traits passifs
    TraitSystem.onTurnStart(this);
  }
Règle du jeu : le mana peut dépasser son maximum

L'ordre des étapes 1 et 2 de startTurn() est explicitement commenté : « qui peuvent maintenant rajouter du mana par-dessus ». Le mana est d'abord remis à maxMana, puis les reliques s'ajoutent. La Pierre d'Énergie (startOfTurn, gain_mana, valeur 1) vous donne donc maxMana + 1 au début de chaque tour. Rien dans EntityStats ne borne currentMana à maxMana : le dépassement est voulu.

L'ordre relatif de ces deux appels est protégé par un commentaire explicite dans le gestionnaire de phases, qui orchestre les deux contrôleurs.

Dette technique : le déclencheur de fin de tour vit dans le widget

Les six autres déclencheurs sont appelés depuis la couche « état » (RunController, CombatController). endOfTurn, lui, est appelé depuis le onEndTurnTap d'un bouton, dans game_screen.dart. Conséquence concrète : si un jour le tour se termine autrement que par un clic — un effet « votre tour se termine immédiatement », un timer, une fin de tour automatique quand la main est vide — les reliques endOfTurn ne se déclencheront pas. Trois reliques sont concernées (Rune de Protection, Anneau de Régénération, Bandage de voyage). Le bon geste, si vous reprenez ce code : déplacer ces deux lignes dans TurnPhaseManager, à côté de startPlayerTurn.

Un dernier détail honnête, découvert en traçant les appels : HerosDraftGame déclare un callback final void Function() onEnemyKilled; (ligne 63), que game_screen.dart renseigne consciencieusement (lignes 252 à 254) pour appeler runController.onEnemyKilled(). Or ce callback n'est jamais invoqué dans le moteur Flame. Le déclenchement réel passe uniquement par cleanDeadEnemies. C'est un vestige : sans lui, les reliques onEnemyKilled se déclencheraient deux fois par mort.

4. applyRelicEffect : l'aiguillage

Nous y voilà. applyRelicEffect est la méthode qui donne un sens à la chaîne effectType. C'est un unique switch de onze branches, dans lib/game/controllers/run/player_stats_manager.dart, lignes 191 à 397. Il n'existe aucun autre endroit du projet où un effectType de relique soit interprété.

Les six effets simples

Six effectType couvrent vingt des vingt-cinq reliques. Ils suivent tous le même patron, et ce patron est la clé du système :

La règle du startOfRun

Dans quatre des six cas simples, la branche commence par tester if (relic.trigger == RelicTrigger.startOfRun). Si oui, on modifie une statistique permanente du héros via applyHeroStatModifier. Pourquoi la durée 99 signifie « pour tout le combat »

Le nombre 99 revient trois fois dans le fichier, toujours avec le même commentaire : // 99 tours (durée du combat). Pour comprendre pourquoi ce n'est pas un « nombre magique » douteux mais un idiome parfaitement solide ici, il faut trois faits.

Fait 1 — les statuts perdent 1 de durée par tour. À l'étape 3 de startTurn(), StatusEffectProcessor.processPlayerStatuses se termine par un appel à tickStatuses() :

lib/models/entity_stats.dartdart
  /// Décrémente la durée des statuts et supprime ceux expirés
  EntityStats tickStatuses() {
    List<StatusEffect> newStatuses = statuses
        .map((s) {
          if (s.id == 'freeze') {
            return s;
          }
          if (s.id == 'burn') {
            return s.copyWith(
              value: s.value - 1,
              duration: s.duration - 1,
            );
          }
          return s.copyWith(duration: s.duration - 1);
        })
        .where((s) => s.duration > 0 && (s.id != 'burn' || s.value > 0))
        .toList();

    return copyWith(statuses: newStatuses);
  }

Fait 2 — le combat remet les statuts à zéro. La première instruction de startCombat() est statuses: []. Aucun statut ne survit d'un combat à l'autre, quelle que soit sa durée résiduelle.

Fait 3 — aucun combat ne dure 99 tours. Le budget de rencontre du chapitre 11 produit des combats de quelques tours ; 99 est simplement un plafond hors d'atteinte.

Conclusion : un statut de durée 99 posé pendant un combat expire en pratique avec le combat, jamais avant. C'est un « pour toujours, borné » — plus sûr qu'une durée infinie, puisque même si le nettoyage de startCombat disparaissait un jour, l'effet finirait par s'éteindre au lieu de contaminer la run entière.

Bonne pratique

Quand vous avez besoin d'un effet « jusqu'à la fin de la scène » dans un système qui ne connaît que des durées entières, préférez une grande durée bornée à une valeur sentinelle comme -1 ou null. Une sentinelle oblige chaque site de calcul à connaître la convention ; une grande durée traverse tout le code existant sans modification. Le commentaire // 99 tours (durée du combat) à côté de la valeur est ce qui rend le procédé lisible plutôt que mystérieux.

    List<StatusEffect> newStatuses = List.from(statuses);

    if (index != -1) {
      newStatuses[index] = newStatuses[index].combine(effect);

  /// Retourne un nouvel effet combiné si stackable, sinon rafraîchit la durée
  StatusEffect combine(StatusEffect other) {
    if (id != other.id) return this;
    if (isStackable) {
      return copyWith(
        value: value + other.value,
        duration: duration > other.duration
            ? duration
            : other.duration, // Ne pas additionner les durées
      );
    } else {
      // Rafraîchit la durée si elle est plus grande
      return copyWith(
        duration: other.duration > duration ? other.duration : duration,
        value: other.value > value ? other.value : value,
      );
    }
  }

C'est ici que isStackable: true prend tout son sens : les valeurs s'additionnent (1 + 1 = 2 charges), et la durée prend le maximum des deux — elle ne s'additionne jamais. Un compteur de durée 1 réalimenté trois fois dans le même tour reste de durée 1 ; il expirera bien au tour suivant.

Dette technique : deux switch à garder synchronisés

applyRelicEffect et removeRelicEffect sont deux switch sur une String, dans deux méthodes différentes, sans aucun lien vérifié par le compilateur. Le jour où vous ajoutez un effectType permanent (par exemple gain_max_hp en startOfRun) et que vous oubliez la branche du retrait, la relique deviendra gratuite : le joueur la sacrifiera au nœud d'échange en gardant son bonus. Aucun test, aucun avertissement de l'analyseur ne vous le signalera. Si vous devez durcir un seul point de ce chapitre, c'est celui-là.

exchangeRelics : l'orchestration

Le nœud d'échange offre une relique de rareté N contre trois reliques de rareté N−1. La méthode qui applique la transaction fait trois choses, dans cet ordre :

lib/game/controllers/run/player_stats_manager.dartdart
  void exchangeRelics(List<RelicData> sacrificed, RelicData gained) {
    for (var relic in sacrificed) {
      removeRelicEffect(relic);
    }
    final sacrificedIds = sacrificed.map((r) => r.id).toList();
    ref.read(inventoryProvider.notifier).removeRelics(sacrificedIds);
    ref.read(inventoryProvider.notifier).addRelic(gained);
  }
  1. Annuler les effets permanents des trois sacrifiées (removeRelicEffect ne fait rien pour celles qui ne sont pas startOfRun).
  2. Les retirer de l'inventaire par leurs identifiants.
  3. Ajouter la gagnée — ce qui, via addRelic, applique immédiatement son effet si elle est startOfRun.

L'ordre compte. Retirer avant d'annuler fonctionnerait aussi (removeRelicEffect travaille sur l'objet RelicData passé, pas sur l'inventaire), mais annuler après avoir ajouté la nouvelle relique serait dangereux si les deux touchaient la même statistique. Le code choisi — retrancher, puis ajouter — est le plus sûr.

L'échange coûte exactement trois reliques du cran de rareté inférieur (_selectedOriginalIndices.length != 3 bloque la validation, et la sélection est plafonnée à trois). 7. L'inventaire : stockage, sauvegarde, reconstruction

Les reliques ne vivent pas dans RunState mais dans un état séparé, InventoryState, exposé par son propre provider Riverpod. C'est un modèle de trois champs.

lib/models/inventory_state.dartdart
class InventoryState {
  final int gold;
  final List<RelicData> relics;
  final int bonusShopCards;

  const InventoryState({
    this.gold = 0,
    this.relics = const [],
    this.bonusShopCards = 0,
  });

  InventoryState copyWith({
    int? gold,
    List<RelicData>? relics,
    int? bonusShopCards,
  }) {
    return InventoryState(
      gold: gold ?? this.gold,
      relics: relics ?? this.relics,
      bonusShopCards: bonusShopCards ?? this.bonusShopCards,
    );
  }

Trois champs, trois natures différentes : gold est une ressource dépensable, relics est une collection permanente, et bonusShopCards est un compteur d'améliorations achetées à la boutique — il élargit l'étal de 3 cartes à 3 + bonusShopCards. Ils cohabitent parce qu'ils partagent la même durée de vie : celle de la run.

Le contrôleur qui les manipule est court, et deux de ses méthodes méritent un examen.

lib/game/controllers/inventory_controller.dartdart
  void addRelic(RelicData relic) {
    state = state.copyWith(relics: [...state.relics, relic]);
    if (relic.trigger == RelicTrigger.startOfRun) {
      ref.read(runProvider.notifier).applyRelicEffect(relic);
    }
  }

  void removeRelics(List<String> relicIds) {
    final List<RelicData> newRelics = List.from(state.relics);
    for (final id in relicIds) {
      final index = newRelics.indexWhere((r) => r.id == id);
      if (index != -1) {
        newRelics.removeAt(index);
      }
    }
    state = state.copyWith(relics: newRelics);
  }

addRelic est le point d'entrée unique pour gagner une relique : il est appelé depuis la récompense de combat (reward_controller.dart:232), depuis les événements de carte (event_controller.dart:127) et depuis l'échange. À chaque fois, l'effet startOfRun est appliqué au passage. Rien à faire de plus côté appelant.

removeRelics est plus subtil qu'il n'y paraît. Elle prend une liste d'identifiants, pas d'objets, et pour chaque identifiant elle supprime un seul exemplaire — indexWhere renvoie la première correspondance, removeAt ne retire que celle-là. C'est exactement le comportement voulu : si vous sacrifiez un Talisman de Fer alors que vous en possédez trois, il vous en reste deux. Une implémentation naïve avec removeWhere((r) => relicIds.contains(r.id)) vous aurait pris les trois.

Bonne pratique

Quand une collection peut contenir des doublons signifiants, une suppression « par identité de donnée » est presque toujours un bug. Ici, la boucle indexWhere + removeAt traduit fidèlement « retire trois jetons de ce type », qui est la sémantique du jeu. Le coût est un peu de verbosité ; le bénéfice est l'absence d'une classe entière de bugs.

La sérialisation minimaliste

Vient la sauvegarde. Une RelicData contient dix champs — mais on n'en écrit que trois sur le disque.

Pourquoi ne pas tout écrire ? Parce que relics.json est la source de vérité. Si vous rééquilibrez le Bouclier Ancestral de 5 à 6 points d'Armure entre deux versions du jeu, une sauvegarde qui aurait recopié la valeur 5 continuerait à donner 5 après la mise à jour. En ne stockant que l'id, la sauvegarde reste une référence, pas une copie. Les statistiques du joueur, elles, sont sauvegardées telles quelles : un bonus startOfRun déjà appliqué reste acquis.

Restent nameFr et nameEn, qui semblent contredire ce principe. Ils ne sont là que pour un cas : celui où la relique n'existe plus.

Bonne pratique : échouer partiellement, pas totalement

La stratégie inverse — « une référence inconnue, donc la sauvegarde est corrompue, on efface » — est plus simple à écrire mais brutale pour le joueur, qui perd une run de deux heures parce qu'une relique a été renommée. Ce patron est répliqué à l'identique pour le deck, la run et les améliorations de forge.

Règle du jeu : les passifs profitent de la Maîtrise d'Armure, pas les reliques

Comparez les deux lignes. Passif : armure + passive.value + stats.effectiveArmorMastery. Relique : armure + relic.value. Avec 2 de Maîtrise d'Armure, la Régénération d'Armure donne 4 points par fin de tour au lieu de 2, tandis que la Rune de Protection en donne toujours 3. Cette différence n'est écrite dans aucune description en jeu, mais elle est bien intentionnelle du côté des passifs — la formule est répétée aux trois endroits de TraitSystem et les descriptions de passives.json mentionnent explicitement « (+ Maîtrise) ».

Ironie du système : le Croc Kunaï donne de la Maîtrise d'Armure via un statut armor_mastery, que effectiveArmorMastery additionne. Une relique alimente donc un bonus dont seuls les passifs bénéficient.

Pourquoi cette duplication ?

On pourrait vouloir tout fusionner : un seul applyEffect pour les reliques et les passifs. Regardons ce qui s'y oppose vraiment.

Cardinalité

Les reliques sont une liste à filtrer ; le passif est unique et toujours présent. Le code de dispatch n'a pas la même forme.

Formules divergentes

gain_armor ne calcule pas la même chose des deux côtés : la Maîtrise d'Armure entre dans l'une et pas dans l'autre.

Granularité du déclencheur

Le passif spellArmor teste le type de carte dans le code ; les reliques ont trois déclencheurs dédiés pour ça.

Portée de l'effet

Une relique peut modifier une statistique permanente et doit savoir se retirer ; un passif ne fait qu'agir dans le combat.

La conclusion honnête : l'enum partagé est justifié, la duplication des moteurs l'est aussi, et c'est le nom RelicTrigger qui est mal choisi. Il devrait s'appeler GameTrigger ou EffectTrigger. Un développeur qui découvre PassiveData et y voit RelicTrigger se demande légitimement s'il vient de tomber sur un copier-coller malheureux, alors qu'il s'agit d'un choix délibéré : un vocabulaire temporel commun à tout ce qui se déclenche dans le jeu.

Bonne pratique : nommer d'après le concept, pas d'après le premier usage

RelicTrigger a été nommé quand seules les reliques l'utilisaient. Dès qu'un deuxième client est apparu, le nom est devenu un mensonge coûteux — en confusion, pas en bugs. Renommer un enum est l'un des refactorings les plus sûrs qui soient (une recherche-remplacement, que l'analyseur valide entièrement). Si vous reprenez ce projet, c'est un excellent premier commit.

Mode d'emploi : ajouter une nouvelle relique en 3 étapes

Terminons par le mode d'emploi promis en introduction. Prenons un exemple concret : une relique « Grimoire Vorace », peu commune, qui donne 2 points d'Armure chaque fois qu'on joue une carte Compétence — donc sur le déclencheur onSkillPlayed, aujourd'hui inutilisé.

Étape 1 — l'entrée JSON. Ajoutez l'objet à assets/data/relics.json. Le déclencheur et l'effet doivent s'écrire exactement comme dans le code (attention à la casse).

Le déclencheur onSkillPlayed est déjà appelé par combat_controller.dart:305, la couleur et le libellé sont déjà gérés par les trois écrans. La relique fonctionne dès le rechargement des données. Si en revanche vous inventiez un effet inédit — disons gain_armor_per_missing_hp — vous ajouteriez une branche dans applyRelicEffect, et, si et seulement si l'effet est permanent et destiné à startOfRun, la branche symétrique dans removeRelicEffect.

La checklist en une phrase

Une entrée dans relics.json avec un trigger valide et un effectType déjà connu suffit. Un nouvel effectType coûte une branche dans applyRelicEffect, plus une dans removeRelicEffect s'il est permanent. Un nouveau trigger, en revanche, coûte cher : une valeur d'enum, un appel applyRelics au bon endroit de la boucle de combat, et trois switch d'interface à compléter — ce que le compilateur vous rappellera, puisque les switch sur enum doivent être exhaustifs.

Quiz — vérifiez vos acquis

1. Combien d'attaques faut-il jouer dans le même tour pour déclencher le Croc Kunaï, et que gagne-t-on ?

  • 2 attaques, et on gagne 1 point d'Armure immédiat
  • 3 attaques, et on gagne un statut armor_mastery de valeur 1 pour tout le combat
  • 3 attaques, et on gagne 3 points de Force pour le tour en cours
  • 5 attaques, et on gagne 1 Maîtrise d'Armure permanente pour la run
Réponse : la branche charge_armor_mastery_combat de player_stats_manager.dart teste if (newVal >= 3), puis ajoute un StatusEffect(id: 'armor_mastery', value: relic.value, duration: 99) — soit 1 point, puisque "value": 1 dans le JSON, pour la durée du combat. Les 5 cartes et les 3 points de Force sont ceux de la Plume de scribe.

2. D'où part l'appel applyRelics(RelicTrigger.endOfTurn) ?

  • De run_controller.dart, dans une méthode endTurn()
  • De combat_controller.dart, dans endEnemyTurn()
  • De lib/ui/screens/game_screen.dart, dans le onEndTurnTap du bouton de fin de tour
  • De turn_phase_manager.dart, dans startEnemyTurn()
Réponse : c'est le seul des neuf déclencheurs appelé depuis la couche interface, à la ligne 473 de game_screen.dart, juste après TraitSystem.onTurnEnd et juste avant discardHand(). Conséquence : un tour qui se terminerait sans clic ne déclencherait pas les reliques de fin de tour.

3. Pourquoi les statuts posés par les reliques ont-ils une durée de 99 ?

  • Parce que 99 est la valeur maximale acceptée par le champ duration
  • Parce que les statuts de durée supérieure à 50 ne sont jamais décrémentés
  • Parce que 99 est une valeur sentinelle interprétée comme « infini » par tickStatuses()
  • Parce qu'un statut perd 1 de durée par tour, qu'aucun combat n'atteint 99 tours, et que startCombat() vide de toute façon la liste des statuts
Réponse : 99 n'a aucune signification spéciale pour le code — tickStatuses() le décrémente comme n'importe quelle autre durée. C'est un plafond hors d'atteinte, et le nettoyage statuses: [] en tête de startCombat() garantit qu'aucun reliquat ne franchit la frontière entre deux combats.

4. Combien de reliques de relics.json utilisent les déclencheurs onSkillPlayed et onPowerPlayed ?

  • Aucune : les deux déclencheurs sont câblés dans le code mais inutilisés par les données
  • Une chacun : l'Amulette du Mage et la Plume de scribe
  • Deux chacun, comme onAttackPlayed
  • Ils n'existent pas dans l'enum RelicTrigger
Réponse : les deux valeurs existent bien dans l'enum, sont appelées aux lignes 305 et 307 de combat_controller.dart et sont affichées par les trois écrans d'interface — mais aucune des 25 reliques ne les déclare. C'est de l'infrastructure posée d'avance. L'Amulette du Mage et la Plume de scribe sont sur onCardPlayed.

5. Que fait removeRelicEffect quand on sacrifie un Talisman de Fer (startOfTurn, gain_armor, valeur 2) au nœud d'échange ?

  • Elle retire 2 points d'Armure au héros
  • Elle retire le statut armor de durée 99 posé par la relique
  • Rien du tout : la méthode ne traite que les reliques dont le trigger est startOfRun
  • Elle lève une exception, car gain_armor n'a pas de branche de retrait
Réponse : la méthode s'ouvre sur if (relic.trigger == RelicTrigger.startOfRun) ; tout le reste sort sans rien faire. C'est suffisant : une fois la relique retirée de l'inventaire par removeRelics, le filtre where((r) => r.trigger == trigger) de applyRelics ne la retient plus et l'effet cesse de lui-même. Les cinq case couvrent uniquement les effets permanents.

6. Que contient exactement la sauvegarde pour une relique, et pourquoi ?

  • Les dix champs de RelicData, pour que la sauvegarde soit autonome
  • {id, nameFr, nameEn} : l'id sert à retrouver la relique dans relics.json, les deux noms à afficher un message lisible si elle a disparu du catalogue
  • Uniquement l'id, les noms étant reconstruits par AppLocalizations
