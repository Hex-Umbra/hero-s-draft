Riverpod — l'état partagé du jeu

Riverpod est le cerveau de Hero's Draft : toute règle du jeu y vit. Ce chapitre explique la bibliothèque puis passe en revue les onze providers du projet.

1. Le problème que Riverpod résout

Un jeu de cartes roguelike, c'est une longue liste de questions du type « combien de PV a le héros ? », « combien de cartes reste-t-il dans la pioche ? », « le joueur a-t-il assez d'or ? ». Ces réponses changent en permanence, et surtout : elles sont posées depuis des endroits très éloignés les uns des autres. La barre de vie du HUD, la carte du monde, le moteur Flame qui dessine l'arène, la boutique, la sauvegarde… tout le monde a besoin de la même vérité.

Pourquoi pas setState ?

Vous avez vu au chapitre précédent que setState est le mécanisme de base de Flutter : il dit à un widget « ton état a changé, redessine-toi ». C'est parfait pour un état purement visuel et purement local. D'ailleurs le projet s'en sert encore, par exemple dans GameScreen pour afficher ou masquer l'avertissement « il te reste du mana » :

lib/ui/screens/game_screen.dartdart
  bool _showManaWarning = false;
  bool _showRemainingManaWarning = false;
  bool _isVictoryHandled = false;

Ces trois booléens ne concernent que cet écran. Personne d'autre n'a besoin de savoir si un bandeau jaune est affiché. Mais essayez d'appliquer la même méthode aux points de vie du héros : il faudrait que GameScreen détienne la valeur, puis la passe en paramètre à CombatBottomHud, qui la passerait à ses enfants, pendant qu'un callback remonterait dans l'autre sens à chaque dégât subi. On appelle ça du prop drilling : on perce un tunnel de paramètres à travers dix widgets pour faire passer une donnée entre deux points qui, eux, sont à dix widgets l'un de l'autre. Et le jour où l'écran de la boutique a lui aussi besoin des PV, il faut recommencer un autre tunnel.

Avec Riverpod, n'importe quel widget de l'arbre demande directement la donnée, sans que ses parents ne soient au courant. Voici le fichier le plus simple du projet qui fait ça : le petit panneau de stats affiché sur la carte du monde.

lib/ui/widgets/map/hero_mini_stats_panel.dartdart
class HeroMiniStatsPanel extends ConsumerWidget {
  const HeroMiniStatsPanel({super.key});

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final runState = ref.watch(runProvider);
    final stats = runState.heroStats;

    final locale = Localizations.localeOf(context).languageCode;
    // ... construit le panneau à partir de `stats`

Trois choses à retenir de cet extrait, on y reviendra en détail :

  • le widget étend ConsumerWidget au lieu de StatelessWidget ;
  • sa méthode build reçoit un paramètre supplémentaire, WidgetRef ref ;
  • ref.watch(runProvider) renvoie l'état courant et abonne le widget : dès que le héros perd un PV, ce panneau — et lui seul — se reconstruit.

Pourquoi pas un singleton global ?

L'autre réflexe naturel serait d'écrire class GameState { static int heroHp = 100; } et d'y accéder de partout. Ça marche… jusqu'à ce que trois problèmes vous rattrapent :

Rien ne prévient l'UI

Modifier une variable statique ne redessine aucun widget. Il faudrait recoller un système de notification par-dessus — c'est-à-dire réécrire Riverpod, mal.

Pas de remise à zéro

Une variable globale vit aussi longtemps que le processus. Entre deux runs, ou entre deux tests, elle garde ses valeurs sales.

Impossible à substituer

On ne peut pas remplacer un singleton par une version de test sans toucher au code de production.

Ce que ça change pour les tests

C'est l'argument décisif. Un provider Riverpod n'est pas la donnée : c'est une recette pour fabriquer la donnée. La donnée elle-même vit dans un conteneur, le ProviderContainer. En production, ProviderScope en crée un pour toute l'application. Dans un test, on en crée un à la main, on le pilote, et on le jette. Aucun widget, aucun écran, aucun moteur de rendu.

exempledart
// Un test peut instancier tout l'état du jeu sans lancer Flutter :
final container = ProviderContainer();
addTearDown(container.dispose);

// On appelle une méthode métier...
container.read(inventoryProvider.notifier).gainGold(120);

// ...et on lit le résultat.
expect(container.read(inventoryProvider).gold, 120);

Le même code de contrôleur tourne dans le jeu et dans le test, sans branche if (isTest), parce qu'il ne dépend jamais d'un BuildContext ni d'un widget. C'est la contrepartie concrète de la règle d'architecture du projet.

Règle du projet

Tout l'état métier vit dans lib/game/controllers/, dans des Notifier Riverpod 2.x exposés par des NotifierProvider — jamais dans les widgets, jamais dans les composants Flame, jamais dans des variables globales ou des singletons. Les composants Flame sont « visuels et réactifs uniquement » : ils lisent l'état Riverpod et le rendent à l'écran, ils ne possèdent aucune logique de jeu.

Cette règle a une conséquence pratique très utile quand vous cherchez un bug : si une valeur du jeu est fausse (des dégâts, un prix, un cooldown), la cause est forcément dans lib/game/controllers/ ou dans un service appelé depuis là. Jamais dans un widget.

2. Les briques : ProviderScope, Provider, FutureProvider, Notifier

Riverpod tient en quatre concepts. Le projet déclare flutter_riverpod: ^2.5.1 dans son pubspec.yaml (résolu en 2.6.1), c'est-à-dire la génération « Riverpod 2.x » — celle qui introduit Notifier.

2.1 ProviderScope : le conteneur racine

Sans ProviderScope, aucun provider ne peut être lu : c'est le widget qui crée le ProviderContainer dans lequel vivent tous les états. Il est posé une fois pour toutes, tout en haut de l'application.

lib/main.dartdart
void main() {
  WidgetsFlutterBinding.ensureInitialized();
  runApp(const ProviderScope(child: HerosDraftApp()));
}

class HerosDraftApp extends ConsumerWidget {
  const HerosDraftApp({super.key});

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    // Force l'activation de l'écoute d'autosave dès le démarrage de l'app.
    ref.watch(autosaveOrchestratorProvider);

    return MaterialApp(
      onGenerateTitle: (context) => AppLocalizations.of(context)!.appTitle,
      theme: AppTheme.darkNeonTheme,
      // ...

Notez que HerosDraftApp est déjà un ConsumerWidget : la toute première chose que fait l'application, avant même de construire le MaterialApp, est de réveiller le provider d'autosauvegarde. On expliquera pourquoi en section 8.

2.2 Provider : une valeur calculée une fois

Le Provider tout court expose une valeur immuable, construite à la première lecture puis mise en cache. On s'en sert pour les objets « outils » : un registre, une dépendance injectable. Dans Hero's Draft, il y en a trois. Le plus parlant est le registre des effets de carte.

lib/game/services/effects/effect_strategy.dartdart
final effectRegistryProvider = Provider<EffectRegistry>((ref) {
  final registry = EffectRegistry();
  registry.register('damage', DamageEffectStrategy());
  registry.register('heal', HealEffectStrategy());
  registry.register('armor', ArmorEffectStrategy());
  registry.register('gain_mana', GainManaEffectStrategy());
  registry.register('draw', DrawEffectStrategy());
  registry.register('apply_status', ApplyStatusEffectStrategy());
  return registry;
});

Ce provider ne change jamais d'état : il assemble six stratégies une seule fois et les rend disponibles au reste du jeu. On y revient en section 7.

2.3 FutureProvider : une valeur asynchrone

Quand la valeur demande une opération asynchrone — lire des fichiers, appeler le réseau — on utilise un FutureProvider. Il ne renvoie pas directement la valeur mais un AsyncValue<T>, un objet qui vaut « en cours », « chargé » ou « en erreur ». Le projet en a exactement un, pour charger les données JSON du jeu. Toute la section 5 lui est consacrée.

2.4 Notifier + NotifierProvider : un état qui évolue

C'est la brique centrale du projet. Un Notifier<T> est une classe qui détient un état de type T et expose des méthodes pour le modifier ; le NotifierProvider l'expose au reste de l'application. Le plus court du projet, dans checkpoint_controller.dart, tient en une dizaine de lignes :

lib/game/controllers/checkpoint_controller.dartdart
class CheckpointNotifier extends Notifier<int> {
  @override
  int build() => 0;

  /// Signale qu'un nœud de la carte vient d'être résolu (combat, boutique,
  /// repos, event, forge, échange de reliques, ou draft de Level Up).
  void bump() => state = state + 1;
}

final checkpointProvider =
    NotifierProvider<CheckpointNotifier, int>(CheckpointNotifier.new);

Tout est là : l'état est un simple int, build() donne sa valeur initiale, et bump() le fait avancer. Notez la syntaxe CheckpointNotifier.new : ce n'est pas un appel de constructeur, c'est une référence au constructeur. Riverpod l'appellera lui-même, au moment où il en aura besoin — c'est ce qui lui permet de recréer proprement l'état.

2.5 StateNotifier vs Notifier : pourquoi le projet a migré

Riverpod 1.x proposait StateNotifier, une classe venue d'un autre paquet (state_notifier). Elle fonctionne, mais elle a deux défauts que Notifier corrige :

StateNotifier (ancien)Notifier (Riverpod 2.x)
État initialPassé au constructeur : NotificationNotifier() : super([])Renvoyé par la méthode build()
Accès à refAucun. Il faut se le faire passer à la main dans le constructeur du providerref est un champ de la classe, disponible partout
DéclarationStateNotifierProvider<N, T>((ref) => N())NotifierProvider<N, T>(N.new)
RecréationLe provider doit reconstruire l'objet entierRiverpod rappelle build(), l'objet est réutilisable

Le point qui compte le plus ici est le deuxième. Dans Hero's Draft, les contrôleurs se parlent en permanence : jouer une carte touche le deck, le combat et le héros. Avoir ref disponible directement dans la classe rend ces appels naturels — vous le verrez dans SkillController en section 3.

La migration des contrôleurs est terminée : les neuf contrôleurs de lib/game/controllers/ étendent tous Notifier. Il reste exactement un StateNotifier dans le dépôt, et c'est volontaire.

lib/ui/widgets/notification_overlay.dartdart

C'est la file de toasts : les petits bandeaux « VICTOIRE ! », « Deck remélangé », qui s'empilent en haut à gauche, se limitent à quatre à l'écran et disparaissent après 3,5 secondes. Cet état est purement décoratif — il ne contient aucune règle de jeu, il n'est pas sauvegardé, et perdre son contenu ne casse rien. Il n'a d'ailleurs jamais besoin de ref : il ne parle à aucun autre provider. Le migrer n'apporterait rien.

À retenir

Pour tout nouvel état dans ce projet : Notifier + NotifierProvider. Le StateNotifier de notification_overlay.dart est une exception historique et documentée, pas un modèle à suivre.

3. Écrire un Notifier

Passons à l'anatomie complète. Un contrôleur du projet suit toujours le même squelette :

illustrationdart
class XController extends Notifier<XState> {   // 1. le type de l'état
  @override
  XState build() {                            // 2. l'état initial
    return const XState();
  }

  void faireQuelqueChose() {
    state = state.copyWith(champ: nouvelleValeur);   // 3. on remplace l'état
    ref.read(autreProvider.notifier).reagir();       // 4. on parle aux voisins
  }
}

final xProvider = NotifierProvider<XController, XState>(XController.new);
  1. extends Notifier<XState> — le paramètre générique est le type de l'état exposé. Ici XState, mais ça peut être un int (CheckpointNotifier) ou une List.
  2. build() — appelée par Riverpod à la première lecture du provider, et jamais avant. Elle renvoie l'état de départ. C'est aussi l'endroit où l'on prépare les dépendances internes (section 7).
  3. state = ... — la seule façon de notifier. Affecter state déclenche la comparaison avec l'ancienne valeur et prévient tous les abonnés. Il faut donc affecter un nouvel objet : muter un champ de l'objet existant ne déclencherait rien.
  4. ref — disponible directement, sans le déclarer. C'est la porte vers les autres providers.

3.1 InventoryController en entier

Voici le contrôleur d'inventaire, dans son intégralité — le fichier complet fait 65 lignes, imports compris. Il gère l'or, les reliques, et le nombre de cartes bonus en boutique.

lib/game/controllers/inventory_controller.dartdart
class InventoryController extends Notifier<InventoryState> {
  @override
  InventoryState build() {
    return const InventoryState();
  }

  /// Remplace intégralement l'état par une sauvegarde chargée
  void hydrate(InventoryState savedState) {
    state = savedState;
  }

  void gainGold(int amount) {
    state = state.copyWith(gold: state.gold + amount);
  }

  bool spendGold(int amount) {
    if (state.gold < amount) return false;
    state = state.copyWith(gold: state.gold - amount);
    return true;
  }

  void addRelic(RelicData relic) {
    state = state.copyWith(relics: [...state.relics, relic]);
    if (relic.trigger == RelicTrigger.startOfRun) {
      ref.read(runProvider.notifier).applyRelicEffect(relic);
    }
  }

  void buyShopExpansion() {
    state = state.copyWith(bonusShopCards: state.bonusShopCards + 1);
  }

  void removeRelics(List<String> relicIds) {
    final List<RelicData> newRelics = List.from(state.relics);
    for (final id in relicIds) {
      final index = newRelics.indexWhere((r) => r.id == id);
      if (index != -1) {
        newRelics.removeAt(index);
      }
    }
    state = state.copyWith(relics: newRelics);
  }

  void reset({
    int initialGold = 50,
    List<RelicData> initialRelics = const [],
    int initialBonusShopCards = 0,
  }) {
    state = InventoryState(
      gold: initialGold,
      relics: initialRelics,
      bonusShopCards: initialBonusShopCards,
    );
  }
}

final inventoryProvider =
    NotifierProvider<InventoryController, InventoryState>(InventoryController.new);

Ce fichier illustre quatre habitudes constantes du projet :

  • L'état est immuable. InventoryState n'a que des champs final. Pour retirer des reliques, removeRelics copie la liste (List.from), la modifie, puis affecte la copie. Modifier state.relics directement ne préviendrait personne — et Riverpod comparerait l'ancien et le nouvel état, verrait le même objet, et n'émettrait aucune notification.
  • Les méthodes renvoient un verdict quand il y a un échec possible. spendGold renvoie false si l'or est insuffisant, et surtout ne touche pas à l'état dans ce cas. L'appelant décide quoi en faire — c'est la boutique qui affiche « pas assez d'or », pas le contrôleur.
  • Une méthode hydrate. Elle remplace l'état d'un bloc au chargement d'une sauvegarde. Quatre contrôleurs l'exposent : RunController, DeckNotifier, InventoryController et SkillController — exactement les quatre états sérialisés par SaveService (section 8).
  • Les effets de bord passent par ref. Dans addRelic, si la relique se déclenche en début de run, l'inventaire demande au RunController d'appliquer son effet. L'inventaire ne sait pas comment une relique modifie les stats du héros ; il sait seulement à qui poser la question.

3.2 SkillController : quand une action peut échouer

Le contrôleur des sorts est encore plus court, mais il montre un aller-retour complet entre deux providers. Le héros a deux sorts, chacun avec un cooldown en tours et un coût (mana ou pourcentage de PV).

lib/game/controllers/skill_controller.dartdart
class SkillController extends Notifier<SkillState> {
  @override
  SkillState build() {
    return const SkillState();
  }

  /// Remplace intégralement l'état par une sauvegarde chargée
  void hydrate(SkillState savedState) {
    state = savedState;
  }

  void tickCooldowns() {
    state = SkillState(
      skill1Cooldown: state.skill1Cooldown > 0 ? state.skill1Cooldown - 1 : 0,
      skill2Cooldown: state.skill2Cooldown > 0 ? state.skill2Cooldown - 1 : 0,
    );
  }

  bool triggerSkill1(int cd, {int mana = 0, int hpPercent = 0}) {
    if (state.skill1Cooldown > 0) return false;
    final success = ref
        .read(runProvider.notifier)
        .consumeResource(mana: mana, hpPercent: hpPercent);
    if (!success) return false;
    state = state.copyWith(skill1Cooldown: cd);
    return true;
  }

  // triggerSkill2 est strictement symétrique.

  void resetCooldowns() {
    state = const SkillState();
  }
}

final skillProvider = NotifierProvider<SkillController, SkillState>(SkillController.new);

Regardez l'ordre des opérations dans triggerSkill1, il est important :

  1. vérifier le cooldown local — si le sort n'est pas prêt, on sort immédiatement, sans rien toucher ;
  2. demander au RunController de consommer les ressources ; c'est lui qui sait si le héros a assez de mana ou de PV ;
  3. si le paiement a échoué, on sort — et le cooldown n'est pas armé ;
  4. seulement à la fin, on modifie state.

Autrement dit : aucune modification d'état avant que toutes les conditions soient validées. C'est ce qui évite les états incohérents du type « cooldown lancé mais sort non joué ». Le motif se répète partout dans le projet, notamment dans ShopController où chaque achat commence par un spendGold qui peut refuser.

Piège de débutant

state = state ne notifie rien : Riverpod compare l'ancienne et la nouvelle valeur avec == et n'émet que si elles diffèrent. Même piège avec state.relics.add(relic) : la liste change, mais l'objet InventoryState reste identique, donc l'UI ne bouge pas. Il faut toujours reconstruire : state = state.copyWith(relics: [...state.relics, relic]).

4. Lire un provider : watch, read, listen

Trois verbes, trois usages qui ne sont pas interchangeables. C'est la source d'erreur numéro un chez les débutants Riverpod, donc prenons le temps.

4.1 ref.watch — s'abonner et reconstruire

ref.watch(p) renvoie la valeur courante et enregistre une dépendance. À chaque nouvel état, le widget est reconstruit. C'est le mode par défaut pour tout ce qui est affiché. Dans GameScreen, la méthode build commence par quatre watch :

lib/ui/screens/game_screen.dartdart
  @override
  Widget build(BuildContext context) {
    final runState = ref.watch(runProvider);
    final deckState = ref.watch(deckProvider);
    final combatState = ref.watch(combatProvider);
    final gameData = ref.watch(gameDataLoaderProvider).requireValue;

L'écran de combat dépend donc de quatre providers : dès que l'un d'eux change, il se redessine. C'est exactement ce qu'on veut ici — cet écran affiche les PV, le mana, le nombre de cartes en pioche et l'état des ennemis.

Remarquez au passage que GameScreen est un ConsumerStatefulWidget et non un ConsumerWidget : il a besoin d'un initState pour créer l'instance Flame HerosDraftGame, et de setState pour ses booléens purement visuels. Dans un ConsumerState, ref est un champ de la classe : pas besoin de le recevoir en paramètre de build, il est accessible depuis toutes les méthodes.

4.2 ref.read — lire une fois, pour agir

ref.read(p) renvoie la valeur courante sans s'abonner. On l'utilise dans les gestionnaires d'événements : au moment d'un clic, on veut la valeur d'maintenant, et on ne veut surtout pas que le fait d'avoir cliqué crée un abonnement.

lib/ui/screens/game_screen.dartdart
                      onEndTurnTap: () {
                        final currentMana = runState.heroStats.currentMana;
                        if (currentMana > 0 && !_showRemainingManaWarning) {
                          // ... premier clic : on avertit qu'il reste du mana
                          return;
                        }
                        // ...
                        TraitSystem.onTurnEnd(ref.read(runProvider.notifier));
                        ref
                            .read(runProvider.notifier)
                            .applyRelics(RelicTrigger.endOfTurn);
                        ref.read(deckProvider.notifier).discardHand();
                        _game.executeTurn();
                      },

Ce bouton « fin de tour » enchaîne quatre effets : les traits passifs, les reliques de fin de tour, la défausse de la main, puis le tour des ennemis côté Flame. Aucun de ces appels n'a besoin d'un abonnement.

Piège : ne jamais ref.read dans build

ref.read dans build compile, ne plante pas, et produit un bug très difficile à voir : le widget lit une valeur correcte la première fois, puis ne se reconstruit plus jamais. L'affichage se fige sur une valeur périmée pendant que le reste de l'écran continue de vivre. Si vous avez besoin d'une valeur pour l'afficher, c'est ref.watch. ref.read appartient aux callbacks : onTap, onPressed, initState (dans un Future.microtask), et aux méthodes des Notifier.

Le projet respecte cette règle, y compris dans le cas délicat de l'initialisation. Dans GameScreen.initState, on doit lancer le combat — mais on ne peut pas modifier un provider pendant la construction d'un widget. La solution employée est de repousser l'appel juste après la première frame :

lib/ui/screens/game_screen.dartdart
  @override
  void initState() {
    super.initState();

    Future.microtask(() {
      ref.read(combatProvider.notifier).startPlayerCombat();

      final runState = ref.read(runProvider);
      // ...
      final gameData = ref.read(gameDataLoaderProvider).requireValue;
      ref
          .read(combatProvider.notifier)
          .initializeCombat(
            runState.currentLevel,
            runState.currentNodeType,
            gameData.enemies,
            // ...
          );
    });

4.3 ref.read(xProvider.notifier) — appeler une méthode

Vous avez déjà croisé la syntaxe une dizaine de fois. Elle mérite une explication explicite, parce que c'est là que beaucoup de débutants se perdent. Un NotifierProvider expose deux choses :

ExpressionType obtenuUsage
ref.watch(runProvider)RunStateLire les données : runState.heroStats.currentPv
ref.read(runProvider)RunStateLire les données une fois, dans un callback
ref.read(runProvider.notifier)RunControllerAppeler une méthode : .takeDamage(12)

Sans .notifier, on obtient l'état (une donnée figée) ; avec .notifier, on obtient l'objet contrôleur (le comportement). Et on utilise presque toujours read avec .notifier : le contrôleur, lui, ne change pas d'identité quand son état change, donc s'y abonner n'aurait pas de sens.

4.4 ref.listen — réagir à un changement

Parfois, il ne faut pas afficher le changement mais y réagir : ouvrir une boîte de dialogue, naviguer, jouer un son, afficher un toast. Faire ça dans build serait une faute — build peut être appelé de nombreuses fois, et doit rester une fonction pure qui ne fait que construire des widgets.

ref.listen résout ça : on le déclare dans build, mais le callback ne se déclenche qu'aux changements réels, avec l'ancienne et la nouvelle valeur. Les deux exemples du projet sont côte à côte :

lib/ui/screens/game_screen.dartdart
    ref.listen<CombatState>(combatProvider, (previous, next) {
      final wasEnded = previous?.isCombatEnded ?? false;
      if (next.isCombatEnded && next.isVictory && !wasEnded) {
        _handleCombatVictory();
      }
    });

    ref.listen<DeckState>(deckProvider, (previous, next) {
      if (previous != null && next.reshuffleCount > previous.reshuffleCount) {
        context.showNotification(
          '${AppLocalizations.of(context)!.deckReshuffled}',
          type: NotificationType.info,
        );
      }
    });

Premier listener — la victoire. _handleCombatVictory() déclenche toute la séquence de récompenses : tirage de relique, écran de draft de cartes, or et XP, puis retour à la carte. Ce n'est pas de l'affichage, c'est de la navigation et de la mutation d'état. Le test next.isCombatEnded && next.isVictory && !wasEnded garantit qu'on ne déclenche qu'une seule fois, au moment exact de la transition vers la victoire : si le combat était déjà terminé à l'état précédent, on ne refait rien. La méthode se protège d'ailleurs une deuxième fois avec un drapeau _isVictoryHandled.

Second listener — le remélange. C'est le plus instructif, parce qu'il explique un choix de conception dans DeckState.

4.5 Pourquoi reshuffleCount est un compteur

Quand la pioche est vide et qu'il faut piocher, le jeu remet la défausse dans la pioche et la mélange. C'est un événement, pas un état : ça arrive à un instant précis, puis c'est fini. Or Riverpod ne transporte que des états. Comment faire passer un événement dans un canal qui ne connaît que des valeurs ?

La réponse du projet : un compteur monotone.

lib/game/controllers/deck_controller.dartdart
  /// Nombre de remélanges défausse → pioche depuis le début du combat.
  /// Remis à 0 par `startCombat`. Observé par l'UI pour signaler l'événement.
  final int reshuffleCount;
lib/game/controllers/deck_controller.dartdart
  void drawCards(int amount, {required int maxHandSize}) {
    final result = _drawInto(
      draw: List<CardInstance>.from(state.drawPile),
      hand: List<CardInstance>.from(state.hand),
      discard: List<CardInstance>.from(state.discardPile),
      amount: amount,
      maxHandSize: maxHandSize,
      random: _random,
    );

    state = state.copyWith(
      drawPile: result.draw,
      hand: result.hand,
      discardPile: result.discard,
      reshuffleCount: state.reshuffleCount + result.reshuffles,
    );
  }

Un booléen hasReshuffled poserait deux problèmes. D'abord, il faudrait le remettre à false après l'avoir consommé — ce qui veut dire que l'UI devrait écrire dans le contrôleur du deck, une inversion de responsabilité désagréable. Ensuite, deux remélanges consécutifs (possible : _drawInto peut remélanger plusieurs fois dans une seule pioche, et renvoie le nombre exact dans result.reshuffles) donneraient true puis true : le second passerait inaperçu, puisque l'état n'aurait pas changé.

Avec un compteur, la comparaison next.reshuffleCount > previous.reshuffleCount est toujours juste, quel que soit le nombre de remélanges par pioche, et le contrôleur n'a rien à nettoyer. La remise à zéro se fait naturellement au début de chaque combat, dans startCombat.

Bonne pratique

Pour transporter un événement dans un état immuable, préférez un compteur croissant à un booléen. L'observateur compare l'ancien et le nouveau compteur ; personne n'a besoin de remettre de drapeau à zéro, et aucun événement ne peut être avalé.

5. FutureProvider et le chargement des données

Hero's Draft est 100 % data-driven : les cartes, les ennemis, les héros, les reliques, les événements sont décrits dans des fichiers JSON sous assets/data/, pas dans le code Dart. Il faut donc les lire au démarrage — et lire un fichier est asynchrone.

lib/services/game_data_service.dartdart

Neuf fichiers, chargés en parallèle avec Future.wait, puis convertis en objets Dart typés et regroupés dans un GameDataRegistry. Deux détails qui comptent :

  • cards.json et hero_cards.json sont fusionnés en une seule liste (allCards) avant d'être convertis : les cartes de héros vivent dans le même catalogue que les cartes normales.
  • Il n'existe pas de classe GameDataService. Le provider est le point d'entrée — le fichier ne contient que deux fonctions privées d'aide et cette déclaration.

5.1 AsyncValue et .when

Un FutureProvider<T> n'expose pas un T mais un AsyncValue<T> : un objet qui représente les trois issues possibles d'une opération asynchrone. La méthode .when vous force à traiter les trois cas — impossible d'oublier la gestion d'erreur.

lib/ui/screens/splash_screen.dartdart
class SplashScreen extends ConsumerWidget {
  const SplashScreen({super.key});

  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final gameData = ref.watch(gameDataLoaderProvider);

    return Scaffold(
      body: Center(
        child: gameData.when(
          data: (_) =>
              const HomeScreen(), // Si les données sont chargées, on affiche l'écran d'accueil
          loading: () =>
              const CircularProgressIndicator(), // Pendant le chargement
          error: (error, stack) =>
              Text('Erreur de chargement: $error'), // En cas d'erreur
        ),
      ),
    );
  }
}

Trois points à noter. Le ref.watch est bien un watch : le splash doit se reconstruire quand le futur se termine. Le paramètre du cas data est ignoré ((_)) : le splash ne se sert pas des données, il attend seulement qu'elles soient là. Et le FutureProvider ne démarre son chargement qu'à sa première lecture — c'est donc SplashScreen qui, en le watchant, met la machine en route.

5.2 .requireValue et le contrat implicite

Une fois le splash passé, écrire un .when à chaque écran serait insupportable : il faudrait gérer un cas « en cours de chargement » qui ne peut plus se produire. Le projet emploie donc .requireValue, qui extrait la valeur et lève une exception si elle n'est pas là.

lib/ui/screens/game_screen.dartdart
  void _handleCombatVictory() {
    if (_isVictoryHandled) return;
    _isVictoryHandled = true;

    final runState = ref.read(runProvider);
    final gameData = ref.read(gameDataLoaderProvider).requireValue;
    // ...

    ref.read(rewardProvider.notifier).handleVictory(
      defeatedEnemies: ref.read(combatProvider).defeatedEnemies,
      currentNode: currentNode,
      allRelics: gameData.relics,
      allCards: gameData.cards,
      luck: runState.heroStats.luck,
      act: runState.act,
    );

    _presentNextReward();
  }

Le contrat implicite est le suivant : « si on est passé par le splash, la donnée est là ». Comme SplashScreen n'affiche HomeScreen que dans la branche data, et que tous les autres écrans sont atteints depuis HomeScreen, aucun écran du jeu ne peut être construit avant la fin du chargement. Et comme un provider Riverpod met sa valeur en cache, la lecture suivante est instantanée : il n'y a pas de second chargement.

Ce contrat est utilisé treize fois dans le code. Deux écrans font toutefois exception et gèrent quand même le cas asynchrone : lib/ui/screens/relic_exchange_screen.dart et lib/ui/screens/card_dictionary_screen.dart repassent par .when, et lib/ui/widgets/map/dialogs/stats_dialog.dart utilise .value avec un test if (gameData == null) qui affiche un indicateur de chargement.

Point d'attention

.requireValue est un contrat non vérifié par le compilateur. Il tient tant que tout chemin de navigation passe par le splash. Le jour où quelqu'un ouvre un écran directement — un deep link, une route de debug, un test de widget qui monte ShopScreen isolément — l'application lève une exception au lieu d'afficher un chargement. Dans un test, la parade est de surcharger le provider : gameDataLoaderProvider.overrideWith((ref) async => unRegistreDeTest).

6.1 Qui lit qui

Le tableau dit qui écrit. Le schéma ci-dessous dit qui lit — c'est-à-dire quels providers un contrôleur consulte depuis ses propres méthodes.

Deux observations sur ce graphe. D'abord, runProvider est le pivot : six providers le consultent. Ensuite, il y a des cycles : runProvider lit inventoryProvider (pour connaître les reliques) et inventoryProvider lit runProvider (pour appliquer l'effet d'une relique gagnée). Même chose avec skillProvider.

À retenir

Ces cycles sont légaux parce que ce sont des ref.read ponctuels, faits à l'intérieur des méthodes, et non des ref.watch. Un ref.watch croisé entre deux providers créerait une dépendance circulaire, que Riverpod détecte et signale par une erreur au démarrage. Dans lib/game/controllers/, il n'y a aucun ref.watch : uniquement des ref.read.

7. Composer sans tout casser

Un contrôleur qui grossit devient un fourre-tout. Le projet emploie deux parades, toutes deux visibles depuis build().

7.1 Le pattern « Notifier + managers »

RunController gère les stats, la progression sur la carte, l'or, les reliques, la forge… Plutôt que d'entasser 1 200 lignes dans une classe, il délègue à trois managers créés dans build() :

lib/game/controllers/run_controller.dartdart
class RunController extends Notifier<RunState> {
  RunState get currentState => state;

  late final MapProgressionManager _mapProgressionManager;
  late final GoldManager _goldManager;

Chaque manager reçoit deux choses : this (le contrôleur, pour lire et écrire l'état) et ref (pour parler aux autres providers). Un manager n'est pas un provider : c'est un objet Dart ordinaire, sans magie, qui n'existe qu'à travers son contrôleur.

Le type Ref est le même objet que le ref d'un Notifier : on peut le passer, le stocker, le transmettre. C'est ce qui rend le découpage possible sans multiplier les providers. Le manager de l'or, encore plus court, montre le couple complet « lire l'état + écrire chez le voisin » :

lib/game/controllers/run/gold_manager.dartdart
class GoldManager {
  final RunController controller;
  final Ref ref;

  GoldManager(this.controller, this.ref);

  /// Achète un slot de forge bonus si possible. Retourne true si l'achat a réussi.
  bool buyBonusForgeSlot() {
    if (controller.currentState.bonusForgeSlots >= 4) return false;
    final costs = [50, 80, 120, 175];
    final cost = costs[controller.currentState.bonusForgeSlots];
    final success = ref.read(inventoryProvider.notifier).spendGold(cost);
    if (!success) return false;

    controller.updateState(
      controller.currentState.copyWith(
        bonusForgeSlots: controller.currentState.bonusForgeSlots + 1,
      ),
    );
    return true;
  }
}

Quatre slots de forge bonus maximum, à 50, 80, 120 puis 175 d'or. Et toujours la même discipline : on vérifie la limite, on tente le paiement, et on ne modifie l'état qu'en cas de succès. CombatController applique exactement le même pattern avec un TurnPhaseManager créé dans son propre build().

Bonne pratique

Un manager n'a pas besoin d'être un provider. S'il n'a pas d'état propre et n'est utilisé que par un seul contrôleur, en faire un objet simple créé dans build() évite de polluer le graphe de providers — tout en gardant l'accès à ref.

Deuxième parade : au lieu d'un switch géant sur le type d'effet d'une carte, on enregistre une classe par type dans un registre — c'est effectRegistryProvider, vu en section 2, qui en assemble les six exemplaires. Toutes respectent le même contrat :

7.3 deckRandomProvider : injecter l'aléatoire

La pioche mélange des cartes. Un mélange, c'est du hasard, et le hasard rend un test inutilisable : la même suite d'actions donne un résultat différent à chaque exécution. La solution : ne pas laisser DeckNotifier créer son Random, mais le lui faire fournir par un provider.

lib/game/controllers/deck_controller.dartdart
/// Source d'aléatoire de la pioche. Surchargeable en test via
/// `deckRandomProvider.overrideWithValue(Random(42))` pour rendre les
/// séquences de pioche reproductibles.
final deckRandomProvider = Provider<Random>((ref) => Random());

final deckProvider = NotifierProvider<DeckNotifier, DeckState>(DeckNotifier.new);
lib/game/controllers/deck_controller.dartdart
class DeckNotifier extends Notifier<DeckState> {
  late final Random _random;

  @override
  DeckState build() {
    _random = ref.read(deckRandomProvider);
    return const DeckState();
  }

En production, deckRandomProvider fournit un Random() sans graine : le jeu est imprévisible. En test, on remplace la recette avant même que le deck n'existe :

exempledart
final container = ProviderContainer(
  overrides: [
    deckRandomProvider.overrideWithValue(Random(42)),
  ],
);
addTearDown(container.dispose);

// À partir d'ici, tout mélange de la pioche est reproductible :
// la même graine donne toujours la même séquence de cartes.
container.read(deckProvider.notifier).startCombat(handSize: 5, maxHandSize: 10);

C'est le mécanisme de surcharge (override) de Riverpod : au moment de créer le conteneur, on remplace la recette d'un provider par une autre. Tous ceux qui le lisent — ici DeckNotifier — reçoivent la version de test sans le savoir. Et parce que _drawInto reçoit son Random en paramètre et ne touche pas à state, la logique de pioche est une fonction pure, entièrement déterministe une fois la graine fixée.

Bonne pratique — injection d'aléatoire

Tout ce qui est non déterministe (hasard, horloge, réseau, stockage) mérite son propre provider. Un Provider<Random> d'une ligne transforme une fonctionnalité intestable en fonctionnalité vérifiable carte par carte, sans ajouter le moindre paramètre seed aux méthodes métier ni la moindre branche if (isTest).

Piège

L'injection n'est utile que si toutes les sources d'aléatoire passent par un provider. Dans Hero's Draft, seule la pioche est injectée : EventController crée encore ses Random() localement — ses méthodes acceptent en échange des paramètres mockRoll et mockRelicIndex pour rester testables. Deux stratégies différentes pour le même problème ; l'injection par provider est la plus propre des deux.

8. Effets de bord et orchestration

Reste un cas qu'aucune des briques précédentes ne couvre : « quand X change, fais Y », où Y n'est pas un état mais une action — écrire sur le disque, par exemple. C'est le rôle de l'autosauvegarde.

8.1 Un Provider<void> qui ne fait qu'écouter

Le fichier complet tient en 24 lignes, imports compris :

lib/game/controllers/checkpoint_controller.dartdart
import 'package:flutter_riverpod/flutter_riverpod.dart';
import '../../services/save_service.dart';

class CheckpointNotifier extends Notifier<int> {
  @override
  int build() => 0;

  /// Signale qu'un nœud de la carte vient d'être résolu (combat, boutique,
  /// repos, event, forge, échange de reliques, ou draft de Level Up).
  void bump() => state = state + 1;
}

final checkpointProvider =
    NotifierProvider<CheckpointNotifier, int>(CheckpointNotifier.new);

/// Écoute checkpointProvider et déclenche une sauvegarde à chaque bump().
/// Doit être lu une fois au démarrage de l'app pour s'activer (voir main.dart).
final autosaveOrchestratorProvider = Provider<void>((ref) {
  ref.listen<int>(checkpointProvider, (previous, next) {
    SaveService.save(ref.read);
  });
});

Le découpage est élégant. D'un côté, un compteur qui ne sait rien de la sauvegarde : il dit seulement « un nœud vient d'être résolu ». De l'autre, un orchestrateur qui ne sait rien du jeu : il écoute le compteur et sauvegarde. Les deux appelants de bump() sont map_progression_manager.dart (à la fin de completeCurrentNode) et player_stats_manager.dart (dans decrementPendingDrafts, après un draft de montée de niveau).

Remarquez que autosaveOrchestratorProvider n'expose rien : son type est void. Il n'existe que pour son effet de bord — c'est un branchement, pas une valeur. Et c'est là qu'intervient le point le plus contre-intuitif de tout ce chapitre.

8.2 Pourquoi il faut le ref.watch dans main.dart

Les providers Riverpod sont paresseux : leur fonction de création n'est exécutée qu'à la première lecture. Un provider que personne ne lit n'existe pas — son code ne tourne jamais. Pour un Provider<int>, c'est une optimisation invisible. Pour un provider dont tout l'intérêt est un ref.listen, c'est fatal : si personne ne le lit, le listen n'est jamais installé, et la sauvegarde ne part jamais. Sans erreur, sans avertissement — simplement rien.

lib/main.dartdart
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    // Force l'activation de l'écoute d'autosave dès le démarrage de l'app.
    ref.watch(autosaveOrchestratorProvider);

    return MaterialApp(

Cette ligne, dont on ignore volontairement la valeur de retour, sert uniquement à allumer le provider. Et c'est bien un watch, pas un read, pour une raison précise : watch établit un abonnement depuis HerosDraftApp, qui est le widget racine et vit aussi longtemps que l'application. Tant que cet abonnement existe, Riverpod garde le provider vivant. Un read ponctuel le créerait aussi, mais sans le maintenir en vie.

Point d'attention

Dans le callback, SaveService.save(ref.read) est appelé sans await — c'est un Future lancé puis oublié. Si l'écriture dans shared_preferences échoue, l'erreur n'est ni interceptée ni remontée : la partie continue en pensant être sauvegardée. Le commentaire de SaveService précise d'ailleurs que la sauvegarde n'est « jamais appelée en plein combat », ce qui limite les dégâts, mais l'absence de gestion d'erreur reste une dette identifiée.

8.3 typedef RefReader : un problème de types bien réel

Dernier morceau. SaveService a besoin de lire quatre providers pour les sérialiser, et d'en écrire quatre pour les restaurer. Il est appelé depuis trois contextes différents :

  • depuis autosaveOrchestratorProvider, où l'objet disponible est un Ref ;
  • depuis home_screen.dart (bouton « Continuer »), où c'est un WidgetRef ;
  • depuis un test, où ce serait un ProviderContainer.

Ces trois types exposent tous une méthode read au comportement identique. Mais en riverpod 2.6.1, ils n'ont aucun supertype commun : on ne peut pas écrire static Future<void> save(Ref ref) et espérer passer un WidgetRef. La parade du projet est un typedef qui décrit la seule capacité nécessaire :

lib/services/save_service.dartdart
/// The subset of Ref/WidgetRef/ProviderContainer that SaveService needs:
/// a plain synchronous provider read. Accepting this instead of `Ref`
/// lets the same code run from a Notifier's `ref`, a widget's `WidgetRef`,
/// and a bare `ProviderContainer` in tests — none of which share a common
/// supertype in riverpod 2.6.1, but all of which expose this exact method.
typedef RefReader = T Function<T>(ProviderListenable<T> provider);

Ce typedef décrit une fonction générique : elle prend un ProviderListenable<T> et rend un T. C'est exactement la signature de Ref.read, de WidgetRef.read et de ProviderContainer.read. Comme en Dart une méthode peut être passée comme valeur (on écrit ref.read sans parenthèses, c'est ce qu'on appelle un tear-off), les trois appelants passent simplement leur méthode :

lib/services/save_service.dartdart
  static Future<void> save(RefReader read) async {
    final prefs = await SharedPreferences.getInstance();
    final payload = {
      'schemaVersion': _schemaVersion,
      'savedAt': DateTime.now().toIso8601String(),
      'run': read(runProvider).toJson(),
      'deck': read(deckProvider).toJson(),
      'inventory': read(inventoryProvider).toJson(),
      'skills': read(skillProvider).toJson(),
    };
    await prefs.setString(_saveKey, jsonEncode(payload));
  }

À l'intérieur de save et load, read se comporte comme une méthode ordinaire : read(runProvider) renvoie un RunState, read(skillProvider.notifier) renvoie un SkillController sur lequel on appelle hydrate(...). Le service ignore complètement s'il tourne dans un widget, dans un Notifier ou dans un test.

À retenir

Quand une API vous impose trois types incompatibles pour une même capacité, ne dupliquez pas le code et n'inventez pas une classe d'adaptation : décrivez la capacité avec un typedef de fonction. C'est du duck typing statique — vérifié par le compilateur, et sans dépendance ajoutée.

ProviderScope

Posé une fois dans main.dart. Sans lui, aucun provider n'est lisible.

build()

Renvoie l'état initial et prépare les managers. Appelée à la première lecture, pas avant.

state = ...

Toujours un nouvel objet. Muter l'ancien ne notifie personne.

watch / read / listen

Afficher / agir / réagir. read jamais dans build.

.notifier

Sans lui on obtient l'état, avec lui on obtient le contrôleur et ses méthodes.

overrides

Remplacer un provider à la création du conteneur : la clé des tests déterministes.

Quiz — vérifiez vos acquis

1. Quel est le seul StateNotifier encore présent dans Hero's Draft ?

  • CheckpointNotifier, parce que son état est un simple int
  • DeckNotifier, à cause de son champ late final Random _random
  • La file de toasts NotificationNotifier de lib/ui/widgets/notification_overlay.dart
  • RunController, trop volumineux pour être migré
Réponse : la migration des contrôleurs vers Notifier est terminée ; il ne reste que NotificationNotifier, qui gère la file de toasts (4 notifications maximum, auto-suppression après 3 500 ms). Cet état est purement décoratif, ne contient aucune règle de jeu et n'a jamais besoin de ref.

2. Dans DeckState, pourquoi le remélange est-il signalé par un compteur reshuffleCount plutôt que par un booléen ?

  • Parce que Riverpod ne sait pas comparer des booléens dans ref.listen
  • Parce qu'un compteur croissant rend le test next.reshuffleCount > previous.reshuffleCount toujours valide, y compris pour deux remélanges consécutifs, et n'oblige personne à remettre un drapeau à false
  • Parce que le nombre de remélanges est affiché dans le HUD de combat
  • Parce que copyWith n'accepte pas de paramètre booléen
Réponse : _drawInto peut remélanger plusieurs fois au cours d'une même pioche et renvoie le nombre exact dans result.reshuffles. Avec un booléen, le second remélange ne changerait pas l'état et passerait inaperçu ; avec un compteur, le ref.listen<DeckState> de game_screen.dart détecte chaque occurrence. La remise à zéro se fait dans startCombat.

3. Où et comment autosaveOrchestratorProvider est-il activé ?

  • Automatiquement, dès que checkpointProvider change
  • Dans SaveService.save, qui l'instancie au premier appel
  • Dans splash_screen.dart, en même temps que le chargement des données
  • Dans lib/main.dart, par un ref.watch(autosaveOrchestratorProvider) au début du build de HerosDraftApp
Réponse : les providers Riverpod sont paresseux — celui qui n'est jamais lu n'exécute jamais son code, donc son ref.listen ne serait jamais installé. Le ref.watch du widget racine le crée et le maintient vivant pendant toute la durée de vie de l'application.

4. Comment rendre les séquences de pioche reproductibles dans un test ?

  • En appelant DeckNotifier.setSeed(42) avant chaque pioche
  • En créant le ProviderContainer avec deckRandomProvider.overrideWithValue(Random(42))
  • En passant un paramètre seed: à drawCards
  • En remplaçant shuffle() par un tri alphabétique en mode test
Réponse : deckRandomProvider est un Provider<Random> déclaré dans deck_controller.dart précisément pour ça ; DeckNotifier.build() fait _random = ref.read(deckRandomProvider). La surcharge se déclare à la création du conteneur, avant toute lecture du deck.

5. Combien de fichiers JSON gameDataLoaderProvider charge-t-il en parallèle via Future.wait ?

  • 5
  • 7
  • 9
  • 12
Réponse : neuf — enemies, heroes, skills, cards, events, passives, relics, hero_cards et forge_upgrades. Les listes cards et hero_cards sont ensuite fusionnées en un seul catalogue avant d'alimenter le champ cards du GameDataRegistry.

6. À quoi sert typedef RefReader = T Function<T>(ProviderListenable<T> provider); dans save_service.dart ?

  • À accepter indifféremment un Ref, un WidgetRef ou un ProviderContainer, qui n'ont pas de supertype commun en riverpod 2.6.1 mais exposent tous cette méthode read
  • À rendre la sauvegarde asynchrone sans utiliser async
  • À éviter d'importer flutter_riverpod dans save_service.dart
  • À convertir automatiquement les états en JSON
Réponse : SaveService.save est appelé depuis l'orchestrateur d'autosave (un Ref) et SaveService.load depuis home_screen.dart (un WidgetRef) ; un test utiliserait un ProviderContainer. Le typedef décrit la seule capacité partagée — une lecture synchrone de provider — et chaque appelant passe simplement ref.read.
