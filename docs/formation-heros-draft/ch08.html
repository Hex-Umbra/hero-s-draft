Chapitre 08

Le héros : stats, classes, passifs et progression

Toutes les statistiques du jeu — héros comme ennemis — passent par une seule classe : EntityStats. Ce chapitre en fait le tour, puis suit le héros du choix de classe jusqu'à la montée de niveau.

Dans ce chapitre

  2. Les getters « effectifs »

Dans un jeu de cartes roguelike, « le héros » n'est pas un objet compliqué. C'est un paquet de nombres : des points de vie, du mana, de l'armure, une attaque, un niveau. Ce paquet de nombres vit dans RunState.heroStats, et il est du type EntityStats.

Le point intéressant — et c'est la décision d'architecture centrale de ce chapitre — c'est que la même classe décrit aussi les ennemis. Il n'y a pas de HeroStats et de EnemyStats séparés. Un seul type, deux usages. Cela simplifie énormément le pipeline de dégâts (un attaquant et un défenseur, tous deux des EntityStats), mais impose une discipline : tout ce qui est spécifique au joueur doit être rangé ailleurs.

1. EntityStats, la classe partagée

Le fichier fait environ 210 lignes et se lit d'un trait. Commençons par la déclaration des champs et le constructeur, où sont écrites toutes les valeurs par défaut.

lib/models/entity_stats.dartdart
@immutable
class EntityStats {
  final int maxPv;
  final int currentPv;
  final int maxMana;
  final int currentMana;
  final int armure;
  final int armorMastery; // Bonus permanent ajouté à chaque gain d'armure
  final int attaque;
  final int luck;
  final int level;
  final int xp;
  final int xpToNextLevel;
  final int critChance;
  final double critMultiplier;
  final List<StatusEffect> statuses;
  final bool lastActionWasCrit;

  EntityStats({
    required this.maxPv,
    required this.currentPv,
    this.maxMana = 0,
    this.currentMana = 0,
    required this.armure,
    this.armorMastery = 0,
    required this.attaque,
    this.luck = 0,
    this.level = 1,
    this.xp = 0,
    this.xpToNextLevel = 100,
    this.critChance = 0,
    this.critMultiplier = 1.5,
    List<StatusEffect> statuses = const [],
    this.lastActionWasCrit = false,
  }) : statuses = List.unmodifiable(statuses);

Trois détails de Dart méritent un mot pour un débutant :

  • @immutable (du package meta) est une annotation d'analyse : elle indique que tous les champs doivent être final. On ne modifie jamais un EntityStats existant, on en fabrique un nouveau avec copyWith.
  • required this.maxPv : le paramètre est nommé et obligatoire. Les champs sans required ont une valeur par défaut écrite juste après le =.
  • : statuses = List.unmodifiable(statuses) est une liste d'initialisation. Elle s'exécute avant le corps du constructeur et garantit que la liste stockée ne peut plus être modifiée en place — même si l'appelant garde une référence sur la liste d'origine.

À retenir

Aucun de ces 15 champs ne parle de cartes, de deck, de main ou de pioche. C'est volontaire : une EntityStats décrit un corps qui prend des coups, pas un joueur qui construit un deck.

Une classe, deux usages

Voici la preuve que la même classe sert des deux côtés. Au moment d'instancier les ennemis, le CombatController construit exactement le même type d'objet que le héros :

lib/game/controllers/combat_controller.dartdart
final stats = EntityStats(
  maxPv: (data.maxHp * enemyHpMultiplier).round(),
  currentPv: (data.maxHp * enemyHpMultiplier).round(),
  armure: 0,
  attaque: (data.baseDamage * enemyDamageMultiplier).round(),
  level: enemyLevel,
  critChance: data.critChance,
);

var enemy = EnemyInstance(data: data, stats: stats, isBoss: isBoss);

L'ennemi ne passe ni maxMana, ni xp, ni armorMastery : les valeurs par défaut suffisent. C'est précisément à ça que servent les défauts à 0 vus plus haut. Et comme les deux camps partagent le type, le pipeline de dégâts peut s'écrire une seule fois, avec un attackerStats et un defenderStats interchangeables.

La conséquence : cardsPerTurn n'est pas là

Le jeu a besoin de savoir combien de cartes le joueur pioche chaque tour. Une relique (increase_cards_per_turn) peut faire monter ce nombre. La tentation naturelle serait de poser un champ cardsPerTurn sur EntityStats, à côté de maxMana. Le projet a explicitement refusé, et l'a écrit noir sur blanc :

lib/game/controllers/run_controller.dartdart
  final int pendingDrafts; // Nombre de drafts de montée de niveau en attente

  /// Cartes piochées au début de chaque tour, et taille de la main d'ouverture.
  /// Règle de run propre au joueur : elle n'a pas sa place sur `EntityStats`,
  /// qui est partagé avec les ennemis.
  final int cardsPerTurn;

cardsPerTurn est donc un champ de RunState, avec une valeur par défaut de 5. Il a même sa propre méthode de modification, distincte de celle qui touche aux statistiques :

lib/game/controllers/run/player_stats_manager.dartdart
  /// Applique un modificateur aux règles de run propres au joueur.
  /// Distinct d'`applyHeroStatModifier`, qui opère sur `EntityStats` — lequel
  /// est partagé avec les ennemis et n'a donc pas à porter de notion de deck.
  void applyRunRuleModifier({int cardsPerTurnAcc = 0}) {
    controller.updateState(
      controller.currentState.copyWith(
        cardsPerTurn: controller.currentState.cardsPerTurn + cardsPerTurnAcc,
      ),
    );
  }
Bonne pratique

Quand un type est partagé par deux acteurs, la question à se poser n'est pas « ce champ est-il pratique ici ? » mais « ce champ a-t-il un sens pour les deux ? ». Un ennemi n'a pas de main de cartes : cardsPerTurn n'a donc rien à faire sur EntityStats. Le commentaire du code sert de garde-fou pour les contributions futures.

Le reste de la classe est de la plomberie classique et parfaitement symétrique : un copyWith qui reprend les 15 champs, un fromJson qui les relit avec les mêmes défauts (json['critMultiplier'] as num?)?.toDouble() ?? 1.5), et un toJson qui les réécrit tous. Cette symétrie est ce qui permet à la sauvegarde de restaurer un héros au champ près.

2. Les getters « effectifs »

Trois statistiques existent en deux versions : la valeur permanente stockée dans le champ, et la valeur effective qui ajoute les bonus temporaires en cours. Les getters sont écrits sur le même moule.

lib/models/entity_stats.dartdart
  int get effectiveArmorMastery {
    int bonus = 0;
    for (var status in statuses) {
      if (status.id == 'armor_mastery') {
        bonus += status.value;
      }
    }
    return armorMastery + bonus;
  }

  /// Calcule l'attaque effective en prenant en compte les buffs de force
  int get effectiveAttaque {
    int bonus = 0;
    for (var status in statuses) {
      if (status.id == 'strength') {
        bonus += status.value;
      }
    }
    return attaque + bonus;
  }

  int get effectiveCritChance {
    int bonus = 0;
    for (var status in statuses) {
      if (status.id == 'crit_chance') {
        bonus += status.value;
      }
    }
    return critChance + bonus;
  }

Le motif est toujours le même : parcourir statuses, additionner les value des statuts dont l'id correspond, et renvoyer champ + bonus. Le mot-clé get déclare un getter : on écrit stats.effectiveAttaque sans parenthèses, comme si c'était un champ, mais le calcul est refait à chaque lecture.

Pourquoi séparer permanent et temporaire ?

Parce que les deux ont des durées de vie radicalement différentes, et surtout des règles de nettoyage différentes. Comparez deux façons d'augmenter l'attaque du héros.

Permanente — une récompense de draft, qui doit survivre à tout :

lib/game/controllers/run/player_stats_manager.dartdart
    controller.updateState(
      controller.currentState.copyWith(
        heroStats: currentStats.copyWith(
          maxPv: newMaxPv,
          currentPv: newCurrentPv,
          maxMana: newMaxMana,
          currentMana: newCurrentMana,
          attaque: currentStats.attaque + attackAcc,
          armorMastery: currentStats.armorMastery + armorAcc,
          luck: currentStats.luck + luckAcc,
          critChance: currentStats.critChance + critChanceAcc,
          critMultiplier: currentStats.critMultiplier + critDamageAcc,
        ),
      ),
    );

Temporaire — un buff de combat, qui doit expirer :

lib/game/controllers/run/player_stats_manager.dartdart
  /// Applique un buff d'attaque pour une durée donnée
  void applyAttackBuff(int duration) {
    int bonus = (controller.currentState.heroStats.maxPv * 0.15).round();
    controller.updateState(
      controller.currentState.copyWith(
        heroStats: controller.currentState.heroStats.addStatus(
          StatusEffect(
            id: 'strength',
            name: 'Attaque',
            type: StatusType.buff,
            value: bonus,
            duration: duration,
          ),
        ),
      ),
    );
  }

Le premier écrit dans attaque : la valeur est dans la sauvegarde, elle traverse les combats, elle ne disparaît jamais. Le second ajoute un StatusEffect dans statuses : sa duration est décrémentée à chaque tour par tickStatuses(), et surtout la liste entière est vidée au début de chaque combat (startCombat()) et à la fin de chaque nœud (completeCurrentNode()). Sans cette séparation, il faudrait retrancher manuellement chaque buff expiré du champ permanent — un bug garanti.

Piège

L'affichage ne montre pas la même chose selon l'endroit. StatsDialog et HeroMiniStatsPanel affichent stats.attaque (la valeur permanente) mais stats.effectiveArmorMastery (la valeur effective). Ce n'est pas une incohérence gratuite : les panneaux de stats se consultent sur la carte du monde, hors combat, où les buffs de force ont déjà été purgés — alors qu'une relique peut, elle, poser un armor_mastery de longue durée.

Côté critique, la lecture se fait dans le pipeline de dégâts, sur l'attaquant :

lib/game/services/damage_pipeline.dartdart
    // 2. Coup critique de l'attaquant : multiplie les dégâts par critMultiplier

    if (canCrit) {
      final random = Random();
      if (random.nextInt(100) < attackerStats.effectiveCritChance) {
        totalDamage = (totalDamage * attackerStats.critMultiplier).round();

Notez l'asymétrie : c'est effectiveCritChance (avec bonus temporaires) mais critMultiplier brut — il n'existe pas de statut qui augmente le multiplicateur, seuls les drafts le font monter via critDamageAcc.

3. takeDamage : comment l'armure absorbe

C'est la méthode la plus lue du fichier, et la plus courte à comprendre. Elle tient en une quinzaine de lignes.

lib/models/entity_stats.dartdart
  EntityStats takeDamage(int amount, {bool isCrit = false}) {
    if (amount <= 0) return copyWith(lastActionWasCrit: isCrit);

    // 2. Absorption via Armure
    int damageAfterArmor = amount - armure;
    int newArmor = armure;
    int newPv = currentPv;

    if (damageAfterArmor > 0) {
      // L'armure est brisée, le reste va aux PV
      newArmor = 0;
      newPv -= damageAfterArmor;
    } else {
      // L'armure encaisse tout
      newArmor -= amount;
    }

    if (newPv < 0) newPv = 0;

    return copyWith(armure: newArmor, currentPv: newPv, lastActionWasCrit: isCrit);
  }

L'ordre exact est le suivant :

  1. Si amount <= 0, on sort immédiatement — mais en mettant quand même à jour lastActionWasCrit.
  2. On calcule damageAfterArmor = amount - armure.
  3. Si ce reste est strictement positif : l'armure tombe à 0 et le reste est retiré aux PV.
  4. Sinon : les PV ne bougent pas du tout, et l'armure perd exactement amount.
  5. Les PV sont bornés en bas à 0 (jamais de PV négatifs affichés).
Règle du jeu

L'armure est un bouclier tout ou rien par coup : elle absorbe la totalité d'une attaque tant qu'elle est supérieure ou égale aux dégâts, mais elle est intégralement consommée dès qu'elle est dépassée. Avoir 12 d'armure face à deux coups de 10 ne protège que du premier (12 → 2, puis 2 d'armure contre 10 dégâts = 8 PV perdus).

À retenir

takeDamage ne connaît ni les critiques, ni la vulnérabilité, ni la faiblesse. Tous ces modificateurs sont appliqués avant, par DamagePipeline.calculate, qui renvoie un couple (int damage, bool isCrit). takeDamage ne fait que soustraire, et transporte le drapeau isCrit jusqu'à lastActionWasCrit pour l'animation.

Les six cartes de classe

Le champ skills de heroes.json ne pointe pas vers des sorts mais vers des identifiants de cartes, définis dans assets/data/hero_cards.json. Le chaînage se fait par une extension Dart :

lib/models/data/hero_skills_link.dartdart
extension HeroSkillsLink on HeroData {
  List<CardData> getHeroCards(GameDataRegistry gameData) {
    return skills
        .map((skillId) {
          final matches = gameData.cards.where((c) => c.id == skillId);
          return matches.isNotEmpty ? matches.first : null;
        })
        .whereType<CardData>()
        .toList();
  }
}

Une extension ajoute des méthodes à un type existant sans le modifier : heroData.getHeroCards(gameData) se lit comme une méthode de HeroData, alors que le code vit dans un autre fichier. Les cartes sont cherchées dans gameData.cards, qui est la concaténation de cards.json et de hero_cards.json faite au chargement (lib/services/game_data_service.dart). Elles sont ensuite ajoutées automatiquement au deck de départ, en plus des 5 cartes choisies par le joueur :

Les trois passifs partagent le même effet — gagner de l'armure — mais diffèrent par leur moment de déclenchement. Tout le comportement est concentré dans un seul fichier de 68 lignes, avec trois méthodes statiques qui correspondent aux trois trigger possibles.

lib/game/systems/trait_system.dartdart
class TraitSystem {
  /// Appelé au début du tour du joueur
  static void onTurnStart(RunController controller) {
    final passive =
        controller.currentState.activePassive ??
        PassiveData.fallback(controller.currentState.passiveTrait ?? '');
    final stats = controller.currentState.heroStats;

    if (passive.trigger == RelicTrigger.startOfTurn) {
      if (passive.effectType == 'berserker_armor') {
        // Gagne X d'Armure (+Maîtrise) pour chaque tranche de 10 PV manquants
        final missingHp = stats.maxPv - stats.currentPv;
        final multiplier = missingHp ~/ 10;
        final armorGain = multiplier * passive.value;
        if (armorGain > 0) {
          controller.setHeroStats(
            armure: stats.armure + armorGain + stats.effectiveArmorMastery,
          );
        }
      } else if (passive.effectType == 'gain_armor') {
        controller.setHeroStats(
          armure: stats.armure + passive.value + stats.effectiveArmorMastery,
        );
      }
    }
  }

        controller.currentState.activePassive ??
        PassiveData.fallback(controller.currentState.passiveTrait ?? '');
    final stats = controller.currentState.heroStats;

    if (passive.trigger == RelicTrigger.onCardPlayed) {
      if (passive.effectType == 'spell_armor') {
        if (card.data.type == CardType.skill) {
          controller.setHeroStats(
            armure: stats.armure + passive.value + stats.effectiveArmorMastery,
          );
        }
      }
    }

Notez l'opérateur ~/ dans missingHp ~/ 10 : c'est la division entière de Dart. Un Berserker à 80 PV max et 37 PV courants a 43 PV manquants, donc 43 ~/ 10 == 4 — soit 4 points d'armure, et non 4,3. Le garde if (armorGain > 0) évite d'appeler setHeroStats pour rien quand le héros est à moins de 10 PV manquants.

Le rôle du + stats.effectiveArmorMastery

Ce terme apparaît quatre fois dans TraitSystem, à chaque gain d'armure passif. C'est le sens exact de « (+ Maîtrise) » dans les descriptions françaises des passifs.

Règle du jeu

La maîtrise d'armure n'octroie jamais d'armure par elle-même : elle majore chaque déclenchement du passif de classe. Un Paladin avec 3 de maîtrise gagne 2 + 3 = 5 d'armure en fin de tour. Un Berserker avec 3 de maîtrise et 25 PV manquants gagne (25 ~/ 10) × 1 + 3 = 2 + 3 = 5 d'armure — le bonus de maîtrise est ajouté une seule fois, pas une fois par tranche.

Cette maîtrise se gagne au draft. Attention au nommage : dans applyHeroStatModifier, le paramètre s'appelle armorAcc mais il alimente armorMastery, pas armure :

C'est cohérent avec le reste du système : donner de l'armure brute au draft serait inutile, puisqu'elle serait remise à 0 dès le tour suivant (section 6). Seule la maîtrise, qui est permanente, a du sens comme récompense.

PassiveData.fallback(id) : la ceinture et les bretelles

Les trois méthodes de TraitSystem commencent par la même ligne : controller.currentState.activePassive ?? PassiveData.fallback(...). Le scénario couvert est précis :

  1. le joueur sauvegarde une partie avec le passif spellArmor ;
  2. une mise à jour renomme ou supprime cette entrée de passives.json ;
  3. au chargement, PassiveData.getById renvoie null ;
  4. l'élément est signalé au joueur via MissingSaveItem ;
  5. et fallback fournit malgré tout un passif valide, pour que la partie continue.
Bonne pratique

Un fallback codé en dur est acceptable quand il est (a) limité à un petit nombre d'entrées stables, (b) accompagné d'un signalement à l'utilisateur, et (c) le seul moyen d'éviter un crash au chargement. Ici les trois conditions sont réunies. Le cas default renvoie un passif 'none' de valeur 0 : inerte, mais non nul — TraitSystem ne plantera jamais.

Piège

PassiveData.fallback sert aussi de valeur initiale hors sauvegarde : RunController.build() démarre sur PassiveData.fallback('regenArmor') et un héros paladin à 100 PV. C'est un état de secours qui n'est jamais joué tel quel — startNewRun le remplace intégralement dès que le joueur valide son deck de départ.

6. Mana et armure : les deux ressources qui se réinitialisent

Le héros a deux jauges qui ne se cumulent pas d'un tour à l'autre. Elles sont remises à leur valeur de départ à des moments très précis, et l'ordre de ces remises compte.

startCombat() — une fois par combat

lib/game/controllers/run_controller.dartdart
  void startCombat() {
    // 1. Nettoyage des buffs/debuffs du combat précédent,
    // et restauration du mana au max (l'armure est remise à 0 en fin de combat dans completeCurrentNode)
    state = state.copyWith(
      heroStats: state.heroStats.copyWith(
        statuses: [],

    applyRelics(RelicTrigger.startOfCombat);
    // 3. Déclenchement des passifs de début de combat/tour pour le tour 1 (ex: Berserker)
    TraitSystem.onTurnStart(this);

Trois étapes seulement, et un détail important : startCombat() ne touche pas à l'armure. Le commentaire explique pourquoi — c'est completeCurrentNode() qui s'en charge à la fin du combat précédent. L'appel final à TraitSystem.onTurnStart est là parce que le premier tour ne passe pas par startTurn() : au montage du GameScreen, seul startPlayerCombat() est appelé. Sans cette ligne, le Berserker n'aurait pas son armure au tour 1.

startTurn() — à chaque tour

lib/game/controllers/run_controller.dartdart
  void startTurn() {
    // 1. Restaurer le Mana à sa valeur maximale (ne se cumule pas d'un tour à l'autre) et reset l'armure
    state = state.copyWith(
      heroStats: state.heroStats.copyWith(
        armure: 0,
        currentMana: state.heroStats.maxMana,
      ),

    applyRelics(RelicTrigger.startOfTurn);

    // 3. Appliquer les effets de début de tour (ex: Poison, Regen) et décrémenter les statuts via le StatusEffectProcessor
    final updatedStats = StatusEffectProcessor.processPlayerStatuses(state.heroStats);
    state = state.copyWith(heroStats: updatedStats);

    // 4. Décrémenter les cooldowns via le skill provider
    ref.read(skillProvider.notifier).tickCooldowns();

    // 5. Déclencher les traits passifs
    TraitSystem.onTurnStart(this);
  }

7. XP, niveaux et drafts en attente

L'XP n'est gagnée qu'à la victoire : RewardController.collectGoldAndXp() appelle ref.read(runProvider.notifier).gainXp(state.xpGained), où xpGained est la somme des enemy.data.xp pondérés par 1.0 + 0.10 * (enemy.stats.level - 1). Tout le calcul de progression tient ensuite dans une seule méthode.

lib/game/controllers/run/player_stats_manager.dartdart
  /// Ajoute de l'Expérience au joueur.
  /// Gère les montées de niveaux successives avec conservation de l'XP excédentaire (carry-over).
  /// Retourne [true] si au moins un niveau a été gagné.
  bool gainXp(int amount) {
    if (amount <= 0) return false;

    var currentStats = controller.currentState.heroStats;
    int newXp = currentStats.xp + amount;
    int currentLevel = currentStats.level;
    int currentXpToNext = currentStats.xpToNextLevel;
    bool leveledUp = false;
    int levelsGained = 0;

    while (newXp >= currentXpToNext) {
      newXp -= currentXpToNext;
      currentLevel++;
      // Formule d'XP requise pour le nouveau niveau: 100 * (1.5 ^ (level - 1))
      currentXpToNext = (100 * pow(1.5, currentLevel - 1)).round();
      leveledUp = true;
      levelsGained++;
    }

    controller.updateState(
      controller.currentState.copyWith(
        heroStats: currentStats.copyWith(
          level: currentLevel,
          xp: newXp,
          xpToNextLevel: currentXpToNext,
        ),
        pendingDrafts: controller.currentState.pendingDrafts + levelsGained,
      ),
    );

    return leveledUp;
  }

Trois mécanismes cohabitent dans cette boucle :

  • Le carry-over. À chaque passage de niveau, on fait newXp -= currentXpToNext au lieu de remettre l'XP à zéro. Le surplus est conservé et compte pour le niveau suivant. Le champ xp représente donc l'XP dans le niveau courant, pas l'XP totale.
  • Les montées multiples. C'est une boucle while, pas un if : une grosse récompense peut faire gagner plusieurs niveaux d'un coup.
  • Le compteur de drafts. levelsGained est incrémenté à chaque tour de boucle, puis ajouté à pendingDrafts. Un niveau gagné = un draft dû.

La fonction pow vient de dart:math et renvoie un double ; .round() arrondit au plus proche entier (à la moitié, Dart s'éloigne de zéro, donc 337,5 devient 338). Voici les dix premiers seuils, calculés avec (100 * pow(1.5, level - 1)).round() :

Un niveau gagné = un draft obligatoire = une progression de carte impossible tant qu'il n'est pas consommé. Le joueur ne peut donc jamais « mettre de côté » ses récompenses de niveau pour plus tard.

level

Niveau d'expérience du héros, sur EntityStats. Fixe le seuil suivant.

xp

XP accumulée dans le niveau courant. Remise à zéro par soustraction, jamais par affectation.

xpToNextLevel

Recalculé après chaque montée. Défaut 100, croissance ×1,5.

pendingDrafts

Sur RunState, pas sur EntityStats. Verrouille la carte tant qu'il est > 0.

L'enchaînement est net : on refuse si le cooldown n'est pas écoulé, puis on tente de payer, puis seulement on arme le cooldown. Si consumeResource échoue, la compétence n'est pas mise en recharge — le joueur ne perd rien. resetCooldowns() est appelé au démarrage d'une run (startNewRun) et à chaque nouveau niveau (nextLevel) ; tickCooldowns() est appelé à l'étape 4 de startTurn().

consumeResource : payer en mana ou en PV

lib/game/controllers/run/player_stats_manager.dartdart
  /// Consomme les ressources nécessaires. Retourne false si insuffisant.
  bool consumeResource({int mana = 0, int hpPercent = 0}) {
    int hpCost = 0;
    if (hpPercent > 0) {
      hpCost = (controller.currentState.heroStats.currentPv * (hpPercent / 100.0)).round();
      if (hpCost < 1) hpCost = 1;
      if (controller.currentState.heroStats.currentPv <= hpCost) return false;
    }

    if (mana > 0 && controller.currentState.heroStats.currentMana < mana) {
      return false;
    }

    controller.updateState(
      controller.currentState.copyWith(
        heroStats: controller.currentState.heroStats.copyWith(
          currentMana: controller.currentState.heroStats.currentMana - mana,
          currentPv: controller.currentState.heroStats.currentPv - hpCost,
        ),
      ),
    );
    return true;
  }

Quatre garde-fous méritent d'être relevés :

  • le coût en PV est un pourcentage des PV courants, pas des PV max ;
  • il est plancher à 1 (if (hpCost < 1) hpCost = 1;) : payer en PV coûte toujours au moins 1 PV ;
  • la comparaison currentPv <= hpCost est stricte — une compétence ne peut jamais tuer son lanceur ;
  • les deux vérifications ont lieu avant toute écriture : soit tout est payé, soit rien ne bouge.

Point d'attention — skills.json et les classes actuelles

En l'état du dépôt, skills.json ne semble relié à aucune classe jouable. Les faits vérifiés dans le code :

  • heroes.json déclare "skills": ["holy_shield", "smite"] pour le Paladin ; or ces identifiants sont ceux de cartes de hero_cards.json. Aucun des six ids de skills.json (paladin_shield, mage_nova…) n'apparaît dans heroes.json.
  • HeroSkillsLink.getHeroCards résout ce champ contre gameData.cards (cards.json + hero_cards.json), jamais contre gameData.skills.
  • skills.json est bien chargé et parsé dans GameDataRegistry.skills (lib/services/game_data_service.dart), mais une recherche sur gameData.skills et registry.skills dans lib/ui/ ne donne aucun résultat : aucun écran ne lit cette liste.
  • De même, SkillController.triggerSkill1 / triggerSkill2 et HerosDraftGame.executeSkill ne sont appelés depuis aucun autre fichier de lib/. Le seul appel à CombatController.executeSkill est le branchement du callback onExecuteSkill dans lib/ui/screens/game_screen.dart.

La lecture prudente : le système de compétences est entièrement implémenté côté logique et données, mais sans point d'entrée dans l'interface — le champ skills de heroes.json a visiblement été réaffecté aux cartes de classe. Les cooldowns restent cependant sérialisés (SkillState dans save_service.dart) et testés (test/unit/skill_controller_test.dart), donc la fonctionnalité est vraisemblablement gardée en réserve plutôt qu'abandonnée. Avant toute modification, il faut vérifier soi-même ces points sur la version courante du dépôt.

À retenir

Le chemin réellement emprunté par le jeu, aujourd'hui, est celui des cartes : les effets de hero_cards.json passent par le résolveur d'effets de cartes, et le passif de classe est déclenché par TraitSystem.onCardPlayed. C'est là qu'il faut regarder pour comprendre ce que fait concrètement une classe en combat.

Quiz — vérifiez vos acquis

1. Quelle est la valeur par défaut de critMultiplier dans le constructeur d'EntityStats ?

  • 1.0
  • 1.5
  • 2.0
  • Aucune : le paramètre est required
Réponse : this.critMultiplier = 1.5 dans lib/models/entity_stats.dart. C'est le seul champ double de la classe, et fromJson reprend le même défaut avec ?? 1.5.

2. Un héros a 12 d'armure et encaisse un coup de 10 dégâts. Que vaut son armure après takeDamage(10), et combien de PV perd-il ?

  • Armure 0, il perd 0 PV
  • Armure 0, il perd 2 PV
  • Armure 2, il perd 0 PV
  • Armure 12, il perd 10 PV
Réponse : damageAfterArmor = 10 - 12 = -2, donc la branche else s'applique : newArmor -= amount soit 12 − 10 = 2, et newPv n'est jamais touché.

3. Pourquoi cardsPerTurn est-il un champ de RunState et non d'EntityStats ?

  • Parce que c'est un int et qu'EntityStats n'accepte que des double
  • Parce que sa valeur change à chaque tour
  • Parce qu'il n'est pas sauvegardé dans le JSON
  • Parce qu'EntityStats est partagé avec les ennemis, qui n'ont pas de deck
Réponse : le commentaire de run_controller.dart le dit mot pour mot : « Règle de run propre au joueur : elle n'a pas sa place sur EntityStats, qui est partagé avec les ennemis. » Sa valeur par défaut est 5 et il est sérialisé.

4. Un Berserker (80 PV max) est à 37 PV, avec 0 de maîtrise d'armure et 0 d'armure. Combien d'armure lui donne berserkerArmor au début du tour ?

  • 4
  • 5
  • 8
  • 43
Réponse : missingHp = 80 - 37 = 43, puis 43 ~/ 10 = 4 (division entière), fois passive.value qui vaut 1, plus effectiveArmorMastery qui vaut 0 : soit 4 points d'armure.

5. Un héros vient de passer au niveau 5. Que vaut son xpToNextLevel ?

  • 338
  • 500
  • 506
  • 759
Réponse : (100 * pow(1.5, 5 - 1)).round() = (100 × 5,0625).round() = 506. 338 est le seuil du niveau 4 et 759 celui du niveau 6.

6. Le Berserker affiche "baseDamage": 15 dans heroes.json. Quel est l'effet réel de cette valeur en jeu ?

  • Elle initialise heroStats.attaque à 15 au démarrage de la run
  • Elle sert de plancher de dégâts pour toutes les cartes d'attaque
  • Elle est ajoutée à effectiveAttaque à chaque attaque
  • Aucun : elle n'est lue que pour l'affichage sur l'écran de sélection de classe
Réponse : startNewRun écrit explicitement attaque: 0, // Force de base à 0. Le seul usage de HeroData.baseDamage dans lib/ est class_selection_screen.dart ligne 343, dans un badge d'affichage.
