1. « Tout est widget »

En Flutter, il n'y a pas de fichier de mise en page séparé, pas de XML, pas de HTML. L'interface est décrite en Dart, par des objets appelés widgets. Un bouton est un widget, un texte est un widget, mais aussi une marge (Padding), un alignement (Center), une contrainte de taille (SizedBox), une opacité (Opacity) et même une zone d'écoute de la souris (MouseRegion). Cette uniformité est déroutante au début, puis devient l'atout principal du framework : il n'y a qu'un seul concept à maîtriser.

Ces widgets sont assemblés en un arbre. Chaque widget déclare ses enfants — soit un seul via child:, soit plusieurs via children:. La racine de l'arbre de Hero's Draft, c'est runApp() dans lib/main.dart.

lib/main.dartdart
import 'package:flutter/material.dart';
import 'package:flutter_riverpod/flutter_riverpod.dart';
import 'package:flutter_localizations/flutter_localizations.dart';
import 'package:roguelike_card_game/l10n/app_localizations.dart';
import 'ui/screens/splash_screen.dart';
import 'ui/widgets/notification_overlay.dart';
import 'game/controllers/checkpoint_controller.dart';
import 'ui/theme/app_theme.dart';
void main() {
  WidgetsFlutterBinding.ensureInitialized();
  runApp(const ProviderScope(child: HerosDraftApp()));
}
class HerosDraftApp extends ConsumerWidget {
  const HerosDraftApp({super.key});
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    // Force l'activation de l'écoute d'autosave dès le démarrage de l'app.
    ref.watch(autosaveOrchestratorProvider);
    return MaterialApp(
      onGenerateTitle: (context) => AppLocalizations.of(context)!.appTitle,
      theme: AppTheme.darkNeonTheme,
      debugShowCheckedModeBanner: false,
      localizationsDelegates: const [
        AppLocalizations.delegate,
        GlobalMaterialLocalizations.delegate,
        GlobalWidgetsLocalizations.delegate,
        GlobalCupertinoLocalizations.delegate,
      ],
      supportedLocales: const [Locale('en', ''), Locale('fr', '')],
      home: const SplashScreen(),
      builder: (context, child) {
        return Stack(
          children: [
            child ?? const SizedBox.shrink(),
            const GameNotificationOverlay(),
          ],
        );
      },
    );
  }
}

Lisez ce fichier de haut en bas, c'est la carte du jeu entier :

  • WidgetsFlutterBinding.ensureInitialized() initialise le pont entre Dart et la plateforme. Obligatoire dès qu'on touche à des services natifs avant runApp.
  • ProviderScope vient de Riverpod : c'est le conteneur qui héberge tous les états partagés du jeu. Il est au-dessus de l'application, donc accessible depuis n'importe quel widget en dessous.
  • MaterialApp apporte le Navigator (la pile d'écrans), le thème, la localisation et les transitions de pages.
  • home: const SplashScreen() est la première route de la pile. Retenez ce détail : toute la section 7 sur popUntil en dépend.
  • builder: est un point d'insertion : Flutter vous donne le child (c'est-à-dire le Navigator et tout ce qu'il affiche) et vous le rendez enveloppé. Ici, on le place dans un Stack avec GameNotificationOverlay par-dessus, ce qui garantit que les notifications du jeu flottent au-dessus de tous les écrans, quel que soit celui qui est affiché.
À retenir

Un widget n'est pas un objet graphique. C'est une description immuable de ce qui doit être affiché — l'équivalent d'un plan, pas du bâtiment. C'est pour cette raison que la quasi-totalité des widgets du projet sont déclarés const avec des champs final : ils sont créés, comparés, jetés et recréés des dizaines de fois par seconde.

La reconstruction : la méthode build

Chaque widget qui a du contenu implémente une méthode build. Elle renvoie un nouveau sous-arbre de widgets. Flutter l'appelle :

  • à la première insertion du widget dans l'arbre ;
  • quand un setState() est déclenché dans un State au-dessus ou dans ce widget ;
  • quand un provider observé par ref.watch(...) change de valeur ;
  • quand une dépendance héritée change (rotation d'écran, changement de langue, changement de thème).

Ce que Flutter fait ensuite n'est pas de tout redessiner : il compare l'ancien arbre de widgets et le nouveau, position par position. Si le type et la key d'un widget n'ont pas changé, il conserve l'élément et son State existant et se contente de mettre à jour les propriétés. C'est ce qui rend acceptable un build qui reconstruit visuellement tout un écran : ce sont des allocations d'objets Dart très légers, pas des opérations graphiques.

Piège

build doit être pur : pas d'appel réseau, pas d'écriture de fichier, pas de setState, pas de modification de provider. Il peut être appelé à n'importe quel moment et plusieurs fois d'affilée. Le projet enfreint cette règle une fois, dans lib/ui/screens/map_screen.dart — on y revient en section 3.

Le widget racine des écrans : ScreenScaffold

Pour éviter de recopier le même fond dégradé sur 17 écrans, le projet définit un widget maison, ScreenScaffold, qui compose Scaffold + fond + SafeArea + éventuellement PopScope. Sa méthode build est un excellent exemple de « composition conditionnelle » : on part du body et on l'emballe couche par couche.

lib/ui/widgets/screen_scaffold.dartdart
@override
Widget build(BuildContext context) {
  Widget content = body;
  if (useSafeArea) {
    content = SafeArea(child: content);
  }
  Decoration? decoration;
  Color? backgroundColor;
  switch (backgroundType) {
    case ScreenBackgroundType.dark:
      decoration = BoxDecoration(
        gradient: LinearGradient(/* noir → 0xFF1A0A00 → noir */),
      );
      backgroundColor = const Color(0xFF0D0D1A);
      break;
    // ... parchment / none
  }
  Widget scaffoldBody = content;
  if (decoration != null) {
    scaffoldBody = Container(
      width: double.infinity, height: double.infinity,
      decoration: decoration, child: content,
    );
  }
  Widget mainWidget = Scaffold(
    backgroundColor: backgroundColor, appBar: appBar, body: scaffoldBody,
  );
  if (canPop != null || onPopInvokedWithResult != null) {
    mainWidget = PopScope(
      canPop: canPop ?? true,
      onPopInvokedWithResult: onPopInvokedWithResult,
      child: mainWidget,
    );
  }
  return mainWidget;
}

Notez l'ordre d'emballage : SafeArea est appliqué en premier, donc il se retrouve le plus bas dans l'arbre ; PopScope est appliqué en dernier, donc il se retrouve le plus haut. Voici l'arbre réel obtenu pour l'écran de carte du monde.

Un StatefulWidget est en réalité deux classes. Le widget lui-même reste immuable et jetable (ses champs sont final) ; c'est l'objet State, lui, qui survit aux reconstructions. Dans le State, on accède aux paramètres du widget via widget.xxx — vous le verrez partout : widget.isLatest, widget.patch, widget.currentPv.

ConsumerWidget — SplashScreen

Riverpod ajoute ConsumerWidget : un StatelessWidget dont la méthode build reçoit un second paramètre, WidgetRef ref, qui donne accès aux providers. Le premier écran du jeu s'en sert pour attendre le chargement des JSON.

lib/ui/screens/splash_screen.dartdart
class SplashScreen extends ConsumerWidget {
  const SplashScreen({super.key});
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final gameData = ref.watch(gameDataLoaderProvider);
    return Scaffold(
      body: Center(
        child: gameData.when(
          data: (_) =>
              const HomeScreen(), // Si les données sont chargées, on affiche l'écran d'accueil
          loading: () =>
              const CircularProgressIndicator(), // Pendant le chargement
          error: (error, stack) =>
              Text('Erreur de chargement: $error'), // En cas d'erreur
        ),
      ),
    );
  }
}

Trois états, trois branches, zéro if : c'est le pattern when de Riverpod. Notez surtout que HomeScreen n'est pas une route à part entière — c'est le contenu de la route SplashScreen. Ce détail explique pourquoi le menu pause peut revenir au menu principal avec popUntil((route) => route.isFirst).

Bonne pratique

Choisissez la classe la moins puissante qui fait le travail : StatelessWidget par défaut, ConsumerWidget s'il faut lire un provider, StatefulWidget seulement si un AnimationController, un TextEditingController, un ScrollController ou un booléen local est nécessaire. Un widget stateless est plus facile à tester et à raisonner.

Point d'attention

Deux widgets du projet trichent : _InteractiveClassCard (lib/ui/screens/class_selection_screen.dart) et _MergeDialog (lib/ui/screens/deck_screen.dart) sont de simples StatefulWidget qui reçoivent un final WidgetRef ref; par leur constructeur, puis appellent widget.ref.watch(gameDataLoaderProvider) dans leur build. Cela fonctionne ici parce que le provider observé ne change jamais après le chargement, mais c'est fragile : la souscription est rattachée au widget parent, pas à l'enfant. La forme correcte est ConsumerStatefulWidget, qui expose ref nativement.

Pourquoi on ne peut pas simplement écrire son code dans initState

Il y a une contrainte forte : pendant initState, on est au milieu de la construction de l'arbre. Modifier un provider à ce moment-là ferait muter un état pendant que Flutter est en train de bâtir la frame, ce qui déclenche l'erreur classique « Tried to modify a provider while the widget tree was building ». La solution est de différer l'appel après la construction. Le projet utilise deux techniques, selon les fichiers.

Technique 1 — Future.microtask : la fonction est mise en file d'attente et exécutée dès que la pile d'appels courante est vide, c'est-à-dire juste après la fin de initState, mais éventuellement avant que la première frame ne soit peinte.

lib/ui/screens/event_screen.dartdart
class _EventScreenState extends ConsumerState<EventScreen> {
  @override
  void initState() {
    super.initState();
    Future.microtask(() {
      final gameData = ref.read(gameDataLoaderProvider).requireValue;
      ref.read(eventProvider.notifier).initializeEvent(gameData.events);
    });
  }

Le if (!mounted) return; après un await

C'est la règle de sécurité la plus importante du chapitre. Considérez ce déroulé :

  1. Le joueur appuie sur « Continuer ». _continueGame() démarre.
  2. Le code atteint await SaveService.load(ref.read) et rend la main. Pendant ce temps, Flutter continue de tourner.
  3. Le joueur appuie sur retour, ou l'écran est retiré pour une autre raison. Le State est disposé.
  4. La lecture de la sauvegarde se termine, le code reprend… et appelle setState() sur un State mort, ou lit context qui n'est plus rattaché à l'arbre. Exception.

La propriété mounted du State vaut false dès que le widget a été retiré. On la teste systématiquement après chaque await. HomeScreen le fait trois fois dans la même méthode :

lib/ui/screens/home_screen.dartdart
Future<void> _continueGame() async {
  final result = await SaveService.load(ref.read);
  if (!mounted) return;
  // ...
  if (result.missingItems.isNotEmpty) {
    final locale = Localizations.localeOf(context).languageCode;
    // ... affichage du dialogue des objets manquants
  }
  if (!mounted) return;
  await Navigator.of(context).push(
    MaterialPageRoute(builder: (context) => const MapScreen()),
  );
  // The pause menu and the death overlay both return here via
  // Navigator.popUntil((route) => route.isFirst) rather than recreating
  // this screen, so the save state must be re-checked on return.
  if (mounted) setState(() {});
}

Notez la dernière ligne : Navigator.push renvoie un Future qui ne se résout que lorsque l'écran poussé est dépilé. On peut donc écrire du code « au retour de l'écran » simplement en mettant un await devant, ce que le projet fait pour rafraîchir la présence d'une sauvegarde.

Piège

Dans un StatelessWidget ou dans un callback qui n'a pas de State, il n'existe pas de mounted local. On teste alors context.mounted, comme dans lib/ui/widgets/hud/death_overlay.dart : await SaveService.clear(); if (!context.mounted) return;.

dispose : tout ce qu'on crée, on le détruit

Un AnimationController s'abonne au ticker de Flutter (60 à 120 rappels par seconde). Si on ne le libère pas, il continue de tourner après la disparition de l'écran : fuite mémoire et batterie. La règle est mécanique — un controller créé dans initState, un controller.dispose() dans dispose, et super.dispose() en dernier.

lib/ui/screens/class_selection_screen.dartdart
@override
void initState() {
  super.initState();
  _floatController = AnimationController(
    duration: const Duration(seconds: 3),
    vsync: this,
  )..repeat(reverse: true);
  _floatAnimation = Tween<double>(begin: -4, end: 4).animate(
    CurvedAnimation(parent: _floatController, curve: Curves.easeInOut),
  );
}
@override
void dispose() {
  _floatController.dispose();
  super.dispose();
}

4. La mise en page

Flutter n'a ni flexbox ni grille CSS : la mise en page se fait en imbriquant des widgets dont c'est l'unique rôle. Le vocabulaire de base utilisé dans le projet :

Scaffold

La structure Material d'un écran : appBar, body, couleur de fond. Un par écran.

Column / Row

Empile les enfants verticalement / horizontalement. mainAxisAlignment gère l'axe principal, crossAxisAlignment l'axe perpendiculaire.

Stack

Superpose les enfants. Le dernier de la liste est devant. Se combine avec Positioned et Positioned.fill.

Expanded

Dans une Row ou une Column, prend tout l'espace restant, réparti selon flex.

Flexible

Comme Expanded, mais l'enfant peut être plus petit que l'espace offert. Sert à laisser un texte rétrécir sans déborder.

Spacer

Un Expanded vide : pousse ce qui l'entoure vers les extrémités.

Container

Le couteau suisse : couleur, dégradé, bordure, ombre, coins arrondis, marge, padding, taille.

SizedBox

Juste une taille. Plus léger qu'un Container vide, et const-able.

Wrap

Comme une Row, mais passe à la ligne quand la place manque. spacing et runSpacing.

                  children: [ /* _ShopServiceWidget × n */ ],
                ),
              ),
            ),
          ],
        ),
      ),
    ],

Quatre idées sont empilées ici, et elles reviennent partout dans le projet :

  • crossAxisAlignment: CrossAxisAlignment.stretch force les enfants à occuper toute la hauteur de la Row, sinon chaque colonne aurait la hauteur de son contenu.
  • VerticalDivider(width: 40) ne fait pas 40 px de trait : width est l'espace réservé, le trait est fin et centré dedans. Il produit donc le séparateur et la gouttière de 40 px entre les deux colonnes.
  • Expanded imbriqué dans la Column : la zone de contenu prend toute la hauteur restante sous le titre, ce qui permet au SingleChildScrollView d'avoir une hauteur finie et donc de défiler.
  • Wrap plutôt que GridView : les cartes ont une largeur fixe (SizedBox(width: 150)) et le nombre de colonnes s'adapte tout seul à la largeur disponible.
Piège

L'erreur de débutant la plus fréquente est « RenderFlex overflowed by N pixels ». Elle survient quand le contenu d'une Column ou d'une Row dépasse. Trois remèdes selon l'intention : Expanded / Flexible si un enfant doit se partager l'espace, SingleChildScrollView si le contenu doit défiler, Wrap si les éléments doivent passer à la ligne. Ne « corrigez » jamais un overflow en réduisant les tailles au jugé : le bug reviendra sur un autre écran.

void _onPointerMove(PointerEvent event, Size cardSize) {
  if (cardSize.width == 0 || cardSize.height == 0) return;

  // Relative position from center (-0.5 to 0.5)
  final double relX = (event.localPosition.dx / cardSize.width) - 0.5;
  final double relY = (event.localPosition.dy / cardSize.height) - 0.5;

    // Limit tilt angle (approx 0.025 radians max)
    _tiltX = relX * 0.05;
    _tiltY = relY * 0.05;
    _mousePosition = event.localPosition;
  });
}

L'extension context.showNotification(...)

C'est l'astuce la plus élégante du projet. Plutôt que d'exiger un ref pour afficher une notification, le fichier notification_overlay.dart déclare une extension Dart sur BuildContext, qui récupère le conteneur Riverpod à partir du contexte :

lib/ui/widgets/notification_overlay.dartdart
extension NotificationContextExtension on BuildContext {
  void showNotification(
    String message, {
    NotificationType type = NotificationType.info,
  }) {
    try {
      ProviderScope.containerOf(
        this,
        listen: false,
      ).read(notificationProvider.notifier).show(message, type: type);
    } catch (e) {
      debugPrint("Notification: $message (Type: $type)");
    }
  }
}

Résultat : n'importe quel widget, même un StatelessWidget sans accès aux providers, peut écrire une seule ligne. C'est utilisé partout — au feu de camp :

  l10n.restCampSnackbarHeal(healAmount),
  type: NotificationType.success,
);

Le listen: false est important : on lit le conteneur pour envoyer une commande, on ne s'y abonne pas. Le try / catch couvre le cas des tests unitaires où aucun ProviderScope n'existe au-dessus : la notification se dégrade alors en simple debugPrint au lieu de faire planter le test.

Règle du jeu

Une notification vit 3 500 ms avant disparition automatique, et la pile en affiche au maximum 4 : au-delà, la plus ancienne est retirée (state = [...state.sublist(1), notification]). Quatre types existent — info (bleu #007AFF), success (vert #34C759), warning (jaune #FFCC00) et error (rouge #FF3B30).

8. Les animations

Flutter propose deux familles. La première est déclarative et sans effort ; la seconde donne le contrôle total. Le projet utilise massivement les deux.

Famille 1 — les animations implicites

Le principe : un widget dont le nom commence par Animated… prend une valeur cible et une duration. Chaque fois que la valeur change entre deux build, il interpole automatiquement de l'ancienne vers la nouvelle. Vous ne gérez ni contrôleur, ni dispose.

Famille 2 — les animations explicites

Dès qu'il faut boucler, séquencer, inverser ou piloter plusieurs propriétés depuis une même horloge, on passe à l'AnimationController. La recette est toujours la même :

  1. Ajouter with SingleTickerProviderStateMixin au State (ou TickerProviderStateMixin s'il y a plusieurs contrôleurs). Ce mixin fournit le vsync, c'est-à-dire la source des battements d'horloge, synchronisée avec l'écran.
  2. Créer le contrôleur dans initState avec sa duration.
  3. Le passer dans un Tween (de quelle valeur à quelle valeur) et une CurvedAnimation (avec quelle courbe d'accélération).
  4. Reconstruire la portion concernée avec AnimatedBuilder ou une transition prête à l'emploi (ScaleTransition, FadeTransition, RotationTransition).
  5. Appeler dispose() sur le contrôleur.

L'overlay de montée de niveau montre une subtilité de plus : deux animations différentes pilotées par le même contrôleur, décalées dans le temps grâce à Interval.

lib/ui/widgets/map/level_up_overlay.dartdart
class _LevelUpOverlayState extends State<LevelUpOverlay>
    with SingleTickerProviderStateMixin {
  late AnimationController _controller;
  late Animation<double> _scaleAnimation;
  late Animation<double> _opacityAnimation;
  @override
  void initState() {
    super.initState();
    _controller = AnimationController(
      vsync: this,
      duration: const Duration(milliseconds: 1200),
    );
    _scaleAnimation = Tween<double>(begin: 0.0, end: 1.0).animate(
      CurvedAnimation(
        parent: _controller,
        curve: const Interval(0.2, 1.0, curve: Curves.elasticOut),
      ),
    );
    _opacityAnimation = Tween<double>(begin: 0.0, end: 1.0).animate(
      CurvedAnimation(
        parent: _controller,
        curve: const Interval(0.0, 0.4, curve: Curves.easeInOut),
      ),
    );
    _controller.forward();
  }
  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }

Traduction en secondes : le contrôleur court de 0.0 à 1.0 en 1 200 ms. Réagir à un changement de paramètre : didUpdateWidget

La barre de vie du joueur est le morceau d'animation le plus intéressant du projet. L'effet recherché est celui des jeux de combat : quand on prend des dégâts, la barre verte tombe instantanément et une barre rouge derrière descend lentement pour montrer ce qui vient d'être perdu ; quand on se soigne, c'est l'inverse.

Or PlayerHealthBar ne connaît que widget.currentPv, une valeur qui lui est fournie de l'extérieur. Pour savoir qu'il y a eu un changement, il compare l'ancien et le nouveau widget dans didUpdateWidget :

lib/ui/widgets/hud/player_health_bar.dartdart
@override
void didUpdateWidget(covariant PlayerHealthBar oldWidget) {
  super.didUpdateWidget(oldWidget);
  if (widget.currentPv != oldWidget.currentPv) {
    final double activeGreen = currentGreen;
    final double activeCatchUp = currentCatchUp;
    final double newPv = widget.currentPv.toDouble();
    if (newPv < activeGreen) {
      // Damage: green drops instantly, catchUp animates down
      _controller.duration = const Duration(milliseconds: 1200);
      _greenStart = newPv;
      _greenEnd = newPv;
      _catchUpStart = activeCatchUp;
      _catchUpEnd = newPv;
    } else {
      // Healing: catchUp jumps instantly, green animates up
      _controller.duration = const Duration(milliseconds: 500);
      _catchUpStart = newPv;
      _catchUpEnd = newPv;
      _greenStart = activeGreen;
      _greenEnd = newPv;
    }
    _controller.forward(from: 0.0);
  } else {
    _controller.duration = const Duration(milliseconds: 500);
  }
}

Trois idées à retenir de ce bloc :

  • La durée n'est pas fixe : 1 200 ms pour un dégât (le rouge traîne, on voit ce qu'on a perdu) contre 500 ms pour un soin.
  • La nouvelle animation repart de la valeur interpolée en cours (currentGreen, currentCatchUp), pas de la dernière valeur cible. C'est ce qui évite les saccades quand deux dégâts s'enchaînent en moins d'une seconde.
  • forward(from: 0.0) redémarre le contrôleur depuis le début à chaque changement.

9. Dessiner soi-même

Quand aucun assemblage de widgets ne convient — une courbe, un trait pointillé animé, une forme libre — on descend d'un cran avec CustomPaint et CustomPainter. Le projet compte neuf CustomPainter, dont le plus instructif est celui qui relie les nœuds de la carte du monde.

Un CustomPainter impose deux méthodes :

  • void paint(Canvas canvas, Size size) — le dessin proprement dit. canvas offre drawLine, drawCircle, drawPath, drawRect… size est la taille allouée par le parent.
  • bool shouldRepaint(covariant T oldDelegate) — Flutter appelle cette méthode quand un nouveau painter remplace l'ancien. Renvoyer false quand rien n'a changé évite un repeint inutile.

C'est la ligne la plus importante du fichier. Le constructeur de CustomPainter accepte un Listenable nommé repaint. Quand cet objet notifie ses auditeurs, Flutter redessine le painter — sans reconstruire l'arbre de widgets. Comme un AnimationController est un Listenable qui notifie à chaque frame, il suffit de le passer là pour obtenir une animation continue à 60 fps qui ne coûte ni setState, ni build, ni AnimatedBuilder.

Le contrôleur en question est créé dans la carte du monde et tourne en boucle infinie :

  super.initState();
  _dashController = AnimationController(
    vsync: this,
    duration: const Duration(seconds: 2),
  )..repeat();
  _transformationController.value =
      Matrix4.translationValues(-200.0, -1500.0, 0.0) *
      Matrix4.diagonal3Values(0.8, 0.8, 1.0);

  _dashController.dispose();
  _transformationController.dispose();
  super.dispose();

La valeur du contrôleur (0 → 1 en 2 secondes, en boucle) est convertie en décalage de pointillés : final double phase = animation.value * totalDash * 2;, puis double currentDist = (phase % totalDash) - totalDash;. Les tirets défilent donc le long des chemins, deux cycles complets par tour de contrôleur.

À retenir

Le dessin des tirets est fait à la main, segment par segment, avec canvas.drawLine et des positions bornées par clamp. Le commentaire du fichier explique pourquoi : « Clamped math-based dashes to prevent WASM path allocation heap leak ». L'approche « naturelle » (construire un Path par tiret) fuyait en mémoire sur la cible WebAssembly. C'est un bon rappel : dans paint, on est appelé 60 fois par seconde, chaque allocation compte.

RepaintBoundary

Par défaut, Flutter regroupe les widgets voisins dans une même « couche » de rendu. Si un seul élément de la couche change, toute la couche est repeinte. RepaintBoundary isole son sous-arbre dans sa propre couche : ce qui se repeint dedans n'oblige plus le reste à se repeindre, et inversement.

C'est le seul RepaintBoundary du projet, et il est exactement au bon endroit : autour de la seule chose qui bouge en permanence.

Bonne pratique

N'ajoutez pas de RepaintBoundary « au cas où » : chaque frontière crée une couche supplémentaire, donc de la mémoire vidéo et une composition en plus. On les place uniquement autour d'un sous-arbre qui se repeint beaucoup plus souvent (ou beaucoup moins souvent) que ses voisins — typiquement une animation continue, un canvas, ou une liste très longue.

À retenir

Trois niveaux de granularité, du moins coûteux au plus coûteux, pour animer quelque chose : repeindre (un CustomPainter avec repaint:) < reconstruire un petit sous-arbre (AnimatedBuilder avec un child: constant) < reconstruire l'écran (setState). Choisissez toujours le plus bas des trois qui suffit.
