Les cartes et le deck

1. CardData vs CardInstance — le modèle de données

Posons d'abord le problème. Dans une partie de Hero's Draft, le joueur peut très bien avoir trois « Frappe » dans son deck. Ces trois cartes portent le même nom, le même coût, la même description. Mais l'une a été améliorée à la forge et inflige 2 dégâts de plus, une autre est passée de commune à rare après une fusion, et la troisième est restée telle quelle. Elles sont donc à la fois identiques et différentes.

Le projet règle ça avec deux classes qui vivent dans deux fichiers distincts :

CardData Données

lib/models/data/card_data.dart — la définition d'une carte, lue une seule fois depuis le JSON au démarrage. Immuable, partagée, sans identité propre.

CardInstance Riverpod

lib/models/card_instance.dart — un exemplaire précis dans la run du joueur. Possède un uniqueId, sa propre rareté et ses propres runes de forge.

La règle est simple : tout ce qui est identique pour toutes les copies (nom, coût, type, cible, liste d'effets de base) vit dans CardData. Tout ce qui appartient à une copie précise (son identité, sa rareté acquise, ses améliorations) vit dans CardInstance. Et CardInstance ne recopie jamais les champs de CardData : il garde simplement une référence vers l'objet partagé.

lib/models/card_instance.dartdart
class CardInstance {
  final String uniqueId;
  final CardData data;
  final CardRarity rarity;
  final List<String> forgeUpgrades;

  CardInstance({
    String? uniqueId,
    required this.data,
    CardRarity? rarity,
    List<String>? forgeUpgrades,
  })  : uniqueId = uniqueId ?? const Uuid().v4(),
        rarity = rarity ?? data.rarity,
        forgeUpgrades = forgeUpgrades != null
            ? List<String>.unmodifiable(forgeUpgrades)
            : const <String>[];

Trois choses méritent qu'on s'y arrête dans ce constructeur, parce qu'elles sont typiques de Dart :

  • uniqueId = uniqueId ?? const Uuid().v4() — l'identifiant est optionnel à la construction. Si on ne le fournit pas, le paquet uuid en génère un (UUID v4, aléatoire). C'est ce qui se passe quand une carte est ajoutée au deck : elle reçoit une identité toute neuve. Si on le fournit, c'est qu'on reconstruit une carte existante (chargement d'une sauvegarde, copyWith) et il faut conserver l'identité.
  • rarity = rarity ?? data.rarity — la rareté de l'instance retombe par défaut sur celle de la définition. Une carte fraîchement créée hérite de la rareté du JSON ; une carte fusionnée ou améliorée porte une rareté supérieure à celle de sa définition.
  • List<String>.unmodifiable(...) — la liste des runes est verrouillée. Impossible de faire card.forgeUpgrades.add('sharp:1') : ça lèverait une UnsupportedError à l'exécution. Pour modifier les runes, il faut passer par le contrôleur du deck, qui crée une nouvelle instance. On y revient en section 8.

La liste par défaut est const <String>[] : une liste vide constante, allouée une seule fois pour tout le programme. Sur un deck de trente cartes sans amélioration, ça évite trente allocations inutiles.

Le champ data de chaque instance pointe vers le même objet en mémoire. Si vous aviez recopié les 16 champs de CardData dans chaque instance, un deck de 30 cartes en tiendrait 30 copies, et modifier une définition (par exemple lors d'un rechargement de données) demanderait de parcourir tout le deck.

Sérialisation et rechargement

Attention toutefois : CardInstance.toJson() sérialise data.toJson() en entier dans la sauvegarde. Au rechargement, chaque instance est donc reconstruite avec une CardData issue du fichier de sauvegarde, potentiellement périmée. C'est pourquoi DeckState._decodePile fait un aller-retour par le registre de données :

lib/game/controllers/deck_controller.dartdart
for (final entry in (rawPile ?? const [])) {
  final instance = CardInstance.fromJson(entry as Map<String, dynamic>);
  final freshData = CardData.getById(instance.data.id);
  if (freshData == null) {
    missing.add(
      MissingSaveItem(
        id: instance.data.id,
        nameFr: instance.data.nameFr,
        nameEn: instance.data.nameEn,
        category: 'card',
      ),
    );
    continue;
  }
  final (validUpgrades, upgradesMissing) =
      ForgeUpgradeData.filterValidRefs(instance.forgeUpgrades);
  missing.addAll(upgradesMissing);
  kept.add(instance.copyWith(data: freshData, forgeUpgrades: validUpgrades));
}

Traduction : on relit l'instance sauvegardée, on récupère la vraie définition à jour via CardData.getById(id), et on la réinjecte avec copyWith(data: freshData). Si la carte n'existe plus dans le JSON (elle a été supprimée entre deux versions du jeu), elle est retirée de la pile et signalée dans un rapport MissingSaveItem. Résultat : une sauvegarde ancienne ne fige jamais d'anciennes valeurs d'équilibrage, et le chargement ne plante pas.

Bonne pratique

La séparation « définition partagée / instance de run » est le patron de base de tout deckbuilder. On la retrouve à l'identique pour les ennemis (EnemyData / EnemyInstance). Dès qu'un objet du jeu peut exister en plusieurs exemplaires personnalisables, c'est le bon découpage.

CardType.values.firstWhere((e) => e.name == json['type']) est l'idiome Dart standard pour convertir une chaîne en valeur d'enum : chaque valeur d'enum expose son nom via .name, et on cherche celle qui correspond. Trois des quatre enums fournissent un orElse de repli ; type n'en a pas. Une faute de frappe dans "type" lève donc une StateError au chargement — ce qui est volontairement brutal, puisque le type d'une carte détermine son comportement entier.

Piège

Cette erreur remonte au démarrage, pas au moment de jouer la carte. Le service de chargement l'enveloppe dans un message explicite qui contient l'index et le contenu de l'entrée fautive : Erreur de parsing dans le modèle "CardData" à l'index i (données: …). Si l'application refuse de démarrer après une modification du JSON, c'est le premier endroit à regarder.

Quatre champs seulement, dont deux facultatifs. Remarquez que type est une simple String, pas un enum : c'est volontaire. 4. Les raretés et le multiplicateur

Dans Hero's Draft, la rareté n'est pas un badge décoratif : c'est un coefficient multiplicateur appliqué à toutes les valeurs d'effet de la carte. Il est défini par un simple switch sur l'instance :

lib/models/card_instance.dartdart
int get currentCost => data.cost;

double get rarityMultiplier {
  switch (rarity) {
    case CardRarity.common:
      return 1.0;
    case CardRarity.uncommon:
      return 1.2;
    case CardRarity.rare:
      return 1.4;
    case CardRarity.epic:
      return 1.6;
    case CardRarity.legendary:
      return 2.0;
    case CardRarity.unique:
      return 1.0;
  }
}

La progression n'est pas linéaire : les paliers montent de 0,2 en 0,2 jusqu'à l'épique, puis sautent directement à 2,0 pour la légendaire. La légendaire vaut donc à elle seule un bond de +40 %, autant que les trois premiers paliers réunis. C'est ce qui rend la chaîne complète de fusions intéressante.

Le cas unique surprend au premier coup d'œil : la rareté « la plus haute » de l'enum a le multiplicateur le plus bas. C'est logique une fois qu'on sait à quoi elle sert : elle marque les cartes de classe, dont les valeurs de base sont déjà calibrées (reckless_strike inflige 15 dégâts contre 6 pour strike_basic) et qui compensent par leurs 5 fentes de runes. Elle sert de marqueur « intouchable », pas de niveau de puissance.

Où le multiplicateur est appliqué

Un seul endroit fait autorité : la boucle finale de EffectResolver.resolveCard.

lib/game/services/effect_resolver.dartdart
for (var effect in card.data.effects) {
  final int baseValue = effect.value;
  int scaledValue = (baseValue * card.rarityMultiplier).round();
  if (effect.type == 'damage') {
    scaledValue += extraDamage;
  } else if (effect.type == 'armor') {
    scaledValue += extraArmor;
  }

  final strategy = registry.get(effect.type);
  if (strategy != null) {
    strategy.resolve(
      card: card,
      effect: effect,
      scaledValue: scaledValue,
      runController: runController,
      deckController: deckController,
      combatController: combatController,
      selectedEnemyId: selectedEnemyId,
    );
  }
}

L'ordre des opérations est capital : on multiplie d'abord par la rareté, on arrondit, puis on ajoute les bonus de forge. Une rune sharp:1 vaut +2 dégâts en dur (extraDamage += 2 * k dans la boucle de parsing des runes) et ces 2 points ne sont pas multipliés par la rareté. Un strike_basic légendaire avec sharp:1 inflige donc (6 × 2,0).round() + 2 = 14, et non ((6 + 2) × 2,0) = 16.

.round() en Dart arrondit à l'entier le plus proche, les demis s'éloignant de zéro. Comme le résultat est un double, on obtient parfois des surprises agréables : 6 × 1,6 = 9,6 qui remonte à 10.

6. La pioche, en détail

Toute la pioche du jeu passe par une seule fonction, _drawInto. Elle est static, ne lit ni n'écrit state, et reçoit tout ce dont elle a besoin en paramètre — y compris sa source d'aléatoire. C'est le cœur du contrôleur, et c'est vingt lignes.

lib/game/controllers/deck_controller.dartdart
/// Cœur de la pioche. Fonction pure : ne touche pas à `state`, mute les
/// listes qu'on lui passe et rend le nombre de remélanges effectués.
///
/// Deux conditions d'arrêt, dans cet ordre :
///  1. la main a atteint [maxHandSize] — on s'arrête sans consommer de carte
///     ni déclencher de remélange ;
///  2. pioche ET défausse vides — le deck est épuisé, sortie propre.
static ({
  List<CardInstance> draw,
  List<CardInstance> hand,
  List<CardInstance> discard,
  int reshuffles,
}) _drawInto({
  required List<CardInstance> draw,
  required List<CardInstance> hand,
  required List<CardInstance> discard,
  required int amount,
  required int maxHandSize,
  required Random random,
}) {
  var reshuffles = 0;

  for (var i = 0; i < amount; i++) {
    if (hand.length >= maxHandSize) break;
    if (draw.isEmpty) {
      if (discard.isEmpty) break;
      draw
        ..addAll(discard)
        ..shuffle(random);
      discard.clear();
      reshuffles++;
    }
    hand.add(draw.removeLast());
  }

  return (draw: draw, hand: hand, discard: discard, reshuffles: reshuffles);
}

Lecture ligne à ligne

Le type de retour est un record Dart 3 à champs nommés : ({List<CardInstance> draw, List<CardInstance> hand, List<CardInstance> discard, int reshuffles}). Un record est un agrégat anonyme, sans classe à déclarer, et on accède aux champs par leur nom : result.draw, result.reshuffles. C'est exactement ce qu'il faut ici : la fonction doit rendre quatre choses, et créer une classe _DrawResult pour trois usages internes serait du bruit.

for (var i = 0; i < amount; i++) — une itération par carte demandée. Le compteur ne descend jamais : si la boucle sort en avance, les cartes restantes sont simplement perdues, pas mises en attente.

if (hand.length >= maxHandSize) break; — première condition d'arrêt, et elle est testée avant tout le reste. C'est ce qui produit la règle dite d'arrêt net.

Règle du jeu — l'arrêt net de la pioche

Quand la main atteint maxHandSize = 10, la pioche s'arrête immédiatement : aucune carte n'est retirée de la pioche, aucune carte n'est défaussée, et surtout aucun remélange n'est déclenché. Le test de main pleine est la première ligne de la boucle, avant le test de pioche vide. Un joueur qui a 10 cartes en main et qui joue concentration (pioche 2) ne perd rien de sa pioche : les deux cartes sont simplement jamais tirées.

Cet ordre n'est pas anodin. Si les deux if étaient inversés, une pioche demandée main pleine viderait la défausse dans la pioche et la mélangerait pour rien — ce qui, en plus d'être gratuit, changerait l'ordre des cartes du reste du combat et ferait grimper reshuffleCount sans raison visible pour le joueur.

if (draw.isEmpty) { if (discard.isEmpty) break; … } — deuxième condition d'arrêt, imbriquée. On ne regarde la défausse que si la pioche est vide. Si les deux le sont, le deck est épuisé : on sort proprement, sans exception, sans état bancal. Un joueur qui a joué toutes ses cartes et les a toutes épuisées finit simplement son tour avec la main qu'il a.

La cascade draw ..addAll(discard) ..shuffle(random); — l'opérateur cascade .. de Dart enchaîne plusieurs appels sur le même objet sans le répéter. C'est équivalent à draw.addAll(discard); draw.shuffle(random);. On verse la défausse dans la pioche, on mélange le tout avec la source d'aléatoire injectée, on vide la défausse (discard.clear()) et on incrémente le compteur. Puis la boucle continue : le remélange se produit au milieu d'une pioche, sans l'interrompre.

hand.add(draw.removeLast()) — on tire par la fin de la liste. C'est un choix de performance : sur une List Dart, removeLast() est en temps constant, alors que removeAt(0) décale tous les éléments restants. Comme la pioche est mélangée, tirer par la fin ou par le début est strictement équivalent en termes de jeu.

Piège

_drawInto mute les listes qu'on lui passe : hand.add, discard.clear(), draw.removeLast(). Elle n'est « pure » que du point de vue de state. C'est pour cela que les deux appelants lui donnent systématiquement des copies fraîches (List<CardInstance>.from(state.drawPile)) et jamais les listes de l'état. Passer state.hand directement corromprait l'état précédent et casserait la détection de changement de Riverpod.

La main d'ouverture

Trois points à noter :

  • List<CardInstance>.from(state.masterDeck)..shuffle(_random) — on part d'une copie du deck maître, qu'on mélange. Le masterDeck lui-même n'est jamais mélangé ni modifié ; c'est ce qui lui permet de survivre au combat intact.
  • La main et la défausse partent vides. La condition « pioche ET défausse vides » s'applique donc dès le premier tour : si le joueur possède moins de cartes que handSize, la boucle s'arrête d'elle-même, sans erreur.
  • La main d'ouverture emprunte exactement le même chemin que toutes les autres pioches. Pas de code dupliqué, pas de règle spéciale : le plafond de 10 cartes, la sortie propre sur deck vide, l'ordre des tests, tout est partagé.

La pioche en cours de tour

lib/game/controllers/deck_controller.dartdart
/// Pioche [amount] cartes. Remélange la défausse dans la pioche dès que
/// celle-ci est vide, y compris au milieu d'une pioche. Une seule
/// affectation de `state`, donc une seule notification Riverpod.
void drawCards(int amount, {required int maxHandSize}) {
  final result = _drawInto(
    draw: List<CardInstance>.from(state.drawPile),
    hand: List<CardInstance>.from(state.hand),
    discard: List<CardInstance>.from(state.discardPile),
    amount: amount,
    maxHandSize: maxHandSize,
    random: _random,
  );

  state = state.copyWith(
    drawPile: result.draw,
    hand: result.hand,
    discardPile: result.discard,
    reshuffleCount: state.reshuffleCount + result.reshuffles,
  );
}

Trois copies en entrée, un calcul, une seule affectation de state. C'est le point le plus important du fichier, et il mérite qu'on explique pourquoi.

Avec Riverpod, chaque affectation à state déclenche une notification à tous les ref.watch(deckProvider) de l'application, donc une reconstruction de widgets. Une implémentation naïve qui écrirait state à chaque carte piochée provoquerait, pour une pioche de 5 cartes avec un remélange au milieu, six notifications successives — et l'interface afficherait fugitivement des états intermédiaires incohérents (une pioche vide, une défausse à moitié recyclée). Ici, l'extérieur ne voit qu'une transition atomique : avant la pioche, après la pioche.

Le compteur reshuffleCount est accumulé (state.reshuffleCount + result.reshuffles) et non remplacé, puisqu'il compte les remélanges depuis le début du combat. L'interface l'observe pour déclencher son animation de remélange : voir passer le compteur de 0 à 1 suffit à savoir qu'un recyclage a eu lieu, même s'il s'est produit au milieu d'une pioche de cinq cartes.

Le même souci de sobriété se retrouve dans discardHand, la méthode qui vide la main en fin de tour : elle commence par if (currentHand.isEmpty) return; et sort donc avant toute affectation de state si la main est déjà vide. Pas de notification, pas de reconstruction de widgets pour un changement qui n'en est pas un.

lib/game/controllers/deck_controller.dartdart
/// Joue une carte : la retire de la main et l'envoie dans la défausse (ou l'épuise si pouvoir)
void playCard(CardInstance card) {
  var currentHand = List<CardInstance>.from(state.hand);
  var currentDiscardPile = List<CardInstance>.from(state.discardPile);
  var currentExhaustPile = List<CardInstance>.from(state.exhaustPile);

  // Trouver l'index pour ne supprimer qu'un seul exemplaire si doublons (sécurité)
  final index = currentHand.indexWhere((c) => c.uniqueId == card.uniqueId);

  if (index != -1) {
    final cardToPlay = currentHand.removeAt(index);

    final isExhausted = cardToPlay.data.isExhaust && !cardToPlay.forgeUpgrades.contains('enduring:1');

    if (cardToPlay.data.type == CardType.power || isExhausted) {
      currentExhaustPile.add(cardToPlay);
    } else {
      currentDiscardPile.add(cardToPlay);
    }

    state = state.copyWith(
      hand: currentHand,
      discardPile: currentDiscardPile,
      exhaustPile: currentExhaustPile,
    );
  }
}

Pourquoi retirer par uniqueId et non par valeur ?

La ligne currentHand.indexWhere((c) => c.uniqueId == card.uniqueId) pourrait être remplacée par currentHand.remove(card). Ce serait un bug, pour deux raisons.

Première raison : CardInstance ne redéfinit ni operator == ni hashCode. En Dart, l'égalité par défaut est l'identité de l'objet. remove(card) ne retirerait donc la carte que si l'appelant passe très exactement la même référence que celle stockée dans la liste. Or la carte remonte depuis l'UI Flame, éventuellement après un copyWith ou une reconstruction : une instance qui décrit la même carte mais qui n'est pas le même objet ne serait jamais trouvée, et la carte resterait en main après avoir été jouée.

Seconde raison : les doublons. Même si l'égalité était redéfinie par valeur, un joueur peut avoir deux strike_basic communes en main, avec les mêmes champs à l'exception de l'uniqueId. Une comparaison par valeur risquerait de retirer la mauvaise — ou, pire, l'implémentation d'une future méthode removeWhere les retirerait toutes les deux. Le commentaire du code le dit explicitement : « ne supprimer qu'un seul exemplaire si doublons ».

L'uniqueId résout les deux problèmes d'un coup : il identifie un exemplaire, survit à la sérialisation et aux copies, et removeAt(index) n'enlève qu'une entrée. Et si l'index vaut -1 (carte absente de la main, par exemple à cause d'un double clic), la méthode ne fait rien du tout : pas d'affectation de state, donc pas de notification inutile.

Remarquez List<String>.from(c.forgeUpgrades)..add(upgrade) dans addForgeUpgrade : on ne peut pas faire c.forgeUpgrades.add(...) puisque la liste est unmodifiable. Il faut copier, ajouter, puis reconstruire l'instance. Point d'attention

Deux méthodes publiques n'ont aucun appelant dans lib/ : upgradeCard et addCardToDiscardPile. Le feu de camp, malgré son nom d'action « améliorer », passe en réalité par RestCardSelectionScreen → ForgeUpgradeDialog → addForgeUpgrade : il pose une rune, il ne monte pas la rareté. La seule voie vers une rareté supérieure aujourd'hui est donc la fusion de trois cartes. Ce n'est pas un bug, mais du code mort à surveiller : il compile, il est testable, et rien ne garantit qu'il reste cohérent avec le reste.

La fusion 3 → 1

L'écran « Mon Deck » regroupe les cartes avant de les afficher, et c'est la clé de regroupement qui définit ce que « trois cartes identiques » veut dire :

lib/ui/screens/deck_screen.dartdart
// Grouper les cartes pour identifier les fusions possibles
final Map<String, List<CardInstance>> groups = {};
for (var card in masterDeck) {
  final key = '${card.data.id}_${card.rarity.name}';
  groups.putIfAbsent(key, () => []).add(card);
}

La clé combine l'identifiant de la définition et le nom de la rareté de l'instance, par exemple strike_basic_common ou strike_basic_rare. Les conséquences pratiques sont importantes :

  • Deux strike_basic communes et une strike_basic rare forment deux groupes (2 et 1), pas un groupe de 3. On ne peut fusionner que des cartes de même rareté.
  • Les runes de forge n'entrent pas dans la clé. Une « Frappe » commune nue et une « Frappe » commune avec sharp:2 sont regroupées ensemble, et l'écran n'affiche que la première du groupe (cardList.first) avec un badge x3. Le joueur doit ouvrir la boîte de dialogue pour voir le détail des runes de chaque exemplaire.
  • Le bouton n'apparaît qu'à partir de count >= 3, et jamais pour card.rarity == CardRarity.unique : les cartes de classe sont exclues côté interface aussi.
lib/game/controllers/deck_controller.dartdart
/// Fusionne 3 cartes identiques en une carte de rareté supérieure
void mergeCards(List<String> selectedIds, List<String> inheritedUpgrades) {
  if (selectedIds.length != 3) return;
  var currentMasterDeck = List<CardInstance>.from(state.masterDeck);

  final List<CardInstance> selectedCards = [];
  for (var id in selectedIds) {
    final cardIdx = currentMasterDeck.indexWhere((c) => c.uniqueId == id);
    if (cardIdx != -1) {
      selectedCards.add(currentMasterDeck[cardIdx]);
    }
  }

  if (selectedCards.length == 3) {
    if (selectedCards.any((c) => c.rarity == CardRarity.unique)) {
      return;
    }
    final baseCardData = selectedCards[0].data;
    final rarity = selectedCards[0].rarity;

    // Retire les 3 exemplaires
    currentMasterDeck.removeWhere((c) => selectedIds.contains(c.uniqueId));

    // Détermine la rareté suivante
    final nextRarityIndex = min(rarity.index + 1, CardRarity.values.length - 1);
    final nextRarity = CardRarity.values[nextRarityIndex];

La méthode se protège trois fois avant d'agir : exactement 3 identifiants en entrée, les 3 cartes doivent être retrouvées dans le deck, et aucune ne doit être unique. Chaque garde est un return silencieux : la fusion n'a pas lieu, le deck n'est pas modifié, et aucune notification Riverpod n'est émise.

Règle du jeu — la fusion

Trois exemplaires de même identifiant et de même rareté se fusionnent en un seul, d'une rareté supérieure d'un cran. Les cartes de rareté unique (les 6 cartes de classe) sont refusées. Les runes des trois cartes sont consolidées par somme des tiers, rune par rune, puis plafonnées à baseMaxForgeUpgrades + nextRarityIndex. Le deck perd donc deux cartes à chaque fusion — c'est un mécanisme de compression autant que d'amélioration.

La consolidation des runes

lib/game/controllers/deck_controller.dartdart
    // Auto-fusionne les upgrades identiques (cumul des tiers)
    final Map<String, int> consolidatedMap = {};
    for (var upgrade in inheritedUpgrades) {
      final parts = upgrade.split(':');
      if (parts.length != 2) continue;
      final id = parts[0];
      final tier = int.tryParse(parts[1]) ?? 0;
      if (tier <= 0) continue;
      consolidatedMap[id] = (consolidatedMap[id] ?? 0) + tier;
    }

    var finalUpgrades = consolidatedMap.entries.map((e) => '${e.key}:${e.value}').toList();

    // Limite à la capacité de la rareté supérieure
    final capacity = baseCardData.baseMaxForgeUpgrades + nextRarityIndex;
    if (finalUpgrades.length > capacity) {
      finalUpgrades = finalUpgrades.sublist(0, capacity);
    }

    // Ajoute la carte de rareté supérieure avec les upgrades finalisés
    currentMasterDeck.add(
      CardInstance(
        data: baseCardData,
        rarity: nextRarity,
        forgeUpgrades: finalUpgrades,
      ),
    );

    state = state.copyWith(masterDeck: currentMasterDeck);

Une rune est toujours une chaîne 'id:tier' — par exemple 'sharp:2'. La consolidation en trois temps :

  1. Découpage : upgrade.split(':'). Toute entrée qui ne donne pas exactement deux morceaux est ignorée (continue), tout comme un tier non numérique (int.tryParse renvoie null, remplacé par 0) ou nul.
  2. Cumul : consolidatedMap[id] = (consolidatedMap[id] ?? 0) + tier. Trois cartes portant sharp:1, sharp:2 et hardened:1 produisent {sharp: 3, hardened: 1}, soit deux runes au lieu de trois — et un sharp qui vaut désormais +6 dégâts, puisque extraDamage += 2 * k.
  3. Plafonnement : si le nombre de runes distinctes dépasse la capacité de la nouvelle rareté, on tronque avec sublist(0, capacity).

La capacité suit la même formule que l'affichage des fentes : baseCardData.baseMaxForgeUpgrades + nextRarityIndex. Pour une carte globale (baseMaxForgeUpgrades = 1) :

FusionnextRarityIndexCapacité de runesMultiplicateur obtenu
3 communes → 1 peu commune11 + 1 = 21,2
3 peu communes → 1 rare21 + 2 = 31,4
3 rares → 1 épique31 + 3 = 41,6
3 épiques → 1 légendaire41 + 4 = 52,0

Point d'attention

La dernière ligne du tableau est un piège du calcul min(rarity.index + 1, CardRarity.values.length - 1). CardRarity.values.length - 1 vaut 5, c'est-à-dire unique — une rareté qui n'a jamais été pensée comme un palier de progression et dont le rarityMultiplier retombe à 1,0. Fusionner trois cartes légendaires (×2,0) produirait donc une carte à ×1,0 : neuf cartes communes converties en une carte de force strictement identique à une commune. La même formule est reprise à l'identique dans upgradeCard et dans deck_screen.dart. Plafonner à CardRarity.legendary.index serait plus sûr.

Deuxième point de vigilance, plus discret : mergeCards prend baseCardData et rarity depuis selectedCards[0] sans vérifier que les trois cartes ont bien le même data.id ni la même rareté. C'est l'écran qui garantit l'homogénéité, via la clé de regroupement. Un futur appelant qui passerait trois uniqueId quelconques obtiendrait une fusion silencieusement absurde — trois cartes différentes remplacées par une copie améliorée de la première.

Piège

Cette duplication du calcul entre EffectResolver (règle) et CardCompactDescription / buildDetailedDescription (affichage) est une source classique de désynchronisation. Le jour où l'ordre « multiplier puis ajouter » change dans le resolver, il faut penser à corriger les deux widgets — sans quoi la carte affichera un chiffre et en infligera un autre.

À retenir

Le deckbuilding tient en cinq gestes : choisir 5 cartes au départ, ajouter après chaque combat, retirer au feu de camp ou en boutique, enrichir de runes à la forge, et fusionner 3 exemplaires pour monter d'une rareté. Toutes ces opérations ne touchent qu'au masterDeck ; les quatre autres piles sont recalculées à chaque combat.

Quiz — vérifiez vos acquis

1. Le joueur pioche alors qu'il a déjà 10 cartes en main et que sa pioche est vide. Que se passe-t-il exactement ?

  • La défausse est remélangée dans la pioche, puis la pioche est annulée
  • La carte est piochée puis immédiatement défaussée
  • Rien : la boucle sort au premier test, sans consommer de carte ni remélanger
  • Une exception est levée et le tour se termine
Réponse : dans _drawInto (lib/game/controllers/deck_controller.dart), if (hand.length >= maxHandSize) break; est la première ligne de la boucle, avant le test draw.isEmpty. C'est la règle d'arrêt net : aucune carte consommée, aucun remélange, reshuffleCount inchangé. maxHandSize vaut 10 (GameConstants.maxHandSize).

2. Quels dégâts inflige un strike_basic de rareté épique portant la rune sharp:1 ?

  • 13 — (6 + 2) × 1,6 arrondi
  • 12 — (6 × 1,6).round() = 10, puis +2
  • 10 — la rune ne s'applique pas aux attaques
  • 9 — 6 × 1,6 tronqué à 9, la rune est déjà comptée
Réponse : EffectResolver.resolveCard calcule scaledValue = (baseValue * card.rarityMultiplier).round() puis ajoute seulement ensuite extraDamage. Épique vaut 1,6 : (6 × 1,6) = 9,6 → 10, et sharp:1 ajoute 2 * 1 = 2, soit 12. Les bonus de forge ne sont jamais multipliés par la rareté.

3. Combien de cartes le joueur possède-t-il dans son masterDeck juste après avoir validé l'écran de deck de départ ?

  • 5 — uniquement les cartes globales choisies
  • 17 — tout le pool global
  • 10 — 5 choisies plus 5 imposées
  • 7 — les 2 cartes de la classe plus les 5 cartes globales choisies
Réponse : _startAdventure dans starter_deck_draft_screen.dart ajoute d'abord widget.playerClass.getHeroCards(gameData) — soit les 2 identifiants du champ skills du héros dans heroes.json — puis les 5 cartes globales sélectionnées. Total : 7 CardInstance.

4. Pourquoi playCard retire-t-elle la carte par uniqueId plutôt qu'avec currentHand.remove(card) ?

  • Parce que CardInstance ne redéfinit pas operator == : remove comparerait par identité d'objet et pourrait ne rien retirer
  • Parce que remove n'existe pas sur les List en Dart
  • Parce que remove retirerait la carte de toutes les piles à la fois
  • Parce que uniqueId est plus rapide à comparer qu'un objet entier
Réponse : CardInstance (lib/models/card_instance.dart) n'implémente ni operator == ni hashCode : l'égalité par défaut de Dart est l'identité de référence. Une instance reconstruite (via copyWith ou fromJson) ne serait donc jamais trouvée. L'indexWhere sur l'uniqueId garantit en plus qu'un seul exemplaire est retiré en cas de doublon.

5. Quelle carte part à l'épuisement même si elle porte la rune enduring:1 ?

  • concentration, parce qu'elle coûte 0 mana
  • holy_shield, parce qu'elle est de rareté unique
  • demon_form, parce qu'elle est de type power
  • Aucune : la rune annule toujours l'épuisement
Réponse : la condition est if (cardToPlay.data.type == CardType.power || isExhausted). Le test du type power est indépendant de isExhausted, donc de la rune. Les deux power du jeu sont demon_form et metallicize.

6. On fusionne trois « Frappe » peu communes portant respectivement sharp:1, sharp:2 et hardened:1. Que contient la carte obtenue ?

  • Une rare avec sharp:1, sharp:2 et hardened:1 — les runes sont conservées telles quelles
  • Une rare avec sharp:3 et hardened:1, capacité 3
  • Une épique avec sharp:3, car trois cartes font sauter deux paliers
  • Une rare sans aucune rune : la fusion les efface
Réponse : mergeCards additionne les tiers par identifiant de rune (consolidatedMap[id] = (consolidatedMap[id] ?? 0) + tier), d'où sharp:3 et hardened:1. La rareté monte d'un seul cran (uncommon index 1 → rare index 2) et la capacité vaut baseMaxForgeUpgrades + nextRarityIndex = 1 + 2 = 3 : les deux runes tiennent largement.
