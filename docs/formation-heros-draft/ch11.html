Chapitre 11

Les ennemis et la courbe de difficulté

Hero's Draft ne place pas ses ennemis à la main. Chaque combat est acheté avec un budget calculé à partir de la puissance réelle du joueur. Ce chapitre démonte la formule, terme par terme.

Dans la plupart des jeux de cartes roguelike, les rencontres sont écrites : un designer décide que l'étage 3 contient « deux gobelins et un squelette ». Hero's Draft fait l'inverse. Un seul fichier, Données lib/game/systems/encounter_system.dart, calcule un budget en points, attribue un prix à chaque ennemi du bestiaire, puis dépense le budget jusqu'à épuisement. Aucune rencontre n'est écrite nulle part.

Ce choix a une conséquence directe pour vous : si vous voulez rendre le jeu plus dur ou plus facile, vous ne touchez pas à cinquante fichiers de niveau — vous changez une constante. Mais il faut d'abord comprendre exactement ce que chaque constante fait. C'est l'objet de ce chapitre.

1. Les quatre ennemis du bestiaire

Tout part de assets/data/enemies.json. Le fichier est court : quatre entrées, pas une de plus. Tout le reste — la variété des combats, la montée en difficulté sur douze actes — est produit par des multiplicateurs appliqués à ces quatre archétypes.

Le champ intents : un cycle scripté

Une intention est ce que l'ennemi annonce qu'il va faire au tour suivant — l'icône affichée au-dessus de sa tête. Le type est un simple enum à trois valeurs.

  final IntentType type;
  final int value;

  EnemyIntent({required this.type, required this.value});

Quand intents est renseigné, la liste n'est pas tirée au hasard : elle est parcourue en boucle, dans l'ordre. Un compteur intentStep stocké sur l'instance avance d'un cran à chaque tour et repasse à zéro grâce à un modulo.

lib/game/controllers/combat_controller.dartdart
  EnemyInstance rollIntent(EnemyInstance enemy) {
    final data = enemy.data;
    EnemyIntent nextIntent;
    int nextStep = enemy.intentStep;

    if (data.intents != null && data.intents!.isNotEmpty) {
      nextIntent = data.intents![enemy.intentStep];
      nextStep = (enemy.intentStep + 1) % data.intents!.length;
    } else {
      final random = Random();
      final roll = random.nextInt(100);

      if (roll < 60) {
        nextIntent = EnemyIntent(
          type: IntentType.attack,
          value: data.baseDamage,
        );
      } else if (roll < 85) {
        nextIntent = EnemyIntent(
          type: IntentType.defend,
          value: 5 + random.nextInt(6),
        );
      } else {
        nextIntent = EnemyIntent(type: IntentType.buff, value: 2);
      }
    }
    return enemy.copyWith(currentIntent: nextIntent, intentStep: nextStep);
  }
Règle du jeu — le cycle d'intentions

Un ennemi qui déclare des intents est parfaitement prévisible. L'Orc Furieux joue toujours attack 8, puis buff 2, puis attack 12, puis recommence. Le joueur qui observe ce cycle sait qu'il doit garder son armure pour le troisième tour. Les quatre ennemis du bestiaire déclarent tous leurs intents : la branche aléatoire (60 % attaque, 25 % défense, 15 % buff) n'est jamais atteinte avec les données actuelles. C'est un filet de sécurité pour du contenu futur.

Attention à un piège de lecture : la valeur écrite dans le JSON (value: 12 pour l'orc) n'est pas la valeur affichée en jeu. Elle est remise à l'échelle au moment de l'affichage, proportionnellement au multiplicateur de dégâts appliqué au spawn.

lib/models/enemy_instance.dartdart
  EnemyIntent? get effectiveIntent {
    final intent = currentIntent;
    if (intent == null) return null;
    if (intent.type == IntentType.attack) {
      final double spawnMultiplier = data.baseDamage > 0
          ? stats.attaque / data.baseDamage
          : 1.0;
      final int scaledValue = (intent.value * spawnMultiplier).round();
      final int inBattleBonus = stats.effectiveAttaque - stats.attaque;
      int finalValue = (stats.effectiveAttaque > (scaledValue + inBattleBonus))
          ? stats.effectiveAttaque
          : (scaledValue + inBattleBonus);
      if (stats.statuses.any((s) => s.id == 'freeze')) {
        finalValue = (finalValue * 0.5).round();
      }
      return EnemyIntent(

        value: finalValue,

    }

Exemple concret : un orc invoqué avec stats.attaque = 14 (au lieu de son baseDamage de 8) obtient un spawnMultiplier de 14 / 8 = 1,75. Son intention attack 12 s'affiche donc à 12 × 1,75 = 21. Le buff 2, lui, n'est pas touché : seules les intentions de type attack passent par cette remise à l'échelle.

Le champ tier : un palier de déblocage

tier ne modifie pas les statistiques de l'ennemi. Il joue deux rôles distincts, que l'on détaillera aux sections 3 et 7 :

Prix plancher

Le tier vaut tier × 15 points dans le Combat Rating. Un orc coûte 45 points rien que par son tier, avant même de compter ses PV.

Verrou de progression

Un ennemi n'est éligible que si son tier est débloqué à l'acte courant : tier 1 jusqu'à l'acte 5, tier 2 dès l'acte 6, tier 3 dès l'acte 11.

Autrement dit, le squelette (tier 2) et l'orc (tier 3) ne peuvent pas apparaître avant respectivement l'acte 6 et l'acte 11. Sur les cinq premiers actes, le joueur n'affronte que des slimes et des gobelins — mais des slimes et des gobelins de plus en plus gros.

Les champs xp et gold

Ces deux champs ne servent qu'à la victoire. Ils sont multipliés par le niveau de l'ennemi, avec un gain de 10 % par niveau au-dessus de 1 :

lib/game/controllers/reward_controller.dartdart

Un orc de niveau 5 rapporte donc round(100 × (1 + 0,10 × 4)) = 140 XP et round(25 × 1,4) = 35 or. Notez que le multiplicateur suit le niveau de l'ennemi (calculé section 7), pas l'acte : deux orcs identiques croisés à l'acte 2 et à l'acte 9 rapportent la même chose si le joueur a le même niveau.

Dette technique — xp disparaît à la sérialisation

EnemyInstance.toJson() (dans lib/models/enemy_instance.dart) recopie maxHp, baseDamage, tier, critChance, gold et intents… mais pas xp. Comme EnemyData.fromJson applique json['xp'] as int? ?? 20, un aller-retour JSON transformerait l'orc à 100 XP en orc à 20 XP. Le bug est aujourd'hui dormant : SaveService ne persiste pas l'état de combat. Il se réveillera le jour où quelqu'un ajoutera la sauvegarde en plein combat.

2. Le budget de combat

On entre dans le cœur du système. La méthode EncounterSystem.calculateBudget répond à une seule question : combien de points de menace ce combat a-t-il le droit de dépenser ? Elle ne choisit aucun ennemi, elle ne connaît même pas le bestiaire. Elle produit sept grandeurs, regroupées dans un record Dart nommé.

lib/game/systems/encounter_system.dartdart
/// Breakdown of the combat budget calculation — see [EncounterSystem.calculateBudget].

  double playerPower,
  double expectedPower,

  double nodeMultiplier,
  double finalBudget,
});

Un record (syntaxe ({ ... })) est un tuple à champs nommés introduit par Dart 3. Il évite d'écrire une classe entière pour un simple sac de valeurs de retour. On y accède avec budget.finalBudget, exactement comme un champ d'objet, mais sans constructeur ni copyWith à maintenir.

Terme 1 — playerPower

playerPower = maxHP + attaque×10 + maxMana×15 + reliques×5 + cartes×2

C'est une estimation scalaire de la puissance réelle du joueur. Les coefficients disent ce que le designer considère comme équivalent : un point d'attaque vaut 10 points de vie, un point de mana maximum en vaut 15, une relique en vaut 5, une carte en vaut 2. Le mana est la ressource la plus chère du modèle — logique, puisqu'il conditionne le nombre de cartes jouables par tour.

ComposanteCoefficientLecture
playerMaxHp× 1L'unité de référence du modèle.
playerAttaque× 101 point de force = 10 PV.
playerMaxMana× 15La ressource la mieux valorisée.
playerRelicsCount× 5Compte les reliques, pas leur puissance.
playerCardsCount× 2Compte la taille du deck, pas sa qualité.
Piège — le modèle compte, il n'évalue pas

Une relique légendaire et une relique commune pèsent toutes les deux 5 points. Une carte « Frappe » de départ et une carte légendaire pèsent toutes les deux 2 points. Conséquence de jeu : purger son deck à la boutique fait baisser le playerPower, donc le budget des combats suivants — alors qu'un deck épuré est objectivement plus fort. C'est un exploit connu de ce type de modèle. À l'inverse, accumuler des cartes faibles gonfle artificiellement la difficulté.

Terme 2 — expectedPower

expectedPower = 145 + (playerLevel − 1)×15 + (act − 1)×20

C'est la puissance que le joueur devrait avoir à ce stade de la partie. La constante 145 n'est pas arbitraire : c'est exactement le playerPower produit par les valeurs par défaut de generateEnemiesForLevel — playerMaxHp = 100, playerAttaque = 0, playerMaxMana = 3, aucune relique, aucune carte, soit 100 + 0 + 45 + 0 + 0 = 145. Le joueur de référence à l'acte 1, niveau 1, obtient donc un ratio exactement égal à 1,0.

La courbe attendue croît de 15 points par niveau de héros et de 20 points par acte.

Terme 3 — baseBudget

baseBudget = 40 + (playerLevel − 1)×10 + (act − 1)×25

C'est l'enveloppe brute, avant toute correction. 40 points au tout début de la partie — de quoi s'offrir un gobelin (33 points, voir section 3) et rien d'autre. La progression par acte (+25) est 2,5 fois plus rapide que la progression par niveau de héros (+10) : le système considère que traverser un acte est un événement plus structurant que gagner un niveau.

Terme 4 — powerRatio

powerRatio = playerPower / expectedPower

Un joueur exactement dans la norme donne 1,0. Un joueur qui a bien drafté donne 1,2 ou 1,3. Un joueur qui a enchaîné les mauvais choix donne 0,85.

Terme 5 — powerModifier, l'amortissement de moitié

powerModifier = 1 + (powerRatio − 1) × 0,5

C'est la ligne la plus importante du fichier, et la plus facile à mal lire. Elle ne dit pas « la difficulté suit la puissance du joueur ». Elle dit : la difficulté suit la moitié de l'écart à la norme.

Règle du jeu — la récompense du sur-optimisé

Un joueur deux fois plus puissant que la norme n'affronte pas des combats deux fois plus durs, mais seulement 1,5 fois plus durs. Le sur-investissement reste rentable. C'est l'intention de game design derrière le facteur 0,5 : un rubber-banding qui empêche la partie de devenir triviale, sans annuler le bénéfice d'un bon draft. Sans l'amortissement (facteur 1,0), un joueur qui double sa puissance retrouverait exactement la même difficulté relative — et le draft n'aurait plus aucun intérêt.

Symétriquement, un joueur en difficulté voit son budget baisser, mais deux fois moins vite que sa puissance. Le jeu l'aide un peu, pas complètement : la spirale de la mort reste possible.

Une propriété utile : comme playerPower est toujours positif ou nul, le powerRatio est ≥ 0, donc powerModifier ne peut jamais descendre sous 0,5. Il n'y a aucun clamp explicite dans le code, mais la borne basse existe mathématiquement. En revanche, il n'y a aucune borne haute : un joueur au ratio 5,0 obtiendrait un modificateur de 3,0.

Terme 7 — finalBudget

Le détail à ne pas rater : le terme (act − 1)×10 est ajouté après la multiplication par nodeMultiplier. Il n'est donc pas doublé sur un boss. C'est un plancher additif par acte, identique quel que soit le type de nœud.

3. Le prix d'un ennemi : le Combat Rating

Le budget est une somme d'argent. Il faut maintenant des étiquettes de prix. C'est le rôle de calculateCombatRating : convertir un ennemi, dans un contexte donné (acte, niveau, type de nœud), en un nombre unique de points de menace.

lib/game/systems/encounter_system.dartdart
  /// Calculates the combat rating for a given enemy under specific parameters.
  static double calculateCombatRating({
    required EnemyData data,
    required int enemyLevel,
    required int act,
    required bool isBoss,
    required bool isElite,
  }) {
    final bool isCustomBoss = data.id.startsWith('boss_');

    final double hpMultiplier = getHpMultiplier(
      enemyLevel: enemyLevel,
      act: act,
      isBoss: isBoss,
      isElite: isElite,
      isCustomBoss: isCustomBoss,
    );

    final double damageMultiplier = getDamageMultiplier(
      enemyLevel: enemyLevel,
      act: act,
      isBoss: isBoss,
      isElite: isElite,
      isCustomBoss: isCustomBoss,
    );

    final int hpScale = (data.maxHp * hpMultiplier).round();
    final int damageScale = (data.baseDamage * damageMultiplier).round();

    return (data.tier * 15.0) + (hpScale / 4.0) + (damageScale * 2.0) * (1.0 + data.critChance / 100.0);
  }

La formule finale se lit en trois termes :

Prix de surviehpScale / 4Combien de tours l'ennemi va tenir.

Piège — la priorité des opérateurs

Écrite en une seule ligne, la formule peut se lire de travers. En Dart comme en maths, la multiplication est prioritaire sur l'addition : (1.0 + critChance / 100.0) multiplie uniquement le terme de dégâts, pas la somme entière. Un ennemi à 15 % de critique ne voit pas ses PV ni son tier majorés de 15 % — seulement ses dégâts.

Le point clé, souvent mal compris : hpScale et damageScale ne sont pas les valeurs du JSON. Ce sont les valeurs déjà multipliées par getHpMultiplier et getDamageMultiplier — c'est-à-dire par le niveau de l'ennemi, le facteur d'acte et le multiplicateur de nœud (sections 6 et 7). Un même ennemi coûte donc de plus en plus cher au fil de la partie. Les deux valeurs sont arrondies à l'entier (.round()) avant d'entrer dans la formule : le CR se calcule sur les PV et dégâts réellement affichés en jeu, pas sur des flottants.

Le CR des quatre ennemis à l'acte 1, joueur niveau 1, nœud normal

Dans ce cas de référence, tout se simplifie : enemyLevel = 1 donc le terme de niveau vaut 1,0 ; getHpActFactor(1) = 1,0 et getDamageActFactor(1) = 1,0 ; le nœud est normal donc le multiplicateur vaut 1,0. Les deux multiplicateurs valent exactement 1,0, et hpScale = maxHp, damageScale = baseDamage.

Rapportez-les au budget de départ (40 points à l'acte 1, niveau 1, nœud normal) : le premier combat de la partie peut s'offrir un slime ou un gobelin, et rien de plus. Après un gobelin il reste 7 points, insuffisants pour quoi que ce soit.

Notez aussi l'effet du forfait de tier. Le squelette n'a que 22 PV — moins que le gobelin — mais son tier 2 lui coûte 30 points d'entrée. Il vaut 1,6 fois le gobelin. L'orc, lui, vaut 2,3 gobelins. Le tier est le levier de prix dominant sur les petits ennemis, et il ne cesse de l'être que quand les facteurs d'acte gonflent suffisamment hpScale.

4. L'algorithme de composition

Budget d'un côté, prix de l'autre : la composition de la rencontre est une boucle d'achat. Elle tient en une vingtaine de lignes.

lib/game/systems/encounter_system.dartdart
    final List<EnemyData> generatedEnemies = [];
    double remainingBudget = finalBudget;

    // Choose enemies without exceeding remaining budget or the act-scaled cap
    while (remainingBudget > 0 && generatedEnemies.length < maxEnemies) {
      final candidates = enemyPool.where((enemy) {
        final rating = calculateCombatRatingForEnemy(enemy);
        return rating <= remainingBudget;
      }).toList();

      if (candidates.isEmpty) {
        break;
      }

      final chosen = candidates[_rng.nextInt(candidates.length)];
      generatedEnemies.add(chosen);
      remainingBudget -= calculateCombatRatingForEnemy(chosen);
    }

Trois observations de lecture :

  1. La condition de boucle a deux gardes : le budget doit rester strictement positif et le nombre d'ennemis doit rester sous maxEnemies. C'est le premier des deux qui saute qui arrête la boucle.
  2. Le filtrage rating <= remainingBudget est recalculé à chaque tour. Le pool ne rétrécit pas : c'est le budget qui rétrécit, donc la liste des candidats se réduit mécaniquement au fil des achats.
  3. Le tirage est uniforme : candidates[_rng.nextInt(candidates.length)]. Aucune pondération, aucun poids de rareté. Un slime abordable a exactement la même probabilité d'être choisi qu'un orc abordable.
Règle du jeu — un biais implicite vers les petits ennemis

Le tirage uniforme ne garantit pas des compositions équilibrées, mais il produit un biais intéressant : plus le budget se vide, plus les gros ennemis sortent du filtre, et plus la probabilité de tirer un petit ennemi augmente. Les rencontres tendent donc naturellement vers « un gros + plusieurs petits » plutôt que « plusieurs gros », sans qu'aucune règle ne le dise explicitement.

6. Le scaling par acte

Les quatre ennemis du bestiaire doivent rester crédibles pendant douze actes. Deux fonctions s'en chargent, et elles ont une forme particulière : un saut géométrique tous les deux actes, plus une petite rampe à l'intérieur du palier.

lib/game/systems/encounter_system.dartdart
  static const double _hpBracketGrowthRate = 1.35;
  static const double _dmgBracketGrowthRate = 1.25;
  static const double _hpIntraBracketStep = 0.05;
  static const double _dmgIntraBracketStep = 0.03;
  static const int _actBracketSize = 2;

  /// Which 2-act difficulty bracket this act falls in (0 for acts 1-2, 1 for acts 3-4, ...).
  static int getActBracket(int act) => ((act - 1) / _actBracketSize).floor();

  /// Position within the current 2-act bracket (0 to 1).
  static int getActPositionInBracket(int act) => (act - 1) % _actBracketSize;

  /// Combined act factor for HP: a geometric jump every 2 acts, plus a gentle
  /// ramp that resets each bracket. Replaces the old direct `(1 + 0.35*(act-1))`
  /// term, which double-counted the act inside `enemyLevel` as well.
  static double getHpActFactor(int act) {
    final bracket = getActBracket(act);
    final positionInBracket = getActPositionInBracket(act);
    final bracketMultiplier = pow(_hpBracketGrowthRate, bracket).toDouble();
    final intraBracketRamp = 1.0 + positionInBracket * _hpIntraBracketStep;
    return bracketMultiplier * intraBracketRamp;
  }

  /// Same as [getHpActFactor] but for damage, using the damage-specific rates.
  static double getDamageActFactor(int act) {
    final bracket = getActBracket(act);
    final positionInBracket = getActPositionInBracket(act);
    final bracketMultiplier = pow(_dmgBracketGrowthRate, bracket).toDouble();
    final intraBracketRamp = 1.0 + positionInBracket * _dmgIntraBracketStep;
    return bracketMultiplier * intraBracketRamp;
  }

La mécanique se lit en deux temps :

  • Le palier — getActBracket(act) = ((act − 1) / 2).floor() : les actes 1 et 2 sont dans le palier 0, les actes 3 et 4 dans le palier 1, etc. Le multiplicateur de palier est taux ^ palier, avec un taux de 1,35 pour les PV et de 1,25 pour les dégâts.
  • La rampe — getActPositionInBracket(act) = (act − 1) % 2 vaut 0 au premier acte du palier et 1 au second. Elle ajoute +5 % de PV et +3 % de dégâts au second acte du palier, puis se réinitialise au palier suivant.
Règle du jeu — un rythme en dents de scie contrôlé

Le joueur ressent la structure : le second acte d'un palier est une légère montée (+5 % PV), le passage au palier suivant est une marche nette (×1,35 / 1,05 ≈ ×1,286 par rapport à l'acte précédent). La progression alterne donc « respiration, marche, respiration, marche ». Les PV montent toujours plus vite que les dégâts : les combats s'allongent plus qu'ils ne deviennent létaux, ce qui laisse le temps de jouer son deck.

getEnemyLevel

getHpActFactor / getDamageActFactor

Seul endroit du code où l'acte influence les statistiques d'un ennemi.

Bonne pratique — une variable, un chemin

Quand une même entrée (ici l'acte) alimente deux facteurs qui se multiplient ensuite, la courbe réelle est le produit des deux et devient impossible à raisonner. La règle à retenir : chaque variable de difficulté ne doit avoir qu'un seul point d'entrée dans la chaîne de calcul. Le commentaire du code documente explicitement cette décision — c'est ce qui permet de ne pas réintroduire le bug six mois plus tard.

Quatre points de conception dans ces quinze lignes :

  • if (!kDebugMode) return; — kDebugMode vient de package:flutter/foundation.dart. C'est une constante de compilation : en build release, le compilateur Dart élimine tout le corps de la méthode (tree shaking). Le coût en production est nul, y compris celui de construire les chaînes de caractères.
  • Les codes ANSI colorent la sortie dans un vrai terminal. Dans la console de l'IDE, ils s'affichent parfois tels quels (\x1B[36m) : c'est normal, ce n'est pas un bug.
  • StringBuffer plutôt que des concaténations : un seul debugPrint à la fin, donc un bloc atomique qui ne sera pas entrelacé avec d'autres logs.
  • buildLine encadre chaque ligne d'un cadre ASCII de 76 caractères utiles. Attention : padRight complète mais ne tronque pas. Les deux lignes de formules les plus longues dépassent le cadre — le bord droit se décale. Cosmétique, mais surprenant la première fois.

Bonne pratique — un log qui ne peut pas mentir

La tentation classique est de recopier les formules dans le logger « pour éviter de trimballer sept paramètres ». Six mois plus tard, quelqu'un change 0.5 en 0.6 dans EncounterSystem et le log affiche sereinement l'ancienne valeur — on débogue alors une formule qui n'est plus exécutée. Ici, la valeur affichée est la valeur utilisée.

Une exception à cette règle : les colonnes HP et Dmg

La section GENERATED ENEMIES mélange deux sources. Le Combat Rating est recalculé sur place par EncounterSystem.calculateCombatRating, tandis que HP et Dmg réutilisent les multiplicateurs passés en paramètre :

lib/game/services/combat_debug_logger.dartdart
    for (var data in enemyDataList) {
      final rating = EncounterSystem.calculateCombatRating(
        data: data,
        enemyLevel: enemyLevel,
        act: act,
        isBoss: isBoss,
        isElite: isElite,
      );
      final enemyLine = '  - Enemy: ${data.nameEn} (Tier: ${data.tier}), HP: ${(data.maxHp * hpMultiplier).round()}, Dmg: ${(data.baseDamage * damageMultiplier).round()}, CR: $rating';
      buffer.writeln(buildLine(enemyLine, prefix: magenta, suffix: reset));
    }

Or calculateCombatRating commence par final bool isCustomBoss = data.id.startsWith('boss_'); et propage ce drapeau aux deux multiplicateurs. Les hpMultiplier et damageMultiplier reçus en paramètre, eux, viennent de ce calcul dans initializeCombat :

lib/game/controllers/combat_controller.dartdart
    final double hpMultiplier = EncounterSystem.getHpMultiplier(
      enemyLevel: enemyLevel,
      act: act,
      isBoss: isBoss,
      isElite: isElite,
    );

    final double damageMultiplier = EncounterSystem.getDamageMultiplier(
      enemyLevel: enemyLevel,
      act: act,
      isBoss: isBoss,
      isElite: isElite,
    );
Point d'attention — les colonnes HP et Dmg ignorent isCustomBoss

L'appel ci-dessus ne passe pas isCustomBoss : le paramètre garde sa valeur par défaut false, donc le multiplicateur boss de 3.0 est conservé. Ces deux double servent uniquement au logger. Juste en dessous, la boucle qui crée réellement les EnemyInstance recalcule enemyHpMultiplier et enemyDamageMultiplier avec isCustomBoss.

Sur un nœud boss contenant un ennemi préfixé boss_ (joueur niveau 3, acte 1, ennemi à 50 PV / 8 dégâts / tier 3 / 15 % crit), la ligne de log afficherait : HP: 186, Dmg: 28, CR: 81.2 — alors que l'ennemi réellement créé aurait 62 PV et 9 dégâts. Les colonnes HP et Dmg sont trois fois trop grandes, tandis que la colonne CR, elle, est correcte. Les trois chiffres d'une même ligne ne décrivent pas le même ennemi.

Le bug est latent : aucun ennemi de assets/data/enemies.json ne porte aujourd'hui un identifiant boss_, donc les deux calculs coïncident. Il se déclenchera au premier boss scripté ajouté. Correctif : dériver isCustomBoss par ennemi dans la boucle du logger, comme le fait déjà calculateCombatRating.

Piège — les flottants bruts

1.8584999999999998 au lieu de 1,8585, 145.6730769230769 au lieu de 145,673077 : le logger imprime les double sans formatage. Ce n'est pas une erreur de calcul, c'est la représentation binaire IEEE 754. Ne cherchez pas de bug là-dedans — mais évitez de comparer deux de ces valeurs avec == dans un test : utilisez closeTo(1.8585, 0.0001).

À retenir — la chaîne complète

Stats du joueur → playerPower → ratio à expectedPower → amortissement de moitié → baseBudget × modificateur × multiplicateur de nœud + rampe d'acte = budget. En face : bestiaire → filtre de tier → CR de chaque ennemi (tier, PV scalés, dégâts scalés, critique) → boucle d'achat plafonnée par maxEnemies → liste d'ennemis → instanciation avec les multiplicateurs de niveau, d'acte et de nœud → 5 actifs + file d'attente. Une seule ligne de constante à changer suffit à déplacer toute la courbe.

Quiz — vérifiez vos acquis

1. Un joueur atteint un powerRatio de 1,40. Quel powerModifier le système applique-t-il ?

  • 1,40 — le budget suit exactement la puissance du joueur
  • 1,80 — l'écart est doublé pour compenser le sur-investissement
  • 1,20 — seule la moitié de l'écart à la norme est répercutée
  • 0,70 — le budget est divisé par deux pour rééquilibrer
Réponse : powerModifier = 1.0 + (powerRatio - 1.0) * 0.5 dans calculateBudget, soit 1 + 0,40 × 0,5 = 1,20. L'amortissement de moitié fait que le sur-investissement reste rentable pour le joueur.

2. À l'acte 1, face à un joueur de niveau 1, sur un nœud de combat normal, quel est le Combat Rating du Squelette (22 PV, 8 dégâts, tier 2, 10 % de critique) ?

  • 41,5
  • 53,1
  • 56,1
  • 75,9
Réponse : les deux multiplicateurs valent 1,0 dans ce contexte, donc (2 × 15) + (22 / 4) + (8 × 2) × 1,10 = 30 + 5,5 + 17,6 = 53,1. Attention : le facteur de critique ne multiplie que le terme de dégâts, pas la somme entière.

3. Combien d'ennemis au maximum un nœud élite peut-il générer à l'acte 5 ?

  • 3
  • 5
  • 2
  • 1
Réponse : _maxEnemiesFromStep(5, 2) = 1 + ((5 - 1) / 2).floor() = 1 + 2 = 3. Un combat normal en autoriserait 5 (pas de 1) et un boss 1 (pas de 5).

4. Que vaut getHpActFactor(4) ?

  • 1,3500 — le palier 1 sans rampe
  • 2,0500 — 1,35 + 0,05 × 4
  • 1,8225 — 1,35 au carré
  • 1,4175 — 1,35 × 1,05
Réponse : l'acte 4 est dans le palier ((4 - 1) / 2).floor() = 1, en position (4 - 1) % 2 = 1. Le facteur vaut donc pow(1.35, 1) × (1 + 1 × 0.05) = 1,35 × 1,05 = 1,4175.

5. À partir de quel acte l'Orc Furieux (tier 3) peut-il apparaître, et pourquoi le plafond maxTierAuthored = 3 existe-t-il ?

  • Acte 6 ; le plafond empêche les boss d'être trop forts
  • Acte 3 ; le plafond limite le nombre d'ennemis par combat
  • Acte 11 ; le plafond évite de débloquer un tier 4 qui n'existe dans aucun fichier de données
  • Acte 15 ; le plafond correspond au nombre d'actes du jeu
Réponse : getUnlockedTier(act) = 1 + ((act - 1) / 5).floor() atteint 3 à l'acte 11. Sans le plafond, l'acte 16 renverrait 4 et le filtre enemy.tier <= unlockedTier attendrait un contenu tier 4 inexistant.

6. Dans la section GENERATED ENEMIES du CombatDebugLogger, quelle divergence existe entre les colonnes HP/Dmg et la colonne CR ?

  • Aucune : les trois valeurs viennent du même appel à calculateCombatRating
  • HP et Dmg utilisent des multiplicateurs calculés sans isCustomBoss (donc avec le ×3 boss), alors que le CR le prend en compte
  • Le CR est arrondi à l'entier alors que HP et Dmg restent des double
  • HP et Dmg incluent le nodeMultiplier du budget, pas le CR
Réponse : initializeCombat calcule hpMultiplier et damageMultiplier sans passer isCustomBoss (valeur par défaut false, donc multiplicateur boss 3.0), alors que calculateCombatRating le dérive lui-même de data.id.startsWith('boss_'). Sur un boss custom, la ligne afficherait 186 PV au lieu des 62 réellement instanciés.
