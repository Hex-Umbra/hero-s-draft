Chapitre 12

La carte du monde procédurale

Chaque acte génère un graphe orienté acyclique de dix étages. Ce chapitre suit l'algorithme des quatre étapes qui le construit, puis les règles qui décident où le joueur peut aller.

Dans un roguelike, la carte n'est pas un décor : c'est la structure de décision du jeu. Elle décide combien de combats le joueur devra encaisser avant de trouver une boutique, s'il pourra éviter une élite, et à quel moment il aura le droit de se reposer. Si elle est mal générée, tout le reste du jeu déraille : un joueur qui tombe sur cinq combats d'affilée sans repos meurt sans avoir joué mal.

Hero's Draft ne stocke aucune carte prédéfinie. À chaque nouvel acte, un algorithme reconstruit un graphe complet. Le point d'entrée tient en cinquante lignes, lib/services/map_generator_service.dart, mais il délègue à quatre classes spécialisées qui font chacune un travail bien délimité. Ce chapitre les prend une par une, puis remonte jusqu'à l'écran qui affiche le résultat.

Un graphe, pas une grille

Les nœuds ne sont pas alignés : chaque étage a sa propre largeur, tirée au hasard entre 2 et 5.

Dirigé et acyclique

Une connexion va toujours de l'étage y vers l'étage y + 1. On ne redescend jamais.

Quatre étapes

Nœuds, connexions, quotas, contenus spéciaux — dans cet ordre, jamais mélangées.

Régénérée par acte

Battre un boss détruit la carte courante et en génère une neuve pour l'acte suivant.

1. Le modèle MapNode

Avant l'algorithme, la donnée. Tout ce que la carte connaît d'un point d'intérêt tient dans une seule classe, lib/models/map_node.dart. Elle est volontairement pauvre : pas de logique, pas de méthode de gameplay, seulement neuf champs et la sérialisation JSON pour la sauvegarde.

L'identifiant n'est pas un UUID ni un compteur global : c'est une coordonnée déguisée en chaîne. Il est fabriqué à un seul endroit, dans la double boucle du générateur de nœuds.

Cette convention n'est pas décorative : plusieurs endroits du code s'en servent comme d'une information métier. Et l'interface s'en sert pour reconnaître l'étage de départ sans avoir à parcourir la liste : node.id.startsWith('node_0_') apparaît trois fois dans map_screen.dart et une fois dans map_path_highlighter.dart. C'est un raccourci commode, mais notez qu'il crée un couplage : renommer le préfixe casserait silencieusement la détection de l'étage 0.

Un DAG orienté du bas vers le haut

« DAG » veut dire Directed Acyclic Graph : graphe orienté sans cycle. C'est le commentaire même du code : Generates a procedural map as a Directed Acyclic Graph. La propriété est garantie par construction, pas par une vérification a posteriori — le constructeur de connexions ne relie jamais qu'un nœud de l'étage y à un nœud de l'étage y + 1. Il est donc impossible de revenir sur ses pas ou de tourner en rond.

Règle du jeu — la structure imposée

Sur une carte de dix étages, quatre étages ne sont jamais aléatoires :

Étage 0 — uniquement des combats (le tirage renvoie combat de force quand floor == 0). Étage 5 (le milieu, floors ~/ 2) — un seul nœud, toujours une Élite : c'est le goulot d'étranglement, tout le monde passe par là. Étage 8 (floors - 2) — que des Repos, pour souffler avant le boss. Étage 9 (floors - 1) — exactement trois Boss, un par type de récompense. Le joueur choisit sa récompense en choisissant son boss.

Le sens vertical mérite une précision, parce qu'il est contre-intuitif : l'étage 0 est en bas de l'écran et le boss en haut. C'est la formule de position qui inverse l'axe, on y revient à la section 3.

2. Vue d'ensemble de la génération

Le point d'entrée est une méthode statique unique. Elle ne contient aucune logique : elle orchestre quatre appels, dans un ordre qui n'est pas interchangeable.

lib/services/map_generator_service.dartdart
class MapGeneratorService {
  static final Random _random = Random();

  /// Generates a procedural map as a Directed Acyclic Graph.
  /// [floors] is the height of the map.
  /// [maxWidth] is the maximum number of nodes per floor.
  static List<MapNode> generateMap({int floors = 10, int maxWidth = 5, int act = 1}) {
    final middleFloor = floors ~/ 2;

    // 1. Create nodes for each floor
    final nodesByFloor = MapNodeGenerator.generateRawNodes(
      floors: floors,
      maxWidth: maxWidth,
      middleFloor: middleFloor,
      random: _random,
    );

    // Flatten all nodes
    List<MapNode> allNodes = [];
    for (var floor in nodesByFloor) {
      allNodes.addAll(floor);
    }

    // 2. Create connections between floors
    MapConnectionBuilder.buildConnections(
      nodesByFloor: nodesByFloor,
      floors: floors,
      random: _random,
    );

    // 3. Balance quotas and apply anti-repetition rules
    MapValidator.optimizeMapTypes(
      allNodes: allNodes,
      floors: floors,
      random: _random,
    );

    // 4. Place special events
    MapContentPlacer.placeSpecialEvents(
      allNodes: allNodes,
      act: act,
      random: _random,
    );

    return allNodes;
  }
}

Trois détails de cette méthode valent qu'on s'y arrête.

Le paramètre middleFloor est calculé ici, pas dans les sous-classes. floors ~/ 2 est une division entière (l'opérateur ~/ de Dart) : avec floors = 10, elle donne 5. Cette valeur est passée explicitement au générateur de nœuds, mais MapValidator, lui, la recalcule localement quatre fois dans son propre fichier. Duplication bénigne aujourd'hui — les deux calculs sont identiques — mais c'est le genre de chose qui diverge le jour où quelqu'un change la règle.

La liste plate et la liste par étages pointent sur les mêmes objets. C'est un point fondamental de Dart, et un piège classique pour qui vient d'un langage à valeur. Après allNodes.addAll(floor), on n'a pas copié les nœuds : on a copié des références. Quand l'étape 2 ajoute des connexions via nodesByFloor, l'effet est immédiatement visible dans allNodes. C'est précisément ce qui permet à l'étape 2 de travailler par rangées (elle a besoin de la structure en étages) et aux étapes 3 et 4 de travailler à plat (elles ont besoin de compter globalement).

Le Random est statique, partagé, et non initialisé avec une graine. static final Random _random = Random(); : une seule instance pour toute la durée de vie de l'application, sans seed. Conséquence directe : il n'existe aucun moyen de rejouer une carte. Deux parties lancées avec les mêmes réglages donneront deux graphes différents, et un bug de génération ne peut pas être reproduit à l'identique.

Point d'attention — pas de graine, pas de reproductibilité

Ajouter un paramètre int? seed à generateMap et construire Random(seed) quand il est fourni coûterait trois lignes, et permettrait à la fois d'écrire des tests déterministes sur la génération et de proposer un mode « graine partagée » aux joueurs. En l'état, tout test sur la carte doit se contenter d'assertions statistiques (« il y a entre 12 et 22 combats ») plutôt que d'égalités exactes.

L'ordre des étapes est contraint par les dépendances. L'étape 3 a besoin des connexions (la règle anti-répétition remonte les prédécesseurs, donc les arêtes). L'étape 4 doit passer après l'équilibrage, sans quoi les nœuds convertis en relicExchange ou forgeFusion seraient recomptés par les quotas — or ces deux types n'ont pas d'entrée dans la table des quotas et seraient traités comme des types en excès permanent.

3. Étape 1 — fabriquer les nœuds

MapNodeGenerator produit une List<List<MapNode>> : une liste de rangées. Deux boucles imbriquées, y pour l'étage et x pour la position dans la rangée. Commençons par la largeur.

La largeur d'une rangée

lib/services/map/map_node_generator.dartdart
for (int y = 0; y < floors; y++) {
  List<MapNode> floorNodes = [];
  int rowWidth = 2 + random.nextInt(maxWidth - 1); // 2 to maxWidth nodes

  // Special case: Chokepoint at middle floor
  if (y == middleFloor) {
    rowWidth = 1;
  }

  // Special case: Boss floor always has 3 nodes
  if (y == floors - 1) {
    rowWidth = 3;
  }

Décomposons 2 + random.nextInt(maxWidth - 1). En Dart, nextInt(n) renvoie un entier de 0 inclus à n exclu. Avec maxWidth = 5, on a nextInt(4), donc une valeur dans {0, 1, 2, 3}, et rowWidth dans {2, 3, 4, 5}. Le commentaire « 2 to maxWidth » est donc exact, et les quatre largeurs sont équiprobables (25 % chacune).

Les deux cas particuliers sont écrits en if séparés, pas en else if : si un jour middleFloor valait floors - 1, le second gagnerait. Avec floors = 10, middleFloor = 5 et l'étage boss est le 9 : aucun conflit.

Le tirage du type

lib/services/map/map_node_generator.dartdart
static MapNodeType getRandomNodeType(int floor, int totalFloors, Random random) {
  if (floor == 0) return MapNodeType.combat; // Start with combat

  double r = random.nextDouble();
  if (r < 0.6) return MapNodeType.combat; // 60% Combat
  if (r < 0.75) return MapNodeType.event; // 15% Event
  if (r < 0.85) return MapNodeType.shop; // 10% Shop
  if (r < 0.95) return MapNodeType.rest; // 10% Rest
  return MapNodeType.elite; // 5% Elite
}

C'est le patron classique de la roulette cumulative : un seul tirage nextDouble() dans [0, 1[, comparé à des seuils croissants. Chaque intervalle a une largeur égale à la probabilité du type correspondant. C'est plus rapide et plus lisible que de tirer un entier sur 100.

Deux remarques honnêtes sur cette fonction. D'abord, le paramètre totalFloors n'est jamais utilisé dans le corps : il est passé, ignoré, et conservé sans doute pour un usage futur (moduler les probabilités selon la hauteur). Sans importance ici, mais c'est exactement le genre de détail qui rend une génération non reproductible même avec une graine fixe si on refactorise l'ordre des appels.

L'étage boss illustre bien la logique de design du jeu : les trois boss sont mécaniquement identiques, seule change la récompense. Le joueur choisit donc sa récompense en choisissant sa colonne — et comme les connexions de l'étage 8 ne mènent pas forcément aux trois, ce choix est partiellement contraint par le chemin emprunté plus bas.

Piège — le nom doubleXp ment

Le libellé affiché dans la légende est Boss (XP & Or x2) et l'enum s'appelle doubleXp, mais lib/game/controllers/reward_controller.dart applique totalXp *= 3; et totalGold *= 3;. C'est un triplement, pas un doublement. Ne vous fiez jamais au nom d'une constante quand vous équilibrez : allez lire l'endroit qui l'utilise.

Le champ bossEnemyId, lui, est déclaré dans la boucle (String? bossEnemyId;), passé au constructeur… et jamais assigné. Il vaut donc null sur tous les nœuds générés. Ce n'est pas anodin : le côté consommateur existe bel et bien, dans lib/ui/screens/game_screen.dart, qui lit currentNode.bossEnemyId et le transmet à initializeCombat. Le mécanisme de « boss imposé » est donc câblé de bout en bout, mais aucune carte ne l'active aujourd'hui.

4. Étape 2 — tisser les connexions

À la sortie de l'étape 1, les nœuds existent mais leur liste connections est vide : la carte est un nuage de points. MapConnectionBuilder parcourt les étages deux à deux et relie chaque rangée à la suivante.

lib/services/map/map_connection_builder.dartdart
for (int y = 0; y < floors - 1; y++) {
  List<MapNode> currentFloor = nodesByFloor[y];
  List<MapNode> nextFloor = nodesByFloor[y + 1];

  for (int i = 0; i < currentFloor.length; i++) {
    MapNode node = currentFloor[i];

    // Ensure each node has at least one connection
    // Connect to nodes within a certain range to avoid long horizontal lines
    int nextIndexBase = (i * nextFloor.length / currentFloor.length).floor();

    // Connect to 1 or 2 nodes in the next floor
    int numConnections = 1 + random.nextInt(2);
    Set<int> targets = {};

    for (int j = 0; j < numConnections; j++) {
      int offset = random.nextInt(3) - 1; // -1, 0, or 1
      int targetIdx = (nextIndexBase + offset).clamp(
        0,
        nextFloor.length - 1,
      );
      targets.add(targetIdx);
    }

    for (int targetIdx in targets) {
      node.connections.add(nextFloor[targetIdx].id);
    }
  }

La boucle externe s'arrête à floors - 1 exclu : le dernier étage n'est jamais une source. Les trois nœuds boss ont donc une liste connections vide, ce qui aura une conséquence très concrète sur l'accessibilité (section 7).

nextIndexBase : la projection proportionnelle

C'est la ligne la plus importante du fichier. Elle répond à la question : « le i-ième nœud d'une rangée de n nœuds, à quel nœud d'une rangée de m nœuds correspond-il ? » La réponse est une règle de trois, arrondie vers le bas : (i × m / n).floor().

Prenons une rangée de 3 nœuds sous une rangée de 2 :

illustrationtext
currentFloor.length = 3, nextFloor.length = 2

i = 0  ->  (0 * 2 / 3).floor() = (0.000).floor() = 0
i = 1  ->  (1 * 2 / 3).floor() = (0.667).floor() = 0
i = 2  ->  (2 * 2 / 3).floor() = (1.333).floor() = 1

Sans cette projection, un nœud de l'index 4 d'une rangée large pourrait se connecter à l'index 4 d'une rangée étroite qui n'existe pas, ou tirer un trait qui traverse toute la carte à l'horizontale — le commentaire du code le dit explicitement : to avoid long horizontal lines. Le décalage random.nextInt(3) - 1 ajoute ensuite -1, 0 ou +1 à cette base, avec des chances égales, puis .clamp(0, nextFloor.length - 1) ramène le résultat dans les bornes de la rangée cible.

À retenir — pourquoi un Set

Set<int> targets = {} déduplique les cibles. Quand numConnections vaut 2, les deux tirages peuvent produire le même index (par exemple deux fois l'offset 0, ou deux offsets différents ramenés à la même valeur par le clamp). Dans ce cas le Set n'en garde qu'un et le nœud n'a qu'une seule connexion. Autrement dit : « 1 ou 2 connexions » est une intention, pas une garantie de 2 — les nœuds de bord, dont l'offset est souvent écrasé par le clamp, sont statistiquement plus pauvres en arêtes.

La passe de rattrapage

Le tirage aléatoire ne garantit rien : un nœud de l'étage supérieur peut très bien n'être visé par personne. Il serait alors visible sur la carte mais inatteignable — un cul-de-sac inversé. La seconde boucle corrige ce cas.

    if (!reachable) {
      // Connect the closest node from current floor
      int sourceIdx = (j * currentFloor.length / nextFloor.length).floor();
      currentFloor[sourceIdx].connections.add(nextFloor[j].id);
    }
  }

C'est la même règle de trois, mais dans l'autre sens : on part de l'index j dans la rangée cible et on projette vers la rangée source. Le nœud choisi reçoit une arête supplémentaire, qui peut lui en faire trois. Cette passe est ce qui garantit l'invariant central du graphe : tout nœud d'un étage supérieur à 0 a au moins un prédécesseur, et tout nœud d'un étage inférieur au dernier a au moins un successeur. Le graphe est donc entièrement connecté de l'étage 0 à l'étage 9, sans îlot.

Sur ce petit graphe, remarquez que node_0_0 et node_0_1 mènent tous les deux à node_1_0. C'est normal et fréquent : les chemins fusionnent et se rouvrent constamment. Sur une vraie carte de dix étages, l'étage 5 fusionne tous les chemins en un seul nœud, puis le graphe se rouvre.

5. Étape 3 — équilibrer les quotas

Avec un tirage à 60 % de combats, une carte brute est presque toujours mauvaise : trop de combats, pas assez de boutiques, parfois zéro élite en dehors du chokepoint. L'étape 3 corrige le tirage après coup, en réécrivant des types jusqu'à ce que la répartition rentre dans des bornes définies à la main.

La boucle principale

lib/services/map/map_validator.dartdart
static void optimizeMapTypes({
  required List<MapNode> allNodes,
  required int floors,
  required Random random,
}) {
  for (int iter = 0; iter < 15; iter++) {
    balanceQuotas(allNodes: allNodes, floors: floors, random: random);

    bool changedAny = false;
    for (var node in allNodes) {
      if (node.type == MapNodeType.elite || node.type == MapNodeType.rest) {
        if (hasThreeConsecutive(node, allNodes, node.type, 1)) {
          final chain = getChainOfThree(node, allNodes, node.type);
          for (var chainNode in chain) {
            final y = chainNode.floor;
            final middleFloor = floors ~/ 2;
            if (y != 0 && y != middleFloor && y != floors - 2 && y != floors - 1) {
              final choices = [MapNodeType.combat, MapNodeType.shop, MapNodeType.event];
              chainNode.type = choices[random.nextInt(choices.length)];
              changedAny = true;
              break;
            }
          }
          if (changedAny) break;
        }
      }
    }

    if (!changedAny) break;
  }
  balanceQuotas(allNodes: allNodes, floors: floors, random: random);
}

La structure est un cycle équilibrer puis corriger, répété au plus 15 fois. À chaque tour, on rééquilibre les quotas, puis on cherche une seule violation de la règle anti-répétition et on la casse. Les deux break imbriqués font que l'itération s'arrête dès la première correction : on ne casse jamais deux chaînes dans le même tour, parce que la première correction a pu invalider les quotas et qu'il faut donc repasser par balanceQuotas.

La sortie anticipée if (!changedAny) break; est la condition de convergence : si un tour complet ne trouve plus rien à corriger, la carte est bonne, on arrête. Et quel que soit le chemin de sortie, un dernier balanceQuotas est exécuté après la boucle — parce que la dernière correction anti-répétition a pu, elle aussi, déséquilibrer les compteurs.

Les quatre étages verrouillés apparaissent en clair dans la condition : y != 0 && y != middleFloor && y != floors - 2 && y != floors - 1. C'est-à-dire les étages 0, 5, 8 et 9. Cette même condition est répétée quatre fois dans balanceQuotas, à l'identique. C'est la duplication la plus visible du fichier ; une petite fonction bool _isLocked(int y, int floors) ferait le travail.

balanceQuotas : combler, puis raboter

Chaque tentative recompte tout depuis zéro, puis effectue au plus une seule conversion avant de repartir avec continue. C'est volontairement naïf — recompter 40 nœuds cent fois ne coûte rien — mais cela rend l'algorithme facile à suivre : un tour, un changement.

La recherche d'un candidat à convertir applique deux filtres. D'abord l'étage ne doit pas être verrouillé. Ensuite, et c'est plus subtil, le type actuel du candidat doit être en surnombre par rapport à son propre minimum : if ((counts[currentType] ?? 0) > currentMin). Sans ce test, combler le déficit d'un type creuserait celui d'un autre et l'algorithme oscillerait indéfiniment.

Voilà un patron qui vaut d'être reconnu : appliquer, tester, annuler. On écrit provisoirement le nouveau type, on vérifie que la carte reste valide, puis on restaure l'ancien avant même d'avoir décidé. Le nœud n'est réellement converti que plus loin, une fois élu candidat (candidate.type = deficientType;). C'est une simulation à coût nul, possible uniquement parce que type n'est pas final.

La seconde moitié de balanceQuotas est le miroir de la première : on cherche un type en excès, on cherche un type d'accueil qui n'a pas encore atteint son maximum (counts[type] < max && type != excessiveType), et on convertit un nœud de l'un vers l'autre — toujours avec le même essai-annulation contre la règle des trois d'affilée.

Point d'attention — le repli qui accepte la violation

Les deux moitiés se terminent par un bloc explicite : Fallback: if no candidate avoids violation, take any valid candidate. Autrement dit, les quotas priment sur la règle anti-répétition. Comme optimizeMapTypes se termine par un balanceQuotas final dont le résultat n'est plus vérifié, une carte livrée peut contenir trois Repos ou trois Élites d'affilée. C'est rare, mais ce n'est pas impossible — et si vous observez ce cas en jeu, ce n'est pas un bug de tirage, c'est ce repli.

La règle des trois d'affilée

lib/services/map/map_validator.dartdart
static bool hasThreeConsecutive(
  MapNode node,
  List<MapNode> allNodes,
  MapNodeType targetType,
  int currentChainLength,
) {
  if (node.type != targetType) {
    return false;
  }
  if (currentChainLength == 3) {
    return true;
  }

  final predecessors = allNodes.where((n) => n.connections.contains(node.id)).toList();
  for (var pred in predecessors) {
    if (pred.type == targetType) {
      if (hasThreeConsecutive(pred, allNodes, targetType, currentChainLength + 1)) {
        return true;
      }
    }
  }
  return false;
}

La récursion remonte le graphe à contre-courant. Un prédécesseur, c'est n'importe quel nœud dont la liste connections contient l'identifiant du nœud courant — et comme les arêtes ne vont que vers le haut, un prédécesseur est forcément à l'étage inférieur. Le compteur currentChainLength démarre à 1 (le nœud lui-même) et s'incrémente d'un cran par étage descendu ; il atteint 3 quand on a trouvé le nœud, son parent et son grand-parent tous du même type.

La terminaison est garantie par deux mécanismes indépendants : la profondeur est bornée par la condition currentChainLength == 3, et le parcours ne peut de toute façon pas boucler puisqu'il descend strictement d'un étage à chaque appel. Pas besoin d'ensemble de nœuds visités.

Il faut bien lire ce que la règle interdit : trois nœuds du même type sur un même chemin du graphe, pas trois sur trois étages consécutifs. Deux Repos côte à côte sur le même étage ne violent rien, tant qu'aucun chemin ne les enfile. Et la règle ne concerne que elite et rest : rien n'empêche cinq combats à la suite.

getChainOfThree reconstruit la chaîne fautive pour que l'appelant sache quels nœuds sont candidats à la correction. Sa logique est délibérément plus simple que celle de hasThreeConsecutive : elle prend le first prédécesseur du bon type, deux fois de suite, sans exploration. Sur un graphe où plusieurs chaînes se croisent, elle peut donc renvoyer une chaîne différente de celle qui a déclenché la détection — l'appelant modifie alors un nœud qui ne résout pas forcément la violation détectée. La boucle des 15 itérations rattrape ce cas au tour suivant.

Point d'attention — des quotas parfois mathématiquement impossibles

La somme des minimums vaut 12 + 3 + 3 + 2 + 4 = 24 nœuds non-boss. Or une carte étroite ne compte que 20 nœuds au total, dont 3 boss : il ne reste que 17 nœuds à répartir pour 24 exigés. Dans ce cas, balanceQuotas épuise ses candidats, tombe sur break et rend la main avec des quotas non satisfaits. L'algorithme ne plante pas et ne signale rien — il fait de son mieux. Retenez donc que nodeQuotas est une cible, pas un contrat.

6. Étape 4 — placer les contenus spéciaux

Les deux derniers types de nœuds n'existent pas dans le tirage initial et ne sont pas comptés par les quotas. Ils sont greffés à la fin, sur des nœuds déjà validés, par MapContentPlacer. C'est le seul endroit du pipeline où le paramètre act intervient.

L'Autel des reliques

La Forge de fusion

La forge est plus prudente que l'autel : elle n'écrase qu'un combat ou un event. Les types précieux — boutique, repos, élite — sont protégés. Le filtre d'étages floor >= 3 && floor <= 7 couvre nominalement cinq étages, mais l'étage 5 est le chokepoint et vaut toujours elite : il ne passe donc jamais le test de type. En pratique, la forge n'apparaît que sur les étages 3, 4, 6 et 7.

L'ordre des deux blocs a un effet concret : l'autel est placé en premier. Si sa cible était un combat de l'étage 3, ce nœud devient relicExchange et n'est plus éligible à la forge. Les deux contenus spéciaux ne peuvent donc jamais atterrir sur le même nœud.

À retenir — combien de nœuds spéciaux au maximum

Chaque bloc place au plus un nœud, et il n'y a que deux blocs. Une carte contient donc au grand maximum un autel et une forge. À l'acte 5, la configuration la plus riche possible est : un autel garanti, plus une forge avec 25 % de chances.

Le rôle de originalType

Les deux blocs partagent le même geste, dans le même ordre : chosenNode.originalType = chosenNode.type; puis chosenNode.type = MapNodeType.forgeFusion;. On archive avant d'écraser. originalType conserve donc la mémoire de ce que le nœud aurait dû être : un combat devenu forge se souvient qu'il était un combat. L'information survit à la sauvegarde, puisque toJson écrit 'originalType': originalType?.name et que fromJson la relit.

Point d'attention — un champ écrit mais jamais lu

Une recherche sur originalType dans tout lib/ ne renvoie que quatre familles d'occurrences : la déclaration dans map_node.dart, la sérialisation JSON, les deux écritures de map_content_placer.dart, et… une variable locale du même nom dans map_validator.dart, qui n'a aucun rapport (c'est le final originalType = node.type; du patron appliquer-tester-annuler). Aucun écran, aucun contrôleur ne lit le champ. L'information est produite et persistée pour rien.

Ce n'est pas forcément à supprimer : le champ prépare des fonctionnalités évidentes — afficher « Forge (anciennement Combat) » dans l'infobulle, ou revenir au contenu d'origine si le joueur refuse l'échange. Mais tant que personne ne le lit, c'est une donnée morte qu'il faut connaître pour ne pas la croire active.

completeCurrentNode — le point de bascule

/// Marque le nœud actuel comme complété
void completeCurrentNode() {
  if (controller.currentState.currentNodeId == null) return;

  MapNode? completedNode;
  final updatedNodes = controller.currentState.mapNodes.map((node) {
    if (node.id == controller.currentState.currentNodeId) {
      node.isCompleted = true;
      completedNode = node;
    }
    return node;
  }).toList();

  // Reset de l'armure et nettoyage des statuts à la fin du combat pour préserver les passifs
  controller.updateState(
    controller.currentState.copyWith(
      mapNodes: updatedNodes,
      heroStats: controller.currentState.heroStats.copyWith(armure: 0, statuses: []),
    ),
  );

  if (completedNode != null && completedNode!.type == MapNodeType.boss) {
    advanceToNextWorld();
  }

  ref.read(checkpointProvider.notifier).bump();
}

Cette méthode fait quatre choses, dans cet ordre :

  1. Marquer le nœud. Le map(...) ne crée pas de nouveaux nœuds : il mute node.isCompleted en place et renvoie la même référence. Le .toList() produit une nouvelle liste, ce qui suffit à faire réagir Riverpod, mais les objets sont partagés. C'est cohérent avec le choix de laisser isCompleted mutable, même si un observateur strict de l'immuabilité tiquerait.
  2. Nettoyer le héros. heroStats.copyWith(armure: 0, statuses: []) : l'armure gagnée pendant un combat ne se reporte jamais sur le suivant, et les effets de statut (poison, buffs) sont vidés. Le commentaire précise l'intention : préserver les passifs, qui eux vivent ailleurs.
  3. Enchaîner sur l'acte suivant si c'était un boss. Le test porte sur le type du nœud, capturé dans la fermeture pendant le map.
  4. Signaler un point de sauvegarde. checkpointProvider.notifier.bump() incrémente un simple entier ; un ref.listen déclare ailleurs déclenche SaveService.save. La sauvegarde n'est donc jamais appelée directement par le gameplay, ce qui évite d'avoir à y penser dans chaque écran.

_isNodeAvailable : la règle d'accessibilité

C'est la fonction qui décide, pour chaque nœud affiché, s'il est cliquable, en pleine opacité, et avec un curseur « main ». Elle est appelée une fois par nœud à chaque reconstruction de l'écran.

lib/ui/screens/map_screen.dartdart
bool _isNodeAvailable(
  MapNode node,
  List<MapNode> allNodes,
  String? currentNodeId,
) {
  final runState = ref.read(runProvider);
  if (runState.pendingDrafts > 0) return false;

  if (currentNodeId == null) {
    return node.id.startsWith('node_0_');
  }

  try {
    final currentNode = allNodes.firstWhere((n) => n.id == currentNodeId);

    // Si le nœud actuel n'est pas complété, on ne peut pas avancer.
    // Seul le nœud actuel lui-même est actif afin de pouvoir y ré-entrer.
    if (!currentNode.isCompleted) {
      return node.id == currentNodeId;
    }

    return currentNode.connections.contains(node.id);
  } catch (e) {
    // Cas de repli si le noeud actuel n'est plus dans la liste (ex: changement d'acte mal synchronisé)
    return node.id.startsWith('node_0_');
  }
}

Quatre règles, évaluées dans l'ordre. Prenons-les une par une.

1. pendingDrafts > 0 → toute la carte est gelée. pendingDrafts compte les montées de niveau non consommées : chaque niveau gagné donne droit à un draft de carte. Tant que le joueur n'a pas fait ses choix, aucun nœud n'est disponible. Ce n'est pas la seule barrière — _onNodeTap commence par le même test, et un LevelUpOverlay est affiché par-dessus la carte — mais c'est la barrière visuelle : tous les nœuds passent à 20 % d'opacité, ce qui rend le blocage évident au lieu d'un clic qui ne fait rien.

2. currentNodeId == null → seul l'étage 0 est ouvert. C'est l'état de départ d'un acte, celui que produisent startNewRun (currentNodeId: null) et advanceToNextWorld (resetCurrentNode: true). Le joueur n'est encore nulle part sur la carte : le pion n'est même pas affiché, puisque le Stack ne le construit que if (currentNodeId != null). Tous les nœuds dont l'identifiant commence par node_0_ sont cliquables, et le joueur choisit sa colonne de départ.

3. Nœud courant non complété → seul lui-même est actif. C'est le cas le plus subtil, et le commentaire du code l'assume : « Seul le nœud actuel lui-même est actif afin de pouvoir y ré-entrer ». Le joueur a cliqué sur un nœud (donc travelToNode a écrit currentNodeId) mais n'a pas terminé ce qu'il y avait à faire. Aucun successeur n'est ouvert — on ne saute pas une étape — mais le nœud courant reste cliquable pour y revenir.

4. Nœud courant complété → ses successeurs, et rien d'autre. currentNode.connections.contains(node.id). Notez ce que cette ligne implique : le nœud courant lui-même n'est plus disponible une fois complété (il n'est pas dans sa propre liste de connexions), et aucun nœud d'un étage antérieur ne l'est non plus. Il n'y a pas de retour en arrière.

Piège — on peut re-rentrer dans un nœud non complété

Rien n'oblige un écran à appeler completeCurrentNode(). Si le joueur quitte une boutique ou un repos par le geste de retour du système au lieu du bouton « quitter », le nœud reste isCompleted == false alors que currentNodeId pointe déjà dessus. De retour sur la carte, la règle 3 s'applique : un seul nœud est cliquable, celui où il se trouve. Le joueur doit le refaire pour continuer.

Concrètement, cela veut dire qu'une boutique peut être ré-ouverte et un repos re-consommé tant qu'ils n'ont pas été validés. Ce n'est pas un blocage — le jeu reste jouable — mais c'est une porte d'exploitation à connaître. Le même mécanisme est aussi ce qui sauve la partie après une reprise de sauvegarde en plein milieu d'un nœud : l'état est cohérent, le joueur reprend là où il en était.

Le try / catch final mérite un mot. firstWhere lève une StateError quand aucun élément ne correspond ; ici, cela signifie que currentNodeId désigne un nœud absent de mapNodes. Le commentaire cite le cas d'un changement d'acte mal synchronisé. Le repli — rouvrir l'étage 0 — est le bon choix : il rend la carte de nouveau jouable plutôt que de la figer sur une exception. Mais notez qu'il est silencieux : aucun debugPrint, contrairement à RunState.currentNodeType qui, lui, journalise le même incident.

Règle du jeu — comment on quitte un acte

Les trois nœuds de l'étage 9 n'ont aucune connexion sortante : la boucle de construction s'arrête à floors - 1. Si l'on s'en tenait à _isNodeAvailable, terminer un boss laisserait le joueur sur une carte où plus rien n'est cliquable. C'est completeCurrentNode qui débloque la situation en appelant advanceToNextWorld, lequel remplace mapNodes et remet currentNodeId à null — ce qui fait retomber la règle 2 et rouvre l'étage 0 du nouvel acte. La progression entre actes n'est donc pas une transition d'écran : c'est un simple effet de bord de la complétion d'un nœud.

Le calcul est du placement de caméra classique : on convertit la position du nœud cible en coordonnées du conteneur (d'où les + 1000 de padding et le + 80.0 de décalage visuel), on la multiplie par l'échelle, et on translate de façon à ce qu'elle tombe au centre de l'écran.

Le champ int? _lastActCentered mémorise le dernier acte recentré. La méthode est appelée à chaque build, via addPostFrameCallback, mais elle sort immédiatement si l'acte n'a pas changé. Sans ce garde, la caméra se replacerait de force à chaque reconstruction et le joueur ne pourrait littéralement pas déplacer la carte. La conséquence de ce choix est visible en jeu : la caméra ne suit pas le joueur d'un nœud à l'autre. Elle cadre une fois au début de l'acte, et c'est ensuite au joueur de faire défiler.

Notez le cas currentNodeId == null : on cible 500.0 en dur, c'est-à-dire le centre de la largeur de 1000, plutôt que la position du nœud trouvé. C'est cohérent — au début d'un acte, on veut voir toute la rangée de départ, pas se coller sur son premier nœud.

Point d'attention — ce défilement ignore les bornes

Écrire directement dans _transformationController.value court-circuite la logique de InteractiveViewer, qui n'applique ses contraintes (boundaryMargin, minScale, maxScale) que dans ses propres gestionnaires de gestes. Rien ne borne newY : à la molette, on peut sortir la carte de l'écran bien au-delà de ce qu'un glisser-déposer permettrait. Un clamp sur newY, dérivé de la hauteur du conteneur et de l'échelle, corrigerait le comportement.

Bonne pratique — le commentaire qui explique le contournement

Clamped math-based dashes to prevent WASM path allocation heap leak. L'approche naturelle en Flutter (construire un Path par tiret, à chaque frame, pour chaque arête) provoquait une fuite mémoire à la compilation WebAssembly. Le code trigonométrique brut est moins élégant, mais le commentaire dit pourquoi il existe — sans lui, un développeur bien intentionné « simplifierait » ce bloc et réintroduirait le bug. Le + 80.0 ajouté à chaque position.y est le même décalage vertical qu'on retrouve dans MapNodeWidget (top: widget.node.position.y - 35 + 80.0), dans PlayerPawn (top: position.y - 65 + 80.0) et dans le calcul de caméra. C'est une constante magique répétée quatre fois dans trois fichiers : la sortir dans GameConstants économiserait une soirée de débogage le jour où quelqu'un la change à trois endroits sur quatre.

Enfin, le painter enveloppe sa recherche de nœud cible dans un try / catch qui journalise en mode debug uniquement : une connexion pointant vers un identifiant inconnu est ignorée au lieu de faire planter le rendu. Utile pour survivre au chargement d'une sauvegarde produite par une version antérieure du générateur.

La surbrillance du chemin

Au survol d'un nœud, la carte illumine tout le trajet qui y mène depuis la position du joueur. Le calcul est isolé dans un service sans état, lib/game/services/map_path_highlighter.dart.

lib/game/services/map_path_highlighter.dartdart
static bool findPathToCurrent(
  String targetId,
  String? startId,
  List<MapNode> allNodes,
  Set<String> pathNodes,
  Set<(String, String)> pathConnections,
) {
  // Si on a atteint le point de départ (ou l'étage 0 si on n'a pas commencé)
  if (targetId == startId ||
      (startId == null && targetId.startsWith('node_0_'))) {
    pathNodes.add(targetId);
    return true;
  }

  // Trouver tous les parents (noeuds de l'étage précédent qui pointent vers targetId)
  bool foundPath = false;

  // Optimisation : seuls les noeuds de l'étage précédent peuvent être parents
  final targetNode = allNodes.firstWhere((n) => n.id == targetId);
  final targetFloor = targetNode.floor;
  if (targetFloor == 0) return false;

  final parents = allNodes.where((n) {
    return n.floor == targetFloor - 1 && n.connections.contains(targetId);
  });

C'est une recherche à rebours, exactement comme hasThreeConsecutive mais sans limite de profondeur : on part du nœud survolé et on remonte de parent en parent vers le nœud courant. Deux Set passés en paramètre sont remplis au retour de la récursion — un patron d'accumulateur qui évite d'allouer et de fusionner des collections à chaque niveau.

Trois détails importants :

Le cas de base est double. On s'arrête soit sur startId, soit — si le joueur n'a pas encore commencé (startId == null) — sur n'importe quel nœud de l'étage 0. Le survol fonctionne donc dès l'arrivée sur un nouvel acte.

La boucle ne s'arrête pas au premier succès. Elle explore tous les parents et accumule toutes les branches qui mènent au départ. Si trois chemins distincts relient le nœud courant au nœud survolé, les trois sont surlignés. Ce n'est pas « le » chemin, c'est l'ensemble des chemins.

Le type Set<(String, String)>. Les parenthèses forment un record positionnel de Dart 3 — un couple anonyme. Les records ayant une égalité structurelle, pathConnections.contains((node.id, targetId)) fonctionne dans le painter sans qu'on ait eu besoin de déclarer une classe Connection avec ses == et hashCode.
