Chapitre 07

La couche de données : un jeu 100 % data-driven

Pas une seule carte, pas un seul ennemi n'est écrit en Dart. Tout le contenu de Hero's Draft vit dans dix fichiers JSON, et ce chapitre explique comment il en sort pour devenir du code.

1. Ce que « data-driven » veut dire ici

L'expression est galvaudée. Dans ce projet elle a un sens très précis et vérifiable : aucune entité de jeu n'est instanciée en dur dans le code. Il n'existe nulle part une ligne du genre final strike = Card(name: 'Frappe', damage: 6);.

À la place, le code contient des modèles — des classes qui savent lire une forme de JSON — et le contenu vit dans assets/data/. Les conséquences sont immédiates :

  • Équilibrer le jeu ne demande pas de savoir programmer. Changer "value": 6 en "value": 5 dans cards.json nerfe la Frappe, partout : en combat, dans la boutique, dans les récompenses, dans le dictionnaire.
  • Ajouter du contenu ne recompile pas la logique. Une nouvelle relique qui réutilise un déclencheur et un type d'effet existants ne demande aucune ligne de Dart.
  • Le contenu est testable comme de la donnée : on peut vérifier qu'aucune carte n'a de coût négatif ou qu'une traduction manque, sans lancer le jeu.
Le contrat de la couche

Extrait de CLAUDE.md : « To add or modify cards, enemies, heroes, relics, skills, or events: edit the relevant JSON file in assets/data/, following the shape of an existing entry. No business-logic code needs to change for pure content additions. »

Le pacte a une contrepartie : dès qu'on change la forme du JSON — un nouveau champ, un renommage — il faut mettre à jour le modèle Dart correspondant dans lib/models/data/. Les deux évoluent toujours ensemble.

Convention du dépôt

patch_notes.json est le seul fichier de assets/data/ qui n'a pas de modèle Dart : l'écran le parse avec des classes privées. Il est aussi le seul à être géré par un agent et à ne jamais devoir être édité à la main — c'est le skill patch-notes-writer qui y ajoute une entrée et synchronise le champ version: de pubspec.yaml.

Une entrée type

Voici la première carte du jeu, telle qu'elle est écrite :

assets/data/cards.jsonjson
{
  "id": "strike_basic",
  "name_en": "Strike",
  "name_fr": "Frappe",
  "description_en": "Deal 6 damage.",
  "description_fr": "Inflige 6 dégâts.",
  "cost": 1,
  "type": "attack",
  "category": "global",
  "rarity": "common",
  "target": "singleEnemy",
  "animation": "melee",
  "effects": [
    {
      "type": "damage",
      "value": 6
    }
  ]
}

Onze champs, dont six sont des chaînes qui correspondent exactement à des valeurs d'énumération Dart : type → CardType.attack, category → CardCategory.global, rarity → CardRarity.common, target → CardTarget.singleEnemy. Le champ animation, lui, pilote directement la mise en scène côté Flame.

Une carte plus riche, avec deux effets dont l'un applique une altération d'état :

assets/data/cards.jsonjson
{
  "id": "poison_stab",
  "name_fr": "Coup Empoisonné",
  "cost": 1,
  "type": "attack",
  "target": "singleEnemy",
  "animation": "poison",
  "effects": [
    { "type": "damage", "value": 3 },
    { "type": "apply_status", "statusId": "poison", "value": 1, "duration": 2 }
  ]
}

Un effet est donc un petit objet à quatre champs — type, value, et optionnellement statusId et duration — et une carte n'est qu'une liste d'effets. Cette uniformité est ce qui rend le résolveur d'effets si simple (chapitre 10).

3. Le chargement : gameDataLoaderProvider

Tout part d'un unique FutureProvider, déclaré dans lib/services/game_data_service.dart. C'est le seul endroit du projet qui touche rootBundle pour de la donnée de jeu.

lib/services/game_data_service.dartdart
final gameDataLoaderProvider = FutureProvider<GameDataRegistry>((ref) async {
  final List<List<dynamic>> results = await Future.wait([
    _loadJsonList('assets/data/enemies.json'),
    _loadJsonList('assets/data/heroes.json'),
    _loadJsonList('assets/data/skills.json'),
    _loadJsonList('assets/data/cards.json'),
    _loadJsonList('assets/data/events.json'),
    _loadJsonList('assets/data/passives.json'),
    _loadJsonList('assets/data/relics.json'),
    _loadJsonList('assets/data/hero_cards.json'),
    _loadJsonList('assets/data/forge_upgrades.json'),
  ]);

Future.wait lance les neuf lectures en parallèle et attend que toutes soient terminées. L'ordre du tableau de résultats correspond exactement à l'ordre des appels, ce qui explique l'indexation qui suit.

lib/services/game_data_service.dartdart
  final allCards = [
    ...cardsList,
    ...heroCardsList,
  ];

  return GameDataRegistry(
    enemies: _mapList(enemiesList, EnemyData.fromJson, 'EnemyData'),
    heroes: _mapList(heroesList, HeroData.fromJson, 'HeroData'),

    cards: _mapList(allCards, CardData.fromJson, 'CardData'),
    events: _mapList(eventsList, EventData.fromJson, 'EventData'),
    passives: _mapList(passivesList, PassiveData.fromJson, 'PassiveData'),
    relics: _mapList(relicsList, RelicData.fromJson, 'RelicData'),
    forgeUpgrades: _mapList(forgeUpgradesList, ForgeUpgradeData.fromJson, 'ForgeUpgradeData'),
  );
});
À retenir

Les cartes globales et les cartes de classe sont fusionnées en une seule liste registry.cards. Le champ category (global ou characterSpecific) est ce qui permet ensuite de les distinguer : le draft de départ ne propose que les global, la boutique exclut les raretés unique.

Des erreurs qui disent où chercher

Deux fonctions utilitaires encadrent la lecture, et toutes deux ont été écrites pour produire des messages d'erreur exploitables.

lib/services/game_data_service.dartdart
Future<List<dynamic>> _loadJsonList(String path) async {
  try {
    final String content = await rootBundle.loadString(path);
    final decoded = jsonDecode(content);
    if (decoded is! List) {
      throw FormatException('Le fichier JSON doit être une liste à la racine.');
    }
    return decoded;
  } catch (e, stack) {
    throw Exception('Erreur de chargement/décodage pour le fichier "$path": $e\n$stack');
  }
}
lib/services/game_data_service.dartdart
List<T> _mapList<T>(
  List<dynamic> list,
  T Function(Map<String, dynamic>) fromJson,
  String modelName,
) {
  final List<T> result = [];
  for (int i = 0; i < list.length; i++) {
    final item = list[i];
    if (item is! Map<String, dynamic>) {
      throw Exception(
        'L\'élément à l\'index $i pour le modèle "$modelName" n\'est pas un Map<String, dynamic>. Reçu: $item',
      );
    }
    try {
      result.add(fromJson(item));
    } catch (e, stack) {
      throw Exception(
        'Erreur de parsing dans le modèle "$modelName" à l\'index $i (données: $item): $e\n$stack',
      );
    }
  }
  return result;
}
Bonne pratique

Le message d'erreur contient le nom du modèle, l'index de l'entrée et la donnée fautive. Une virgule oubliée dans relics.json ne produit pas un obscur type 'Null' is not a subtype of type 'String' : elle dit exactement quelle entrée relire. C'est peu de code pour beaucoup de temps gagné.

Où le chargement est attendu

Un seul écran attend réellement le Future : SplashScreen, qui est aussi la racine de l'application.

lib/ui/screens/splash_screen.dartdart
final gameData = ref.watch(gameDataLoaderProvider);

return Scaffold(
  body: Center(
    child: gameData.when(
      data: (_) =>
          const HomeScreen(), // Si les données sont chargées, on affiche l'écran d'accueil
      loading: () =>
          const CircularProgressIndicator(), // Pendant le chargement
      error: (error, stack) =>
          Text('Erreur de chargement: $error'), // En cas d'erreur
    ),
  ),
);

Tous les autres écrans utilisent ensuite ref.read(gameDataLoaderProvider).requireValue sans re-tester l'état asynchrone. C'est un contrat implicite : si l'on est passé par le splash, la donnée est là.

Point d'attention

.requireValue lève une exception si le Future n'est pas résolu. Le contrat tient parce que SplashScreen est la seule route racine et qu'aucun écran de jeu n'est accessible avant. Rien dans le compilateur ne le garantit ; c'est une convention à respecter. Deux écrans font exception et gèrent explicitement les trois états : relic_exchange_screen.dart et card_dictionary_screen.dart.

4. Le registre et les recherches par identifiant

GameDataRegistry est une classe très simple : huit listes, et un singleton statique affecté dans le constructeur.

lib/models/data/game_data_registry.dartdart
class GameDataRegistry {
  final List<EnemyData> enemies;
  final List<HeroData> heroes;
  final List<SkillData> skills;
  final List<CardData> cards;
  final List<EventData> events;
  final List<PassiveData> passives;
  final List<RelicData> relics;
  final List<ForgeUpgradeData> forgeUpgrades;

  static GameDataRegistry? _instance;
  static GameDataRegistry? get instance => _instance;

  GameDataRegistry({ /* ... */ }) {
    _instance = this;
  }
}
Piège

Le _instance = this; dans le corps du constructeur est un singleton — et l'architecture du projet interdit par ailleurs les variables globales. C'est une entorse assumée : elle existe pour permettre les recherches par identifiant depuis des endroits où l'on n'a pas de ref Riverpod, typiquement la désérialisation d'une sauvegarde.

Trois modèles exposent un getById statique construit sur ce singleton, tous sur le même moule :

lib/models/data/card_data.dartdart
static CardData? getById(String id) {
  final registry = GameDataRegistry.instance;
  if (registry == null) return null;
  try {
    return registry.cards.firstWhere((c) => c.id == id);
  } catch (e) {
    if (kDebugMode) {
      debugPrint('CardData.getById: no card found for id "$id" ($e)');
    }
    return null;
  }
}
MéthodeRetourUtilisée par
CardData.getById(id)CardData?DeckState._decodePile — recharge la définition fraîche d'une carte sauvegardée
RelicData.getById(id)RelicData?InventoryState.fromJsonWithReport — reconstruit l'inventaire
PassiveData.getById(id)PassiveData?RunState.fromJsonWithReport — retrouve le trait de classe
ForgeUpgradeData.getById(id)ForgeUpgradeData?filterValidRefs, les écrans de forge, l'affichage des runes

Toutes renvoient un type nullable, et c'est délibéré : si une carte a été retirée du jeu entre deux versions, la sauvegarde qui la référence ne doit pas planter. Le chapitre 20 montre comment ce null est transformé en message à l'utilisateur plutôt qu'en crash.

5. L'anatomie d'un modèle de données

Les onze modèles de lib/models/data/ suivent tous la même structure. Prenons CardData, le plus complet.

a) Les énumérations d'abord

lib/models/data/card_data.dartdart
enum CardType { attack, skill, power, status }

enum CardCategory { global, characterSpecific }

enum CardRarity { common, uncommon, rare, epic, legendary, unique }

enum CardTarget { singleEnemy, allEnemies, self, none }

Les noms des valeurs sont exactement les chaînes attendues dans le JSON. C'est ce qui permet le parsing par firstWhere((e) => e.name == json['type']).

À retenir

L'ordre de CardRarity n'est pas décoratif : il porte la progression de rareté. min(rarity.index + 1, CardRarity.values.length - 1) est la formule de montée en rareté utilisée par la fusion. Réordonner cet enum changerait les règles du jeu.

b) Des champs finaux et un constructeur const

lib/models/data/card_data.dartdart
class CardData {
  final String id;
  final String nameEn;
  final String nameFr;
  final String descriptionEn;
  final String descriptionFr;
  final int cost;
  final CardType type;
  final CardCategory category;
  final String? heroClass;
  final CardRarity rarity;
  final CardTarget target;
  final String? spritePath;
  final String? animation; // Type d'animation (ex: 'melee', 'magic', 'buff')
  final bool isExhaust;
  final List<CardEffect> effects;
  final int baseMaxForgeUpgrades;

Tout est final : une CardData chargée ne change jamais. Elle est partagée par toutes les instances de cette carte dans le deck du joueur, donc la muter aurait des effets de bord partout.

c) Une fabrique fromJson tolérante

lib/models/data/card_data.dartdart
factory CardData.fromJson(Map<String, dynamic> json) {
  final nEn = json['name_en'] as String? ?? json['name'] as String? ?? '';
  final nFr = json['name_fr'] as String? ?? json['name'] as String? ?? '';
  // ...
  return CardData(
    id: json['id'] as String,
    cost: json['cost'] as int,
    type: CardType.values.firstWhere((e) => e.name == json['type']),
    category: CardCategory.values.firstWhere(
      (e) => e.name == json['category'],
      orElse: () => CardCategory.global,
    ),
    heroClass: json['heroClass'] as String?,
    rarity: CardRarity.values.firstWhere(
      (e) => e.name == json['rarity'],
      orElse: () => CardRarity.common,
    ),
    target: CardTarget.values.firstWhere(
      (e) => e.name == json['target'],
      orElse: () => CardTarget.singleEnemy,
    ),
    isExhaust: json['isExhaust'] as bool? ?? false,
    effects:
        (json['effects'] as List<dynamic>?)
            ?.map((e) => CardEffect.fromJson(e as Map<String, dynamic>))
            .toList() ??
        [],
    baseMaxForgeUpgrades: json['baseMaxForgeUpgrades'] as int? ?? 1,
  );
}

Trois techniques de tolérance cohabitent :

  • Le repli en cascade json['name_fr'] ?? json['name'] ?? '' : accepte un ancien format monolingue.
  • Le orElse sur les enums : une valeur inconnue retombe sur un défaut raisonnable au lieu de lever.
  • Les valeurs par défaut ?? false, ?? 1, ?? [] sur les champs optionnels : ajouter un champ au JSON n'invalide pas les entrées existantes.
Point d'attention

Le champ type est le seul firstWhere sans orElse de ce modèle. Une faute de frappe dans "type" lève donc une exception au chargement, là où une faute sur "rarity" passera silencieusement en common. Le comportement n'est pas homogène — c'est à savoir en déboguant.

d) Un toJson pour la sauvegarde

CardData est l'un des rares modèles de catalogue à savoir se resérialiser, parce que le deck sauvegardé embarque la définition complète de chaque carte :

lib/models/data/card_data.dartdart
Map<String, dynamic> toJson() => {
      'id': id,
      'name_en': nameEn,
      'name_fr': nameFr,
      'description_en': descriptionEn,
      'description_fr': descriptionFr,
      'cost': cost,
      'type': type.name,
      'category': category.name,
      if (heroClass != null) 'heroClass': heroClass,
      'rarity': rarity.name,
      'target': target.name,
      if (spritePath != null) 'spritePath': spritePath,
      if (animation != null) 'animation': animation,
      'isExhaust': isExhaust,
      'effects': effects.map((e) => e.toJson()).toList(),
      'baseMaxForgeUpgrades': baseMaxForgeUpgrades,
    };

Notez les if (x != null) à l'intérieur du littéral de map : c'est la collection-if de Dart, qui omet purement et simplement la clé quand la valeur est nulle.

6. La localisation inline du contenu

Le projet a deux systèmes de traduction, et il faut bien les distinguer.

InterfaceContenu de jeu
Oùlib/l10n/app_fr.arb et app_en.arbDirectement dans assets/data/*.json
FormeFichiers ARB, une clé par libelléPaires de champs name_fr / name_en
AccèsAppLocalizations.of(context)!.maClédata.getName(locale)
GénérationOui — AppLocalizations est généré par FlutterNon — c'est de la donnée
Exemples« Continuer », « Fin de tour », « Or »« Frappe », « Inflige 6 dégâts. », « Gobelin »

Le second est le plus intéressant ici. Chaque modèle porteur de texte expose deux getters :

lib/models/data/card_data.dartdart
String getName(String locale) => locale == 'fr' ? nameFr : nameEn;
String getDescription(String locale) =>
    locale == 'fr' ? descriptionFr : descriptionEn;

La règle est donc : français si la locale est fr, anglais dans tous les autres cas. Il n'y a pas de repli plus subtil, et c'est volontaire — l'anglais sert de langue par défaut universelle. Un test le vérifie explicitement :

test/unit/localization_test.dartdart
// Verify fallback behavior on unknown/default locale (falls back to English nameEn/descriptionEn)
expect(cardData.getName('es'), 'Strike Test');
expect(cardData.getDescription('de'), 'Deals 6 damage.');

Le même patron se retrouve sur HeroData, EnemyData, RelicData, PassiveData, ForgeUpgradeData, ainsi que sur EventData, EventChoice — qui ajoutent getTitle et getResultText.

Règle du dépôt

« Every JSON entry with user-facing text must include both _fr and _en variants, and the corresponding Dart model in lib/models/data/ must be updated whenever a JSON schema changes. » Ajouter une carte sans sa traduction anglaise n'est pas une erreur bloquante — le repli renverra une chaîne vide — mais c'est une régression silencieuse.

Un cas particulier : ForgeUpgradeData

Les descriptions de runes sont des gabarits avec des marqueurs, puisque la valeur dépend du niveau de la rune :

assets/data/forge_upgrades.jsonjson
{
  "id": "sharp",
  "name_fr": "Tranchant",
  "description_fr": "+{val} Dégâts sur la carte",
  "pools": ["common", "uncommon", "rare"],
  "eligibleCardTypes": ["attack"],
  "valueMultiplier": 2,
  "weight": 100,
  "emoji": "⚔️"
}
lib/models/data/forge_upgrade_data.dartdart
String getDescription(int tier, String locale) {
  final template = locale == 'fr' ? descriptionFr : descriptionEn;
  final val = tier * valueMultiplier;
  return template
      .replaceAll('{tier}', tier.toString())
      .replaceAll('{val}', val.toString());
}

Deux marqueurs : {tier} pour le niveau brut et {val} pour le niveau multiplié par valueMultiplier. Un sharp de niveau 2 affiche donc « +4 Dégâts sur la carte ».

7. Catalogue contre instances

Nous l'avons évoqué au chapitre 6 ; voyons-le concrètement, car c'est la source de confusion la plus fréquente pour qui découvre le dépôt.

lib/models/card_instance.dartdart
class CardInstance {
  final String uniqueId;
  final CardData data;
  final CardRarity rarity;
  final List<String> forgeUpgrades;

  CardInstance({
    String? uniqueId,
    required this.data,
    CardRarity? rarity,
    List<String>? forgeUpgrades,
  })  : uniqueId = uniqueId ?? const Uuid().v4(),
        rarity = rarity ?? data.rarity,
        forgeUpgrades = forgeUpgrades != null
            ? List<String>.unmodifiable(forgeUpgrades)
            : const <String>[];

  int get currentCost => data.cost;

Trois détails à noter :

  • L'uniqueId est un UUID v4 généré à la création si on n'en fournit pas. C'est lui qui permet de retirer une Frappe de la main sans toucher aux autres.
  • La rareté de l'instance retombe par défaut sur celle de la définition, mais peut la dépasser — c'est ce que fait la fusion.
  • currentCost renvoie simplement data.cost : dans l'état actuel du jeu, aucune rune ni aucune rareté ne modifie le coût en mana d'une carte. Le getter existe pour rendre cette évolution possible sans changer les appelants.

Le même schéma s'applique aux ennemis : EnemyData décrit le Gobelin, une EnemyInstance décrit ce Gobelin-ci, avec son EntityStats mis à l'échelle par l'acte et le niveau du joueur.

8. Ajouter du contenu : le mode d'emploi

Cas 1 — Une carte qui réutilise des effets existants

Aucune ligne de Dart. On ajoute une entrée à cards.json :

exemple — à ajouter dans assets/data/cards.jsonjson
{
  "id": "shield_bash",
  "name_en": "Shield Bash",
  "name_fr": "Coup de Bouclier",
  "description_en": "Gain 6 Block and deal 4 damage.",
  "description_fr": "Gagne 6 d'Armure et inflige 4 dégâts.",
  "cost": 1,
  "type": "attack",
  "category": "global",
  "rarity": "common",
  "target": "singleEnemy",
  "animation": "melee",
  "effects": [
    { "type": "armor", "value": 6 },
    { "type": "damage", "value": 4 }
  ]
}

Au prochain lancement, la carte est immédiatement disponible dans le draft de départ, dans la boutique, dans le dictionnaire, dans le miroir magique et dans les récompenses de boss. Rien d'autre à faire.

Cas 2 — Un nouvel ennemi

exemple — à ajouter dans assets/data/enemies.jsonjson
{
  "id": "wolf",
  "name_en": "Dire Wolf",
  "name_fr": "Loup Sinistre",
  "maxHp": 32,
  "baseDamage": 7,
  "spritePath": "enemy_wolf.png",
  "tier": 2,
  "xp": 45,
  "critChance": 20,
  "gold": 18,
  "intents": [
    { "type": "attack", "value": 7 },
    { "type": "attack", "value": 7 },
    { "type": "buff",   "value": 2 }

}

Là il y a une contrainte supplémentaire : l'image. HerosDraftGame.onLoad lit enemies.json et précharge tous les spritePath déclarés. Il faut donc déposer assets/images/enemy_wolf.png. Le tier: 2 signifie que l'ennemi n'apparaîtra qu'à partir de l'acte 6 (chapitre 11).

Checklist avant de valider un ajout de contenu
  1. Les deux variantes _fr et _en sont présentes pour chaque texte visible.
  2. L'id est unique dans son fichier.
  3. Les valeurs d'enum (type, rarity, target, trigger) correspondent exactement à un nom d'énumération Dart.
  4. Si un spritePath ou un iconPath est déclaré, l'image existe dans assets/images/.
  5. flutter test passe, et dart analyze ne remonte rien.

Quiz — vérifiez vos acquis

1. Combien de fichiers JSON gameDataLoaderProvider charge-t-il, et comment ?

  • 10, un par un, séquentiellement
  • 9, séquentiellement
  • 9, en parallèle avec Future.wait
  • 10, en parallèle avec Future.wait
Réponse : neuf fichiers en parallèle. patch_notes.json est le dixième fichier du dossier mais il n'est pas chargé ici : il est lu directement par patch_notes_screen.dart via rootBundle.

2. Que se passe-t-il si "rarity" contient une valeur inconnue dans cards.json ?

  • La carte est chargée avec CardRarity.common grâce au orElse
  • Le chargement échoue avec une exception
  • La carte est ignorée silencieusement
  • La rareté est déduite du coût en mana
Réponse : rarity, category et target ont un orElse ; seul type n'en a pas et lèvera une exception.

3. Où vivent les cartes de classe une fois le jeu chargé ?

  • Dans registry.heroes
  • Dans une liste séparée registry.heroCards
  • Elles ne sont pas chargées, elles sont créées à la volée
  • Dans registry.cards, fusionnées avec les cartes globales
Réponse : final allCards = [...cardsList, ...heroCardsList];. Le champ category (global / characterSpecific) et la rareté unique permettent ensuite de les filtrer.

4. Pourquoi CardData.getById passe-t-il par un singleton statique plutôt que par un provider ?

  • Parce que c'est plus rapide
  • Parce qu'il est appelé depuis la désérialisation d'une sauvegarde, où l'on n'a pas de ref
  • Parce que Riverpod ne gère pas les listes
  • Parce que c'est une exigence de Flame
Réponse : DeckState._decodePile et InventoryState.fromJsonWithReport sont des méthodes statiques de classes d'état, sans accès à Riverpod. Le singleton est une entorse assumée à la règle « pas de variable globale ».

5. Que renvoie getName('es') sur une CardData ?

  • Une chaîne vide
  • Une exception UnsupportedLocale
  • Le nom anglais
  • Le nom français
Réponse : getName(locale) => locale == 'fr' ? nameFr : nameEn;. L'anglais est le repli universel, et test/unit/localization_test.dart le vérifie explicitement pour 'es' et 'de'.

6. Vous ajoutez une carte avec "animation": "shadow", une valeur qui n'existe pas encore. Que se passe-t-il ?

  • Elle joue l'animation de mêlée, car le switch de CardAnimator a un default
  • Le chargement du JSON échoue
  • La carte est invisible en combat
  • L'application plante au moment de jouer la carte
Réponse : animation est une simple String? côté modèle, sans énumération. Le dispatcher de CardAnimator a un case 'melee': default: qui attrape toutes les valeurs inconnues.
